# 変異の仕様書

このディレクトリのファイルは、**各ゲートが何を捕まえなければならないか**を
1件ずつ書いたものです。`scripts/mutate.py` が読み、対象を1箇所だけ壊して、
そのゲートが赤くなることを確かめます。

ゲート自身のテストとは別物です。ゲートのテストは「判定が正しく動くこと」を
確かめます。こちらは「**判定を骨抜きにしたら気づけること**」を確かめます。
上限を1つ上げる、例外リストを空にする、走査の範囲を狭める — どれも
コードは通り、テストも通り、報告される件数だけが静かに正しくなくなります。

## 走らせ方

    python3 scripts/run_mutations.py                 # 全部
    python3 scripts/run_mutations.py server_answer   # 1つ

**並列にはできません。** どのハーネスも復元手順をリポジトリ直下の同じ
`.mutate-journal.json` に書くので、2本同時に走ると片方がもう片方の
journal を上書きします。CI には載せていません — 1本あたり Go のテストを
変異の数だけ回すので、数分かかります。

長く走らせるときは `--isolated` を使ってください。使い捨ての git worktree
で走るので、**元の作業ツリーは最後まで無傷**です。付けないと、測っている
あいだ壊れたコードが「未コミットの変更」として見え続けます。実際にそれで
「未コミットの変更がある」と指摘され、**走行中の変異をコミットしかけました。**

## 落ちるとき

- `SURVIVED` — 壊したのにゲートが赤くなりませんでした。そのゲートは
  その形を見ていません。
- `SKIP (pattern absent)` — **これも失敗です。** 対象が動いて、仕様書の
  patternが当たらなくなっています。放っておくと、走らせるたびに全 SKIP で
  緑を返す文書になります。「壊せない検査」と「壊してみていない検査」は
  同じ形をしています。
- `NOT-A-KILL (build)` — 壊し方が乱暴で、ビルドが落ちただけです。判定が
  働いたのかどうかは分かりません。仕様書側を直します。

## 置いていない変異

1箇所だけ壊すハーネスでは殺せない形があります。仕様書のコメントに
その都度書いてあります。主なものは2つです。

- **ビルドが落ちるだけの壊し方。** 例えば `metrics.` の呼び出しが1つしか
  無いファイルからそれを消すと、import が未使用になります。判定が落ちたのか
  import が落ちたのかが区別できないので、置きません。
- **木がきれいなあいだ、結果が変わらない壊し方。** `main()` が判定の結果を
  無視するようにしても、問題が0件なら出力は同じです。これは汚した入力を
  渡さないと見分けられないので、判定側のテストで見ています
  （`check_prometheus_rules_test.py` の `TestMainActsOnWhatItFound`）。

## ここで見つかったこと

移す作業そのものが、6つ見つけました。**ゲートを1本も直さずに、
ゲートの穴が6つ出ました。**

1. `fail_reaches_someone_test.go` が `if !strings.Contains(body, …)` を
   並べていたので、**探す文字列を空にする変異が生き残りました。**
   ゲートの判定を骨抜きにしても、木がきれいなら誰も気づけません。
   求めるものを一覧にして、負の対照（足りないものを正しく挙げられるか）を
   付けました。
2. 最初に `server_scheduler.py` を走らせたとき、`-run` に
   `tick_outcome_test.go` を入れ忘れていました。実際には存在する検査が
   走らないまま「この形は見られていない」と読み違えました。
   **動いていない検査と、通った検査は、要約行が同じです。**
3. `answerContinueCeiling = 0` が、実測380箇所を380箇所とも除外していました。
   除外の一覧が「行スキャン」ではなく `if err != nil { continue }` 全部を
   返していたためです。0 は「continue で片付けている箇所は無い」と読めますが、
   言えていたのは「どれも何かログを書いている」まででした。
4. フロントエンドのゲート7本が `blankNoise` を **テストファイルから**
   import していました。道具のつもりの import が、そのファイルのテスト
   （65秒かかるものを含む）を毎回連れてきます。時間を測って気づきました。
   `tests/lib/blank-noise.ts` に移して、1回あたり2分20秒 → 1分6秒。
5. `respondsToFailure` が窓を次の fetch の手前で切る行に、検査が
   ありませんでした。**直した箇所に、直したことを守るものが無い** —
   ソースのコメントには実際に起きた事例まで書いてあるのに、消しても
   誰も気づきません。コメントは記録であって、検査ではありません。
6. `run_mutations.py` が `timeout` に落とされたとき、worktree を
   /tmp に残しました。`finally` は SIGTERM では走りません — **ハーネスが
   journal で塞いだのと同じ穴を、それを作る側で作り直していました。**

2 と、`frontend_routes` で「素の fetch を宛先の判定から外す」が生存と
出たのは同じ形です。どちらも検査は在って、私が走らせる対象から
落としていただけでした。**このキャンペーンで3度あり、3度とも
「検査が無い」ではなく「走らせていない」でした。**
