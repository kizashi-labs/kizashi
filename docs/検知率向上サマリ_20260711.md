# 検知率向上サマリ（2026-07-11 スプリント）

**出発点の問い**: 「Kizashi は商用EDR（CrowdStrike / SentinelOne / Defender / Cortex XDR）と
比べてどの程度か。検知率をどう上げるか」。本スプリントは、その問いに対し**当てずっぽうでなく、
コード変更と回帰テストで検証可能な形**で検知率と検知の実効性を引き上げた記録である。

対象ブランチ: `claude/edr-product-comparison-dev8e0`（PR #446）。全コミットはローカルで
全テスト・vet・両モジュール build 緑（CI はスプリント中アカウント起因のランナー障害でペンディング）。

---

## エグゼクティブサマリ

3つのフェーズで **検知エンジンを全系統で回帰保護し、被覆を拡げ、既存検知の回避耐性を底上げ**した。

| 指標 | Before | After |
|---|---|---|
| ビルトイン単一イベント「期待技術」被覆 | 45 | **94** |
| ビルトイン技法拡充（新規） | — | **+36 技法** |
| 回避耐性テスト（evasion_hardening） | 0 | **52 ケース** |
| DBエンジン抽出ルール（実SQLから） | 不可視 | **129 ルール**（sigma 105 / behavioral 22 / yara 2） |
| 本番で死蔵していた critical ルールの是正 | — | **3 件** |
| 回帰保護された検知エンジン系統 | 部分的 | **全系統**（Sigma×2 / 相関×3 / IOC） |

## フェーズ①：検知エンジンの回帰保護（監査・固定）

商用EDR比較で最も痛いのは「コード上は検知するのに、本番では静かに発火しない」隠れた故障。
本フェーズはそれを全系統で潰した。

- **DBエンジン（detection-server）単一イベント層**: マイグレーションSQLから出荷ルールを実バイトで
  抽出するハーネスを新設し、31技法を発火固定。過程で **本番で無言で死んでいた critical ルール3件**を発見・是正:
  - `T1059.004` Linux リバースシェル — description の未クォート YAML（コロン+空白）で**パース必ず失敗**（コンパイル時死蔵）
  - `T1571` / `T1048.003` — 非標準修飾子 `not_in` で**評価のたび err**（match時死蔵、コンパイルは通る）
- **抽出ハーネス自体の穴を是正**: `INSERT … VALUES` 形しか解析できず、冪等な `INSERT … SELECT … WHERE NOT EXISTS`
  形の **32ルール（キルチェーン相関等）を無言でスキップ**していた。SELECT形パーサを追加し 97→129 ルールに。
- **DBエンジン相関層**（SequenceEngine）: 閾値型8＋多段キルチェーン4シナリオを実SQLで発火固定。
- **api-server 相関層**（3系統目 `internal/correlation`）: 出荷される5つのビルトイン相関ルールを end-to-end 固定
  ＋ `AlertPipeline.isDuplicate`（重複抑制）＋設定バリデーションを固定。
  > **⚠️ 訂正（2026-07-20）**: この「end-to-end 固定」は実は end-to-end になっておらず、テストが
  > `ProcessAlert` に *サブタイプを直接* 与えていたため、本番 AlertPipeline が *ベースカテゴリ* しか
  > 渡さないことで **5ルール全てが永久 inert** だった P0 バグを隠蔽していた。是正の詳細は
  > [検知率向上_20260720_相関レイヤ不発の是正.md](検知率向上_20260720_相関レイヤ不発の是正.md)。
- **IOC 経路**: 出荷28 IOC の型別適合性（IP/hash/domain）を回帰固定＝「不正IOCが一度もマッチしない」死蔵を防止。

## フェーズ②：ビルトイン技法の拡充（+36 技法）

商用EDRが重視する現代的攻撃面を中心に、どのOSでも未被覆だった技法を追加（単一イベント 45→94）。

- **クラウド/コンテナ**: T1552.005（インスタンスメタデータ窃取）/ T1613（コンテナ探索）/ T1552.007（K8s トークン）
- **Exfil/C2**: T1102（Webサービス悪用C2）/ T1090.002（トンネリング）/ T1048 系
- **計測回避**: T1562.001（AMSI）/ **T1562.006（ETW、新技法）**
- **資格情報**: T1555.003/005（ブラウザ/パスワードマネージャ）/ T1207（DCShadow）
- **Linux/macOS パリティ**: T1046/T1518.001/T1136.001/T1070.004/T1201/T1217/T1614.001/T1087.001/
  T1547.007/T1546.014/T1037.005/T1548.001 ほか
- **その他**: T1014（ルートキット）/ T1542.003（ブートキット）/ T1091（USB複製）/ T1027.002（UPX）/ T1553.005（MOTW）

## フェーズ③：既存ルールのFN堅牢化（回避耐性 52ケース）

「技法数」ではなく**実際に捕まえられるか**を上げる回。攻撃者の一般的な回避手口を回帰監査で洗い出し是正。
Windows / Linux / macOS の3プラットフォームを一巡。

- **Windows**: エンコードPS接頭辞（`-en`/`-enco`…）/pwsh、シャドウ削除（wbadmin/WMI）、certutil `-verifyctl`、
  LSASS（comsvcs 序数 `#24`/nanodump/dumpert/Out-Minidump）、スケジュールタスク/サービスの PowerShell 経路、
  Defender 無効化（除外/サービス停止/MpCmdRun）、Run鍵/WMI の PowerShell 経路、AMSI/ETW インライン、
  mshta ローカル`.hta`/`about:`
- **Linux**: リバースシェル7変種（perl/ruby/php/socat/mkfifo/nc -e/awk）、curl\|bash・base64 復号実行、
  sudo GTFOBins 追加変種（env/tar/gdb/ページャ）、SUID/capability 列挙、コンテナエスケープ（runc/release_agent/docker.sock）
- **macOS**: DYLD インジェクション（`DYLD_INSERT_LIBRARIES`）

## 商用EDR比較への含意

- **「見かけの被覆」から「実効検知」へ**: 本スプリントの中核は、死蔵ルールの是正と回避耐性の底上げ。
  商用EDR評価（MITRE Engenuity ATT&CK Evaluations 等）で差がつくのは、まさに「回避された時に捕まえられるか」。
- **クラウド/コンテナ/Linux の強化**: CrowdStrike/SentinelOne が訴求する領域（K8s、コンテナエスケープ、
  Linux リバースシェル）の穴を具体的に埋めた。
- **回帰ハーネスの整備**: 3系統の検知エンジンと IOC を実バイト/実SQLで固定したことで、以後の変更で
  「静かに壊れる」リスクを構造的に低減。これは長期の検知品質維持に効く。

## 残課題 / 次の一手

- **curate（1,262 休眠ルール）の段階有効化** と **ライブ計測**: 被覆を最も大きく動かせるが、稼働サーバ必須。
- **センサー深度**: LSASS process_access、キーロガー API フック、AF_PACKET/JA3 実キャプチャ、fanotify/minifilter
  プリライトフック — ルールでなくセンサー実装で、実機が必要。
- **DBエンジン側のフィールド被覆監査**: 出荷 DB sigma ルールが RuleEngine の field mapping で解決可能かの点検
  （ビルトイン側 `TestBuiltinRuleFieldSupportAudit` の DB版）。
