テーマは2系統:

### 設計上の要点（誤検知を増やさないための絞り込み）

- **A-1**: 発火はデバイスクラスでゲート。`storage`（マスストレージ＝感染拡大/USB持ち出しの本命ベクタ, sev5）と `usb`（素の接続＝情報系, sev3）のみ。`input`（キーボード/マウス）・`network` は無発火。切断も無発火。
- **A-2**: 「持続する」ことが採掘の特徴。`cpu_pct ≥ 80%`（システム全体比）を**3スナップショット連続（約90秒）**維持したPIDのみ sev5 で1回発火。単発スパイク（ビルド/バックアップ/エンコード）はリセット、PIDがスナップショットから消えてもリセット（PID再利用対策）。
- **A-3**: サーバ側 `AnalyzeDNSQuery`/`AnalyzeDGA` が既に発火した場合は採用しない（重複アラート防止）。IDN/ホモグラフなどサーバが未モデル化の信号のみ回収。
- **C-1**: `logon_type` は非空時のみ flat map に emit するため、非Windows の auth イベントは不変。

## 2. 既定OFFで死んでいたセンサの有効化（✅ 実機検証を経てマージ済み）

実装済みだが env フラグで opt-in ゲートされ、既定インストールでは no-op になっていたセンサを既定ON（opt-out）へ。**エージェントの既定挙動変更を伴う**ため、`process_etw.go` が既に採用している「opt-out + 失敗時フォールバック」パターンを踏襲しつつ、**本番負荷の確認を経てからマージする前提でレビュー保留**とした。B-2 はその検証で実際に障害を発見し、修正を追加してからマージしている（§2.1）。

### 2.1 B-2 の実機負荷検証 — 想定と違うものが出た（2026-08-01）

**保留の理由は「CPU 負荷が読めない」だったが、実測の結果 CPU は問題なく、代わりに想定していなかったイベント氾濫が見つかった。**

#### 計測手段の用意

隔離サンドボックスには実 Windows 端末が無く、エージェント自身の負荷は測れなかった。そこで**設定・登録・サーバ接続のいずれも不要で、イベントも送信しない計測専用モード** `-memscan-bench` を追加した（稼働中エージェントと並行実行できるため、サービス停止も不要）。運用手順は [ops/メモリスキャン負荷計測ランブック.md](ops/メモリスキャン負荷計測ランブック.md)。

#### 計測結果（Windows Server / 105-109プロセス / SeDebugPrivilege 有効 / 3回実施）

| 項目 | 実測 | 判定 |
|---|---|---|
| 1周の所要時間 | avg 565-593ms（ばらつき5%以内） | — |
| **60秒周期の占有率** | **0.94 - 0.99%** | ✅ 許容範囲 |
| 対象プロセス | 列挙105-109 / 走査94-98 / 未オープン11-12 | — |
| 検査領域 | 約56,000 | — |
| 最遅プロセス | SearchApp.exe 59-66ms | ✅ 単独支配なし |

SeDebugPrivilege の有無で占有率は変わらなかった（0.98% → 0.99%）。**CPU は既定ON化の障害にならないことが確定**した。

#### 発見: 抑制機構の欠如によるイベント氾濫

一方、`findings raw=112 → emit=10` が**3周とも完全に同一**だった。`runMemoryScanService` には周期をまたぐ重複抑制が無く、存在し続ける領域を毎周期そのまま再送していた。

- ノイズ源は**稼働中の powershell.exe 1つ**（.NET CLR の JIT が確保した RWX 領域 10個、8〜180KiB）
- **10件/分 = 約14,400件/日/台**。実検知が1件も無い状態で、である
- これは「ほぼアイドルのサーバ1台」の数字であり、台数分だけ線形に増える

**既定ONにした瞬間、全端末からこの流量が発生していた。** 当初の懸念（CPU）ではなく、アラート疲れとストレージのほうが先に問題になる構図で、実測しなければ見えなかった。

#### なぜ allowlist ではなく抑制機構を採ったか

`powershell.exe` を allowlist に追加すれば流量は消える。しかし**本スキャナが検知対象とするもの（T1059.001 ファイルレス PowerShell、T1055、T1620）がまさに powershell.exe の RWX メモリ上に存在する**ため、それは自己否定になる。JIT の RWX と実装の RWX が同じ場所に同居しているのが、この検知の本質的な難しさである。

採ったのは `memFindingSuppressor`（**初回検出時のみ報告し、存在し続ける間は沈黙**）＝「状態のダンプ」から「変化の検知」への転換。設計詳細は [design/メモリ・インジェクション検知設計.md](design/メモリ・インジェクション検知設計.md) の「M1 の運用設計」を参照。

**検知能力は低下しない。** インジェクションは「直前まで存在しなかった領域」として現れるため、抑制を通過する側に残る。むしろ新規領域の出現がシグナルとして際立つ。

#### 修正後の再計測

```
cycle 1: findings raw=112 候補=10 送信=10 抑制=0    ← 常駐領域の初回報告
cycle 2: findings raw=112 候補=10 送信=0  抑制=10
cycle 3: findings raw=112 候補=10 送信=0  抑制=10
定常イベント量: 0件/周 → 約0件/日/台
```

**14,400件/日/台 → 0件/日/台。** 全CI green を確認のうえマージした。

#### 教訓

- **「負荷検証」を CPU だけの話にしない。** 既定ON化のレビューでは、CPU・イベント量・アラート量の3つを別々に測る。今回 CPU は問題なく、イベント量が唯一の障害だった。
- **周期スキャナは状態を持たないと必ず再送する。** 「毎周期の finding 件数が一定」は正常ではなく、恒常的なイベント流量を意味する。周期実行する検知器を新設する際は、抑制機構の有無を設計時のチェック項目にする。
- **FP 対策として allowlist を足す前に、それが検知対象そのものを盲目にしないか確認する。** 最もノイズの多いプロセスが、最も攻撃者に狙われるプロセスであることは珍しくない。

### あえて既定ONにしなかったもの（B-1）

純粋に加算的で失敗時 no-op に劣化する5センサのみを既定ON化。以下は**成熟した既存パスを置換/差し替えてしまう**ため opt-in を維持:

- **レジストリ収集器** — 既定ONにすると成熟した `RegNotifyChangeKeyValue` パスを ETW 版に置換してしまう。
- **auth / dns / network の ETW トランスポート** — 稼働中の非ETW収集器を差し替えてしまう。

## 3. 到達性監査の方法論（拡張）

サマリ第2章の「emit と consume の契約」監査を、今回は**双方向**に拡張して走査した:

- **(A) センサは emit するが消費側が無い**: `device_event`（A-1）、`process_stats`（A-2）、`is_suspicious`（A-3）、`resource_usage`（未対応・低価値）。
- **(B) 消費側/エイリアスは参照するが emit されない**: `logon_type`（C-1）— `field_support` が supported と宣言しているのに emit 経路が無い、reachability ガードの唯一の穴だった。

C-1 の是正により `field_support` の `logon_type` が実 emit に裏打ちされ、**「supported なのに未 emit」の乖離が解消**した。今後は emit↔supported の同期ガード（`TestEmittedEventFieldsAreSupported`）に加え、この supported→emit 方向も監査対象に含めるべき。

## 5. スキップした項目と残ギャップ

### 費用対効果が低くスキップ
- **threat_intel_confidence / is_encrypted の小口配線** — 精査の結果、前者は既存アラートの深刻度精緻化のみ（新規検知は増えない）、後者は単独では脅威信号にならず FP ノイズ源。「検知率」ではなく「品質」寄りのためスキップ。

### 別途フォローが必要（本バッチのスコープ外）
- **多セッションホストでのメモリスキャン負荷検証** — §2.1 の計測は**ほぼアイドルの Windows Server 1台**（105-109プロセス）でのもの。RDS/ターミナルサーバではプロセス数が数倍〜十数倍になり、占有率も相応に上がる（イベント量は抑制機構により台数・プロセス数に依らず定常0件）。該当ホストが用意でき次第 `-memscan-bench` で確認する。重ければ `EDR_MEMORY_SCAN=0` で個別に opt-out 可能。
- **Windows のメモリ内 YARA（per-region 内容スキャン）** — ~~後フェーズ~~ **2026-08-01 に実装**（`ReadProcessMemory`）。これにより Cobalt Strike / Meterpreter / Mimikatz / Havoc のメモリ内マーカーが、それらが実際に動作する Windows でようやく照合されるようになった。ただし**初回の負荷検証は内容スキャンが無い状態での数値**なので、実装後の再計測が必要（[ops/メモリスキャン負荷計測ランブック.md](ops/メモリスキャン負荷計測ランブック.md) §5）。
- **`device_events` テーブルの実データ化** — A-1 は「検知として発火」させたが、`DeviceEventStore.Insert` を ingest から呼んでテーブルを埋める配線（XDR のエンドポイント相関を有効化）は ingest ホットパスへの DB 書き込み結合を伴うため別PR。
- **T1566.001 フィッシング添付 / T1041 単体C2持ち出し** — 計測上の恒常的 miss だが、メール/添付テレメトリのクラスが未整備で、新センサ実装が前提（隔離サンドボックスでは完結しない）。

## 6. 記録メモ（運用上の事実）

- 本セッションの CI は複数回、**GitHub Actions ランナー基盤の一時障害**（全ジョブが起動数秒で一斉失敗・ログ404）に当たった。コードは無関係。#510 は 2026-08-01 に **main を取り込んで CI を再キックし、全 green を確認してマージ**（単なる再実行ではなく base 追従を選んだのは、11日分進んだ main とのマージ後の状態に近い検証にするため）。障害時と再キック後の差は明確で、`Agent Tests` は前者が2秒で failure、後者は2分31秒かけて success だった。**「全ジョブが数秒で一斉失敗」はコード起因ではないと判断してよい**シグナルとして記録しておく。
- **カバレッジ bot の ❌ Fail は本バッチのブロッカーではない**。ブロッキングゲートは `ci.yml` の 35%（実測36.0%で通過）で、bot コメントの 40% は `ci.yml` に「Next: 40%」と記載された次の目標値。#511 にも同一の 36.0% / ❌ が付いており、特定PRの退行ではなくリポジトリ全体の現状値。
- **B-1/B-2 のマージ判断は 2026-08-01**（記録本体は 07-20 のバッチ）。B-1 は #509 として先にマージ、B-2 は §2.1 の実機検証と抑制機構の追加を経て #511 としてマージ。実 Windows 端末での計測はサンドボックス内では不可能だったため、`-memscan-bench` を追加して利用者側の端末で実行してもらう形を採った。
- `MemoryScanStats` / `ScanSuspiciousMemoryWithYARAStats` / `-memscan-bench` は**常設の診断機能として残している**（当初は一時計測の予定だったが、フリートは均質ではなくプロセス数とアドレス空間サイズが役割ごとに桁で変わるため、同じ計測値が今後のホスト診断に必要になる）。周期ごとの負荷ログは Debug 級（60秒周期では1台あたり約1,440行/日になるため）。
- proto 変更（C-1）に伴う `events.pb.go` の大きな差分は、再生成されたファイルディスクリプタ（rawDesc バイト列）が主体で機能的には等価（`proto/Makefile` の注記どおり buf コンパイラと元の protoc で descriptor 表現が異なる）。意味的変更は `logon_type` フィールドと `GetLogonType()` のみ。
