# 🟤 P5 — エージェント堅牢性・信頼性（field-hardening）

> 台帳の索引は [../技術的負債と改善計画.md](../技術的負債と改善計画.md)。

競合比較（[競合評価.md](../競合評価.md)）の「②エージェント堅牢性」を検証ホスト単一ノードで測る再現テスト・
スイートを整備し（[ops/エージェント堅牢性テストランブック.md](../ops/エージェント堅牢性テストランブック.md) /
`deploy/robustness/run-robustness.sh`、**PR #331**）、実障害モードを `docker pause/stop` で再現＋eBPF が捕捉する
マーカー exec の到達数で「サイレント損失」を定量する。スイートが複数の実問題を捕捉した。

### P5-1. 非UTF-8 command_line によるバッチ全消失 — ✅ 修正済（PR #331）
eBPF argv / inotify ファイル名は任意バイトを含み得るが proto3 string は有効 UTF-8 必須。**1 イベントの不正 UTF-8 で
バッチ全体の marshal が失敗**（wire 送信＋ディスクバッファ双方）し、同梱のクリーンイベントも巻き添えドロップ＋
再接続ループ（実測 4051 失敗/10 分）。→ 送信境界で全イベント型 string を `strings.ToValidUTF8` でサニタイズ
（`sanitizeEventStrings`、`cmd/agent/main.go`）＋単体テスト。halfopen マーカー到達 **1/200 → 204/200（損失ゼロ）**。

### P5-2. ディスクスプールの非有界（ディレクトリ inode 肥大）— ✅ 修正済（PR #331）
バイト上限（`local_buffer_size_mb`）はあるが**ファイル数の上限が無い**ため、長期切断中に小バッチを多数書き込むと
セグメント（`.buf`）が無制限に増える。run1 で 71,446 ファイルに達し ext4 のディレクトリ inode が ~17MB に肥大
（ext4 はディレクトリを縮小しない）→ ディスク浪費＋`recover()`/`ReadDir` 劣化。→ `maxFiles`=10000 と
ドレイン完了時の `shrinkIfDrained`（dir 再生成で inode リセット）を `internal/transport/buffer.go` に追加＋テスト。
※「`du -sm <dir>` が肥大 inode を含む」計測落とし穴も判明（実 `.buf` バイトで測る）。

### P5-3. コマンド受信側のアプリ層半開き（server→agent）— ✅ 修正済（アプリ層=PR #333／ネットワーク層=PR #334）
`sendWithWatchdog`（PR #325）は**送信方向(agent→server)のみ**の application-level half-open を解決していたが、
**受信方向(`receiveCommands.Recv()`)は同じ脆弱性が残り**、隔離適用後などに **server→agent のコマンド
（isolate/unisolate 等）が間欠的に届かなかった**。本堅牢性スイートで追加した receive-log（PR #331）が
「ingestion は "コマンドを送信しました" とログするのに agent は未受信」を可視化し、切り分けの起点になった。
- **アプリ層＝PR #333（✅マージ済）**: 受信版ウォッチドッグ `runRecvWatchdog`＋`recvTimeout` を実装。サーバの
  EventStream 定期 keepalive frame と、Heartbeat unary 応答の `x-edr-keepalive` ヘッダで `serverKeepalive` を
  latch し、**接続直後から**半開き（keepalive が一度も来ない "half-open from birth"＝ハ―ピンNAT の破綻モード）を
  検知して自己回復する。＝当初「受信版ウォッチドッグが要る」とした仮説はこの PR で実装済み。
- **ネットワーク層＝PR #334（同居/ハ―ピンNAT の真因）**: nft `forward` チェーンの `established,related` 許可欠落
  （iptables とのパリティバグ）で、EDRサーバ同居時に管理ストリームが FORWARD 経路を往復し**隔離適用後 +11 秒で
  死亡**していた。nft forward に established 許可を追加＋`EDR_ISOLATION_COLOCATED` で受信方向のみ自ホストIP許可。
- ★**計測の訂正（残置）**: 「手動 API 隔離が agent に届かない」の当初判定は**検証スクリプトが iptables だけを
  見ていた**誤り（この host の agent は **nftables** を使う）。**隔離自体は動作する**。FW 隔離の確認は iptables と
  nftables の**両方**を見る。

### P5-4. 検証EC2 が stale なコンテナイメージを動かし続ける（運用ハザード）— 🟡 運用で復旧（恒久解は予算復旧後）
`docker.yml` が課金で自動再ビルド/再配信されないため、検証EC2のコンテナは古い `:main` イメージ（例: 2026-06-25 ビルド）
のまま残りがち（server イメージは docker.yml 手動 dispatch 必須）。2026-06-30、堅牢性スイートの**大量再接続 churn が
stale な ingestion イメージの潜在クラッシュを誘発**＝`kizashi-ingestion` がクラッシュループ（restarts=40、
panic=`comparing uncomparable type context.CancelFunc`：旧 `handler.go` の
`defer streamSupersede.CompareAndDelete(agentID, cancel)` が比較不能な func 値を CompareAndDelete）。
★**このコード自体は現 main では既に削除済み**（バグは古いイメージにのみ存在）。復旧手順は
[EC2デプロイメモv1.1.0.md](../ops/EC2デプロイメモv1.1.0.md) の追記参照（ソースを main へ `git reset --hard origin/main`
→ `IMAGE_TAG=main docker compose build <svc>` → `up -d --no-deps <svc>`）。**教訓**: 検証/採点の前に対象コンテナの
イメージ鮮度（`docker inspect --format {{.Created}}`）を確認し、必要なら main から再ビルドする。

- 実例: auth ブルートフォース(T1110)が `field: eventName`/`value: 4625`（正規化は `action=failed`）で**一度も発火せず**（PR #346）。

  **inert**（ever_fired=0 で実証、PR #349/migration291）。5検知器のアラート保存が非UUID RuleID(22P02)/存在しない

- **根本対策＝フィールド契約 CI ゲート（PR #349）**: field-support ゲートを behavioral(SequenceEngine)ルールへ拡張

### P5-6. FP自動隔離の `quarantined⟹disabled` 不変条件の破れ — ✅ 根治（PR#354, migration 292, 2026-07-02）
FP自動隔離で `curate_state='quarantined'` になったルールが `enabled=true` のまま**発火し続ける**不整合（3ルールで424 FP/24h）。
quarantine 時に `enabled=false` も保証し、既存の不整合行（quarantined+enabled 3件 / deferred+enabled 96件=inert）を是正した。
CHECK 制約 `rules_quarantine_disabled_check` で再発を構造的に防止（[検知率向上_20260702_curate衛生とplatformゲート.md](../検知率向上_20260702_curate衛生とplatformゲート.md)）。
併せて **CurateScheduler の毎 tick に `ReconcileQuarantined()` を常駐**させ、後続の手動/API 一括有効化で隔離済みルールが
再び有効化されても自動で再無効化する二重防御（`metrics.CurateQuarantineReconciled`／Prometheus `EDRCurateQuarantineReenabled`, PR#357）。
`File and Directory Discovery - MacOS` が Linux プロセスに誤マッチする件は RuleEngine の platform ゲート欠落 → PR#356 で是正。

### P5-8. 相関エンジンのビルトインルールが本番経路で永久 inert — ✅ 根治（commit 3e1ab87, 2026-07-20）
P5-5/P5-7 と同一の「消費側が、流れてこないトークンを参照して永久 inert」クラスが、**3系統目の相関層
（`internal/correlation`）**でも起きていた。出荷ルール `corr-001`〜`corr-005` は Sysmon 風サブタイプ
（`auth_failure`/`credential_dump`/`file_encrypted`/`network_connection` 等）で `EventTypes` を突き合わせるが、
`AlertPipeline` はベースカテゴリ（`auth`/`process`/`file`/`network`）しか `ProcessAlert` に渡さず、完全一致
フィルタのため**5ルールとも `MinEvents` に到達できずインシデントを1件も生成できなかった**。
- **根治**: ベースカテゴリ＋MITREテクニックからサブタイプ集合を導出する `DeriveEventSubtypes()`（新規
  `classify.go`）を追加。パイプラインがテクニックを相関エンジンへ伝播。高severity・低閾値ルール（ランサム/
  資格情報ダンプ）はテクニックでゲートし誤検知を防止。
- ★教訓（P5-5 と同型）: **既存テストが `ProcessAlert` にサブタイプを直接与えており、本番パイプラインが決して
  渡さない入力でルールを発火させてバグを隠蔽**していた（前スプリントの「相関5ルール end-to-end 固定」は
  end-to-end になっていなかった）。本番と同じベースカテゴリ＋テクニックで駆動する発火・誤検知ゲート回帰
  テスト（`builtins_fire_test.go`）を新設。詳細は [検知率向上_20260720_相関レイヤ不発の是正.md](../検知率向上_20260720_相関レイヤ不発の是正.md)。

### P5-9. パリティルールの `builtin-parity` が `rules_source_check` 違反で api-server 起動を阻害 — ✅ 解決済み（2026-07-20 発見 / 2026-08-01 修正）
パリティ移行 **318–356**（Two-engine parity ルール群）は `source = 'builtin-parity'` で `rules` テーブルへ INSERT するが、
`rules_source_check` 制約を定義する移行 **001（作成）/ 276（再定義）** はこの値を許可していなかった（`community`/`custom`/
`threat-intel`/`ai-generated`/`builtin`/`sigmahq` のみ）。
- **実際の故障モード（当初記録「無言 drop」は誤り）**: CHECK 制約違反は**無言 drop ではなく HARD ERROR**。実 Postgres で
  移行 318 を適用すると `ERROR: new row for relation "rules" violates check constraint "rules_source_check"` が発生し、
  トランザクションが abort → `store.RunMigrations` がエラー返却 → `cmd/api/main.go` の `os.Exit(1)`。つまり
  `RUN_MIGRATIONS=true` の api-server が**起動不能**になり、318 以降の移行も一切適用されない（318–356 の 132 行は 0 行挿入）。
- **なぜテストで捕捉されなかったか**: `migration_parity_test.go` / `migration_rules_test.go` は移行 SQL を**直接パースして
  インメモリ RuleEngine にロード**するだけで、制約付き DB へは挿入しない。DB を張る `integration_test.go` は
  `//go:build integration` タグ + `TEST_DB_URL` 必須で通常 CI では走らない（P5-5/P5-7 と同じ「テストは緑・本番は不発」）。
- **修正（実施済み）**: 移行 **318 の先頭**に `rules_source_check` の冪等な広げ込み（276 の許可集合 + `'builtin-parity'`）を
  prepend。**新規の後続移行では不可**——移行はソート済みファイル名順に適用されるため 357 では 318 の後になり手遅れ。
  318（`builtin-parity` を最初に INSERT する移行）自身が INSERT 前に制約を広げる。実 Postgres で
  本番相当（watermark 314 → 315/316/317 → 318）を再現し、132 行が正しく seed されることを確認済み。回帰ガードとして
  `migration_source_constraint_test.go` を新設(DB 不要): 全移行の INSERT `source` が制約許可集合の部分集合であることを
  検証し、許可外の `source` を導入したら CI で赤くなる（fix を外すと実際に赤くなることも確認済み）。

### P5-10. `status='inactive'` を書き込み側だけ導入し読み出し側が未追随 — ✅ 根治（2026-08-02）
migration 315/330 で `agents.status` の CHECK に `'inactive'` を追加し、`DeadAgentCleanup` の
`SET status='inactive'`（30日以上未確認）が通るようになった。しかし **`'offline'` を「生きていない」の
唯一のセンチネルとして扱っている読み出し側が追随しておらず**、退役済みホストが「生きている」側へ回り込んでいた。
P5-5 / P5-7 / P5-8 と同じ「語彙の片側だけ更新」クラス。今回は inert ではなく**過剰発火**に出た。
- **最も重い退行＝オフラインアラートの無期限量産**: `detection/heartbeat_monitor.go` の
  `WHERE a.status NOT IN ('isolated','offline')` は「落ちたばかりのホスト」を拾う意図だが、`'inactive'` が
  除外語彙に無いため 30日死んだホストが**「たった今オフラインになった」と再判定される**。同クエリ内の
  重複抑止は直近 10 分のみ、既定チェック間隔は 2 分なので、退役ホスト 1 台につき severity 7 のアラートが
  **約10分ごと（≒144件/日）に無期限**で生成される。`scheduler.HeartbeatMonitor` は `status='online'` の行しか
  UPDATE しないため `'inactive'` は元に戻らず、自然解消しない。実 DB で該当行が返ることを実測済み。
- **修正した読み出し側**（新規マイグレーションは不要）。2 セッションが並行して同じ領域を調査したため担当が分かれた:
  - **PR #608**: `detection/heartbeat_monitor.go`（核心）/ `autoupdate/manager.go`（一括アップデートの配信対象）/
    `api/handlers/ueba_handler.go`（エンティティ異常）/ `store/agents.go ListExpiringAgents`（証明書失効警告）の
    除外語彙追加、死活サマリ（`router.go` ×2 / `reports/generator.go` / `ops_report_handler.go` ×2）の offline 合算、
    `frontend/types/api.ts` の型追加。
  - **#608 の分類から漏れていた 2 箇所（別 PR で対応）**: `api/handlers/alerts_handler.go`
    （`total` は inactive を含むのに内訳 switch が入れず `total ≠ online+offline+isolated` になる）と

### P5-13. Fast-Flux 検知の誤検知でFPソークゲートが main 上で赤に — ✅ 是正（2026-08-03）

PR #447 が**自分のFPソークを赤くしたままマージされ**、以降すべてのPRがこのゲートを引き継いだ
（IPBlock の件と同じ「赤いままマージ」パターン）。2026-08-02 の main 定期実行の実測:

```
全体: 579件 = 347,395/1000ホスト/日  (ベースライン 445 = 266,999、許容 +42,000 に対し +80,396)
❌ 新規FP "Fast-Flux疑い: 'co.jp'"        20件 (全20ホスト)
❌ 新規FP 'jsdelivr.net' 14 / 'microsoft.com' 12 / 'bing.com' 10 / 'google.com' 10
❌ "[KILLCHAIN] 多段攻撃の疑い" 3,599 → 10,199
```

原因は**3つ**あり、いずれも「良性を良性と扱えていない」形だった。

**① `registrableAndSub` が多ラベル公開サフィックスを扱えない**
`www.example.co.jp` → `co.jp`。**フリート全社のトラフィックが1バケツに潰れる**。
`co.jp` が全20ホストで発火したのはこれで、単なるラベル誤りではなく
「どの単一ドメインも出していない集計量で閾値を超える」状態だった。
`multiLabelPublicSuffixes` を追加（完全なPSLではない実務的部分集合。
未収録は従来の2ラベル動作に劣化するだけで壊れない）。

**② Fast-Flux 検知器のキーが登録ドメインだった**
Fast-Flux は**ひとつの名前**が住所集合を回す現象であって、組織の性質ではない。
登録ドメインで束ねると、dc01/dc02/fs01/wks-… がそれぞれ正当に別ネットブロックの
自分のアドレスを持つ組織は、**ホスト数が閾値を超えた時点で自動的に Fast-Flux に見える**。
`google.com` / `microsoft.com` 等の誤検知も、多数のサブドメインが同じように
プールされた結果である。キーを FQDN に変更（良性親リストの照合は登録ドメインのまま
＝CDN1件の登録で配下サブドメインを覆える性質を維持）。

**③ fleet-sim がDNS応答を毎回ランダムIPで返していた**

```go
func (g *Generator) publicAnswer() string {   // 修正前
    return fmt.Sprintf("%d.%d.%d.%d", 20+g.rnd.IntN(200), g.rnd.IntN(256), ...)
}
```

同じ名前が引かれるたびに**別の /16** へ解決される。応答IPを見る検知器は
**構造上すべての良性トラフィックで発火する**。これは検知器の問題ではなく計測基盤の問題で、
より重い意味を持つ——FPソークは「ここのイベントは全て良性、ゆえに全アラートは誤検知」
という前提の上に成り立っている（`tests/fpsoak/README.md` の設計原則①）。
**偶然に悪性の形をしたテレメトリはその前提を壊し、シミュレータの非現実性を検知器の
誤検知として請求する**。名前からハッシュで安定した /16 内の少数アドレスを返す形に変更。

- ★教訓: **計測基盤自身が測定対象になる。** ベースライン445は Fast-Flux 検知器が入る前の値で、
  応答IPを見る消費者が居なかったため③は露見しなかった。新しい検知器が入った瞬間に、
  古い計測基盤の非現実性が「検知器の退行」として現れる。
- 回帰ガード `dns_registrable_test.go`: 多ラベルサフィックス分割、別組織が同一バケツに
  入らないこと、**企業の複数ホストで発火しないこと**、そして**単一名の実際のFast-Fluxでは
  発火すること**（誤検知を消す最も安い方法は何も検知しなくなるまで絞ることなので、
  良性側だけのテストでは守れない）。②は最初に書いた良性側テストが実際に赤くなって発覚した。

### P5-15. Wazuh 取込経路が CHECK 違反で全損していた（4欠陥） — ✅ 根治（PR #574, 2026-08-03）
Wazuh 連携の取込経路に 4 件の欠陥。3 件は**例外が上がらず静かにデータが消える**種類で、

- **`23514` — 未登録ホスト由来のアラートが 1 件も保存されていなかった**: `ingest_handler.upsertAgent` が

  含み AIX/Solaris が Linux に化ける）。`SanitizeIP` は Wazuh の `"any"` による `22P02` 全損の予防。

### P5-17. LOLBin ルールが「その実行ファイルなら必ず付く」トークンで発火していた（非弁別セレクタ）— ✅ 是正（2026-08-02、番号は再採番）

Sigma の selection リストは **OR** なので、そこに並べたトークンは1つ1つが**単独で十分な一致条件**になる。
ところが4つのビルトインルールが、**その実行ファイルの起動なら良性・悪性を問わずほぼ必ず付く**
トークンを混ぜていた。結果、日常運用で高severityアラートが鳴り続ける。

| ルール | 非弁別トークン | なぜ弁別しないか |
|---|---|---|
| CertUtil Used for File Download (T1105) | `-decode` / `-encode` / `-decodehex` | **ネットワークに一切触れないローカル変換**。完全オフラインの `certutil -decode` が「for File Download」という題のアラートを出していた（2026-07-18 良性バッテリで確認済みのFP） |
| CMSTP Suspicious Execution (T1218.003) | `.inf` | cmstp.exe の**全起動で必須の引数**。通常のプロファイル導入が毎回発火 |
| InstallUtil Proxy Execution (T1218.004) | `/u` | ごく普通の .NET サービスアンインストール。ルールの説明文自身が「while suppressing output」と言っているのに、出力抑制と無関係に発火 |
| Odbcconf Proxy Execution (T1218.008) | `/a` / `.dll` | `CONFIGSYSDSN` など**全アクションで標準の構文**。定型のODBCドライバ設定が高severityで発火 |

**誤検知は「うるさい」だけの問題ではない**。日常業務で鳴り続ける高severityルールは分析者に無視され、
そのルールが本来書かれた真陽性も一緒に捨てられる。P5-5/P5-7/P5-10 の「鳴らないルール」と、
**結果として検知されない**という点では同じである。

- **是正**: certutil はルールを2つに分割（ダウンロード=T1105 / ローカル復号=T1140）。両方に該当する
  ダウンロード＋復号の連鎖ではダウンロード側だけが発火するよう、ローカル側に除外セレクタを置いた。
  技術IDが変わるので**分析者が何が起きたか区別できる**——単に絞るのではなく分割した理由はこれ。
  他3件は、その技術が実際に依存するトークン（`/s`・`/ns` / 出力抑制オプション / `REGSVR`）に限定。
- **回帰ガード**: `certutil_fp_test.go` / `lolbin_condition_fp_test.go`。**良性側と真陽性側の両方**を固定する。
  誤検知を消す一番安い方法は「何も検知しなくなるまで絞る」ことなので、片側だけのテストは意味がない。
- **併せて T1048.003 の穴を塞いだ**: T1048 アップロードツールのルールは curl / wget / tftp /
  Invoke-WebRequest を見ていたが、**全 Windows ホストに最初から在る `ftp.exe` だけが抜けていた**
  （ダウンロードもインストールも要らない転送クライアント）。ただし put/get は対話セッション内で
  打つのでコマンドラインからは方向が分からない。素の `ftp.exe` を条件にすると**起動しただけで鳴る**ため、
  LOLBAS 記載の無人スクリプトモード `-s:` を条件にした。`Image|endswith: \ftp.exe` と区切り込みで
  書いているのは `tftp.exe` を巻き込まないため（テストで固定）。
- ★教訓: **「そのバイナリが使われたか」ではなく「その技術が使われたか」を書く**。バイナリ名＋必須引数は
  前者にしかならない。

導き、Go ソースの `INSERT` 列リストと突き合わせる。SQL パーサではなく契約テストであり、

検査は 2 方向ある。

- **A: 存在しない列を指定していないか**（`TestEveryInsertColumnExistsInMigrations`）
- **B: NOT NULL かつ DEFAULT 無しの列を省いていないか**（`TestEveryInsertSuppliesRequiredColumns`）

#### `CREATE TABLE IF NOT EXISTS` は既存テーブルに対して NO-OP である

これが本クラスの根であり、初版（#630）の抽出器はここを取り違えていた。コメントには正しい意味論を
書きながら、実装は**2 回目以降の宣言の列も足し込む和集合モデル**だった。

和集合は「間違える方向」が悪い。DB に存在しない列を「ある」と報告するので、`audit_logs`
（006 vs 173）や `yara_rules`（041 vs 174）を壊したのと**まさに同じバグに対して緑のまま**になる。
現在このツリーには 2 回目の `CREATE` でしか宣言されない「幻の列」を持つテーブルが 6 つある
（`response_actions` 001/008、`yara_rules` 041/174、`incident_playbooks` 086/162、
`email_security_events` 094/170、`deception_events` 116/165、`api_endpoints` 124/168）。

#638 で `migrate.go` と同じ順序（ファイル名順 → ファイル内はソース順）で migration を再生する
厳密モデルに置き換え、`DROP TABLE` も扱うようにした。Go の INSERT が幻の列を使っている箇所は
**0 件**だったため、厳密化のコストはゼロだった。

#### 「B クラスは判定不能」は誤りだった

#630 の時点で「同じファイルに `CREATE TABLE IF NOT EXISTS`（NOT NULL）と
`ALTER ADD COLUMN IF NOT EXISTS`（nullable）が併存するので判定不能」と報告したが、これは和集合
モデルを前提にした結論で、**順序を正しく再生すれば決定可能**である。367 テーブル中 326 が
「NOT NULL かつ DEFAULT 無し」の列を持ち、380 の INSERT に対して違反 0 件だった（#630 の修正が
このクラスを取りこぼしていなかったことの裏付けでもある）。

主キーは「NOT NULL だが DEFAULT 無し」として扱う。`id UUID PRIMARY KEY` に DEFAULT が無ければ
INSERT は本当に値を要求するので、主キーを常に「DEFAULT あり」とみなすとそれを隠す。両方の扱いで
違反 0 件になることを確認したので、厳しい方を無償で採れた。

#### 教訓: 検査器自身が 2 回、偽陽性を出した

- **#630**: `ALTER TABLE` の複数句のうち最初の 1 つしか読まず、migration 202 が確かに追加している
  `ioc_entries.source_feed` を「存在しない」と報告した（偽陽性 24 件）。
- **#638**: `ALTER TABLE` が未知テーブルにエントリを作り、後続の `CREATE TABLE` を「再宣言＝NO-OP」
  と誤判定した。migration 179 は `DO` ブロックの ELSE 分岐で `CREATE` し、IF 分岐の `ALTER` が
  ファイル上先に現れるため、`detection_rules` の 4 列を「存在しない」と報告した。

どちらも「検査器が、それが検出するために存在するバグのクラスを自分で再現した」形である。
**誤報を出す検査器は無効化され、無効化された検査器はゼロと同じ価値になる**ので、この種の作業では
検査器自身の正しさの検証（変異テスト）が本体と同等に重要になる。

### P5-22. Sigma ルール 4 件の YAML 重複キーで弁別条件が黙って落ちていた — ✅ 是正（migration 371 + CI ゲート, 2026-08-03）

`rules` テーブルの Sigma ルール 4 件が、同じ selection 内で `CommandLine|contains` を
**2 回定義**していた。YAML では重複キーは不正であり、受け付けるパーサでは**後勝ち**になる。
つまり 1 つ目のキー——どの例でも「どのバイナリか」を決める弁別条件——が黙って捨てられ、
2 つ目の OR リストだけが残っていた。

効果は「ルールが緩くなる」ではなく**別のルールになる**である。

| ルール | 意図 | 実際 |
|---|---|---|
| Archive Collected Data (Linux) | `'tar '` かつ (作成フラグ) | (作成フラグ) のみ。`' cf '` や `--create` を含む任意のコマンドラインで発火 |
| Suspicious chmod of Executable in /tmp | `/chmod` かつ (`+x`\|755\|777) かつ (`/tmp/`\|`/dev/shm/`) | `/chmod` かつ (ディレクトリ)。`chmod -R g+w /tmp/build` でも発火 |
| Suspicious wscript/cscript Execution | スクリプトホスト かつ (拡張子) かつ (書込可能ディレクトリ) | ホスト かつ (ディレクトリ)。拡張子の条件が消える |
| Data Exfiltration via curl/wget Upload (Linux) | `'curl'` かつ (アップロードフラグ) 等 | (アップロードフラグ) のみ。`' -T '` や `' -d @'` は汎用的すぎる |

#### ★ 誤検知への効果は測定の結果ゼロだった（当初の見立ては誤り）

当初「この 2 件が誤検知 439 件のうち 29 件（約 6.6%）を出している」と報告したが、**これは誤り
だった**。ルールが FP 一覧に載っていることから発火経路を確認せずに推測したもので、修正前後の
FP ソークで数値は動かなかった。

| ルール | 修正前 | 修正後 |
|---|---|---|
| Archive Collected Data (Linux) | 17 件 | **17 件** |
| Suspicious chmod of Executable in /tmp | 12 件 | **12 件** |
| 総数 | 439 件 | 436 件 |

総数の −3 は、キルチェーン（8→7）・RDP ブルートフォース（8→7）・C2 ビーコン（3→2）・
SSH authorized_keys（13→12）・マルウェア投下（11→12）といったステートフル検知器の
**run 間ばらつき**であって、本修正の効果ではない。

測定後に実際の発火理由を特定した。

- **chmod**: 良性プロファイル（`tests/fpsoak/profiles/dev-machine.toml:136`）の
  `chmod +x /tmp/installer-{{rand}}.sh` が、**修正後の「意図どおりの」ルールに完全一致**する。
  開発者が日常的に行う操作であり、これは YAML 欠陥ではなく**ルール設計そのものの非弁別性**である。
- **Archive Collected Data**: 良性プロファイル（`backup-server.toml:60`）の
  `tar --zstd -cf /vault/...` が、本修正で触っていない `ziptools` 分岐（`zstd ` などが**単独で十分**）
  で発火している。P5-17 と同じ非弁別セレクタが別の分岐に残っている。

本項の修正はルールを意図どおりの意味に戻すもので、それ自体は正しく、**P4-6（DB Sigma を
リアルタイム経路で評価する）の前提条件**でもある（パースできないルールは載せられない）。
ただし**誤検知削減の効果は無かった**。上記 2 つの非弁別セレクタは別途の課題として残る。

> **教訓**: 「FP 一覧に載っているルールに欠陥が見つかった」から「その欠陥が FP の原因である」は
> **導けない**。発火経路を確認するか、修正前後で測るかのどちらかが要る。今回は測って初めて
> 分かった。

#### 続き — 真の原因だった `ziptools` 分岐を是正（migration 372）

測定で特定した 2 つの非弁別セレクタのうち、**Archive Collected Data 側を是正した**。

```yaml
# 修正前 — 「そのツールを起動したか」であって「技術が使われたか」ではない
ziptools:
  CommandLine|contains: ['gzip ','bzip2 ','zip ','xz ','zstd ','7z ','7za ','rar ']
condition: (tar_bin and tar_create) or ziptools
```

P5-17 の LOLBin で是正したのと同じ形——「実行ファイルなら必ず付くトークン」が単独で十分——が、
別の分岐に残っていた。

**弁別子は「圧縮したか」ではなく「収集した機微データを固めたか」である。** T1560.001 は
Archive **Collected Data** であり、収集・ステージングされた機微情報が対象であることが技術の
要件である。アーカイブ作成の動作に加えて、対象が機微パス（`/home/`、`/etc/`、`.ssh`、
`.aws`、`staged`、`loot` 等）であることを要求する形にした。

| コマンド | 種別 | 修正後 |
|---|---|---|
| `tar -P -zcf /home/ubuntu/staged.tar.gz /home/ubuntu/staged` | TP（Caldera Thief 実測） | 発火 ✅ |
| `gzip -9 /home/ubuntu/loot/dump.sql` | TP（同上） | 発火 ✅ |
| `tar --zstd -cf /vault/... /srv/data/share` | 良性（バックアップ） | 沈黙 ✅ |
| `tar -czf /tmp/artifact ./dist` | 良性（ビルド） | 沈黙 ✅ |

`gzip`/`bzip2`/`xz`/`zstd` は既定動作が圧縮なので作成フラグを要求しない（上の TP が `-9` しか
持たない）。逆に `tar`/`zip`/`7z`/`rar` は展開もできるので作成動作を要求し、展開系は除外する。

精度と再現率のトレードオフは承知のうえである。機微パス一覧に無い場所からのアーカイブは
取り逃すが、**任意の圧縮コマンドで発火するアラートは読まれなくなる**方が損失が大きい。

#### ★ テストが「修正前の本文」を検証していた（P5-14 の再発）

コメント自身が「SQL を編集したらこのコピーも更新せよ」と書いていた。その注記では足りず、
migration 371 / 372 が本文を書き換えても**コピーは古い文面を検証し続けていた**

#### 続き — chmod ルールは重大度を下げた（migration 373）

もう一方の `Suspicious chmod of Executable in /tmp`（12 件）は、Archive と違い**セレクタを直す

実行権を与える」は**単一の process_creation イベントとして完全に同一**であり、区別する情報が

|---|---|---|
| 自動隔離 | `AutoIsolateSeverityThreshold` 既定 **9** かつ ルール側 `auto_isolate=true` | 本ルールは severity=7 / `auto_isolate=false`。**元から対象外**、影響なし |

⚠️ これは誤検知の**件数**を減らす変更ではない。ソークは重大度に関わらずアラートを数えるので

> **教訓**: 「重大度を下げると自動隔離に影響する」のような**依存の思い込み**は、保留の理由に

> 最初から存在しなかった。

### P5-29. migration の `UPDATE rules` を harness が取りこぼし、130 migration 前のルールを検証していた — ✅ 是正（PR #647, 2026-08-04）

`extractMigrationRules()`（`migration_rules_test.go`）は、DB ルールの**出荷される本文そのもの**を
読むために P5-14 で導入した harness である。ところがその抽出器が `UPDATE rules SET` の一部の
形を認識できず、**認識できなかった statement を黙って飛ばしていた**。

飛ばされた statement のルールは、harness 上では **INSERT された当初の本文のまま**になる。
つまり「ドリフトを無くすために作った仕組み」自体が、修正前の本文を検証していた——P5-14 と
同じ壊れ方の再発であり、今回は harness の内部で起きていた。

#### 見つかった取りこぼし 4 種

| 形 | 例 | 結果 |
|---|---|---|
| `SET severity = 4, content = $$…$$` | migration 373 | `SET content = $` を literal 要求していたため**何もマッチしない**。severity だけでなく本文書き換えも落ちる |
| `SET enabled = FALSE`（content 無し） | migration 313 | 対応パターンが無く、無効化されたルールを**有効のまま**報告 |
| `\$\$(.*?)\$\$` が自分の閉じ区切りを越える | migration 241 | 1 つ目の statement から**3 つ目の statement の `WHERE name IN`** まで 1 マッチ。IN に並ぶ 2 ルールに**別 statement の本文**が入る |
| assignment 部 `[^$]*?` が `;` を越える | migration 241 | 直前の statement の `SET` から**次の statement の `content =`** に届く |

後ろ 2 つは同じ誤りの別の節での現れである。**遅延量指定子は「その開始位置からの最短一致」しか
保証しない。開始位置が早すぎることは防げない。** RE2 に先読みは無いので、閉じ区切りを
越えられない形（`(?:[^$]|\$[^$])*`）と、statement 終端 `;` の明示除外で境界を与えた。

取りこぼしを直した結果、`TestMigrationRuleCoverage` の T1136.001 / T1003.008 が落ちた。
harness が **migration 241 の本文**をこの 2 ルールに結び付けていたためである。本番が実際に
走らせているのは **migration 243** で、241 → 242 → 243 と 2 回作り直されていた。

| | フィールド名 | 受け付ける値 |
|---|---|---|
| migration 241（harness が検証していた） | `Operation` | `write`, `modify`, `create` … |
| migration 243（本番が走らせている） | `operation` | `modify`, `create` |

テストのイベントは `"Operation": "write"` だった。**この形はプラットフォームが一度も出したことが
無い**——`ingestion/handler.go:1135` が `"operation": f.GetAction().String()` を入れるので、
実体は `FILE_ACTION_MODIFY` である。つまりこのケースは、**存在しないイベント形**に対して
**出荷されていないルール**を突き合わせて緑だった。イベントを実際の形に直した。

#### 再発防止

`TestEveryUpdateRulesStatementIsUnderstood` を追加した。migration 内の全 `UPDATE rules SET` を
数え、rule engine が読む列（`content` / `enabled` / `severity` / `auto_isolate`）を**代入して
いる**ものは、いずれかのパターンが実際にマッチしたことを要求する。現在 31/32。

残る 1 件（`292_curate_quarantine_invariant.sql`）は `unevaluablePredicates` に**理由付きで**
挙げてある。`source` + `curate_state` で一括無効化するため、`DetectionRule` が持たない列を

> **教訓**: 入力を認識できなかったときに**黙って飛ばすパーサは、失敗するパーサより悪い**。
> 前者はカバレッジに見える。そして「ドリフト検出のために作った仕組み」も検証対象であり、
> それ自身がドリフトしていないことを言えるのは、取りこぼしを数える別のテストだけである。

### P5-31. P4-6 が生んだ二重評価と、それを「重複ルール削除」で消せなかった件 — ✅ 是正（PR #647, 2026-08-05）

|---|---|---|
| server-api（`AlertPipeline`） | `rules` テーブル（P4-6 で追加） | `[Sigma] X` |

変わるのは評価するプロセスだけで、api が 1 回評価し detect は無効化行を読まない（2N → N）。

`internal/detection/db_rule_builtin_port_test.go` が両半分を結び付ける。テストイベントは
**旧 builtin が取り逃していたケース**（`wmic /node:` 単独・`sudo docker exec`・`crictl`）を

移設対象の抽出中に、`TestMigrationSigmaRulesParseInProductionEvaluator` の抽出器が

RE2 に後方参照が無く 1 本の正規表現に戻せないので、開き区切りを捕捉して閉じを索引で探す

> 374 は「builtin が DB を包含する 3 件だけ」と明記していたのに、こちらは方針名だけを

#### 続き — FP ソークのゲートが「どのプロセスが出したか」で採点していた

移設を入れた実測（`c891ccb`）で総量は **383 件 / 229,798** まで下がった

実際の増減はこうである：

| ルール | baseline（`[SIGMA]`＋`[Sigma]`） | 移設後 | 差 |
|---|---|---|---|
| 疑わしいPowerShell実行 | 26 | 22 | −4 |
| Container Administration Command | 12＋8 = 20 | 8 | −12 |
| Container Image Build on Host | 12＋8 = 20 | 8 | −12 |
| Linux Shell Init File Modification (FIM) | 12 | 8 | −4 |
| Suspicious chmod of Executable in /tmp | 12 | 8 | −4 |
| Script Execution from World-Writable Directory | 10 | 8 | −2 |
| WMI Remote Command Execution | 5 | 4 | −1 |

**全件が減っている。** 赤の原因は表題の接頭辞だった。`[SIGMA]` は server-detect が、

どのプロセスが出したか**を表す。スコアカードはこれを含む表題をキーにしていたので、

合算される（半分ずつ 2 回通す方が危険なので、これも意図した挙動）。
`TestBaselineLineupIgnoresEnginePrefixCase` は「静かになった移動」が通ることと
「騒がしくなった移動」が落ちることの両方を押さえる。

> **教訓**: **ゲートが赤いことは、退行があることを意味しない。** ここでは総量も個別も
> すべて改善していて、なお赤かった。ゲートの主張（誤検知が増えたか）と実装（表題文字列が
> baseline に在るか）がずれていた。「緑が正しいか」は疑うのに「赤が正しいか」は
> 疑わない、という非対称は自分の中にもあった。

### P5-24. プラットフォーム・ゲートが本番で no-op（エージェントが `EventBatch.Platform` を未設定）— ✅ 是正（2026-08-04）
`RuleEngine` の OS ゲート（#356, 2026-07-02）は `flatMap["platform"]` で判定する。値の出所は
`EventBatch.Platform`（`ingestion/handler.go:503` → `platformString`）だが、**エージェントはこの
フィールドを一度も設定していない**（`agent/` 配下に `Platform_PLATFORM_*` の代入が存在しない）。
結果 `platformString` は常に `"unknown"` を返し、`platformMatchesEvent` の fail-open 分岐
（`canonPlatform` が `""` を返す）で全ルールが通る。**ゲートは実質 no-op。**
- 症状として観測されていた: 2026-07-02 の Windows 計測で `Local System Accounts Discovery - **Linux**`
  が Windows ホストの `net user` に発火している（`live-20260702-windows-discovery-scorecard.csv`）。
  クロス OS 誤検知を消すために入れたゲートが、まさにそれを止められていない。
- fail-open 自体は意図的な設計（「稀なクロス OS FP のほうが、検知のサイレント消失よりまし」）なので、
  ゲートのロジックではなく**送信側が値を埋めていない**ことが欠陥。
- **修正 (2026-08-04)**: `GRPCClient.SendEvents` で `runtime.GOOS` から stamp する。
  各コレクタの batch 生成箇所（`cmd/agent` と `internal/collector` に十数箇所）ではなく
  トランスポート層に置いたのは、**per-site の stamp は必ずドリフトする**から——次に
  追加されるコレクタが忘れれば同じ穴が黙って再発する。`bufferBatch` は `SendEvents`
  内からのみ到達可能なので、オフライン・スプール経由の再送も同じ stamp を運ぶ。
- **棚卸しの結果、リスクは当初想定より小さい**: migration 由来で単一 OS ラベルを持つのは
  windows 69 / linux 51 / darwin 1 で、最多の 132 件は `ARRAY['linux','windows','macos']`
  ＝実質ユニバーサル。SigmaHQ 同期分も `inferPlatforms` が product 不明時に3種すべてを
  返すため、ゲートの影響を受けるのは logsource から OS を特定できたルールに限られる。
  加えて **api 経路の builtin Sigma にはゲートが無い**ので、そちらの被覆は不変。
- **無言の挙動変更にしないための可観測性**: `edr_rules_platform_gated_total{platform}` を追加。
  誤ラベルのルールはエラーも出さずに一致しなくなるため、この counter が唯一の外形的な兆候になる。
  エージェント更新後に跳ね上がり、かつ特定 OS の検知数が落ちていれば誤ラベルを疑う。
  緊急時は `SetPlatformGate(false)` で従来動作へ戻せる。
- **契約テスト**: `platform_contract_test.go` で ingestion の `platformString` が出す値を
  `canonPlatform` が全て解釈できること、未知 OS が fail-open すること、
  ラベル無しルールがゲートされないこと、darwin と macos が同一視されることを固定。
  ingestion 側は unexported のため値のミラーを持つ（`emittedEventFields` と同じ型）。
- ★教訓: **ゲートを入れるときは、判定に使う値が本番で埋まっていることを実データで確認する。**
  fail-open のゲートは「常に開いている」状態と「正しく動いている」状態が外形的に区別できない。
  #356 は正しいロジックを書いたうえで、**送信側が値を埋めていないことだけを見落として**
  出荷され、以後1ヶ月以上 no-op のまま気づかれなかった。
- ★教訓: **「両端で1つの契約」を作ったら、両端を1つのテストで結ぶ。** 片側だけの
  ユニットテストは、相手が値を送っていないことを永久に検出しない。

### P5-25. 状態付き検知器9種が server-detect にしか無く、api 経路に冗長性が無い — 🟡 可用性監視は実施済 (2026-08-04) / 冗長化本体は未着手
`AuthAttackScorer` / `FileBurstScorer` / `DiscoveryScorer` / `KillChainScorer` ほか、レート・相関系の
検知器はすべて `Engine`（server-detect）でのみ生成される（`engine.go` の 1 箇所）。DB ルールも
server-detect 専有。したがって **detection-engine が落ちる／ラグると、これらの検知は丸ごと消える**。
2026-07-26 の Windows 計測がまさにその状態で、窓内アラート 6 件が全部 builtin だった（P5-23）。
- 他の技法が部分点を取れたのは builtin に同等の per-event ルールがあったからで、**冗長性は
  「たまたま両方にルールがある技法」にしか無い**。設計として担保されていない。
- T1110 は特に埋めようがない: ブルートフォースはレート現象で、per-event Sigma では表現できない。
  api 経路に被覆を持たせるには `AuthAttackScorer` 相当を `AlertPipeline` にも置くしかない。
- 選択肢は (a) 状態付き検知器を両エンジンで動かす（状態が二重になるので dedup 設計が要る）、
  (b) 検知器を独立サービスに切り出して両方から使う、(c) 冗長性は諦め、代わりに
  **detection-engine の死活とラグを可用性アラートとして監視する**（最小コスト）。
- **(c) は 2026-08-04 に実施済み**。ただし着手して分かったのは、当初の
  「現状は『検知が出ていない』と『攻撃が無かった』が区別できない」という記述が**不正確**
  だったこと。必要なメトリクスは既にあった:
  `edr_detection_consumer_pending`（`engine.go` の `monitorConsumerLag` が定期採取）と
  `edr_detection_last_event_timestamp_seconds`（イベント処理ごとに更新する
  デッドマンズスイッチ）。Prometheus も `detection:8081` を scrape 済み。
  **欠けていたのは、それを鳴らす側だけだった。** `DetectionLastEventTimestamp` の
  doc コメントは当初から「数分を超えたらアラートせよ」と書いていたのに、そのルールが
  存在しないまま出荷されていた。→ `EDRDetectionDown` /
  `EDRDetectionPipelineStalled` / `EDRDetectionConsumerLagging`(+Critical) を追加。
- ★**その過程で、既存アラート2本が存在しないメトリクスを参照していたことが判明**:
  `CriticalAlertsUnacknowledged`→`edr_alerts_open_total`、`AgentOffline`→`edr_agents_offline_total`。
  どちらも emit されておらず、さらに最も近い `edr_open_alerts` は**宣言のみで書き込みが無く**
  永久に 0 だった。3件とも**一度も発火し得ない**状態。P5-23 の T1110 builtin
  （auth テレメトリが持たない `EventID` を選択していた死蔵ルール）と同じ形である。
  → gauge に writer を付け（`cmd/api/main.go` の 60 秒ポーラー）、ルールを実在名へ是正。
- **CIゲート化**: `TestAlertRulesReferenceRealMetrics` を追加。`prometheus_alerts.yml` の
  `expr:` に現れる `edr_*` 名を、`/metrics` が実際に出力する名前と突合する
  （他 exporter 由来の `up` / `node_*` / `pg_*` / `nats_*` は対象外）。
  P5-20 の教訓どおり**直してからガードを入れ**、意図的に壊して赤くなることも確認済み。
- 🟡 **残**: (a)/(b) の冗長化そのものは未着手。T1110 の api 経路被覆はゼロのまま。
- ★教訓: **二経路構成は冗長化ではない。** 役割が分かれているだけで、片方が落ちれば
  その経路が担当する検知は全滅する。冗長性を主張するなら、技法ごとに両経路の被覆を数える。
- ★教訓: **「監視が無い」と書く前に、メトリクスの有無と『鳴らす側』の有無を分けて確認する。**
  今回はメトリクスも scrape も揃っていて、アラートルールだけが無かった。
  台帳に書いた自分の記述もまた、実装と突合するまでは未検証の主張である
  （[[feedback_docs_are_not_design_intent]] と同じ）。
- ★**アラートルールは「静かな失敗」の温床**。存在しないメトリクスを参照するルールは
  健全な状態と外形が完全に一致し、レビューでも気づけない。名前の突合を機械化するまでは
  「ルールがある」を「監視されている」と読んではいけない。

### P5-26. Windows の認証イベントが購読経路で全損し、T1110 が原理的に検知不能だった — ✅ 根治（2026-08-05）
2026-08-05 の実機再計測で確定。Security ログに 4625 が実在し、エージェントは
「認証イベントをEvtSubscribeでリアルタイム購読します」とログに出しているのに、サーバへ届いた
`auth` イベントは **0 件**だった。`etw-verify` の auth 単独実行でも、検証窓の内側に
4625(08:46:06) と 4624(08:46:20) が実在した状態で 1 件も受信できないことを確認している。
- ★**修正と欠陥が別経路にあった**: 07-26 に直した `timediff()` は**ポーリング**経路
  (`buildAuthQuery`)のクエリ。この環境は `EDR_AGENT_ETW=1` のため**購読**経路を通っており、
  修正が適用される経路ではなかった。症状(auth 0 件)が同じだったため「解消済み」と誤認され、
  07-26 レポートにもそう記録されていた。**同じ症状は同じ原因を意味しない。**
- **真因**: `EvtNext` が FALSE を返したとき、戻り値だけ見て `ERROR_NO_MORE_ITEMS` と解釈していた。
  シグナルイベントは**自動リセット**で待機時に消費済みなので、ここで抜けると保留バッチは
  次のシグナルまで取り残され、次のパスも同じ競合を踏む。→ `GetLastError` で判別し、
  シグナル非依存の 2 秒 sweep で自己回復させる。
- ★**計器を2度も間違えた**。(1)「`Timeout=200` が原因」→ A/B で否定(`0` でも同じエラー)。
  (2)「`ERROR_INVALID_OPERATION` は失敗」→ 購読ハンドルの「今は空」の返し方であり、
  `SetLastError(0)` 後も出るうえイベントは正常配送される。**誤報する計器は出荷できない**ので、
  呼び出し単位のノイズは黙らせ、警報を結果側(「購読中なのに配送 0」)へ移した。
  健全なアイドルと機能停止が外形で区別できる配分にすること。
- **副次で見つけた誤検知**: 4648(明示的資格情報でのログオン**試行**)を無条件に `Success=true` と
  していた。`ValidateCredentials` は失敗 1 回につき 4625 と 4648 をペアで出すため、
  `AuthAttackScorer` が「失敗多発のあとの成功」と読み、**存在しないアカウントに対して
  severity 8 の「ブルートフォース成功＝アカウント侵害」を捏造**していた(実機で観測)。
  `AuthEvent.Success` は bool で「試行・成否不明」を表現できず、4648 の消費者も存在しない
  (Sigma ルールが参照せず、auth に `EventID` も導出されない)ため、収集対象から外した。
- ★**CI の死角を塞いだ**: `parseAuthEvent` は純粋な文字列処理なのに `//go:build windows` 配下に
  あり、Linux CI から一度もコンパイルされていなかった。`auth_query.go` が同じ理由で切り出された
  前例に倣い `auth_parse.go`(タグ無し)へ移し、回帰テスト 6 件を追加。
- 実測: 修正後は `failed` 7 件が届き、`[HEURISTIC] パスワードスプレーの疑い` が MTTD 2 秒で発火。
  偽の「ブルートフォース成功」は出なくなった。
- 詳細: [検知率向上_20260805_未検知4技法の実機解消.md](../検知率向上_20260805_未検知4技法の実機解消.md)

### P5-27. ETW セッションが終了時にリークし、次回起動を壊す — ✅ 根治（2026-08-05）
シャットダウン時に ETW セッションが OS に登録されたまま残る。**正常な `Stop-Service` でも起きる。**
実機では停止のたびに `logman query -ets` に "NT Kernel Logger" と `EDR-Agent-*` が残り、
残る顔ぶれは毎回違った。その状態で起動するとサービスは running を報告した 1 秒後に落ち、
**ログには何も出ない**。2026-08-05 の作業では、エージェントを再起動するたびに手動で
`logman stop` を叩く必要があった(この切り分けだけで数時間を要した)。
- **真因はシャットダウンの競合**。supervisor は `go superviseETWSession(ctx, ...)` という
  裸のゴルーチンで、どの WaitGroup にも登録されていなかった。コレクタの `Start()` は
  ゴルーチンを起こした時点で返るため main の `wg.Wait()` は即座に満たされ、main が return して
  プロセスが終了する——supervisor が teardown を走らせている最中に。**teardown 自体
  (`session.Stop()`)は正しく書かれていたが、到達する前に殺されていた。** 残る顔ぶれが毎回
  違うのは競合そのものの兆候である。
- 修正: supervisor を WaitGroup で追跡し(`Add` はゴルーチン開始**前**——後ろだと `Wait` が
  素通りする)、シャットダウン経路で `waitPlatformShutdown(10s)` を待つ。待ちは有界にし、
  タイムアウト時は復旧コマンド(`logman stop`)を添えて警告する。
- 実測の対照: 旧バイナリ停止後 **9 件残存** / 修正版停止後 **0 件**。掃除なしの再起動も成功。
- 🟡 **未確定**: 「残骸があると起動が失敗する」という因果は証明できていない。`startETW` は
  失敗時にポーリングへフォールバックする設計で、即死の説明にはならない。相関は再現性が
  あるが、リークを塞いだことでこの条件自体が消えたため追跡は打ち切る。
- ★教訓: **`Start()` が即座に返る非同期コレクタは、`wg.Wait()` の対象になっていない。**
  プロセス外に残る状態(ETW セッション、カーネルオブジェクト、ドライバ登録)を持つ処理は、
  終了待ちを明示的に配線しないと必ず競合する。

### P5-28. 「異常なプロセス実行」検知が、プロセス以外のイベントを数えていた — ✅ 是正（2026-08-05）
デプロイ直後の実機で `異常なプロセス実行パターン: kernel32.dll` / `crypt32.dll` /
`System.Web.ni.dll` … が**DLL 1件につき1アラート**の勢いで出ていた。DLL はプロセスではない。
2つの欠陥が重なっていた。
- **サーバ**: `DetectAnomalies` / `UpdateBaselines` のどちらも `event_type` で絞っておらず、
  `raw_data->>'process_name'` を持つ**全イベント種別**を横断して数えていた。`process_name` は
  process だけでなく **image_load / registry / file / network** も持つ。つまりこの検知器は
  「プロセス実行回数の異常」ではなく「その名前を含む任意のイベント数の異常」を測っていた。
  → 両クエリに `event_type = 'process'` を追加。**両方**必要である: 検知側は結果を
  `process_baselines` に INNER JOIN するため、片方だけ絞ると join が空振りして
  **検知が黙って止まる**(エラーではなく無音の欠落になる)。
- **エージェント**: `imageload_etw.go` が `ProcessName: filepath_base(img)` ——
  **ロードされた DLL 自身のベース名**を入れていた。ロード元プロセスではない。`ProcessID` は
  別途取得しているのに名前だけモジュール名になっていた。
  → verify ワーカー(ETW コールバック外)で PID から解決する。既存の `pidToName` を使う。
  コールバックスレッドで OpenProcess を呼んではならない——署名検証を `verifyCh` へ逃がして
  いるのと同じ理由(高頻度コールバックのブロックはイベント欠落を招く)。
  プロセスが既に終了している場合は**空のまま**にする: 不在は正直だが、誤った値は
  `process_name` の全消費者を静かに汚染する。
- **波及**: `alert_pipeline.go` の Image フォールバックは `image_path` が無いとき
  `process_name` を `Image` に入れる。したがって image_load イベントの Sigma `Image` にも
  DLL 名が入っていた。DLL サイドローディング系ルールが `Image`(ホストプロセス)と
  `ImageLoaded`(DLL)を突き合わせる場合、両方が同じ値になっていたことになる。
- **CIゲート化**: `TestAnomalyQueriesAreScopedToProcessEvents`。両クエリに
  `event_type = 'process'` があることを固定する。意図的に外して赤くなることを確認済み。
- ★教訓: **フィールド名が共通というだけで、意味まで共通とは限らない。** `process_name` は
  5種類のイベントに現れるが、「実行されたプロセス」を意味するのは 1 種類だけ。
  JSONB からフィールドを引くクエリは、**どの event_type を対象にするかを必ず明示する。**
- ★教訓: **アラート疲れは検知の失敗と同じくらい重い。** 1 DLL につき 1 アラートは、
  本物の検知を埋もれさせる。今回は他の作業のログ確認中に偶然見つかった。

### P5-29. PowerShell スクリプトが BOM 無し UTF-8 で、`-File` 実行が構文エラーになる — ✅ 是正（2026-08-05）
`deploy/validation/README.md` に書かれているとおりのコマンドが**必ず失敗する**状態だった。

```
powershell -ExecutionPolicy Bypass -File .\deploy\validation\atomic-runner-compact.ps1
→ At C:\...\atomic-runner-<文字化け> ... char:50
   Missing closing ')' in expression.
```

- **原因**: Windows PowerShell 5.1（Windows Server の既定シェル）は、UTF-8 BOM が無い `.ps1` を
  **システム ANSI コードページとして読む**。日本語コメントを含むファイルは文字化けし、
  その結果クォートや括弧に化けたバイトで**実行前にパースが壊れる**。
- **範囲は検証ランナーだけではなかった**: リポジトリの `.ps1` 10 件のうち **8 件**が
  「非ASCII を含むが BOM 無し」だった。`agent/deploy/windows/Install-EDRAgent.ps1`
  ——**顧客が実行するエージェントのインストーラ**——も含まれる。
  唯一 `deploy/install/update.ps1` だけ BOM 付きで、過去に誰かが個別に直したと思われる。
- **エラーが誤誘導する**: 構文自体は正しいのに構文エラーとして出るため、原因がスクリプトの
  中身にあると読んでしまう。実際、07-26 レポートの「ランナー: `atomic-runner-compact.ps1` **相当**」
  という記述は、ファイル実行ではなくコンソール貼り付けで回避していた形跡である
  （＝この経路は一度も通っていなかった）。
- **CIゲート化**: `TestPowerShellScriptsWithNonASCIIHaveBOM`。非ASCII を含む `.ps1` に BOM が
  あることを固定する。ASCII のみのファイルは対象外（コードページが解釈を変えようがない）。
  意図的に BOM を外して赤くなることを確認済み。
- ★教訓: **「手順書どおりに実行する」経路は、誰かが実際に実行するまで検証されない。**
  貼り付けや対話実行で回避していると、ファイル実行の経路が壊れたまま何ヶ月も残る。
  ランブックに載せたコマンドは、そのままの形で 1 度は流すこと。
