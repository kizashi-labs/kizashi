### P0-1. モックデータを「実結果」として返すハンドラ
当初「7ハンドラ」と推測したが、**各コードを精査した結果、真の偽データは2件のみ**だった
（Explore調査が古いコメントを拾っていた）。精査結果と対応状況は下表のとおり。

| 対象 | 箇所 | 精査結果 | 状態 |
|------|------|---------|------|
| API Security `StartScan` | `api_security_handler.go:497` | 実際は `runOWASPScan` で**本物のOWASPパッシブスキャン**（HSTS/CSP/CORS/Server漏洩等を実HTTPプローブ）。L496のコメントが古いだけ | ✅ コメント修正済 |
| Report Template `Preview` | `report_template_handler.go:181` | `buildSectionContent` が `alerts`/`agents`/`incidents` に**実COUNTクエリ**。「実データから生成」と明記済 | ✅ 既に実装済 |
| **Cloud SIEM `ExecuteQuery`** | `cloud_siem_handler.go:437` | ハードコード配列から**乱数で10件の偽ログ**を生成し本物として返していた | ✅ **503化済（本PR）** |
| **Incident Pattern `RunAnalysis`** | `incident_pattern_handler.go:236` | `rand.Float64()` の乱数信頼度で**偽のパターンマッチをDB挿入**していた | ✅ **503化済（本PR）** |
| Deception `SimulateTrigger` | `deception_handler.go:346` | `"simulated":true` / `source:"manual_simulation"` / RFC5737 TEST-NET明示の**正当なシミュレーション機能** | ✅ 対応不要 |
| Honeypot `SimulateAccess` | `honeypot_handler.go:353` | `Simulate` エンドポイントで手動トリガー。記録自体は本物 | ✅ 対応不要 |
| Compliance Evidence `TriggerCollection` | `compliance_evidence_handler.go:163` | 収集イベント自体は実DB挿入。ただし content が `"スナップショット at <時刻>"` のプレースホルダ | 🟡 P2へ（[P2-3](#p2-3-compliance-evidence-の中身が空)） |

**フロント側にも偽データ生成器があった（本PRで併修）:**

| 対象 | 箇所 | 問題 | 状態 |
|------|------|------|------|
| siem-query-builder | `frontend/app/admin/siem-query-builder/page.tsx` | `/siem-queries/execute` のバックエンドルートが**存在せず**、毎回catchに落ちて `generateMockResults` で**常に偽の検索結果**を表示していた | ✅ mock除去＋準備中バナー登録（本PR） |
| cloud-siem クエリタブ | `frontend/app/admin/cloud-siem/page.tsx:224` | `handleExecuteQuery` が600msの偽の実行遅延で空結果を演出 | ✅ 準備中トースト化＋部分バナー（本PR） |

**本PRでの対応方針:** 偽データを返すより 503/準備中の方が誠実、という原則で統一。バックエンドは
503＋明確な準備中メッセージ、フロントはモック生成器を除去し `apiFetch` のエラーメッセージを表示、
バックエンド皆無の `siem-query-builder` は `BACKEND_PENDING_ROUTES`、一部準備中の `cloud-siem`/
`incident-patterns` は `PARTIAL_PENDING_ROUTES` に登録。実ログ検索エンジン／インシデント相関
エンジンの実装は別タスク（P3相当）。

### P0-2. SSO SAML の XML 署名検証 — ✅ 実装済（本PR）
- **元の脆弱性:** `internal/saml/provider.go` の `ParseAndValidate` は base64デコード→XMLパース→
  status/時刻条件のみで、**XML署名を一切検証していなかった**。`idpCertPool` に証明書をロードするが
  一度も使われず、SSOCallback は証明書ロード失敗時も「検証スキップして続行」していた。
  → ACSエンドポイントに任意のSAMLResponseをPOSTすれば任意のメール/NameIDで有効JWTを取得できる
  **完全な認証バイパス**だった。
- **対応（本PR）:**
  - `goxmldsig`（pure-Go、cgo不要）でXML-DSIG署名検証を実装。署名は信頼するIdP証明書（厳密一致）で
    検証し、**フェイルクローズ**（証明書なし/署名なし/改竄/別証明書/暗号化アサーションは全拒否）。
  - 署名検証済みの要素からのみID情報を抽出し、**署名ラッピング攻撃**を防止。Response単位/Assertion単位
    の署名どちらにも対応（Response署名を推奨）。
  - `SSOCallback`: IdP証明書が未設定/ロード失敗なら認証拒否（旧「検証スキップ続行」を撤去）。
  - 署名往復テスト11件追加（署名OK/署名なし拒否/証明書なし拒否/改竄拒否/別証明書拒否/期限切れ拒否 等）。
- **関連:** `EDR_SSO_STUB` 開発バックドアの本番誤設定ガードは [P1-3](#p1-3-edr_sso_stub-開発バックドアの本番誤設定ガード--実装済本pr) で対応済。
