### P2-6. migration 番号の一意性が誰にも守られていなかった — ✅ CI ゲート化（PR #647, 2026-08-04）

CLAUDE.md は「次の未使用番号を使う」としているが、この規約は静かに崩れていた。
**390 個の migration のうち 16 のプレフィクスが 2〜3 ファイルで共有**されている（`329` は 3 ファイル）。
強制するものが無かったので、誰も気づかなかった。

| 番号 | ファイル数 |
|---|---|
| `324` / `325` / `329` / `357` | 3 |
| `029` `200` `315` `322` `323` `326` `327` `328` `330` `331` `340` `365` | 2 |

**現時点で不具合ではない。** `migrate.go` は**ファイル名全体**で `sort.Strings` するので適用順序は
決定的である。ただし決定的なのは**アルファベット順**であって、誰かが意図した順序ではない——
`324_agent_metrics.sql` が `324_rls_force_tenant_isolation.sql` より先に走るのは
"a" < "r" だからであって、それが正しい順序だからではない。**同じ番号を共有する 2 つの
migration は、相対順序が一度も選ばれていない migration である。** 一方が他方に依存する組が
将来現れれば壊れ、しかも「2 つ目が失敗した」という形で現れて「番号が同じ」とは見えない。

#### 既存 16 組はリネームしない

`schema_migrations` は**ファイル名そのもの**を version として記録する（`migrate.go`）。
適用済みの migration をリネームすると、ランナーはそれを**新しいファイルとして再実行**する。
これらの多くは冪等ではない（`IF NOT EXISTS` の無い `ALTER TABLE ... ADD CONSTRAINT` は
2 回目で失敗する）。**命名規約を整えるために既存の全デプロイを壊すことになる。**
割に合わないので、増えるのを止める方だけを実装した。

`server/internal/store/migration_numbering_test.go`（DB 不要）:

- `TestMigrationNumbersAreUnique` — 新規の重複を落とす。既存 16 組は明示的に grandfather する
- `TestGrandfatheredMigrationDuplicatesStillExist` — grandfather 一覧の正直さを保つ。歴史的
  重複がリネーム／削除されたのに一覧に残っていると、**その番号での新規衝突を黙って許可する**
  ことになる（検査が最も弱い場所で静かになる）

どちらも変異テストで赤くなることを確認済み。

> **未処理の観測**: `315_agents_status_inactive.sql` と `330_agents_status_inactive.sql` は
> **番号だけでなく内容の意図も同じに見える**。同じ migration が別番号で二重に存在している
> 可能性があるが、本項の範囲外として手を付けていない。

### P2-4. 本台帳自身が番号衝突と節の消失を起こしていた — ✅ 分割＋CI ゲート化（PR #639, 2026-08-03）

台帳は 1084 行の単一ファイルで、**ほぼ全ての PR が末尾に追記する**構造だった。2026-08-03 の 1 日で
この構造に起因する事故が 5 件起きている。

| 種類 | 件数 | 内訳 |
|---|---|---|
| 番号衝突 | 3 | `P5-11` が `agents.os`(#615) と LOLBin で、`P5-15` が Wazuh(#627) と Defender で二重採番 |
| マージ解決時の節の消失 | 2 | `P5-11` / `P5-12` が main から消失 |

**分割だけでは足りない。** 分割が減らすのは git が競合として検出する noisy な事故だけで、上の
2 種類はどちらも**競合を伴わずに**起きる。別々の場所への追記どうしは git がクリーンにマージするので、
**同じ番号の節が 2 つ並んだファイルが何事もなく main に入る**。消失の方も、消えたことを知らせる
ものが何も無い。サイレントな失敗には規律ではなくチェッカーが要る。

**対応 (1) 構造**: 本文を優先度別に `docs/debt/P0..P5.md` へ分割し、`docs/技術的負債と改善計画.md`
は 147 行の索引にした。**パスと節 ID は変えていない**ので、30 の外部参照はすべて有効なままである。

**対応 (2) CI ゲート**: `server/internal/store/debt_ledger_test.go`（DB もネットワークも不要、
markdown を読むだけ）に 4 つ。

| 検査 | 捕捉するもの |
|---|---|
| ID の重複禁止 | 上記の衝突 3 件 |
| 索引と本体の双方向一致 | 節がマージ解決で消えると索引の行が残る。消失そのものは不可視なので、これが唯一の手がかり |
| 退役 ID の再利用禁止 | 空いた番号を埋めると既存の PR やコミットメッセージが別の項目を指すことになる |
| 引用の解決性 | 存在しない ID の引用。「文書化されているように読めるが実体が無い」＝ inert なルールと同じ false-green の形 |

4 つとも変異テスト（意図的に壊して赤くなることを確認）を通してある。

**分割の検証**: 42 節すべてが byte 単位で一致（欠落・余分ゼロ）。節を `docs/debt/` へ移したことで
`docs/` 直下を指す**相対リンク 20 件が壊れた**——これは分割が持ち込んだ回帰なので `../` を付けて
修正し、差分が `../` の付与のみであることを再度 byte 比較で確認した。

**ついでに見つけた既存の宙ぶらりん参照**: `docs/CI・デプロイ運用とコスト最適化.md` が `P2-1c` を
引用していたが、この ID は台帳に一度も書かれていない。分割とは無関係の既存問題で、引用側から
削除した。4 つ目の検査が今後の発生を止める。

#### 運用ルール（追記する人向け）

- **番号は使い回さない。** 退役した ID（現在 `P5-12` / `P5-16`）は索引に明記してあり、再利用すると
  CI が赤くなる。既存の PR やコミットメッセージが古い番号を指しているためである。
- **節を追加したら索引の「項目一覧」にも行を足す。** 片方だけだと CI が赤くなる（これが節の消失を
  検出する唯一の手段である）。
- **ID の接頭辞と置き場所を一致させる。** `P4-*` は `docs/debt/P4.md` にしか置けない。
- **他ドキュメントから ID で引用する場合、その ID は実在していなければならない。**

#### ★ ゲート自身が守るべき変更で走っていなかった（2026-08-03 追記）

上の 4 検査は `server/internal/store/debt_ledger_test.go` にあり、CI では
`Server Tests (Go)` ジョブで実行される。ところが `ci.yml` は **docs/Markdown のみの変更で
全ジョブをスキップする**（コスト最適化、[CI・デプロイ運用とコスト最適化.md](../CI・デプロイ運用とコスト最適化.md) §2-1）。

台帳の編集は定義上ほぼ常に docs-only なので、**番号衝突を捕捉するために作ったゲートが、
台帳を編集する PR では一度も走らない**状態になっていた。PR #641（本項を含む台帳更新）で
チェックが 1 つも付かなかったことで発覚した。

サイレントな失敗を捕捉するためのゲートが、守るべき変更クラスに対して自分自身がサイレントに
不活性だった——本セッションで繰り返し見た形がそのまま出た。

`.github/workflows/docs-gate.yml` を追加して塞いだ。`docs/**` と `**/*.md` を対象に、
この 4 検査だけを 1 ジョブで走らせる。`ci.yml` の `paths-ignore` を外す選択もあったが、
それでは docs の typo 修正で Playwright E2E や Trivy 4 イメージまで走り、§2-1 が消そうと
したコストがそのまま戻る。

> **教訓**: CI にゲートを足したら、**そのゲートが守る変更を含む PR で実際に走ったか**を
> 一度確認すること。ジョブが緑なのと、ジョブが実行されたのは違う。

同じ日にこの教訓が**さらに 2 回**当たった。いずれも「ゲートが赤いか緑か」ではなく
「**ゲートが動いたか**」の問題である。

- **FP ソークが `server/migrations/**` で起動しない**（2026-08-04 是正）。`pull_request` の
  `paths` は `server/internal/detection/**` を見ていたが、**検知ルールの本体は migration SQL に
  ある**（366 / 371 / 372 がいずれもそう）。ルールだけを変える PR——このソークが測るために
  存在する変更そのもの——で一度も起動しない状態だった。`paths` に追加して是正。
- **FP ソークが静かにキャンセルされた**（2026-08-04 観測）。`concurrency: { group: fp-soak,
  cancel-in-progress: false }` は実行中を殺さないが、**キューに保持されるのは 1 つだけ**で、
  後から入った run が待機中の run を置き換える（P2-4 の元となった #620 に記載済みの制約）。
  PR #646 の測定はこれで消え、`workflow_dispatch` で再実行する必要があった。
  **run 一覧に `cancelled` として残るだけで、PR のチェック欄からは消える**ため、
  「ソークが緑だった」と「ソークが走った」を取り違えやすい。

#### ★ ゲート整備中に、まさにその事故が再発した（2026-08-03）

本項と `docs-gate.yml` を用意している最中に、PR #640 が `P5-20` を取った。同じ番号を使う
別 PR が並行して走っており、**git は競合として検出しなかった**（本項が説明しているとおり、

**ゲートは「入ってから」しか守れない**という当たり前の事実だが、実際に一度起きたので記録する。
これ以降は docs-only の PR でも 4 検査が走る。

### P2-5. 「CRLF でコミットされた .sh がある」は誤診で、汚染は Windows 作業ツリー側だけだった — ✅ 予防措置＋CI ゲート化（2026-08-05）

発端は本物の障害である。`attack-live-measure.yml`（実機計測経路）を初めて回そうとしたところ、
`agent/scripts/run-atomics.sh` が Linux 上でまったく走らなかった。

```
run-atomics.sh: line 16: set: -: invalid option
run-atomics.sh: line 17: $'\r': command not found
run-atomics.sh: line 38: syntax error near unexpected token `$'do\r''
```

そこで `git ls-files '*.sh' | xargs file | grep CRLF` を回すと 38 本中 11 本が CRLF と出た。
出荷物（`deploy/install/install.sh` / `update.sh`、`agent/deploy/linux/install.sh`）も含まれていたため、
「CRLF のままコミットされた .sh が 11 本あり、顧客のインストールが壊れている」と読んだ。**これが誤診だった。**

#### 実際に何がどうなっていたか

`file` が見るのは**作業ツリーの実体**であって、コミットされている内容ではない。リポジトリ側を ref 指定で
確かめると、CR は 1 バイトも無い。

| 確認方法 | 結果 |
|---|---|
| `git grep -I -l -P '\r' origin/main` | **0 件**（`.sh` に限らず追跡ファイル全体） |
| `git ls-files --eol -- '*.sh'` | 38 本すべて `i/lf`（`w/crlf` は作業ツリー側） |
| `git cat-file blob origin/main:<path> \| tr -cd '\r' \| wc -c` | 全 `.sh` で 0 |

CRLF なのは Windows のチェックアウトだけで、原因はシステムの gitconfig（`C:/Program Files/Git/etc/gitconfig`）の
`core.autocrlf=true`。**「11 本」という中途半端な数字も同じ理由で説明がつく**——38 本すべてが CRLF で
チェックアウトされ、その後どこかの PR で編集ツールが書き戻した 27 本だけが LF に戻っていた。残った 11 本は
「久しく誰も触っていない .sh」であり、出荷物 3 本がそこに含まれていたのは偶然である。

念のため、作業ツリーの `.sh` 38 本を `sed -i 's/\r$//'` で LF 化して `git add -u` したところ、
**ステージされた差分はゼロ**だった。これがリポジトリ側が元から健全だったことの直接の証拠になる。

#### 顧客影響の検証（憶測ではなく実行結果）

コミット済みの blob と Windows 作業ツリーの実体を、それぞれ実 Linux（`debian:bookworm-slim`）の bash で
`bash -n` にかけて比較した。

| 対象 | コミット済み（`origin/main`） | Windows 作業ツリーの実体 |
|---|---|---|
| `deploy/install/install.sh` | CR=0 / syntax OK | CR=619 / `line 70: syntax error near unexpected token $'{\r'` |
| `deploy/install/update.sh` | CR=0 / syntax OK | CR=266 / 同上（line 64） |
| `agent/deploy/linux/install.sh` | CR=0 / syntax OK | CR=183 / `line 31: ... $'in\r'` |
| `agent/docker-entrypoint.sh` | CR=0 / syntax OK | CR=22 / `line 23: unexpected end of file` |
| ほか 8 本（計測・デモ・堅牢性スクリプト） | 全て CR=0 / syntax OK | 全て FAIL（`server/cmd/cli/install-deps.sh` のみ 4 行で構文的に無害） |

配布経路も [インストーラ・配信経路アーキテクチャ.md](../インストーラ・配信経路アーキテクチャ.md) と突合した。

- 本番の正統経路（A・`installer_handler`）はスクリプトを**動的生成**するので、静的 `.sh` を一切読まない。
- `deploy/install/{install,update}.sh`（B）は手動・エアギャップ用で、README と手順書が `git clone` 後に
  **Linux 上で** `sudo bash` させる。Linux での clone は LF。
- `agent/deploy/linux/install.sh`（C）は同 doc が「孤立・非推奨、どこからも参照されない」と明記している。
- CI・リリースは `actions/checkout`（Linux）なので常に LF。`docker build` も Linux ランナー上で走る。

→ **顧客影響は無かった**。壊れるのは「Windows の作業ツリーの実体を Linux へ手で送り込む」経路だけで、
実際に壊れたのがまさにそれ（`run-atomics.sh` を Windows から被験ホストへ scp）。CI 経由では再現しないため、
リポジトリだけを見ても原因が見えない形をしている。

#### 対応

- **`.gitattributes` の `*.sh text eol=lf`**。チェックアウト時に LF で書き出させて Windows 作業ツリーの
  CRLF 化そのものを止め、同時に clean フィルタでコミットへの混入も止める（両方向に効く）。CRLF の `.sh` を
  `git add` すると index の blob の CR が 0 バイトになることを実測で確認した。
  本調査と並行して PR #658（実機計測の週次化）が同じ属性を先に main へ入れたため、ここでは**注記の是正だけ**を
  行っている——「既に CRLF でコミットされているファイルを直すには `git add --renormalize` が別途必要」と
  あったが、(a) コミット済みの CRLF は 1 本も無く、(b) `--renormalize` が正規化するのは index だけで
  **作業ツリーの実体は CRLF のまま残る**。実体を戻すには `git rm --cached -r . && git reset --hard` が要る。
- **`server/internal/store/shell_eol_test.go`**（`TestShellScriptsUseLFEndings`）。属性が外れた・`-text` で
  追加された、といった取りこぼしを CI（Server Tests）で捕捉する。DB もネットワークも不要。
  台帳ゲートと同じく「ファイルを読んで整合を主張する」検査なので `internal/store` に置いた。
  歩き回りが壊れて空振りするのを防ぐため、`.sh` を 30 本未満しか見つけられなかったら fail させている。

#### 教訓

- ★**`file` も `git ls-files` も作業ツリーを見る。「コミットされている内容」を問うなら ref を明示する**
  （`git cat-file blob <rev>:<path>` / `git ls-files --eol` の `i/` 側 / `git grep <rev>`）。ここを取り違えると、
  ローカル環境の汚染をリポジトリの欠陥と読み、**差分ゼロの「修正」PR** を出すことになる。今回は
  「出荷物が壊れていて顧客のインストールが失敗する」という、事実なら P0 級の主張まで一歩手前だった。
- ★**再現した事実と、その原因についての推定を分けて扱う。** `$'\r'` エラーは本物で、再現もした。
  誤っていたのは「だからリポジトリに CRLF がコミットされている」という一段先の推定だけである。
  症状が本物であることは、原因の診断を裏書きしない（[[feedback_docs_are_not_design_intent]] と同じ形）。
- ★**一度も実行されていない経路は、壊れていても壊れていなくても外形が同じ。** `attack-live-measure.yml` は
  今回が初回実行で、それまで `run-atomics.sh` を Linux で走らせた者がいなかった。P5-23（死蔵 builtin）や
  P5-25（鳴らす側の無いアラート）と同じく、**「静かなので健全に見える」**クラスの負債である。
