> `etw-verify` ハーネスで **process / network / DNS が全 `[PASS]`**（exit 0）。各ETWセッションが
> 実機で正常起動し、既知活動をPID帰属付きでリアルタイム捕捉、ポーリングへフォールバックせず本物の
> カーネルセッションを開くことを確認。**プロセスは CommandLine / PPID / Username / Hashes まで完全取得**
> （`cmd="cmd.exe /c ping ..."` を実機で確認＝検知に使える形）。
> さらに **本番エージェント(`EDRAgent` サービス)を最新ビルドに更新し `EDR_AGENT_ETW=1` で4テレメトリ
> （プロセス/ネットワーク/DNS/認証）全てがETW/EvtSubscribe経路で実稼働**。agent.log に

> → **商用EDRとの最大の差＝エンドポイント可視性を、検証だけでなく本番ETW稼働まで到達**。
> ※env注入は per-service Environment（`HKLM\...\Services\EDRAgent` の `Environment` REG_MULTI_SZ）。
> サービス実体は `C:\ProgramData\EDRAgent\bin\edr-agent.exe`（ルートではない）。

商用EDRとの最大の差は**エージェントの可視性**。出荷ビルドの主要テレメトリは大半が
userland ポーリング/OSログAPIで、リアルタイムのカーネルイベントストリームではない
（プロセス: Win=WMI/EnumProcesses ポーリング、Linux=/proc、ネットワーク: TCPテーブル 500ms
ポーリング）。短命プロセス/接続を取りこぼし、回避されやすい。FIM(ReadDirectoryChangesW)・
レジストリ(RegNotifyChangeKeyValue)・隔離(WFP/pf)は本物のイベント駆動/カーネル機構。

### P4-1. Windows プロセス監視の ETW 化 — 🟢 実機検証済み（opt-in、2026-06-17 PASS）
- `agent/internal/platform/windows/process_etw.go` に **Microsoft-Windows-Kernel-Process**
  プロバイダの実ETWセッションを配線（`0xrawsec/golang-etw`、TDHパース込み）。ProcessStart/Stop を
  リアルタイム取得し、**PPID も取得**（ポーリング版にはなかった因果情報）。
- **opt-in**: `EDR_AGENT_ETW=1` の時のみ有効。失敗時（非管理者/プロバイダ解決失敗等）は
  自動でポーリングにフォールバック。コールバックは軽量（同期ハッシュ無し）でロスト防止、recover ガード付き。
- ✅ **本番実稼働（2026-06-17, Win Server 2022）**: `[PASS] process - captured create for PID …(cmd.exe)
  ppid=… cmd="cmd.exe /c ping ..." user="…\Administrator"`。本番エージェントのログに
  「ETWプロセス監視を開始しました (Microsoft-Windows-Kernel-Process)」。
- ⚠️→✅ **配線＋補完（#187/#188）**: 当初エージェントは `NewWindowsProcessCollector`(ポーリング)のままで
  ETWプロセスコレクタが未配線だった（ETWハンドラが CommandLine/Username/Hashes を欠き、配線すると検知が
  退行するため）。`handleETWEvent` に `enrichProcessFromHandle`(OpenProcess で CommandLine[PEB,要
  `PROCESS_VM_READ`]/Username/Hashes 補完)を追加し、`platform_windows.go` を opt-in時のみETWに分岐配線。
  → ポーリングの上位互換(同フィールド＋PPID＋リアルタイム)。
- 依存追加: `github.com/0xrawsec/golang-etw`（windows限定import、クロスコンパイル無影響）。

### P4-1b. Windows ネットワーク監視の ETW 化 — 🟢 実機検証済み（opt-in、PR #158、2026-06-17 PASS）

- ✅ **実機検証済み（2026-06-17）**: `[PASS] network - captured outbound connection to 1.1.1.1:443 (pid …)`。

### P4-2. Linux eBPF の出荷ビルド有効化 — 🟢 ビルド＆実機稼働 達成（2026-06-17）／✅ 短命プロセス検知の盲点を根治（2026-06-22, 0→80%）／✅ `prevention` 誤ゲートを全経路で根治（network connect-tracer: 2026-07-26 PR #544 ／ fileless: 2026-08-01）
- ✅ **Linux実機確認（2026-06-17, RHEL 10.1 / kernel 6.12 / EC2）**: edr-agent 稼働・`connected to EDR
  server`（gRPC 9091 でサーバ到達＝E2E疎通）。**eBPF は未稼働＝想定どおり**（/proc ポーリング動作）。
  ただし **`/sys/kernel/btf/vmlinux` 存在＝カーネルは BTF 対応済み**で、ブロッカーは純粋にビルドパイプライン
  （bpf2go 生成物 + clang/libbpf）のみ。**この RHEL EC2 自体が eBPF ビルドホスト候補**になり得る。
  ※出荷ビルド（`-tags ebpf` 無し）では最新版でも /proc ポーリング（`NewEBPFProcessCollector` は名前に反し
  タグ無しで /proc 読取）＝Windowsのような「エージェント更新で改善」は起きない。
- ✅✅ **ビルド＆実機稼働 達成（2026-06-17, RHEL 10.1 / kernel 6.12 / EC2）**: `-tags ebpf` の
  エージェントをビルドし、**本番で eBPF プログラム（handle_exec / handle_exit tracepoint）がロード・
  アタッチ成功**（`bpftool prog show` で 0→2件）。これまでビルド不可だった真の原因を **4つ特定して修正**
  （PR #191）:
  1. `go:generate` のパスが壊れた `internal/ebpf`（`../../ebpf`）を指していた → 正しい
     `agent/ebpf`（`../../../ebpf`）。分岐していた `internal/ebpf/*.bpf.c` は削除して一本化。
  2. cflags に `-D__TARGET_ARCH_x86` が無く `BPF_KPROBE`（PT_REGS_*）がコンパイル不可。
  3. `agent/ebpf/process_monitor.bpf.c` が存在しない `ctx->exit_code`（exit tracepoint template に無い）
     を参照 → 0 に。
  4. `handle_execve`（kprobe）が verifier 拒否（`bpf_probe_read_user_str` のサイズ引数が負になり得る）。
     ローダ未アタッチ・出力未使用のデッドコードのため削除。さらに `ebpf_loader.go` の未使用 import 除去。
- **再現レシピ（proven, RHEL 10）:**
  ```
  dnf install -y clang llvm bpftool libbpf-devel golang     # libbpf-devel は CRB(CodeReady Builder)
  bpftool btf dump file /sys/kernel/btf/vmlinux format c > agent/ebpf/vmlinux.h   # ignore対象
  cd agent && ( cd internal/platform/linux && GOPACKAGE=linux go run \
    github.com/cilium/ebpf/cmd/bpf2go -cc clang -cflags "-O2 -g -target bpf -D__TARGET_ARCH_x86" \
    ProcessMonitor ../../../ebpf/process_monitor.bpf.c )
  go build -tags ebpf -o edr-agent-ebpf ./cmd/agent
  ```
  ※RHEL の go は `GOTOOLCHAIN=local` 固定なので go.mod の go directive を入れ済み版に合わせる。
- **残**: bpf2go 生成物（`processmonitor_*.go/.o`）はまだ未コミット（要 clang 環境で生成）→ コミットすれば
  clang 無しで `-tags ebpf` ビルド可能になる（CI/配信への組込みは次段）。CommandLine は現状空（tracepoint は
  args 非取得）→ ローダで `/proc/<pid>/cmdline` 補完が follow-up（ポーリング版と同様）。
- **✅ 短命プロセス検知の盲点を実機で根治（2026-06-22, RHEL10/kernel6.12 EC2, branch `feat/active-defense-detection-deepening` commit `9062722b`）**:
  当初「eBPF未デプロイ」が原因と見たが、実機の多層診断で **3つのバグ** が判明し全て修正・実証。
  検知率 **0/6 → Technique級 4/5（+reverse shell別途確認＝実効5/6, 80%）**。
  1. **argv未取得**: `handle_exec` で `mm->arg_start..arg_end` から argv をカーネル内取得（verifier対策に
     長さを `MAX_ARGS_LEN-1` クランプ＋`&(MAX_ARGS_LEN-1)` マスク。kernel6.12で受理。過去#191の `R2 negative` を回避）。
  2. **readerのサイズチェック誤り**: `len(record) < unsafe.Sizeof(...)` が全レコードを破棄していた

  3. **★真因＝ktimeタイムスタンプ**: `event->timestamp_ns = bpf_ktime_get_ns()`（**起動相対**）を
     `time.Unix(0, ns)` で **epoch相対**として変換 → **全eBPFプロセスイベントが1970年で保存** →
     時間窓クエリと**検知エンジンの時間窓相関の両方から不可視**（short/long問わず全eBPFイベントに影響＝「サーバに無い」
     「Linux検知0」の正体）。reader受信時刻 `time.Now()` に修正。※当初の「/procレース」診断は誤り（comm/filename も
     カーネル内取得済みで、損失は時刻のみだった）。
  - **検証（実機）**: 1970窓で `create pn=[whoami] cmd=[whoami]` 完全保存を確認 → 修正後2026窓に短命が出現 →
    検知バッテリーで base64難読化(T1140)/curl→tmp(T1105)/SUID(T1166)/`/tmp`実行(T1059) が **Techniqueレベル検知**、

### P4-5. RuleEngine の OS プラットフォーム・ゲート欠落 — ✅ 修正済（PR #356, 2026-07-02）

|---|---|---|---|
| linux | linux | 2,334 | ✅ 正当 |

- `platform` 未設定 or 全 OS 網羅（SigmaHQ の `logsource.product` 無しルール）= universal → 常に評価。

  当たらなくなる**罠があるため `canonPlatform` で吸収。イベント側の値は `ingestion/handler.go` の `platformString`

**安全弁**: `EDR_RULE_PLATFORM_GATE=0`（既定 ON）でゲート無効化可（`SetPlatformGate`）。ラベル誤りのルールが
実検知を抑止した場合の緊急回避用。テスト = `platform_gate_test.go`。

**ライブ実証（検証EC2, docker.yml デプロイ後）**: 再起動後のアラートは `linux×linux` のみで、`windows×linux`/
`macos×linux` のクロス OS FP は**ゼロ化**。正当検知（同 OS）は無傷＝純粋な FP 除去を実機で確認。

### P4-6. DB Sigma ルール（`rules` テーブル）にリアルタイム発火経路が無い — ✅ 結線（PR #647, 2026-08-04）

**症状**: `rules` テーブル（本体の SigmaHQ/seeded Sigma、2214件）のルールが、**追いつき済のリアルタイム経路
（AlertPipeline / `kizashi-api`）で一切評価されない**。評価するのは detection-engine（`kizashi-detection`）の
`RuleEngine` だけだが、そのコンシューマが**慢性ラグ**（EVENTS JetStream で ack floor が固着・未処理 ~128K）で
新イベントに到達しない。結果、`rules` テーブルのルールは**実質リアルタイム未発火**。

**発見の経緯**: PR#445 の CreateRemoteThread 注入検知（ルール「Process Hollowing via Suspicious Executable」,
sev9/auto_isolate, T1055.012）を Windows 実機で E2E 検証したところ、**エージェントは正しく `create_remote_thread`
を emit・取込するのにサーバ側アラートが恒久 0 件**（337件で 0、合成 NATS 投入でも 0）。
詳細スコアカード = [results/live-20260714-createremotethread-verification.md](../results/live-20260714-createremotethread-verification.md)。

**根因（コード実測）= 2パイプライン×3テーブル分裂**:
- `rules` テーブルを読むのは `RuleEngine`（`store.RuleStore.ListEnabled`, `WHERE enabled=true`）のみ。← detection-engine 側、ラグ。
- AlertPipeline の `ReloadFromDB`→`loadSigmaRulesFromPoolTyped`（`server/internal/detection/sigma_db.go`）は
  **`yara_rules`(type=sigma) + `custom_alert_rules` しか読まず `rules` テーブルを読まない**。← api 側、追いつき済だがルール未ロード。
- ∴「リアルタイム経路＝ルール未ロード / 追従経路＝処理未達」の二重ギャップ。
- ★[検知ルールの二重管理とデプロイ.md](../検知ルールの二重管理とデプロイ.md) §1 の旧記述「Detection の Sigma 源＝`detection_rules`」は誤りで、
  実体は `rules`（`detection_rules` は 0 行の空表）。同 §7 に訂正と本件詳細。

**コード自体は健全**: 実イベント data で 4種のオフライン再現（`detection.SigmaEvaluator` / `engine.go` FlatMap 往復 /
`rules.RuleEngine`(sigma-go) / `AlertPipeline` `flattenNormalizedEvent`）いずれも Process Hollowing critical に MATCH=1。
バグは「どの表をどのパイプラインが読むか」の結線のみ（ルール・エイリアス・平坦化・両 Sigma 実装は正しい）。

**修正方針**:
- (a) `loadSigmaRulesFromPoolTyped` の UNION に **`rules` テーブル（`enabled=true AND type='sigma'`）を追加** ＝
  追いつき済 AlertPipeline で全 Sigma を評価（**本命**）。P4-5 の `addSigmaAliases` は既に共通化済なのでフィールド解決は問題なし。
- (b) detection-engine コンシューマの**ラグ/poison（ack floor 固着）を根治**（スループット/毒メッセージ、別課題）。
- `pipelineSubjects` に `events.*.create_remote_thread` を含める（必要条件・単独では不十分）。
- ★**二重発火防止**: (a) を入れると detection-engine と両経路で発火しうる。§5 一本化方針に沿い event_type 単位で
  突合し、`isDuplicateAlert`/時間窓 dedup を両経路で効かせる。

**影響範囲（要棚卸し）**: create_remote_thread 固有ではなく、**`rules` テーブルの全 SigmaHQ/seeded ルールが
リアルタイム経路で未評価**の可能性。migration 投入ルール（283/284/285/307/308/311/named-pipe #464 の custom 等）も
同構造の影響を受けうる。→ 追跡タスク起票済み。

**教訓**: 「DB で enabled なのに本番で発火しない」は、コンパイル失敗（P5-5 / §7 の compiled=N failed=M）に加え、
**「そのルール表を、追いついているコンシューマが読んでいるか」**を必ず疑う。パイプライン・ラグは
`nats consumer info EVENTS <durable>` の `num_pending`/ack floor で一撃確認。

##### 設計上の判断 3 点

**1. タイトル衝突は builtin 優先。** CLAUDE.md の二重管理の節が明記するとおり、
**同じ名前のルールが両方に、異なるマッチングロジックで**存在する。両方ロードすると
1 つのタイトルで 2 つのルールが評価され、アラートを読んだ人がどちらの YAML が出したのか
特定できない。builtin を優先すると、衝突タイトルでの api サーバの挙動は本変更の前後で
完全に同一になる——差分がレビュー可能である理由もそこにある。

**2. `mitre_tags` 列を YAML タグのフォールバックとして使う。** これは体裁の問題ではない。
**225 件中 65 件は YAML の `tags:` が空**で、MITRE 帰属が DB の列にしか無い（P4-6 が
診断された当のルール `Process Hollowing via Suspicious Executable` を含む）。
server-detect は列を読むので正しく帰属するが、YAML だけを読むローダは同じ検知を
`mitre_technique` NULL で出す。そして `dedup.deduplicateByTechnique` は
`mitre_technique IS NOT NULL` で絞るので、**帰属の無いアラートは重複排除もされない**——
server-detect 側の同一所見と永久に並ぶことになる。

**3. 環境変数のキルスイッチ `EDR_SIGMA_DB_RULES=0`。** 既定 ON（未発火が本件の趣旨なので）。
評価するルール数がほぼ倍になり、しかも行は当リポジトリの管理下だけに無い（SigmaHQ 同期も
同じ表に書く）。api サーバが苦しくなったオペレータが再ビルドを待たずに負荷を落とせる必要がある。

##### 二重発火について

同じルールが両エンジンで発火しうる。既存の重複排除がこの形を想定している:

- api 側のタイトルは `[Sigma] <title>`、server-detect 側は `<title>`——**タイトルが異なる**
- `deduplicateByTechnique` は「同一 technique・同一エージェント・6 分窓・タイトルが複数」を
  統合するので、この対は対象に入る

⚠️ **残る穴**: MITRE 帰属を持たないルールは `mitre_technique IS NOT NULL` で除外され、統合されない。
上記の判断 2（列からのフォールバック）はまさにこの穴を 65 件ぶん塞ぐためのものだが、
**列も YAML も空のルールが将来入れば同じ穴が開く**。列と YAML の両方が空の Sigma ルールを
弾くゲートは、本 PR では入れていない（別課題）。

##### 観測

`edr_rules_loaded` は `cmd/detection` からしか書かれておらず、**api サーバでは常に 0** を
返していた——「ロードしていない」と区別が付かない値であり、まさに本件の状態そのものだった。
api 側でもコンパイル済み件数を publish するようにした。起動ログも
`loaded=N failed=M skipped_builtin_collision=K` を出す（server-detect の
`compiled=N failed=M` に合わせた形）。**黙って 0 になるのが、この関数が何ヶ月も
全損を隠せた理由である。**

##### ★ FP ソークで測ったら、アラートが二重に出ていた（そして測り方も間違っていた）

マージ前に良性フリートで実測したところ、**新たに検知できるようになったルールは 0 件で、
増えたアラートは全部が既存検知の二重計上**だった。api と server-detect が同じルールを
同じイベントで評価するので当然である。

**さらに、最初の 4 回の測定は目的を測っていなかった。** `fpsoak-report` は

```sql
SELECT count(*) FROM alerts WHERE agent_id = ANY($1) AND created_at BETWEEN $2 AND $3
```

と **`status` を見ずに全行を数える**。一方 dedup は行を削除せず `status='resolved'` にして
**残す**設計である（「rows retained, never deleted」）。つまり**重複排除がどれだけ効いても
ソークの数字は 1 件も動かない**。602 → 541 → 539 → 538 という推移を「dedup の効果」として
報告していたが、あれは別の理由による変動だった。

正しい指標は「アナリストが実際に見る件数」＝ `status='open'` の数である。測り直した:

| 構成 | 全行 | クロスエンジン統合 | タイトル統合 | **SOC が見る件数** |
|---|---|---|---|---|
| 旧 dedup + 301 ルール（**現行本番**） | 425 | 122 | 71 | **232** |
| 旧 dedup + 535 ルール（**P4-6 単体**） | 537 | 226 | 51 | **260** |
| 新 dedup + 535 ルール（**本 PR**） | 538 | 170 | 143 | **225** |

**P4-6 単体では SOC のキューが +28 件（+12%）増える。dedup の 3 修正がそれを吸収し、
正味 −7 件**（run 間ばらつきの幅内なので「悪化しない」が正確）。**P4-6 は dedup 修正と
セットでなければ出せない。**

> **教訓 1**: ゲートが緑でも、そのゲートが**測っている量**を確認すること。FP ソークは
> 「ルールが騒がしくないか」を測る道具で、「重複が統合されているか」は測れない。
> 行を残す設計の重複排除は、行数という指標からは原理的に見えない。

> **教訓 2**: 「クロスエンジン dedup は dead code だった」と一度断定し、コードコメントにも
> 書いた。**誤りだった。** `status='resolved'` を数えたが、`fpsoak-report` は採点後に全行を
> `false_positive` に書き換えるので、その後に数えれば必ず 0 になる。実際には修正前でも
> 122〜226 件を統合していた。**測定アーティファクトを欠陥と誤診した。**

詳細は P5-30。

### P4-9. Sigma 評価エンジンが `logsource.category` を一切見ない（無差別評価）— 🟡 シャドーモード実装済み・フィルタ有効化は本番実測待ち（2026-07-20 発見 / 2026-08-01 main 取り込み）

**症状**: SigmaHQ 同期ルール「Network Connection Initiated Via Notepad.EXE」（`logsource: {category: network_connection}`）が、
`GET /api/v1/alerts/:id` の `raw_event` を見ると **`"type":"image_load"` のイベントで発火**していた。
notepad.exe 自身の実行ファイル読み込み＝`Start-Process notepad.exe` に伴う完全に無害なルーチンイベントで、
本来このルールが一致してよい対象ではない。

**根本原因**: `sigma_evaluator.go` の `EvaluateEvent` が

```go
for _, cr := range rules {
    if cr.Evaluate(event) { matches = append(matches, ...) }
}
```

と、`SigmaRule.LogSource.Category`（YAML の `logsource.category`。構造体には存在しパース済み）を
**評価パスで一度も参照していない**。ロードされている全ルール（builtin + SigmaHQ 同期分）が
**イベント種別を問わず無差別に**評価されており、フィールド名がたまたま重複する別カテゴリのイベントで
誤発火しうる。

**影響範囲（未検証）**: SigmaHQ 同期で入る実ルールは DB にのみ存在しリポジトリからは見えないため、
実際の誤発火件数は不明。ただし `image_load` / `process_creation` / `network_connection` / `registry_event` 等の
Sysmon 系ログソースは `Image` / `CommandLine` / `ProcessName` 等の共通フィールド名を多用する設計なので、
**同種の取り違えは構造的に起きやすい**。本番の FP 率を押し上げている可能性がある。

**なぜシャドーモードか**: フィルタをいきなり有効化するのはブラスト半径が最大級のコアパス変更で、
同期済み DB の実ルール一覧をリポジトリ側から検証できない。**検知は一切変えず記録のみ**とした。

**実装内容**:
- `sigma_category.go`: `eventTypeCategories` マップ。ingestion の全イベント種別
  （`handler.go` の `promoteEventType` / `eventTypeString` の全語彙）と、builtin ルールで実際に
  使われている全 `category` 値を突合して構築。曖昧なケース（例: `file` 型は `file_event` と
  `file_access` の両方を許容 — proto が読み書きを型で分けていない）は**安全側（緩め）**に倒した。
  `memory` / `process_block` 等、Sigma ではなく `typedFindings()`（engine.go）のハードコード Go パスで
  処理される種別は意図的にマップから除外（＝どのルールとも「不一致」判定になる。実際そのはずなので正しい）。
- `sigma_evaluator.go`: ルール一致後に `categoryCompatible()` を検査し、不一致なら `slog.Warn` +
  Prometheus カウンタ `edr_sigma_category_mismatch_total{rule}` を加算するが、
  **マッチは変更せずそのまま返す**（フィルタしない）。
- 回帰テスト: 実バグと同形（network_connection ルール vs image_load イベント）を再現し、
  **「不一致でも発火し続ける」ことを固定**（シャドーモードである事実をテストで保証）。

**次にやるべきこと**: 本番で `edr_sigma_category_mismatch_total` を一定期間観測し、
(a) 想定外に高頻度で不一致になるルールが無いか、(b) `eventTypeCategories` のマッピング漏れが無いかを
確認したうえでフィルタ有効化の可否を判断する。有効化する場合も**是正前後でルール発火数の差分を実機比較**
（想定外に減ったルールが無いか確認）してから投入すること。

### P4-10. WMI サブスクリプション永続化に観測面が無い（T1546.003）— ✅ センサー実装＋実機検証済み（PR #636 / #647, 2026-08-04）

WMI イベントサブスクリプションによる永続化は、**wmic のコマンドラインでしか観測できていなかった**。
builtin `WMIC Process Call Create` も migration 329 の `WMI Event Subscription Persistence (DB)` も
logsource が `process_creation` なので、wmic を経由しない登録経路が素通りする——PowerShell の
`Set-WmiInstance`、.NET の `ManagementClass`、任意のインプロセス WMI クライアント。
ファイルレスで再起動を跨ぎ、親プロセスが WMI を指さない永続化が、**まったく記録されないまま成立する**。

「ルールの精度が足りない」のではなく「イベントがそもそも来ていない」ため、ルールをいくら磨いても
永久に発火しない類である。

**対応**: `Microsoft-Windows-WMI-Activity` の ETW を直接購読し、WMI サブシステム自身が報告する
登録イベントを観測面として追加（`agent/internal/platform/windows/wmi_etw.go`）。

- 対象は **5861**（サブスクリプション登録＝T1546.003）と **5858**（WMI 操作、`ClientMachine` 付きは
  リモート WMI 実行＝T1047）の 2 つのみ。**5857（プロバイダ ロード）は意図的に除外**した。通常の
  管理スクリプトや資産管理エージェントの WMI 利用で常時発火する高レート・低弁別のストリームであり、
  FP soak が測定したとおり非弁別セレクタが誤検知リストの大半を占める（P5-17 と同じ失敗）。
- ルールは**コンシューマの種別**をキーにした。SCCM や監視製品はサブスクリプションを日常的に登録
  するので、登録そのものに発火させれば上記を再生産する。コードを実行するコンシューマ
  （`CommandLineEventConsumer` / `ActiveScriptEventConsumer`）であることが技術の要件。
- ルールは **builtin と `rules` テーブルの両方**に置いた。server-api（AlertPipeline）は builtin を、
  server-detect（Engine）は DB を読むため、DB のみだと主系のアラート経路が暗いままになる。
  migration 329 とは名前を分けてある——DB ルール抽出器は名前で同一視するので、同名にすると 329 の
  内容を静かに上書きする（実際に一度踏んだ）。
- ペイロードのフィールド名は SigmaHQ の `wmi_event` のもの（`event_type`/`consumer`/`query` 等）を
  採用。`sigma_category.go` が `wmi_activity` → `wmi_event` を既にマップしているため、この語彙で
  出さないとコミュニティルールが一切マッチしない（P5-5 / P5-10 と同型）。`field_support.go` への
  登録も必須で、未登録フィールドを選択するルールは「未対応」として評価前に退避され、
  **「WMI 活動が無かった」と見分けのつかない偽のグリーン**になる。
- 配線は `ps_module` / `pipe_created` と同じ `"<type>:<uuid>:<json>"` の `EVENT_TYPE_LOG` 前置
  プロモーションに乗せた（proto 変更なし）。#582 で `AlertPipeline` の購読を `eventTypeCategories`
  から導出するようにしてあったため、**センサーが着地した日からルールが動く**。

**FP soak 実測（#636）**: 439 件 / 263,397.53（ベースライン 266,999.13 から退行なし）。着信イベント
151,851 / 送信 151,851、窓の最後 90 秒のアラート 0 件＝検知エンジンに遅延が無く、この値は下限では
なく実測。**WMI 関連ルールは 99 ルールの誤検知リストに 1 件も出ていない**（良性フリートは
`wmi_activity` を生成しないため、新センサーは誤検知をゼロ件しか増やさなかった）。

当初は「検証環境に Windows ホストが無いので被験 VM が使える時に実測する」として残作業に

### P4-11. エージェント改ざんの検知結果がサーバへ一切届いていなかった — 🟡 ユーザーランド経路を実装（本PR）／ACL・アンインストール保護は未着手

**症状**: 自己保護の検知結果が、**すべてローカルのログファイルにしか出ていなかった**。
`cmd/agent/tamper_linux.go` の eBPF LSM `task_kill` も `cmd/agent/tamper_windows.go` の
`ObRegisterCallbacks` も、kill 試行を捉えたあと `slog.Warn` するだけで、サーバへ送る経路が
コードのどこにも存在しない。**攻撃者が黙らせようとしている当のホストの上にしか記録が残らない。**

さらに、その 2 つはどちらも `prevention` ビルドタグ配下である。`ci.yml` / `release.yml` の
どちらもこのタグを立てないので（Linux は `-tags ebpf` のみ、Windows は無タグ）、
**出荷バイナリでは自己保護そのものが no-op** だった。改ざん検知の実効カバレッジはゼロで、
「改ざんされていない」と「改ざんを見る仕組みが動いていない」が外形上は同じだった。

**本PRで入れたもの（署名・カーネル不要のユーザーランド経路）**:

| 検知 | 実装 | 出荷ビルドで動くか |
|---|---|---|
| ウォッチドッグが観測したエージェントの不審な停止 | `cmd/watchdog` が終了理由を分類しスプールへ記録 → 次回起動時にエージェントが送信 | ✅ |
| エージェントバイナリ／設定の改ざん | 起動時のディスク基準（既存 `integrity.Check`）＋実行中の**メモリ内基準**で定期照合 | ✅ |
| ウォッチドッグ自身の消滅 | ウォッチドッグが自PIDを `EDR_WATCHDOG_PID` で子に渡し、エージェントが生存監視 | ✅ |
| エージェントPIDへの kill／ハンドルオープン試行 | 既存のカーネル層の所見を同じ配送経路に載せた | ⬜（`prevention` タグ必要） |

設計上の要点:

- **拒否はできない**。ユーザーランドの観測に徹しており、管理者権限による停止そのものは止まらない。
  止めるにはカーネル層（P4-4 の Linux LSM / Windows ドライバ）が要り、後者は EV 署名が前提。
  本項が埋めるのは「止められないまでも、黙って止められることはなくなる」までである。
- **完全性の基準はメモリ内に取る**。ディスクに置いた基準は、守る対象と同じディレクトリに
  住むため、バイナリを書ける相手は基準も書ける。再起動を跨ぐ検知は既存の起動時チェックが
  受け持ち、実行中のすり替えはメモリ内基準が受け持つ、という二層構成にした。
- **検知は builtin と `rules` の両方に置いた**（migration 378）。typedFindings 側に寄せると
  server-detect にしか実体が無くなるが、そちらは P4-6 で判明したとおり慢性的にラグする。
  「センサーを止めにきている」は、最も遅い経路にだけ乗せてよい信号ではない。

**この作業で判明した、`<type>:<uuid>:<json>` センサー追加時の追随箇所は 3 点ではなく 4 点**:
`promoteEventType` ／ **`normalizeEventData` の復号** ／ `events_event_type_check` ／
`eventTypeCategories`。P4-4 の教訓が挙げていた 3 点セットに `normalizeEventData` が
抜けていた。抜けたときの症状は特に分かりにくい——**型昇格だけは通るので行は保存され、
`raw_data` だけが `json.Marshal(evt)` にフォールバックしてルールが選択するフィールドが
生成されない**。ルールは沈黙し、その沈黙は「改ざんされていない」と区別がつかない。
E2E テスト（`wireformat_e2e_test.go`）に tamper の 3 ケースを足していたことで捕捉できた。
