### P1-3. `EDR_SSO_STUB` 開発バックドアの本番誤設定ガード — ✅ 実装済（本PR）
- **元の課題:** `EDR_SSO_STUB=true` だけで SSO 認証を完全バイパスしデモ JWT を発行できた（本番置き忘れリスク）。
- **対応:** 二重 opt-in 化。`EDR_SSO_STUB=true` に加え `EDR_SSO_STUB_CONFIRM_INSECURE=true` を必須に。
  - 起動時ガード（`cmd/api/main.go`）: `EDR_SSO_STUB=true` で確認用変数が無ければ**起動拒否**（フェイルクローズ）。
  - ハンドラ（`sso_handler.go` `ssoStubAllowed()`）: 両変数が揃った時のみスタブ許可。
  - テスト `sso_stub_test.go` で5組合せを検証（stray な単独 true は false）。
  - `EDR_SSO_STUB` は設定ファイル/CI/E2E で未使用のため既存運用への影響なし。

### P1-4. マルチテナント RLS 分離が実効していない（クロステナント BOLA）— ✅ コード側是正済（PR #539/#541, 2026-07-26）／⬜ 最終有効化はオペレータ待ち
- **元の課題（Critical）:** RLS でテナント分離しているつもりが**全く効いていなかった**。認証済み非 viewer が URL の `:id` 差し替えで他テナント端末を isolate/kill/quarantine でき、agents/alerts/incidents を閲覧・改変できた。根本原因は3つ（①アプリが DB スーパーユーザ `edr` で接続＝RLS 無条件素通り ②FORCE RLS 未設定 ③`set_config` の `is_local` 取違えで `app.tenant_id` が後続クエリに届かない）。検証環境が単一テナントのため未検出だった。
- **対応（main 反映済み）:**
  - `internal/store/postgres.go` で `app.tenant_id` をセッションスコープ化（原因③）、migration 324 で FORCE RLS（原因②）。
  - migration 325 で非スーパーユーザ `edr_app` を **NOLOGIN・パスワード未設定**で作成＋GRANT、4 サービスの実行時接続を `APP_DATABASE_URL` 優先に（未設定なら従来どおり `DATABASE_URL` にフォールバック＝**挙動不変の準備段階**）。migration は所有者 `edr` で実行し続ける。
  - **多層防御**: agent にコマンドを送出する 7 エンドポイント（isolate/unisolate/scan/scan-cancel/kill-process/quarantine-file/restore-file）に**アプリ層のテナント検証**を追加（`AgentBelongsToTenant` の明示 `AND tenant_id=$2`）。Commander 経由のコマンド送出は RLS 保護テーブルを触らないため **RLS だけでは塞げない経路**であり、`edr_app` 切替前でも BOLA を閉じる。
  - migration 326（`users` に RLS ＋動的 tenant DEFAULT）／327（`schema_migrations` への書込を `edr_app` から REVOKE）／328（alerts・incidents に動的 tenant DEFAULT ＝切替後に NULL テナント行が不可視化するのを予防）。
  - `rules` / `suppression_rules` は**設計上グローバル共有**（コードがテナント非対応・組込ルールの大半が `tenant_id=NULL`）のため、RLS 適用は**意図的に見送り**。
- **残:** ★**最終有効化（`edr_app` へのパスワード付与 ＋ `APP_DATABASE_URL` 設定）はオペレータの明示操作**。未実施の間、原因①が残るためテナント分離は無効のまま。手順は [ops/RLSテナント分離有効化ランブック.md](../ops/RLSテナント分離有効化ランブック.md)、背景は [security/マルチテナント分離ハードニング.md](../security/マルチテナント分離ハードニング.md)。

### P1-5. RLS ポリシーが fail-open（エスケープ節）— ⬜ 未対応（大規模・専用フェーズ）
- **課題:** ポリシーの `app.tenant_id IS NULL OR ''` エスケープ節により、**`app.tenant_id` を設定し損ねた接続は全テナントにアクセスできる**。middleware 適用漏れの新規ルートや tenant_id 欠落 JWT が即クロステナント漏洩になりうる残余リスク。
- **なぜ単純に外せないか（2026-07 監査）:** `app.tenant_id` をセットするのは HTTP リクエスト経路のみ。**cmd/api 内の約35本のバックグラウンドワーカ**（HeartbeatMonitor / DeadAgentCleanup / DataRetentionCleaner / 各種アラート生成 detector・correlator / 集計 collector / 通知系 / in-process 検知パイプライン等）と**認証前 HTTP 経路**（ログイン・heartbeat・enrollment・各種 ingest）が、同一プールを `app.tenant_id` 未設定で共有しエスケープ節に依存している。単純削除は**ログイン全滅・agent 永久オフライン・アラート生成/保持削除/集計/通知の全停止**を招く。
- **必要な設計:** API プロセスに 2 本目のプール（all-tenant worker ロール）を持たせてワーカ＋認証前経路を分離、別プロセス（ingestion/detection）は worker ロールへ、alerts/incidents の INSERT に agent→tenant 解決を追加、その後にポリシーを fail-closed 化。Phase 0〜5 の分割設計は [security/RLS-fail-closed設計.md](../security/RLS-fail-closed設計.md)。
- **優先度メモ:** 主要な BOLA は P1-4 で緩和済みのため、**マルチテナント本番投入前**に完了させれば足りる。
