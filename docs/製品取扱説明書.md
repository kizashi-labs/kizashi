## 1. 製品概要

Kizashi（Endpoint Detection and Response）は、組織内のエンドポイント（PC・サーバー・仮想マシン）をリアルタイムで監視し、サイバー攻撃を検知・調査・対応するためのプラットフォームです。

### 主な機能

| 機能カテゴリ | 内容 |
|------------|------|
| **リアルタイム検知** | プロセス、ファイル、ネットワーク、レジストリの異常を自動検知 |
| **AI自動調査** | GPT-4o/Claudeによるアラートの自動分析と対応推奨 |
| **インシデント管理** | 関連アラートを自動集約し、攻撃全体像を把握 |
| **脅威インテリジェンス** | MITRE ATT&CK・IOC・脅威フィードとの統合 |
| **自動対応（SOAR）** | プレイブックによるエンドポイント隔離・プロセス終了の自動実行 |
| **コンプライアンス** | NIST CSF・CIS Controls・ISO 27001への準拠状況を自動評価 |
| **フォレンジクス** | メモリダンプ・ファイル取得・プロセスツリーのリモート収集 |

### 対応プラットフォーム

- Windows 10/11, Windows Server 2019/2022
- macOS 12 Monterey以降
- Ubuntu 20.04+, RHEL/CentOS 8+, Amazon Linux 2

## 2. ログインと基本操作

### 2-1. ログイン

ブラウザで管理画面のURLにアクセスします。

```
ローカル環境: http://localhost:3020/login
本番環境:     https://<サーバーIPまたはドメイン>/login
```

| 項目 | 初期値 |
|------|--------|
| メールアドレス | `admin@example.com` |
| パスワード | `Admin1234!` |

> **重要:** 初回ログイン後は必ずパスワードを変更してください。
> 右上のユーザーアバター → **プロフィール** → **パスワード変更**

## 3. ダッシュボードの見方

> 📍 画面パス: `/`（ダッシュボード）

メニュー **概要 → ダッシュボード** を開きます。画面は30秒ごとに自動更新されます。

### 3-1. KPIカード（上段）

| カード | 内容 | 確認ポイント |
|-------|------|------------|
| 総エンドポイント数 | 登録されている端末の合計 | エージェント未登録端末がないか |
| オンライン率 | 現在通信中の端末の割合 | 80%以下なら要調査 |
| 未対応アラート | ステータスが「新規」のアラート件数 | 増加傾向なら優先対応 |
| アクティブインシデント | 調査中のインシデント件数 | 長期未解決のものを確認 |
| MTTD | 脅威検知までの平均時間 | 短いほど早期検知できている |
| MTTR | 脅威対応完了までの平均時間 | SLAと比較して評価 |

### 3-2. 重要度別アラート分布（円グラフ）

- **Critical（赤）:** 即時対応が必要な最高リスク
- **High（オレンジ）:** 24時間以内の対応推奨
- **Medium（黄）:** 週次レビューで対応
- **Low（青）:** 定期確認

**例:** Criticalが急増している場合は、ランサムウェアや標的型攻撃の可能性があるため、即座にインシデント対応フローを開始してください。

### 3-3. SOCワークキューウィジェット

ダッシュボードの **SOC ワークキュー** ウィジェット（デフォルト表示）で、未対応アラート・インシデントの件数を一目で確認できます。

| ボックス | 内容 |
|---------|------|
| 🔴 緊急 | Critical(Lv9+) または High(Lv7+)かつ24時間以内 |
| 🟠 今日中 | Medium(Lv5+) または High超過(24h以上) |
| 🔵 今週中 | Low重要度・調査中・封じ込め済み |

各ボックスをクリックすると `/soc-queue`（ワークキューページ）に遷移します。1分ごとに自動更新。

### 3-4. MITRE ATT&CK ヒートマップ

検知された攻撃手法のATT&CKフレームワーク上での分布を表示します。色が濃い箇所ほど該当手法の検知数が多いことを示します。

**例:** 「Credential Access」列が赤くなっている場合、認証情報窃取が試みられている可能性があります。

## 4. アラート対応

> 📍 画面パス: `/alerts`（一覧）　`/alerts/[id]`（詳細）　`/alerts/triage`（トリアージ）

メニュー **検知 → アラート** を開きます。

### 4-1. アラート一覧の操作

| 操作 | 手順 |
|------|------|
| 重要度でフィルター | 上部フィルターバーの `Critical` / `High` / `Medium` / `Low` ボタンをクリック |
| 担当者でフィルター | **フィルター** → **担当者** で自分のアラートのみ表示 |
| キーワード検索 | 検索バーにホスト名・IPアドレス・ルール名を入力 |
| アラート詳細表示 | 一覧の行をクリック |
| ステータス変更 | 詳細画面 → **ステータス** ドロップダウンで変更 |

#### アラートステータスの意味

| ステータス | 意味 | 次のアクション |
|-----------|------|--------------|
| **新規（new）** | 未確認のアラート | 優先度に応じて着手 |
| **調査中（investigating）** | 担当者が調査中 | 調査メモを追記 |
| **解決済み（resolved）** | 対応完了 | 対応内容を記録 |
| **誤検知（false_positive）** | 正常な動作と判断 | 検知ルールの見直しを検討 |

### 4-2. 具体例：ランサムウェア検知アラートへの対応

**状況:** 「Ransomware Encryption Activity Detected」というCriticalアラートが発生

**手順:**

1. **アラート一覧**で該当アラートをクリックして詳細を開く
2. **概要タブ**で以下を確認する
   - 発生ホスト: `DESKTOP-USER01`（感染端末）
   - 発生時刻: `2026-03-25 14:32:00`
   - 検知ルール: `Ransomware_FileEncryption_Pattern`
   - MITRE ATT&CK: `T1486 - Data Encrypted for Impact`
3. **プロセスツリー**タブで `explorer.exe → cmd.exe → suspicious.exe` の実行経路を確認
4. **ネットワーク**タブで外部IPへの不審な通信がないか確認
5. ステータスを **調査中** に変更し、自分のアカウントに割り当て
6. 画面右上の **エンドポイント隔離** ボタンをクリックして、感染端末をネットワークから遮断
7. **インシデントに昇格** をクリックして新規インシデントを作成
8. 対応内容をコメント欄に記録して **解決済み** にする

> **ポイント:** 隔離後はエンドポイントのAIフォレンジクス機能でメモリダンプと感染ファイルを取得すると、被害範囲の特定が迅速になります。

### 4-3. 一括AI分類

大量のアラートを素早くトリアージしたい場合に使用します。

1. アラート一覧でチェックボックスを使って複数アラートを選択（またはすべて選択）
2. **一括操作** → **AI分類** をクリック
3. AIが各アラートを分析し、重要度・推奨ステータスを提案する
4. 提案を確認して **適用** または **却下** を選択

## 5. インシデント管理

> 📍 画面パス: `/incidents`（一覧）　`/incidents/[id]`（詳細）　`/incidents/war-room`（作戦室）

メニュー **検知 → インシデント** を開きます。

### 5-1. インシデントの作成

複数のアラートが同一攻撃に関連している場合、インシデントにまとめて管理します。

**方法A: アラートから作成**
1. アラート詳細を開く
2. **インシデントに昇格** ボタンをクリック
3. タイトル・重要度・担当者を設定して保存

**方法B: 手動作成**
1. インシデント一覧右上の **＋ 新規インシデント** をクリック
2. タイトル例: `2026-03-25 ランサムウェア感染疑い - DESKTOP-USER01`
3. 重要度: `Critical`
4. 関連アラートを検索して紐付ける

### 5-2. インシデント詳細の機能

| タブ | 内容 |
|-----|------|
| **概要** | 発生タイムライン・関連エンドポイント・攻撃フロー |
| **アラート** | 紐付いたアラート一覧 |
| **タイムライン** | 攻撃の時系列イベント表示 |
| **War Room** | チームメンバーとのリアルタイムコラボレーション |
| **エビデンス** | 収集したファイル・スクリーンショット・ログ |
| **対応アクション** | 実施した対応の記録 |

### 5-3. 具体例：複数端末への横展開攻撃のインシデント管理

**状況:** 社内3台のPCでLateral Movement（横展開）が検知された

1. 1台目のアラートからインシデント「社内横展開攻撃 2026-03-25」を作成
2. インシデント詳細 → **アラート** タブ → **アラートを追加** で残り2台のアラートを紐付け
3. **タイムライン** タブで攻撃の進行順序を確認
4. **War Room** でセキュリティチームと作業を分担（例: 1人がフォレンジクス、1人がネットワーク遮断）
5. 対応アクションタブに実施内容を記録（パスワードリセット・端末再イメージング等）
6. 全端末のクリーンアップ後、ステータスを **解決済み** に変更

## 6. エンドポイント管理

> 📍 画面パス: `/endpoints`（一覧）　`/endpoints/[id]`（詳細・ライブレスポンス）

メニュー **エンドポイント → エンドポイント** を開きます。

### 6-1. エンドポイント一覧

| 列 | 意味 |
|----|------|
| ホスト名 | 端末名（クリックで詳細表示） |
| IPアドレス | 現在のIPアドレス |
| OS | Windows/macOS/Linux |
| ステータス | オンライン/オフライン/隔離中 |
| リスクスコア | 0〜100（高いほど危険） |
| 最終通信 | 最後にサーバーと通信した日時 |

### 6-2. エンドポイント詳細

エンドポイント名をクリックすると詳細ページが開きます。

| タブ | 内容 |
|-----|------|
| **概要** | OS情報・ユーザー・IPアドレス・エージェントバージョン |
| **プロセス** | 現在実行中のプロセス一覧 |
| **ネットワーク** | アクティブな接続・通信先IP |
| **ファイルイベント** | 最近のファイル作成・変更・削除 |
| **アラート** | このエンドポイントで発生したアラート履歴 |

### 6-3. エンドポイントの隔離と解除

**隔離（ネットワーク遮断）:**
1. エンドポイント詳細を開く
2. 右上の **隔離** ボタンをクリック
3. 確認ダイアログで理由を入力して **実行**
4. ステータスが「隔離中」に変わる（端末はサーバーとの通信のみ維持）

**隔離解除:**
1. 隔離中の端末詳細を開く
2. **隔離解除** ボタンをクリック
3. 対応完了の確認後に実行

> **注意:** 隔離中でもエージェントはサーバーと通信できます。フォレンジクス調査は隔離中に行うことを推奨します。

### 6-4. フルスキャンとスキャン停止

エンドポイント詳細の「**クイックアクション**」から手動スキャンを実行・停止できます。

**フルスキャンの実行:**
1. エンドポイント詳細を開く
2. クイックアクションの **フルスキャン** ボタンをクリック
3. 「対応アクション履歴」のスキャン行が「実行中」になり、完了すると結果（検知件数 / 走査件数）に変わる

**スキャンの停止:**
- 大量ファイルの走査は長時間化することがあります。誤起動時や緊急時は **スキャン停止** ボタン（クイックアクション、またはスキャン履歴の「実行中」行内の **停止** ボタン）で中断できます。
- 停止後、その行は「**停止済み（N件走査）**」と表示されます。

**スキャン履歴の状態表示:**

| 表示 | 意味 |
|-----|------|
| **実行中** | スキャン実行中。隣の「停止」ボタンで中断可能 |
| **クリーン (N件)** | 完了。脅威なし |
| **⚠ 検知 N件** | 完了。脅威を検知 |
| **停止済み (N件走査)** | ユーザーが停止 |
| **タイムアウト** | 結果が返らないまま一定時間（10分）を超過。エージェント再起動などで取り残された記録で、実行中スキャンは既に存在しません |

> **「タイムアウト」について:** スキャン中にエージェントが再起動（例: バイナリ更新）すると実行中スキャンは消滅し結果が返りません。こうした記録は「実行中」のまま残らず「タイムアウト」と表示されます。停止ボタンの対象ではありません。

**対応アクション履歴の「実行者」列:** 操作したユーザー名が表示されます。エージェントの自動対応は「エージェント (自動)」、システム実行は「システム」と表示されます。

## 7. 脅威インテリジェンスの活用

> 📍 画面パス: `/threat-intel`（フィード管理）　`/ioc`（IOC管理）　`/mitre`（ATT&Cマトリクス）　`/threat-intel/darkweb`（ダークウェブ監視）

### 7-1. IOC（侵害指標）の確認

メニュー **インテリジェンス → IOC** を開きます。

**検索方法:**
- IPアドレス、ドメイン、ファイルハッシュ（MD5/SHA256）で検索
- フィルター: `malicious`（悪意あり）/ `suspicious`（疑わしい）/ `clean`（クリーン）

**例: 不審なIPアドレスを調べる**
1. 検索バーに調査したいIPアドレス（例: `198.51.100.42`）を入力
2. 検索結果でリスクスコアと関連する脅威グループを確認
3. **VirusTotal連携** があれば外部評判も同時表示される

### 7-2. MITRE ATT&CK マッピング

メニュー **インテリジェンス → MITRE ATT&CK** を開きます。

- 自社環境での検知実績がATT&CKマトリクス上に色付きで表示される
- **カバレッジビュー:** どの手法に対して検知ルールがあるか確認できる
- **ギャップ分析:** 未カバーの手法を特定し、ルール追加の優先度付けに使用

**例: 「初期アクセス（Initial Access）」の検知状況を確認する**
1. MITRE ATT&CKページを開く
2. 「Initial Access」列の各手法をクリック
3. 「対応検知ルール数」と「過去30日の検知数」を確認
4. ルールが0件の手法には新しい検知ルールの追加を検討

### 7-3. ダークウェブ監視（v1.3.40以降）

メニュー **インテリジェンス → ダークウェブ監視** を開きます（`/threat-intel/darkweb`）。

ランサムウェアグループのリークサイトに自社の情報が掲載されていないかを自動監視します。

**監視の仕組み:**

| ソース | 更新頻度 | 内容 |
|--------|---------|------|
| ransomwatch（GitHub） | 毎日3:00 | 491以上のランサムウェアグループの .onion URL と被害者リスト |
| ransomware.live | 6時間ごと | 28,000件以上の被害者リスト（country・website 情報付き） |

**初期設定（監視対象の追加）:**
1. 「監視設定」タブを開く
2. 「追加」ボタンから以下を登録:
   - **ドメイン** — 自社ドメイン（例: `example.co.jp`）
   - **キーワード** — 会社名（例: `株式会社〇〇`）
   - **メール** — 担当者メール（例: `admin@example.co.jp`）
3. 次回スキャン（翌3:00または6時間以内）で照合が実行される

**検知時の動作:**
- 被害者リストに監視キーワードが一致した場合、severity=9（Critical）のアラートが自動生成される
- 「検知結果」タブに詳細が表示される（グループ名・説明・検知日時）

> **注意:** Tor コンテナ（`edr-tor`）が動作していないとヘルスチェック（B機能）が無効になります。ランサムウェアのリストとの照合（A機能）は Tor なしでも動作します。

## 8. 検知ルール管理

> 📍 画面パス: `/rules`（Sigmaルール）　`/yara`（YARAルール）　`/admin/suppressions`（抑制ルール）

メニュー **検知 → 検知ルール** を開きます。

### 8-1. ルールの有効化・無効化

1. ルール一覧で対象のルールを見つける（名前・タグ・ATT&CK IDで検索可）

### 8-2. カスタムSigmaルールの追加

メニュー **管理 → 検知 → Sigmaルール** を開きます（adminロール必要）。

1. **＋ ルールを追加** をクリック
2. Sigma YAMLフォーマットでルールを入力

**Sigmaルール例（PowerShellエンコードコマンドの検知）:**

```yaml
title: PowerShell Encoded Command Execution
id: a8b3c7d2-1234-5678-abcd-ef0123456789
status: experimental
description: PowerShellのエンコードされたコマンド実行を検知します
author: SOC Team
date: 2026/03/25
tags:
  - attack.execution
  - attack.t1059.001
logsource:
  category: process_creation
  product: windows
detection:
  selection:
    Image|endswith: '\powershell.exe'
    CommandLine|contains:
      - ' -EncodedCommand '
      - ' -enc '
      - ' -e '
  condition: selection
falsepositives:
  - 正規の管理スクリプト
level: high
```

3. **テスト実行** でルールの動作を検証してから保存

### 8-3. YARAルールの管理

メニュー **管理 → 検知 → YARAルール** を開きます。

ファイルスキャン用のYARAルールを管理します。マルウェアファミリー固有のパターンを追加することで、ゼロデイ攻撃の検知精度を向上できます。

#### コミュニティルールの自動同期（GitHub）

`Yara-Rules/rules` リポジトリから最新のコミュニティルールを一括取得できます。

**同期の実行（API）:**
```bash
# 同期開始（auto_enable: false = 無効状態でインポート、手動でレビュー後に有効化）

  -H "Content-Type: application/json" \
```

> 📍 画面パス: `/reports`（レポート一覧）　`/reports/builder`（カスタムレポート）　`/compliance`（コンプライアンス）

### 11-1. レポートの生成

メニュー **分析 → レポート** を開きます。

| レポート種別 | 内容 |

| コンプライアンスレポート | NIST CSF・CIS・ISO 27001準拠状況 |
| エンドポイントカバレッジ | エージェント導入率・未対応端末リスト |
| 脅威トレンド | 検知傾向と上位攻撃手法の分析 |

**レポート生成手順:**
1. レポート種別を選択
2. 期間を設定（例: 2026年2月1日〜2月28日）
3. **生成** をクリック
4. PDF/CSVでダウンロード
5. メール配信する場合は **スケジュール設定** でメールアドレスと配信日時を設定

### 11-2. コンプライアンス評価

メニュー **対応 → コンプライアンス** を開きます。

各フレームワークのスコアは実際の検知データ・エージェント稼働率・ルール有効率に基づいてリアルタイムで計算されます。

| フレームワーク | スコア算出根拠 | 推奨スコア目標 |
|--------------|--------------|--------------|
| **MITRE ATT&CK** | 検知アラートに付与されたMITREテクニックの種類数（40種類で100%） | 30%以上 |
| **CIS Controls** | 有効な検知ルール率 + エージェント稼働率の平均 | 75%以上 |
| **NIST CSF** | 5機能（特定・防御・検知・対応・回復）の各カテゴリカバレッジ | 70%以上 |
| **ISO 27001** | 情報セキュリティ管理の各ドメインの実装状況 | 80%以上 |

**MITRE ATT&CK スコアについて:**
- エンドポイントで検知されたアラートに自動付与されるMITREテクニックIDの種類数で評価
- アラートが増えるほど（＝より多くの攻撃手法を検知するほど）スコアが上昇する
- 40種類以上のテクニックを検知している場合は100%

**スコア改善の手順:**
1. スコアが低いフレームワークをクリックして詳細を確認
2. **ギャップ** タブで未対応の項目を確認
3. 検知ルールの有効化・エージェントのオンライン維持・IOC登録でスコアが改善される
4. スコアはリアルタイムで再計算される（ページリロードで最新値を反映）

| 確認手順 | コマンド/操作 |
|---------|------------|
| 1. エージェントサービスの状態確認 | `sc query KIZASHIAgent`（Windows） |
| 2. エージェントの再起動 | `sc stop KIZASHIAgent && sc start KIZASHIAgent` |
| 3. ファイアウォール確認 | サーバーのポート443/8443への通信を許可しているか確認 |
| 4. 証明書の有効期限確認 | エンドポイント詳細 → **証明書** タブ |

### アラートが多すぎて処理しきれない

1. **一括AI分類** を活用して自動トリアージ
2. 頻発する誤検知ルールを特定して抑制ルールを追加
   - メニュー: **管理 → 検知 → 抑制ルール**
3. 閾値ベースのアラートは感度を下げることを検討
4. **アラートダイジェスト** 設定で通知頻度を下げる

### ログインできない

| 症状 | 対処法 |
|-----|-------|
| パスワードを忘れた | ログイン画面の **パスワードを忘れた場合** リンクをクリック |
| アカウントがロックされた | admin権限者に連絡してアカウントのロック解除を依頼 |
| SSOでログインできない | IdPの設定とRedirect URIを確認。管理 → 認証設定 |

### ページが「Something went wrong」エラーになる

1. ブラウザのキャッシュをクリア（`Ctrl+Shift+Delete`）
2. ブラウザをリロード（`Ctrl+R`）
3. 別のブラウザで試す
4. 解決しない場合はシステム管理者に連絡

### エンドポイントを隔離したが通信が切れてしまった

隔離後もエージェントはサーバーと通信できます。エージェントのログを確認してください。

```
Windowsのログパス: C:\ProgramData\Kizashi\logs\agent.log
Linux のログパス:  /var/log/kizashi/agent.log
```

## 13. 1人SOC運用ガイド

少人数・1人体制でEDRプラットフォームを運用するための機能と推奨ワークフローです。

### 13-1. SOCワークキュー

メニュー **対応 → ワークキュー** を開きます（`/soc-queue`）。またはダッシュボードの **SOCワークキューウィジェット** からワンクリックで遷移できます。

未対応のアラート・インシデントが重要度と経過時間で自動分類されます：

| レーン | 条件 | 推奨対応時間 |
|---|---|---|
| 🔴 **今すぐ対応** | Critical(Lv9+)、またはHigh(Lv7+)かつ24時間以内 | 1時間以内 |
| 🟠 **今日中に対応** | Medium(Lv5+)、またはHigh超過(24h以上) | その日のうちに |
| 🔵 **今週中に対応** | Low重要度、調査中・封じ込め済み | 今週中 |

- 1分ごとに自動更新されます
- 各カードをクリックすると対象のアラート/インシデントページに遷移します
- ページ下部に **抑制候補**（繰り返し発生するノイズアラート）が表示されます
- ページ下部に **アラートグルーピング**（相関エンジンが検知したグループ）が表示されます（v1.3.32以降）

### 13-2. AIトリアージ自動化

`ANTHROPIC_API_KEY` が設定されている場合、5分ごとにClaudeがAI未分析のアラートを自動評価します：

- **誤検知率が高い**アラートは自動的に `false_positive` としてクローズ
- 分析結果はアラート詳細画面の「AI分析」タブに表示される
- バッチサイズ: 最大10件/回（APIレート制限対策）

**有効化方法:**
```bash
# EC2サーバーの .env に追加
echo "ANTHROPIC_API_KEY=your_key_here" >> ~/edr-platform/.env
docker compose up -d --build --no-deps api
```

### 13-3. デイリーブリーフィング

毎朝8:00に前日サマリーが自動生成されAPIサーバーのログに出力されます：

```
=== SOC デイリーブリーフィング 2026年05月05日 08:00 ===
📊 本日の新規アラート: 47件
🚨 緊急対応が必要: 3件
📁 未処理インシデント: 12件
🤖 AI自動クローズ(本日): 8件
🖥️ オフライン端末: 1台
🎯 上位テクニック: T1059 (12件), T1003 (7件)
→ 推奨アクション: ⚠️ 緊急アラート3件を優先対応してください（/soc-queue を確認）
```

ログを確認するコマンド：
```bash
docker logs kizashi-api --since 1h 2>&1 | grep "デイリーブリーフィング"
```

#### Slack / Webhook への配信（v1.3.32以降）

環境変数を設定することで毎朝のブリーフィングを外部サービスに自動配信できます。

| 環境変数 | 内容 |
|---|---|
| `BRIEFING_SLACK_WEBHOOK_URL` | Slack Incoming Webhook URL。リッチブロック形式でメッセージを送信。 |
| `BRIEFING_WEBHOOK_URL` | 汎用 Webhook URL。`BriefingSummary` を JSON ボディで POST。 |

**Slack 配信の設定例:**
```bash
# EC2 .env に追加
echo 'BRIEFING_SLACK_WEBHOOK_URL=https://hooks.slack.com/services/XXX/YYY/ZZZ' >> ~/edr-platform/.env
docker compose up -d --build --no-deps api
```

未設定の場合はログ出力＋NATS 配信のみ（従来動作を維持）。

### 13-4. 繰り返しアラートの抑制

SOCワークキューページ下部の「抑制候補」セクションに、過去7日間で5回以上発生したアラートが表示されます。

1. 対象の行の「抑制ルール作成」リンクをクリック
2. 抑制ルール設定ページで条件を確認・調整
3. 保存するとそのアラートは以後発生しない（または重要度が下がる）

**抑制候補APIを直接呼び出す場合:**
```bash
curl https://<server>/api/v1/suppressions/candidates?days=7&threshold=5 \
  -H "Authorization: Bearer <token>"
```

### 13-5. アラートグルーピング（相関検知）

相関エンジンが「同一端末・同一MITREテクニックで閾値件数以上のアラート」を検知すると、自動でインシデントを作成し `correlation_groups` に記録します。

SOCワークキューページ下部の **アラートグルーピング** セクションで確認できます：
- テクニック名・エージェントID・アラート件数・最終検知時刻・インシデントリンク
- インシデントが作成済みの場合は「インシデント表示」リンクで直接遷移

**閾値のチューニング（管理者向け）:**
```bash
# .env に追加して detection コンテナを再起動
CORRELATION_THRESHOLD=5          # 5件以上で自動インシデント化（デフォルト: 3）
CORRELATION_WINDOW_MINUTES=120   # 2時間以内の集計（デフォルト: 60）

docker compose up -d --build --no-deps detection
```

### 13-6. 推奨 1日の運用フロー

```
朝 ─── ダッシュボードの SOCキューウィジェットで緊急件数を確認
       ↓ /soc-queue を開いて「今すぐ対応」レーンを処理
       ↓ Slack でデイリーブリーフィングを確認（または APIログ）
       ↓ 緊急アラートを対応→クローズ

昼 ─── 「今日中に対応」レーンを処理
       ↓ AIが誤検知を自動クローズ済みであることを確認
       ↓ アラートグルーピングセクションで相関検知インシデントを確認
       ↓ YARA/Sigmaルールの新規有効化を検討

夕方 ── /compliance でスコアを確認
       ↓ 抑制候補を確認・必要に応じて抑制ルール作成
       ↓ 「今週中に対応」レーンを確認
```
