# PowerShell Module Logging (4103) テレメトリで field-gap の最後の実レバーを消化 — 2026-07-13 セッション総括

2026-07-02 に恒久化した **field-gap カナリア**([検知率向上_20260702_fieldフロンティアと自己点検カナリア.md](検知率向上_20260702_fieldフロンティアと自己点検カナリア.md)
／PR #371)を検証EC2 の実 DB に対して**初めてライブ計測**し、そこが指した残 inert の
最大レバー=**PowerShell Module Logging (EventID 4103)** テレメトリをエージェントに実装した(PR #458)。
これで field 被覆軸の実レバーは exotic な Cobalt Strike named-pipe を残すのみとなった。

---

## 1. field-gap カナリアの初ライブ計測 — field 被覆 98.6%(飽和)

カナリアのロジック(`FieldGapReport` = 有効 sigmahq ルールを field-support 判定し、
非対応ルールを欠落フィールド別に most-rules-first で集計)を、稼働中コンテナを再起動せず
**読み取り専用**で実 DB に対して実行した(手法は §4)。結果:

```
enabled_sigmahq=1981   inert(false-green)=28   (98.6% field-supported)
--- 次に足すべきテレメトリ・フィールド (emit → 有効化ルール数) ---
  22  Payload
   3  ContextInfo
   6  name        (ゲート由来の汎用フィールド疑い)
```

2026-07-02 の false-green 132 から **28 まで縮小**(93→0 消化 + その後のルール増分での
小さな新規裾野)。**field 被覆軸も飽和を実測確認**した。`OriginalFileName=74`(07-02 の
1 位)は 07-03 の PE VERSIONINFO 実装(PR#370/374/377)で既に解消済み。

### 残レバーの正体 = PowerShell 4103

`Payload`/`ContextInfo` は両方とも **PowerShell Module Logging (EventID 4103)** の
イベントフィールドで、該当ルールは:

- `Invoke-Obfuscation RUNDLL/VAR+/STDIN+/… - PowerShell Module`(難読化ランチャー各種)
- `Malicious PowerShell Commandlets - PoshModule`
- `Potential In-Memory Download And Compile Of Payloads`
- `Suspicious Get Information for SMB Share - PowerShell Module` ほか

= DPI 等の構造的死蔵ではなく、**エージェントが emit 可能な実テレメトリ**。ScriptBlock
(4104, `script` 型)はデオブフスクリプト**源**を運ぶが、ps_module ルールが選択する
`Payload`(実行されたコマンド + バインド済みパラメータ)/`ContextInfo`(host/user/
コマンド名の文脈)は供給できていなかった。

## 2. 4103 テレメトリの実装(PR #458, マージ済)

CreateRemoteThread(PR#445)で確立した「ETW collector が sender 経由で JSON-prefix ログ
イベントを直接送出する」パターンを踏襲。**既存の 4104 ScriptBlock 経路には一切触れず**、
proto も変更しない(回帰リスク最小)。

### エージェント
- **`ETWPSModuleCollector`**([agent/internal/platform/windows/psmodule_etw.go](../agent/internal/platform/windows/psmodule_etw.go))
  = 既知の Microsoft-Windows-PowerShell プロバイダ(`powerShellGUID`)の **EventID 4103** を
  収集し、`Payload`/`ContextInfo`/pid を抽出。4104 の script collector とは別セッション
  (`EDR-Agent-PSModule`)を張り、ハンドラで EventID 4103 のみに絞る。
- **`BuildPSModuleEvent`**([agent/internal/collector/ps_module.go](../agent/internal/collector/ps_module.go))
  = `ps_module:<uuid>:<json>`(inner JSON = `{payload, context_info, pid}`)を
  `EVENT_TYPE_LOG` で送出(create_remote_thread / credential_access と同じ ID ワイヤ形式)。
- opt-in `EDR_AGENT_ETW` / sender 経由 / 非 Windows は nil stub / session 失敗で no-op。

### サーバ
- **ingestion**([handler.go](../server/internal/ingestion/handler.go)): `promoteEventType` +
  `normalizeEventData` に `ps_module:` プレフィックス展開を追加(未 promote だと静かに
  ドロップ=既知のサイレント故障クラス)。
- **alias**([alert_pipeline.go](../server/internal/detection/alert_pipeline.go)): `addPipelineSigmaAliases`
  に `payload`→`Payload` / `context_info`→`ContextInfo`。
- **field-gate 対応化**([field_support.go](../server/internal/detection/field_support.go)):
  `SupportedSigmaFields` の kitchen-sink に生キー `payload`/`context_info` を追加
  (alias 適用で `Payload`/`ContextInfo` が supported 判定に入り、ps_module ルールが
  false-green から外れる)。

### テスト
- `BuildPSModuleEvent` wire-format(**4103 の Payload/ContextInfo はコロン・改行を多用**
  するため、サーバの `SplitN(id, ":", 3)` 後も inner JSON が壊れないことを固定)。
- `promoteEventType` の ps_module ケース、`payload→Payload` alias + field-support。
- agent collector テスト PASS / server build 緑。detection・ingestion のユニットテストは
  ローカル Defender がテストバイナリを隔離するため **CI(Linux)で実行**、全チェック緑。

## 3. 設計上の注意点・限界

- **4103 の Payload の豊かさはホストの PowerShell Module Logging 設定に依存**する。
  ScriptBlock(4104)は verbose ETW プロバイダを有効化するだけで policy 無しでも emit される
  が、Module Logging(4103)の pipeline 詳細は `EnableModuleLogging`(+ `ModuleNames=*`)が
  前提。コレクタはプロバイダが配信したものを転送する。
- **既存 4104 ScriptBlockText 検出と重複が見込まれる**(同じ Invoke-Obfuscation は
  script 変種でも発火し得る)ため、純増 recall は 22 より小さく **marginal**。それでも
  field-gap カナリアが指した「残 top レバー」を消化し、field 被覆軸を閉じたことに意味がある。
- **実機発火は Windows 箱で follow-up**(方針A=コード先行、CreateRemoteThread PR#445 と
  同じ運用)。opt-in / additive ゆえマージ低リスク。

## 4. 非破壊ライブ計測法(共有 EC2 の作法)

検証EC2 は**並行セッションのブランチ**がチェックアウトされコンテナも稼働中だった。
ブランチ切替・コンテナ再ビルドは他セッションの作業を壊すため厳禁。カナリアの初出力は
以下の完全非破壊な手順で取得した:

1. `git worktree add --detach /tmp/x origin/main` — 既存チェックアウトの working tree は不変。
2. 読み取り専用 Go ツール(`SupportedSigmaFields`/`RuleSelectedFields`/`RuleFieldSupportWith`
   を直呼びし、`FieldGapReport` と同一ロジックで集計)を、host の Go から postgres コンテナ
   IP:5432 へ接続して実行(ポート未公開でも host は docker bridge のコンテナ IP に到達可能)。
3. `git worktree remove` で撤去、`/tmp` 掃除。コンテナ・ブランチともに元通り。

## 5. 結論: field 被覆軸は閉じた

- field-gap カナリアが「生きたロードマップ」として機能し、**残 top レバー(4103)を数値で
  提示 → 実装 → 消化**という一巡を実データで回した。
- **検知率の field 被覆軸は飽和**(1981 中 false-green 28、実装後さらに縮小見込み)。
  残る実レバーは exotic な Cobalt Strike named-pipe(`pipe_created` テレメトリ)のみ →
  **翌 2026-07-14 に PR #464 で消化済み**(custom ソースゆえ本カナリアには映らなかった
  最後の 1 件。[検知率向上_20260714_named-pipeテレメトリ.md](検知率向上_20260714_named-pipeテレメトリ.md))。
  = **field 被覆軸の実レバーは完全にクローズ**。
- 検知率の次のフロンティアは field 被覆でなく、**別軸(ライブ発火の consumer ラグ等の
  運用信頼性)**へ完全に移った。
