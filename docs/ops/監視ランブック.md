# 監視ランブック

Prometheus のアラートが鳴ったときに開く手順書。
アラートの `runbook_url` はこのファイルの `### アラート名` を指します。

> **この文書の位置づけ。** ここに書いてあるのは、**このリポジトリから
> 確かめられること**だけです。式・閾値・サービス名・スクリプトの場所は
> 実物から起こしています。配備先ごとの事情（どのホストか、誰に連絡するか、
> どこまで落としてよいか）は書いてありません。**そこは各配備で足して
> ください。**

## 目次と現在の網羅

`deploy/prometheus/rules/edr-alerts.yml` と `deploy/prometheus_alerts.yml`
に定義されたアラートは 33 本で、**全部に手順があります。**

`scripts/check_prometheus_rules.py` が、`runbook_url` と見出しの対応を
CI で照合します。リンクだけあって手順が無い状態、手順だけあってリンクが
無い状態、アンカーがずれている状態は、どれも落ちます。**アラートを足す
ときは、リンクと見出しを同時に足してください。**

> **手順があることと、手順が正しいことは別です。** ここに書いたコマンドは
> このリポジトリの compose 構成に対するもので、**実際の障害で通したものでは
> ありません。** 使って違っていたら、その場で直してください —— 障害の
> 最中に読む文書は、読まれた回数だけ正確になります。

## エージェント

### EDRAgentsOffline

**出る条件** `(1 - edr:agents:online_ratio) > 0.10` が 5 分続いたとき
（severity: warning）。記録ルールの中身は
`edr_agents_online / clamp_min(edr_agents_online + edr_agents_offline_total, 1)`
なので、**分母は「登録済みの総数」です。**

**まず見る**

1. 落ちているのが特定の網か、全体かを分ける。全体なら
   サーバ側（`api` / `ingestion`）を先に疑います。
   ```bash
   curl -s http://localhost:8080/metrics | grep -E '^edr_agents_(online|offline_total)'
   ```
2. `api` が受けられているか。
   ```bash
   docker compose logs --tail=200 api | grep -iE 'error|refused|timeout'
   ```

**よくある原因**

- ネットワーク側（VPN / ファイアウォール規則の変更）で、一斉に届かなくなった
- `api` の再起動中。エージェントは再接続するので、数分で戻るなら様子見でよい
- **退役した端末が登録に残っている。** 分母に入り続けるので、比率だけが
  悪化します。台数が動いていないのに比率だけ上がっているときはこれを疑う

**誤報のとき** 退役端末が原因なら、閾値を上げるのではなく登録から外して
ください。閾値を上げると、**本当に 10% 落ちたときも黙ります。**

## API

### EDRHighAPIErrorRate

**出る条件** `edr-api` の 5xx 率が 5% を超えて 3 分続いたとき
（severity: critical）。

**まず見る**

1. 直前のデプロイ。**時刻が一致するなら、まず戻す。** 原因究明は戻した後。
2. どの経路が返しているか。
   ```bash
   docker compose logs --tail=500 api | grep -E ' 5[0-9][0-9] '
   ```
3. データベースが健全か（`PostgresDown` が同時に出ていないか）。
   5xx の多くはここから来ます。

**よくある原因**

- 直前のデプロイ
- DB の接続枯渇（`PostgresHighConnections` が併発しているはず）
- 上流（NATS / 外部連携）のタイムアウトが 5xx に化けている

### EDRAPIHighLatency

**出る条件** `edr-api` の P95 レイテンシが 2 秒を超えて 5 分続いたとき
（severity: warning）。

**まず見る**

1. 遅いのが全経路か、特定の経路かを分ける。全経路なら DB か CPU、
   一部なら問い合わせそのものを疑います。
2. DB 側の重い問い合わせ。
   ```bash
   docker compose exec postgres \
     psql -U edr -d edrplatform -c \
     "SELECT pid, now()-query_start AS dur, left(query,120)
        FROM pg_stat_activity
       WHERE state='active' AND now()-query_start > interval '2s'
       ORDER BY dur DESC;"
   ```
3. 接続プールの枯渇。待ちが積もると、個々の問い合わせが速くても P95 は伸びます。

**誤報のとき** 大量取り込みの時間帯だけ出るなら、その時間帯を除く
条件を式に入れてください。**閾値を上げると、平時の劣化が見えなくなります。**

## インフラ

### PostgresDown

**出る条件** `up{job="postgres"} == 0` が 30 秒続いたとき
（severity: critical）。

**まず見る**

```bash
docker compose ps postgres
docker compose logs --tail=200 postgres
```

**注意** これが出ているあいだ、書き込みは失われます。`api` は 5xx を返し、
取り込みは滞留します。**復旧後に `EDRNATSQueueDepth` と
`EDRDetectionConsumerLagging` が続けて出るのは正常です** —— 溜まった分を
流しているところなので、消化するまで待ってください。

**戻らないとき** ディスクが埋まっていないかを先に見る（`EDRDiskSpaceLow`）。
満杯だと PostgreSQL は起動しても書き込みを拒みます。

### EDRDiskSpaceLow

**出る条件** `/var/lib/postgresql` の空きが 20% を切って 5 分続いたとき
（severity: critical）。

**まず見る**

```bash
df -h /var/lib/postgresql
docker compose exec postgres \
  psql -U edr -d edrplatform -c \
  "SELECT relname, pg_size_pretty(pg_total_relation_size(relid)) AS size
     FROM pg_catalog.pg_statio_user_tables
    ORDER BY pg_total_relation_size(relid) DESC LIMIT 10;"
```

**効く順**

1. **バックアップの世代を先に減らす**（`deploy/backup/cleanup.sh`、
   既定の保持は `RETENTION_DAYS=30`）。データを消す前に、消してよいものを消す
2. イベントの保持期間を見直す。`events` は時系列で、いちばん大きくなります
3. ディスクを足す

**やってはいけないこと** 空きを作るために `events` を無計画に削ると、
**その期間の検知と調査ができなくなります。** 保持方針として決めてから
削ってください。

### EDRNATSQueueDepth

**出る条件** `nats_consumer_num_pending{job="nats"} > 10000` が 5 分続いたとき
（severity: warning）。ラベルに `consumer_name` と `stream_name` が乗ります。

**まず見る**

1. 詰まっている consumer が誰か（アラートのラベル）。
2. その先の処理が動いているか。検知側なら `detection` / `detection-2`。
   ```bash
   docker compose ps detection detection-2
   docker compose logs --tail=200 detection
   ```
3. 増え続けているのか、頭打ちなのか。**増え続けているなら、処理が
   止まっています。** 頭打ちなら流量の一時的な山です。

**よくある原因**

- 消費側が落ちている / 再起動中
- `PostgresDown` の直後（溜まった分を流している最中。待てば減る）
- 取り込み量が消費能力を超えた。`detection` を増やす

## バックアップ

3 本は同じ計測（`deploy/backup/backup.sh`）から出ますが、
**言っていることが違います。**

| アラート | 意味 |
|---|---|
| `EDRBackupFailing` | 失敗が起きている。**古い成功は残っているかもしれない** |
| `EDRBackupStale` | 検証に通ったものが 48 時間ない |
| `EDRBackupNeverSucceeded` | **一度もない。** 古いものがあるのではなく、無い |

### EDRBackupFailing

**出る条件** `increase(edr_backup_failures_total[6h]) > 0` が 5 分続いたとき
（severity: warning）。直近 6 時間に `pg_dump` の失敗、または整合性検査の
不合格があったということです。

**まず見る**

```bash
docker compose logs --tail=300 | grep '\[backup\]'
ls -lh "${BACKUP_DIR:-/var/backups/edr}"
df -h "${BACKUP_DIR:-/var/backups/edr}"
```

**よくある原因**

- 保存先の空き不足（**いちばん多い**）
- `DATABASE_URL` の資格情報が変わった
- `pg_dump` が入っていない / バージョンが合わない（`backup.sh` は
  見つからなければその場で止まります）

### EDRBackupStale

**出る条件** 最後に**検証を通った**バックアップから 48 時間経過した状態が
30 分続いたとき（severity: critical）。
`edr_backup_last_success_timestamp_seconds > 0` が条件に入っているので、
**一度も成功していない場合はこちらではなく `EDRBackupNeverSucceeded` が出ます。**

**まず見る** `EDRBackupFailing` と同じ。加えて、**スケジューラが生きているか**
を見ます。失敗が 0 件のまま古くなっているなら、走っていません。

```bash
cat deploy/backup/ofelia.ini
docker compose -f deploy/backup/docker-compose.backup.yml ps
```

**大事なこと** `pg_dump` が exit 0 でも、切り詰められたダンプは成功に
数えていません。**「取れている」と「戻せる」は別です。**
戻せることを確かめる手順は `deploy/backup/restore.sh` にあります。

### EDRBackupNeverSucceeded

**出る条件** `edr_backup_last_success_timestamp_seconds == 0` が 6 時間続いたとき
（severity: critical）。

**これは設定の問題です。** 運用中に劣化したのではなく、**最初から
動いていません。** 新規配備の直後か、バックアップ一式を入れ替えた直後に出ます。

**まず見る**

1. バックアップの compose を上げているか
   （`deploy/backup/docker-compose.backup.yml`）
2. `DATABASE_URL` と `BACKUP_DIR` が渡っているか
3. 一度手で走らせて、出る内容を見る

```bash
bash deploy/backup/backup.sh
```

## 検知

### EDRDetectionDown

**出る条件** `up{job="edr-detection"} == 0` が 1 分続いたとき
（severity: critical）。

**この間に何が失われるか（重要）**

DB ルール（`rules` テーブル）と、状態を持つ検知器
（discovery / file_burst / auth_attack / lateral_fanout / exfil_volume /
killchain など）は **このプロセスにしかありません。** 停止中はそれらが
まるごと動きません。

**`server-api` の組み込み Sigma は動き続けるので、アラートは出続けます。**
画面を見ている人には、止まっているように見えません。**「アラートが出ている
から検知は動いている」と読まないでください。**

**まず見る**

```bash
docker compose ps detection detection-2
docker compose logs --tail=200 detection
```

**復旧後** 止まっていた間のイベントは、JetStream に残っていれば流れ直します。
`EDRDetectionConsumerLagging` が続けて出るのは、その消化中です。

### EDRDetectionPipelineStalled

**出る条件** 検知エンジンが最後にイベントを処理してから 300 秒経過した状態が
5 分続いたとき（severity: critical）。

**`EDRDetectionDown` との違い** プロセスは**生きています。** 死活監視には
掛かりません。ingestion → NATS → detection のどこかで流れが止まっています。

**まず見る**

1. **本当にイベントが無い時間帯かどうかを先に確かめる。**
   ```bash
   curl -s http://localhost:8080/metrics | grep '^edr_events_ingested_total'
   ```
   取り込みも止まっているなら、原因は上流（エージェント / `ingestion`）です。
2. 取り込みは動いているのに検知に届いていないなら、あいだの NATS。
   ```bash
   curl -sf 'http://localhost:8222/healthz?js-server-only=true'
   docker compose logs --tail=200 ingestion
   ```

**注意** 夜間や休日に流量が落ちる配備では、平常時でも出ます。その場合は
閾値ではなく、**時間帯の条件**を式に足してください。

### EDRDetectionConsumerLagging

**出る条件** `edr_detection_consumer_pending{job="edr-detection"} > 50000` が
10 分続いたとき（severity: warning）。

**意味するところ** 検知が実時間から遅れています。**この状態で検知率を
測っても、結果は信用できません。** 測定の前には必ずこの値が十分小さいことを
確かめてください。

**まず見る**

1. 減っているか、増えているか。減っているなら消化中なので待ちます
   （`PostgresDown` や `EDRDetectionDown` の直後は正常）
2. 増え続けるなら、消費が流量に負けています。`detection` の数を増やす
   （compose に `detection` と `detection-2` があります）
3. `EDRNATSQueueDepth` が同時に出ていれば、同じ詰まりを別の場所から
   見ています

### EDRHashIOCHasNothingToMatch

**出る条件** 直近 1 時間のイベントの半分以上が、ハッシュを 1 つも持たずに
ハッシュ IOC 照合へ届いた状態が 2 時間続いたとき（severity: warning）。

**意味するところ** **既知マルウェアの検知が、その分だけ動いていません。**
照合そのものは動いていて、一致 0 件を返します。**一致 0 件は「安全」では
なく「確かめられていない」です。** 画面上は何も起きません。

**まず見る**

1. どの経路のイベントがハッシュを落としているか。プラットフォーム別に
   偏っていないかを見ます（Windows / Linux / macOS でハッシュの取り方が違う）
2. エージェント側でハッシュ計算が無効になっていないか、
   あるいは対象ファイルに届かず（権限 / パス除外）計算できていないか
3. 取り込み経路でハッシュ欄が落ちていないか

**やってはいけないこと** このアラートを閾値で黙らせること。
**鳴っている間、既知マルウェアは素通りします。**

### EDRDetectionInsertFailures

**出る条件** `sum by (source) (rate(edr_alert_insert_failures_total[15m])) > 0`
が 5 分続いたとき（severity: critical）。ラベルに `source` が乗ります。

**意味するところ** 検知は動いていて、**書き込みだけが落ちています。**
検知した事実がそのまま消えます。画面には何も出ません —— 出るはずの行が
無いだけなので、静かな夜と区別がつきません。

**まず見る**

1. どの `source` かをラベルで見る。1つだけなら、そのルート／ルールの問題です
2. 直前のルール変更・マイグレーション。この失敗は制約違反で出ます:
   - `22P02` — UUID でない `rule_id`
   - CHECK 違反 — `severity` などの値が許された集合の外
   - `42P08` — パラメータの型が決まらない
   ```bash
   docker compose logs --tail=300 detection | grep -iE 'insert|22P02|42P08|constraint'
   ```

**やってはいけないこと** 制約を緩めて通すこと。**通った先に入るのは、
検知の意味を持たない行です。**

### EDRDetectionPipelineSilent

**出る条件** `sum(increase(edr_detections_total[1h])) == 0` が 15 分続いたとき
（severity: warning）。どのエンジン（sigma / behavioral / heuristic / yara /
ioc / chain / baseline / memory / credential_access / process_block）からも
1 時間 1 件も出ていない状態です。

**`EDRDetectionPipelineStalled` との違い** あちらは「イベントが流れていない」、
こちらは「イベントは流れているのに検知が 0 件」です。**0 件は「安全」では
なく「確かめられていない」かもしれません。**

**まず見る**

1. イベントは届いているか。
   ```bash
   curl -s http://localhost:8080/metrics | grep '^edr_events_ingested_total'
   ```
   届いていないなら `EDRDetectionPipelineStalled` の手順へ。
2. 届いているのに 0 件なら、ルールが effectively 無効になっていないか
   （`EDRCurateInertRules` が同時に出ていないか）。
3. 台数の少ない検証環境では、平常時でも 0 件が続きます。その場合は
   閾値ではなく**この環境でこのアラートを使うか**を決めてください。

### EDRCurateInertRules

**出る条件** `edr_curate_inert_rules > 0` が 6 時間続いたとき
（severity: warning）。有効化から 7 日以上たったルールが、直近 7 日で
1 件もアラートを出していない状態です。

**意味するところ** ルールは有効に見えて、**当たりようがない**可能性が
あります。よくあるのは、テレメトリが一度も出さないフィールドを見ている、
別名が壊れている、対象の活動がそもそも無い、のどれかです。

**まず見る**

```bash
docker compose logs --tail=300 detection | grep -i curate
```

CurateScheduler が対象の例を出します。フィールドの実在は
field-contract のゲートで確かめられます。

**注意** 「当たらない」と「当たるべきものが無い」は別です。**外す前に、
そのルールが検知するはずのものを1度作ってみてください。**

### EDRCurateQuarantineReenabled

**出る条件** `increase(edr_curate_quarantine_reconciled_total[6h]) > 0` が
5 分続いたとき（severity: warning）。

**意味するところ** `curate_state='quarantined'`（誤検知が続いて隔離した）
のに `enabled=true` になっていたルールを、突き合わせが再び無効に戻しました。
**戻したこと自体は正常です。問題は、戻す必要があったことです。**
どこかの有効化の経路が、隔離の状態を見ずに `enabled` を立てています。

**まず見る** 手動の一括操作か、カテゴリ単位の `UPDATE` です。
そこを直さないと、6 時間ごとに同じことが起きます。

**やってはいけないこと** 突き合わせを止めること。**止めると、誤検知の
ルールが有効のまま残ります。**

### EDRBackgroundComponentFailing

**出る条件** `sum by (component) (rate(edr_background_failures_total[15m])) > 0`
が 10 分続いたとき（severity: warning）。ラベルに `component` が乗ります。

**意味するところ** 背景の仕事が捨てられています。**画面には何も出ません。**
送られなかった通知も、SIEM に届かなかった文書も、送るものが無い環境も、
見た目が同じです。

**まず見る** ラベルの `component` で当たりをつけます。

```bash
docker compose logs --tail=300 api detection | grep -i "$COMPONENT"
```

**この数字が 0 に戻ったことを、直った証拠にしないでください。**
仕事が来なくなっても 0 になります。

### EDRSchedulerRunningWithoutSucceeding

**出る条件** 最後の起動と最後の成功の差が 1 時間を超えた状態が 15 分続いたとき
（severity: warning）。ラベルに `scheduler` が乗ります。

**意味するところ** **起きて、諦めています。** 実行回数だけは増え続けるので、
「動いている」ように見えます。火曜から証明書の更新に失敗し続けている状態は、
**この 1 つを除くすべての信号で、何事もない状態と同じ形をしています。**

**まず見る**

```bash
docker compose logs --tail=300 api | grep -i "$SCHEDULER"
```

失敗の理由はそこに出ます。出ていないなら、それ自体が所見です
（`EDRBackgroundComponentFailing` と併せて見てください）。

### EDRSchedulerNeverSucceeded

**出る条件** 4 回以上起動して、成功の記録が 1 度も無い状態が 30 分続いたとき
（severity: warning）。

**これは設定の問題です。** 運用中に劣化したのではなく、**最初から
動いていません。** 実行回数だけを見ている限り、健全なワーカーと
見分けがつきません。

**まず見る** そのスケジューラが要る資格情報・接続先・テーブルが
揃っているか。新規配備の直後に出るのが普通です。

## API・インフラ（残り）

### EDRApiDown

**出る条件** `up{job="edr-api"} == 0` が 1 分続いたとき（severity: critical）。

**まず見る**

```bash
docker compose ps api
docker compose logs --tail=200 api
curl -sf http://localhost:8080/healthz
```

止まっている間、画面も API も応答しません。**エージェントは再接続を
続けるので、復旧すれば取りこぼしはある程度戻ります**（`ingestion` が
生きていれば、そちらは受け続けています）。

### EDRApiHighRequestRate

**出る条件** `rate(http_requests_total{job="edr-api"}[1m]) > 500` が
2 分続いたとき（severity: warning）。

**まず見る** 「攻撃」と決める前に、**自分たちの仕掛けを疑ってください。**
多いのは、画面の自動更新の間隔を短くした、エージェントを一斉に配った、
バッチを流した、のどれかです。

```bash
docker compose logs --tail=500 api | awk '{print $NF}' | sort | uniq -c | sort -rn | head
```

送り元が 1 か所に偏っていれば、それが答えです。

### PostgresHighConnections

**出る条件** 使用中の接続が上限の 80% を超えて 5 分続いたとき
（severity: warning）。

**まず見る**

```bash
docker compose exec postgres \
  psql -U edr -d edrplatform -c \
  "SELECT state, count(*) FROM pg_stat_activity
    WHERE datname='edrplatform' GROUP BY state ORDER BY 2 DESC;"
```

`idle in transaction` が多いなら、**接続が足りないのではなく、
返していません。** 上限を上げても増えるだけです。

**関連** `EDRAPIHighLatency` が同時に出ていれば、待ちが伸びている側から
同じことを見ています。

### PostgresDiskUsageHigh

**出る条件** `/var/lib/postgresql` の使用率が 80% を超えて 5 分続いたとき
（severity: warning）。

**`EDRDiskSpaceLow` と同じ条件です。** あちらは「空きが 20% を切る」、
こちらは「使用が 80% を超える」で、**同じ閾値を裏返しただけです**
（`1 - avail/size > 0.8` ⟺ `avail/size < 0.2`）。同じマウントを見ているので、
基本的に一緒に鳴ります。severity だけが違います（critical / warning）。

**片方に寄せるかは運用の判断です。** ここでは事実として書き残します ——
2 通鳴っても、起きていることは 1 つです。手順は `EDRDiskSpaceLow` を
見てください。

### NATSDown

**出る条件** `up{job="nats"} == 0` が 1 分続いたとき（severity: critical）。

**この間、検知は動きません。** ingestion が受けたイベントは detection へ
渡りません。

**まず見る**

```bash
docker compose ps nats-1 nats-2 nats-3
curl -sf 'http://localhost:8222/healthz?js-server-only=true'
docker compose logs --tail=200 nats-1
```

3 台構成なので、1 台落ちても `up` は他が答えます。**このアラートが出て
いるということは、収集対象が全部落ちているか、収集の設定が 1 台しか
見ていないかのどちらかです。**

**復旧後** JetStream に残っていた分が流れ直します。
`EDRNATSQueueDepth` と `EDRDetectionConsumerLagging` が続けて出るのは
その消化中です。

### NATSSlowConsumers

**出る条件** `nats_slow_consumer_count > 10` が 5 分続いたとき
（severity: warning）。

**意味するところ** 受け手が読み切る前に、次が届いています。**JetStream の
消費が遅れている（`EDRNATSQueueDepth`）のとは別で、こちらは取りこぼしが
起きうる形です。**

**まず見る** 遅れている受け手が誰か。多くは `detection` です。

```bash
docker compose logs --tail=200 detection | grep -i slow
```

**効く順** 受け手を増やす（`detection-2`）→ 送る量を減らす（取り込みの
フィルタ）→ NATS 側のバッファを増やす。**最後のものは、遅れを溜める場所を
広げるだけです。**

### HighCPUUsage

**出る条件** CPU の idle 以外が 85% を超えて 10 分続いたとき
（severity: warning）。

**まず見る**

```bash
docker compose stats --no-stream
```

**平常時から高い環境では、これは容量の話です。** 突然上がったのなら、
直前の変更（ルールの追加、取り込み量、バッチ）を見てください。

### HighMemoryUsage

**出る条件** メモリ使用率が 90% を超えて 5 分続いたとき（severity: warning）。

**まず見る** `docker compose stats --no-stream` で、どのサービスかを分けます。

**注意** PostgreSQL は `shared_buffers` と OS のページキャッシュで、
**健全な状態でも空きを使い切ります。** 「使っている」と「足りない」は
別です。スワップと OOM の記録を併せて見てください。

```bash
dmesg -T 2>/dev/null | grep -i -m5 'out of memory' || echo 'OOM の記録なし'
```

### DiskSpaceLow

**出る条件** どれかのファイルシステム（tmpfs を除く）の使用率が 85% を
超えて 5 分続いたとき（severity: warning）。ラベルに `mountpoint` が乗ります。

**`EDRDiskSpaceLow` との違い** あちらは `/var/lib/postgresql` だけを、
より厳しい閾値で見ます。**こちらはマウントを選びません** —— 関係のない
ファイルシステムでも鳴ります。ラベルの `mountpoint` を最初に見てください。

`/var/lib/postgresql` なら `EDRDiskSpaceLow` の手順へ。それ以外なら、
そのマウントが何のためのものかから始めます。

### HighAlertVolume

**出る条件** 直近 1 時間のアラートが 1000 件を超えたとき（severity: warning、
`for` なし＝即時）。

**意味するところ** **2 通りあり、対応が正反対です。**

1. **本当に起きている** —— 侵害、横展開、一斉のスキャン
2. **ルールが壊れた** —— 直前に有効化／編集したルールが当たりすぎている

**先に 2 を確かめてください。** 1 だと思って調査に入ると、時間を全部
使います。

```bash
docker compose exec postgres \
  psql -U edr -d edrplatform -c \
  "SELECT rule_name, count(*) FROM alerts
    WHERE created_at > NOW() - INTERVAL '1 hour'
    GROUP BY rule_name ORDER BY 2 DESC LIMIT 10;"
```

1 本のルールに偏っていれば 2 です。散っていれば 1 を疑います。

**やってはいけないこと** 閾値を上げること。**次の侵害でも鳴らなくなります。**
当たりすぎているルールがあるなら、そのルールを直してください。

### CriticalAlertsUnacknowledged

**出る条件** 未対応の critical が 20 件を超えて 30 分続いたとき
（severity: critical）。

**これは装置の異常ではなく、運用の状態です。** 直すのはコードではなく
運用側です。

**まず見る** 溜まっているのが同じルールなら、そのルールが critical で
あるべきかを見直します（`HighAlertVolume` の 2 と同じ形です）。散って
いるなら、単に手が足りていません。

**注意** このアラートを消すために一括で「対応済み」にすると、
**次に本当に見なければならないものが同じ山に埋まります。**

### AgentOffline

**出る条件** `edr_agents_offline > 0` が 15 分続いたとき（severity: warning）。

**この条件は、実運用ではほぼ常に真です。** 1 台でも 15 分オフラインなら
鳴ります。ノート PC を含む配備では、閉じている端末が常にあります。

**`EDRAgentsOffline` との違い** あちらは**割合**（登録済みの 10% 超）を
見ます。**運用で使えるのはあちらです。** こちらは「0 台であること」を
期待する配備 —— 常時稼働のサーバだけを見ている環境 —— でのみ意味を
持ちます。

**そうでない環境では、このアラートを無効にするか、閾値を台数に合わせて
ください。** 常に鳴っているアラートは、鳴っていないのと同じです。

### EDRDetectionConsumerLagCritical

**出る条件** JetStream の未配信が 100 万件を超えて 10 分続いたとき
（severity: critical）。

**`EDRDetectionConsumerLagging`（5 万件）の重い版です。** ここまで来ると
**検知は実質的に機能していません。** 遅れではなく、追いつく見込みが
無い状態です。

**やること**

1. まず流量を止めるか減らす（取り込み側のフィルタ）。**受け手を増やす
   だけでは追いつきません** —— 100 万件は、平常の処理速度では消化に
   何時間もかかります
2. そのうえで `detection` を増やす
3. 消化のあいだ、**検知は過去のイベントを見ています。** その間に届く
   新しい脅威は、さらに後ろに並びます

**この状態での検知率の測定は無意味です。** 数字は取れますが、何も
表していません。

## 手順のあるアラート

`deploy/prometheus/rules/edr-alerts.yml` と `deploy/prometheus_alerts.yml`
のアラート **33 本すべてに手順があります**。

`scripts/check_prometheus_rules.py` が、`runbook_url` と見出しの対応を
CI で照合します。リンクだけあって手順が無い状態、手順だけあってリンクが
無い状態、アンカーがずれている状態は、どれも落ちます。**アラートを足す
ときは、リンクと見出しを同時に足してください。**

## 書いていて気づいたこと

手順を書くために 33 本を並べたところ、条件そのものに問題のあるものが
3 つ見つかりました。**アラートの定義は直していません** —— 運用で
どちらを採るかの判断が要るので、事実として書き残します。

- **`PostgresDiskUsageHigh` と `EDRDiskSpaceLow` は同じ条件です。**
  `1 - avail/size > 0.8` と `avail/size < 0.2` は同値で、マウントも同じ
  `/var/lib/postgresql` です。severity だけが違います（warning / critical）。
  1 つの事象で 2 通鳴ります
- **`AgentOffline` は実運用でほぼ常に真です。** `edr_agents_offline > 0`
  なので、1 台でも 15 分オフラインなら鳴ります。**常に鳴っている
  アラートは、鳴っていないのと同じです。** 割合を見る
  `EDRAgentsOffline` が実質の代替になっています
- **`DiskSpaceLow` はマウントを選びません。** 関係のない
  ファイルシステムでも鳴ります
