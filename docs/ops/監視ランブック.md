## 1. Prometheus アラート対応手順

### Prometheus アラートルール定義

以下のアラートルールを `deploy/monitoring/alerts.yaml` に定義します。

```yaml
# deploy/monitoring/alerts.yaml
groups:
  - name: kizashi_edr
    interval: 30s
    rules:

      # ----------------------------------------------------------------
      # エージェント監視
      # ----------------------------------------------------------------
      - alert: EDRAgentsOffline
        expr: |
          (
            sum(kizashi_agents_online_total) /
            sum(kizashi_agents_registered_total)
          ) < 0.9
        for: 10m
        labels:
          severity: warning
          team: ops
        annotations:
          summary: "EDR エージェントのオンライン率が 90% を下回っています"
          description: "登録エージェントの {{ $value | humanizePercentage }} がオフラインです"
          runbook: "docs/ops/monitoring-runbook.md#edragentsoffline"

      - alert: EDRAgentsMajorityOffline
        expr: |
          (
            sum(kizashi_agents_online_total) /
            sum(kizashi_agents_registered_total)
          ) < 0.5
        for: 5m
        labels:
          severity: critical
          team: ops
        annotations:
          summary: "EDR エージェントの過半数がオフラインです"
          runbook: "docs/ops/monitoring-runbook.md#edragentsoffline"

      # ----------------------------------------------------------------
      # API 監視
      # ----------------------------------------------------------------
      - alert: EDRHighAPIErrorRate
        expr: |
          sum(rate(http_requests_total{job="kizashi-api",code=~"5.."}[5m])) /
          sum(rate(http_requests_total{job="kizashi-api"}[5m])) > 0.01
        for: 5m
        labels:
          severity: warning
          team: ops
        annotations:
          summary: "EDR API の 5xx エラーレートが 1% を超えています"
          description: "現在のエラーレート: {{ $value | humanizePercentage }}"
          runbook: "docs/ops/monitoring-runbook.md#edrhighaperiorrate"

      - alert: EDRHighAPIErrorRateCritical
        expr: |
          sum(rate(http_requests_total{job="kizashi-api",code=~"5.."}[5m])) /
          sum(rate(http_requests_total{job="kizashi-api"}[5m])) > 0.05
        for: 2m
        labels:
          severity: critical
          team: ops
        annotations:
          summary: "EDR API の 5xx エラーレートが 5% を超えています"

      - alert: EDRAPIHighLatency
        expr: |
          histogram_quantile(0.99,
            rate(http_request_duration_seconds_bucket{job="kizashi-api"}[5m])
          ) > 2.0
        for: 10m
        labels:
          severity: warning
          team: ops
        annotations:
          summary: "EDR API の p99 レイテンシが 2 秒を超えています"
          description: "現在の p99 レイテンシ: {{ $value | humanizeDuration }}"
          runbook: "docs/ops/monitoring-runbook.md#edrapihighlatency"

      # ----------------------------------------------------------------
      # ストレージ監視
      # ----------------------------------------------------------------
      - alert: EDRDiskSpaceLow
        expr: |
          (
            node_filesystem_avail_bytes{mountpoint="/var/lib/postgresql"} /
            node_filesystem_size_bytes{mountpoint="/var/lib/postgresql"}
          ) < 0.20
        for: 5m
        labels:
          severity: warning
          team: ops
        annotations:
          summary: "EDR データベースボリュームの空き容量が 20% を下回っています"
          description: "残り容量: {{ $value | humanizePercentage }}"
          runbook: "docs/ops/monitoring-runbook.md#edrdiskspacelow"

      - alert: EDRDiskSpaceCritical
        expr: |
          (
            node_filesystem_avail_bytes{mountpoint="/var/lib/postgresql"} /
            node_filesystem_size_bytes{mountpoint="/var/lib/postgresql"}
          ) < 0.10
        for: 1m
        labels:
          severity: critical
          team: ops
        annotations:
          summary: "EDR データベースボリュームの空き容量が 10% を下回っています"

      # ----------------------------------------------------------------
      # NATS 監視
      # ----------------------------------------------------------------
      - alert: EDRNATSQueueDepth
        expr: |
          nats_stream_pending_count{stream_name="ALERTS"} > 10000
        for: 5m
        labels:
          severity: warning
          team: ops
        annotations:
          summary: "NATS ALERTS ストリームのキュー深度が 10,000 を超えています"
          description: "現在のキュー深度: {{ $value }}"
          runbook: "docs/ops/monitoring-runbook.md#edrnatsqueuedepth"

      - alert: EDRNATSQueueDepthCritical
        expr: |
          nats_stream_pending_count{stream_name="ALERTS"} > 50000
        for: 2m
        labels:
          severity: critical
          team: ops
        annotations:
          summary: "NATS ALERTS ストリームのキュー深度が 50,000 を超えています"

      # ----------------------------------------------------------------
      # データベース監視
      # ----------------------------------------------------------------
      - alert: EDRDatabaseDown
        expr: |
          up{job="kizashi-postgresql"} == 0
        for: 1m
        labels:
          severity: critical
          team: ops
        annotations:
          summary: "EDR データベースが応答していません"
          runbook: "docs/ops/monitoring-runbook.md#postgresdown"

      # ----------------------------------------------------------------
      # Detection エンジン監視
      # ----------------------------------------------------------------
      - alert: EDRDetectionEngineDown
        expr: |
          up{job="kizashi-detection"} == 0
        for: 2m
        labels:
          severity: critical
          team: ops
        annotations:
          summary: "EDR Detection エンジンが応答していません"
          runbook: "docs/ops/monitoring-runbook.md#edrdetectiondown"

      # 検知パイプライン死活監視 (dead-man's-switch)。
      # プロセス生存 (up==1 / readiness 緑) でも ingestion→NATS→detection の
      # どこかが停滞すればアラート生成は静かに止まる。edr_detection_last_event_
      # timestamp_seconds は detection がイベントを処理する度に更新されるため、
      # 更新が途絶えたら「健全に見えるのに検知が死んでいる」サイレント障害。
      - alert: EDRDetectionPipelineStalled
        expr: |
          time() - edr_detection_last_event_timestamp_seconds > 600
        for: 5m
        labels:
          severity: critical
          team: ops
        annotations:
          summary: "検知パイプラインが 10 分以上イベントを処理していません"
          description: "最終処理から {{ $value | humanizeDuration }} 経過。プロセスは生存しているが検知が停止している疑い"
          runbook: "docs/ops/monitoring-runbook.md#edrdetectionpipelinestalled"

      # 検知コンシューマのバックプレッシャー (完全停止の前兆)。
      - alert: EDRDetectionConsumerLag
        expr: |
          edr_detection_consumer_pending > 5000
        for: 10m
        labels:
          severity: warning
          team: ops
        annotations:
          summary: "Detection consumer が ingestion に追いつけていません (pending > 5000)"
          description: "現在の pending: {{ $value }}。継続的な上昇は検知遅延・取りこぼしの前兆"
          runbook: "docs/ops/monitoring-runbook.md#edrdetectionconsumerlagging"

      # ----------------------------------------------------------------
      # バックアップ健全性監視 (SLO)
      # ----------------------------------------------------------------
      # edr_backup_last_success_timestamp_seconds は「整合性検証に通った」
      # 最新バックアップの時刻。pg_dump が exit 0 でも切り詰め/空ダンプは
      # 検証で failed 扱いになり本メトリクスを更新しない。復旧時=災害時に
      # 初めて壊れたバックアップに気づく事態を防ぐための唯一の先行指標。
      - alert: EDRBackupStale
        expr: |
          time() - edr_backup_last_success_timestamp_seconds > 172800
        for: 10m
        labels:
          severity: critical
          team: ops
        annotations:
          summary: "48 時間以上、検証済みの成功バックアップがありません"
          description: "最終成功から {{ $value | humanizeDuration }} 経過。バックアップがサイレントに失敗している疑い"
          runbook: "docs/ops/monitoring-runbook.md#edrbackupstale"

      - alert: EDRBackupFailing
        expr: |
          increase(edr_backup_failures_total[6h]) > 0
        for: 5m
        labels:
          severity: warning
          team: ops
        annotations:
          summary: "自動バックアップが失敗しています (pg_dump エラーまたは整合性検証失敗)"
          runbook: "docs/ops/monitoring-runbook.md#edrbackupstale"

      # ----------------------------------------------------------------
      # 証明書監視
      # ----------------------------------------------------------------
      - alert: EDRCertificateExpiry
        expr: |
          (
            probe_ssl_earliest_cert_expiry{job="blackbox"} - time()
          ) / 86400 < 14
        for: 1h
        labels:
          severity: warning
          team: ops
        annotations:
          summary: "EDR TLS 証明書の有効期限が 14 日以内です"
          description: "証明書の有効期限: {{ $value | humanizeDuration }}"
          runbook: "docs/ops/monitoring-runbook.md#edrcertificateexpiry"
```

### EDRAgentsOffline

**重大度**: Warning (90% 未満) / Critical (50% 未満)
**意味**: 登録済みエージェントのオンライン率が低下しています

#### 確認コマンド

```bash
# ─────────────────────────────────────────────────────────
# Step 1: 現在のエージェント状況確認
# ─────────────────────────────────────────────────────────

# 全体のエージェント数とオンライン数
kubectl exec -n edr-system deploy/kizashi-api -- \
  psql -h kizashi-postgresql -U kizashi -d kizashi -t << 'SQL'
SELECT
  count(*) AS total,
  count(*) FILTER (WHERE last_seen > NOW() - INTERVAL '5 minutes') AS online,
  count(*) FILTER (WHERE last_seen <= NOW() - INTERVAL '5 minutes') AS offline,
  count(*) FILTER (WHERE last_seen <= NOW() - INTERVAL '1 hour') AS long_offline
FROM agents;
SQL

# オフラインエージェントの一覧 (最終通信時刻と共に)
kubectl exec -n edr-system deploy/kizashi-api -- \
  psql -h kizashi-postgresql -U kizashi -d kizashi -t << 'SQL'
SELECT
  hostname,
  ip_address,
  os_type,
  last_seen,
  NOW() - last_seen AS offline_duration
FROM agents
WHERE last_seen <= NOW() - INTERVAL '5 minutes'
ORDER BY last_seen ASC
LIMIT 20;
SQL

# ─────────────────────────────────────────────────────────
# Step 2: Ingestion サービスの状態確認
# ─────────────────────────────────────────────────────────
kubectl get pods -n edr-system | grep ingestion
kubectl logs -n edr-system deploy/kizashi-ingestion --tail=100 | grep -E "(ERROR|WARN)"

# gRPC エンドポイントの疎通確認
kubectl exec -n edr-system deploy/kizashi-api -- \
  nc -zv kizashi-ingestion 9091

# ─────────────────────────────────────────────────────────
# Step 3: ネットワーク経路の確認
# ─────────────────────────────────────────────────────────
# Ingestion Service の External IP / LoadBalancer 確認
kubectl get svc -n edr-system | grep ingestion

# アクティブな gRPC 接続数の確認
kubectl exec -n edr-system deploy/kizashi-ingestion -- \
  ss -tnp | grep ":9091" | wc -l
```

#### 対応手順

```bash
# ─── ケース A: Ingestion Pod がクラッシュしている場合 ────────────────
kubectl rollout restart deployment/kizashi-ingestion -n edr-system
kubectl rollout status deployment/kizashi-ingestion -n edr-system

# ─── ケース B: Ingestion の容量が不足している場合 ────────────────────
# HPA のスケールアップ (手動トリガー)
kubectl scale deployment/kizashi-ingestion --replicas=5 -n edr-system

# ─── ケース C: ネットワーク障害 (LoadBalancer IP が変更された等) ─────
# エージェントが接続するエンドポイントを確認
kubectl get svc kizashi-ingestion -n edr-system -o jsonpath='{.status.loadBalancer.ingress}'

# ─── ケース D: 特定テナントのエージェントのみオフライン ──────────────
# テナント別の状況確認
kubectl exec -n edr-system deploy/kizashi-api -- \
  psql -h kizashi-postgresql -U kizashi -d kizashi -t << 'SQL'
SELECT
  tenant_id,
  count(*) AS total_agents,
  count(*) FILTER (WHERE last_seen > NOW() - INTERVAL '5 minutes') AS online
FROM agents
GROUP BY tenant_id
ORDER BY online / count(*)::float ASC
LIMIT 10;
SQL
```

**エスカレーション基準**:
- オフライン率 > 50% → P1 エスカレーション
- Ingestion 再起動後も回復しない → インフラリードへエスカレーション

### EDRHighAPIErrorRate

**重大度**: Warning (1% 超) / Critical (5% 超)
**意味**: API の 5xx エラーレートが上昇しています

#### ログ確認

```bash
# ─────────────────────────────────────────────────────────
# Step 1: エラーログの確認
# ─────────────────────────────────────────────────────────

# 直近のエラーログ (詳細)
kubectl logs -n edr-system -l app.kubernetes.io/component=api \
  --tail=200 --prefix=true | grep -E "(ERROR|FATAL|panic)"

# エラーパスの特定 (どのエンドポイントでエラーが多いか)
kubectl logs -n edr-system -l app.kubernetes.io/component=api \
  --tail=1000 | grep '"status":5' | \
  jq -r '.path' | sort | uniq -c | sort -rn | head -20

# ─────────────────────────────────────────────────────────
# Step 2: データベース接続の確認
# ─────────────────────────────────────────────────────────
kubectl exec -n edr-system deploy/kizashi-api -- \
  pg_isready -h kizashi-postgresql -p 5432 -U kizashi

# DB 接続数の確認
kubectl exec -n edr-system deploy/kizashi-api -- \
  psql -h kizashi-postgresql -U kizashi -d kizashi -t << 'SQL'
SELECT count(*), state
FROM pg_stat_activity
WHERE datname = 'kizashi'
GROUP BY state;
SQL

# ─────────────────────────────────────────────────────────
# Step 3: メモリ / CPU の確認
# ─────────────────────────────────────────────────────────
kubectl top pods -n edr-system | grep api
kubectl describe pods -n edr-system -l app.kubernetes.io/component=api | grep -A5 "Limits\|Requests\|OOM"
```

#### スケールアップ手順

```bash
# API レプリカを増加 (緊急スケールアップ)
kubectl scale deployment/kizashi-api --replicas=5 -n edr-system
kubectl rollout status deployment/kizashi-api -n edr-system

# エラーレートの改善を確認 (Prometheus クエリ)
# sum(rate(http_requests_total{job="kizashi-api",code=~"5.."}[5m])) /
# sum(rate(http_requests_total{job="kizashi-api"}[5m]))

# ─── スケールアップで解決しない場合: ローリング再起動 ───────────────
kubectl rollout restart deployment/kizashi-api -n edr-system

# ─── DB 接続枯渇の場合: 既存コネクションの強制終了 ──────────────────
kubectl exec -n edr-system deploy/kizashi-api -- \
  psql -h kizashi-postgresql -U kizashi -d kizashi -t << 'SQL'
SELECT pg_terminate_backend(pid)
FROM pg_stat_activity
WHERE datname = 'kizashi'
  AND state = 'idle'
  AND state_change < NOW() - INTERVAL '5 minutes';
SQL
```

**エスカレーション基準**:
- スケールアップ後もエラーレートが改善しない → P1
- DB 障害が原因 → `EDRDatabaseDown` の手順へ

### EDRAPIHighLatency

**重大度**: Warning (p99 > 2 秒)
**意味**: API の応答時間が増加しています

#### プロファイリング手順

```bash
# ─────────────────────────────────────────────────────────
# Step 1: レイテンシの原因特定
# ─────────────────────────────────────────────────────────

# エンドポイント別のレイテンシ確認 (Prometheus クエリ)
# histogram_quantile(0.99,
#   sum(rate(http_request_duration_seconds_bucket{job="kizashi-api"}[5m]))
#   by (le, path)
# )

# ─────────────────────────────────────────────────────────
# Step 2: データベースのスロークエリ確認
# ─────────────────────────────────────────────────────────
kubectl exec -n edr-system deploy/kizashi-api -- \
  psql -h kizashi-postgresql -U kizashi -d kizashi << 'SQL'
-- 実行中の長時間クエリ
SELECT
  pid,
  now() - query_start AS duration,
  state,
  LEFT(query, 100) AS query_snippet
FROM pg_stat_activity
WHERE state = 'active'
  AND now() - query_start > INTERVAL '5 seconds'
ORDER BY duration DESC;
SQL

# pg_stat_statements で上位クエリを確認
kubectl exec -n edr-system deploy/kizashi-api -- \
  psql -h kizashi-postgresql -U kizashi -d kizashi << 'SQL'
SELECT
  LEFT(query, 80) AS query,
  calls,
  ROUND(mean_exec_time::numeric, 2) AS mean_ms,
  ROUND(total_exec_time::numeric, 2) AS total_ms,
  ROUND(stddev_exec_time::numeric, 2) AS stddev_ms
FROM pg_stat_statements
ORDER BY mean_exec_time DESC
LIMIT 15;
SQL

# ─────────────────────────────────────────────────────────
# Step 3: pprof によるプロファイリング (ENABLE_PPROF=true の場合のみ)
# ─────────────────────────────────────────────────────────

# CPU プロファイル (30 秒間)
kubectl port-forward -n edr-system deploy/kizashi-api 6060:6060 &
PF_PID=$!
sleep 2

curl -sf "http://localhost:6060/debug/pprof/profile?seconds=30" \
  -o /tmp/cpu-profile.pprof

# goroutine ダンプ (デッドロック確認)
curl -sf "http://localhost:6060/debug/pprof/goroutine?debug=2" \
  | head -100

kill $PF_PID

# プロファイル分析
go tool pprof -top /tmp/cpu-profile.pprof
```

#### 対応手順

```bash
# ─── ケース A: DB スロークエリが原因 ────────────────────────────────
# 長時間クエリの強制終了
kubectl exec -n edr-system deploy/kizashi-api -- \
  psql -h kizashi-postgresql -U kizashi -d kizashi -t << 'SQL'
SELECT pg_terminate_backend(pid)
FROM pg_stat_activity
WHERE state = 'active'
  AND now() - query_start > INTERVAL '30 seconds'
  AND datname = 'kizashi';
SQL

# VACUUM ANALYZE で統計情報を更新
kubectl exec -n edr-system deploy/kizashi-api -- \
  psql -h kizashi-postgresql -U kizashi -d kizashi \
  -c "VACUUM ANALYZE;"

# ─── ケース B: API Pod の CPU / メモリ逼迫 ──────────────────────────
# スケールアップ
kubectl scale deployment/kizashi-api --replicas=6 -n edr-system

# ─── ケース C: 外部 API (VirusTotal 等) のタイムアウト ──────────────
# 外部 API 呼び出しのタイムアウトログを確認
kubectl logs -n edr-system -l app.kubernetes.io/component=api \
  --tail=200 | grep -i "timeout\|virustotal\|openai"
```

### EDRDiskSpaceLow

**重大度**: Warning (20% 未満) / Critical (10% 未満)
**意味**: データベースボリュームの空き容量が少なくなっています

#### 緊急クリーンアップ手順

```bash
# ─────────────────────────────────────────────────────────
# Step 1: 現在の使用状況確認
# ─────────────────────────────────────────────────────────

# PVC の使用状況
kubectl exec -n edr-system kizashi-postgresql-0 -- \
  df -h /var/lib/postgresql/data

# テーブルサイズの確認
kubectl exec -n edr-system deploy/kizashi-api -- \
  psql -h kizashi-postgresql -U kizashi -d kizashi << 'SQL'
SELECT
  schemaname,
  tablename,
  pg_size_pretty(pg_total_relation_size(schemaname||'.'||tablename)) AS total_size,
  pg_size_pretty(pg_relation_size(schemaname||'.'||tablename)) AS table_size,
  pg_size_pretty(pg_indexes_size(schemaname||'.'||tablename)) AS index_size
FROM pg_tables
WHERE schemaname = 'public'
ORDER BY pg_total_relation_size(schemaname||'.'||tablename) DESC
LIMIT 15;
SQL

# TimescaleDB チャンクの確認
kubectl exec -n edr-system deploy/kizashi-api -- \
  psql -h kizashi-postgresql -U kizashi -d kizashi << 'SQL'
SELECT
  hypertable_name,
  count(*) AS chunk_count,
  pg_size_pretty(sum(pg_total_relation_size(chunk_schema||'.'||chunk_name))) AS total_size
FROM timescaledb_information.chunks
GROUP BY hypertable_name
ORDER BY sum(pg_total_relation_size(chunk_schema||'.'||chunk_name)) DESC;
SQL

# ─────────────────────────────────────────────────────────
# Step 2: 緊急クリーンアップ (警告レベル: 20% 未満)
# ─────────────────────────────────────────────────────────

# 古い TimescaleDB チャンクの圧縮 (7日以上前のデータ)
kubectl exec -n edr-system deploy/kizashi-api -- \
  psql -h kizashi-postgresql -U kizashi -d kizashi << 'SQL'
SELECT compress_chunk(c)
FROM show_chunks('events', older_than => INTERVAL '7 days') c
WHERE NOT is_compressed;
SQL

# VACUUM FULL (テーブルのデッドタプルを回収) — 注意: テーブルロックが発生
# ※ 業務時間外に実施すること
# kubectl exec -n edr-system deploy/kizashi-api -- \
#   psql -h kizashi-postgresql -U kizashi -d kizashi \
#   -c "VACUUM FULL ANALYZE events;"

# ─────────────────────────────────────────────────────────
# Step 3: 緊急削除 (Critical: 10% 未満) ─ 必ず上長承認を得てから実施
# ─────────────────────────────────────────────────────────

# 90 日以上前の TimescaleDB チャンクを削除
kubectl exec -n edr-system deploy/kizashi-api -- \
  psql -h kizashi-postgresql -U kizashi -d kizashi << 'SQL'
SELECT drop_chunks('events', INTERVAL '90 days');
```

#### docker compose 環境のディスク逼迫

EC2 検証環境のように docker compose で動かしている場合、`/` が単一ボリュームなので
**DB 以外の要因で逼迫することの方が多い**。削る順序を間違えると、消さなくてよいものを
消してロールバック不能になるため、下記の順に進めること。

##### Step 1: どこが食っているかを測る (推測で消さない)

```bash
df -h /
docker system df                       # Images / Build Cache / Volumes の内訳
sudo du -sh /var/lib/containerd         # イメージ実体 (containerd イメージストア使用時)
sudo du -sh /var/lib/docker/containers/*/*-json.log 2>/dev/null | sort -h | tail
docker exec -i kizashi-postgres psql -U edr -d edrplatform -c \
  "SELECT pg_size_pretty(pg_database_size('edrplatform'));"
```

> `docker system df` の合計と `du /var/lib/docker` が食い違う場合は
> **containerd イメージストア**が有効。イメージとビルドキャッシュの実体は
> `/var/lib/containerd` 側にある(同じ `/` なので prune すれば空きは増える)。

##### Step 2: ビルドキャッシュ (最優先・完全に安全)

```bash
docker builder prune -af
```

`docker compose build` のたびに積み上がる。特に `--no-cache` ビルドを回すと一気に
増える。削除しても壊れるものは無く、次回ビルドが遅くなるだけ。

##### Step 3: 未使用イメージ (★選別が必要)

**`docker image prune -a` は使わないこと。** `updater` によるバージョンロールバックには
旧タグのイメージが必要で、まとめて消すと切り戻せなくなる
([システム更新ロールバック手順.md](システム更新ロールバック手順.md))。一覧を確認して
個別に消す:

```bash
docker images --format '{{.Repository}}:{{.Tag}}\t{{.Size}}\t{{.CreatedSince}}' | sort -k3
docker rmi <IMAGE_ID>          # 明らかに不要な <none> や古いタグのみ
```

##### Step 4: DB (ここまでで足りない場合のみ)

保持期間の短縮はデータポリシーの変更なので、独断で実施しない。現状把握は:

```bash
docker exec -i kizashi-postgres psql -U edr -d edrplatform -c \
  "SELECT hypertable_name, pg_size_pretty(total_bytes) FROM timescaledb_information.hypertables h,
   LATERAL hypertable_detailed_size(format('%I.%I', h.hypertable_schema, h.hypertable_name))
   ORDER BY total_bytes DESC;"
```

既定の保持期間は `events` = 90日、`network_connections` = 30日 (migration 002)。

##### 再発防止: ビルドキャッシュの週次整理

```bash
(crontab -l 2>/dev/null; \
 echo "0 4 * * 0 /usr/bin/docker builder prune -af --filter until=168h >/dev/null 2>&1") | crontab -
```

`until=168h` により直近1週間分は残るので、通常のビルド速度には影響しない。

### EDRDetectionPipelineStalled

**重大度**: Critical
**意味**: プロセスは生存 (`up==1` / `/readyz` 緑) しているのに、Detection エンジンが 10 分以上イベントを処理していません。「健全に見えるのに検知が死んでいる」サイレント障害です。`EDRDetectionEngineDown` (プロセス死) とは異なり、こちらは**生存しているのに機能が止まっている**状態を捕捉します。

想定原因: ①NATS consumer の詰まり/切断 ②detection の goroutine デッドロック ③ingestion→NATS の上流断 ④エージェントからのテレメトリが実際に来ていない (全エージェントオフライン等)。

```bash
# Step 1: メトリクスで停止時刻とバックプレッシャーを確認
#   detection の /metrics (:8081) を直接叩く
kubectl exec -n edr-system deploy/kizashi-detection -- \
  wget -qO- http://localhost:8081/metrics | grep -E "edr_detection_(last_event|consumer_pending)"
#   last_event が古い & consumer_pending が高い → consumer が詰まっている
#   last_event が古い & consumer_pending が 0    → 上流 (ingestion / エージェント) が無音

# Step 2: 上流の生存を切り分け — ingestion がイベントを受けているか
kubectl exec -n edr-system deploy/kizashi-ingestion -- \
  wget -qO- http://localhost:8082/readyz    # DB/NATS 到達性
#   events テーブルに直近の書き込みがあるか (ingestion は生きているか)
kubectl exec -n edr-system deploy/kizashi-postgresql -- \
  psql -U edr -d edrplatform -tc \
  "SELECT now() - max(time) FROM events WHERE time > now() - interval '30 min';"

# Step 3: NATS 側の pending を確認 (EVENTS ストリーム / detection-engine consumer)
kubectl exec -n edr-system "${NATS_POD}" -- \
  nats consumer info EVENTS detection-engine --server nats://localhost:4222 | grep -E "Pending|Unprocessed"

# Step 4: 詰まりが detection 側なら再起動でドレイン (JetStream durable なので取りこぼしなし)
kubectl rollout restart deployment/kizashi-detection -n edr-system

# Step 5: 上流 (エージェント) が無音なら EDRAgentsOffline 手順へ合流
```

### EDRDetectionConsumerLagging

**重大度**: Warning
**意味**: Detection consumer の pending (未配信) メッセージ数が高止まりしています。検知が ingestion の流量に追いつけておらず、放置すると `EDRDetectionPipelineStalled` に発展します。

> **⚠️ レプリカ追加は「最初の一手」ではない。** 2026-07-20 の本番調査で、pending 増加の真因が
> **再配信ストーム**（consumer 設定の不整合）だったケースがある。この状態ではレプリカを増やしても
> 追加分が再配信の空転に消えて**まったく効かない**。さらにホストが CPU 律速の場合、同一ホストへの
> レプリカ追加は**スループットを下げる**（実測: 19/s → 10/s）。必ず下の Step 1〜3 で切り分けてから
> 対処すること。詳細は [検知率向上_20260721_配信層ラグと発生源ノイズ削減.md](../検知率向上_20260721_配信層ラグと発生源ノイズ削減.md)。

```bash
# Step 1: 「本当に消化できているか」を ack_floor で見る (最重要)
#   pending や delivered だけを見てはいけない。delivered は再配信で水増しされるため、
#   ストーム中は「配信は進んでいるのに実際は1件も消化できていない」状態を見逃す。
#   真の前進 = ack_floor.consumer_seq が増えているか。
NATS_POD=$(kubectl get pod -n edr-system -l app=nats -o name | head -1)
for i in 1 2; do
  kubectl exec -n edr-system "${NATS_POD}" -- \
    nats consumer info EVENTS detection-engine --server nats://localhost:4222 \
    | grep -E "Acknowledgment floor|Unprocessed|Redelivered|Outstanding Acks"
  sleep 30
done
#   ack_floor が 30 秒でまったく動かない → 消化ゼロ。Step 2 の再配信ストームを疑う
#   ack_floor が進んでいて pending も減少 → 一時的なスパイク。見守る

# Step 2: 再配信ストームの判定 (Redelivered の増加率 ≒ Delivered の増加率 なら黒)
#   配信のほぼ全部が再配信 = worker が重複処理に空転し、新規消化が進まない状態。
#   原因は MaxAckPending が実 worker 並列を大きく超えていること (プリフェッチ滞留が
#   AckWait を超過し、処理される前に再配信される)。
kubectl exec -n edr-system deploy/kizashi-detection -- \
  wget -qO- http://localhost:8081/metrics \
  | grep -E "edr_detection_consumer_pending|go_goroutines"
kubectl logs -n edr-system deploy/kizashi-detection --tail=5 | grep "検知consumerを起動"
#   ログの concurrency と max_ack_pending を確認。
#   max_ack_pending >> concurrency なら設定不整合 → パフォーマンスチューニング.md §3.2 を参照し是正
#   (現行実装の既定は concurrency*3。DETECTION_MAX_ACK_PENDING / DETECTION_ACK_WAIT_SEC で調整)

# Step 3: ストームが無い場合のみ、律速がどこかを判定
kubectl top pods -n edr-system -l app.kubernetes.io/component=detection
kubectl top nodes
#   ノードの CPU に余裕がない → レプリカ追加は逆効果。ノード増強か、
#   発生源のイベント量削減 (下記) を先に行う
#   CPU に余裕がある → スケールアウトが有効
kubectl scale deployment/kizashi-detection -n edr-system --replicas=3

# Step 4: 供給側を削る (最も効くことが多い)
#   流入がそもそも過大なら、消化側をいくら増やしても追いつかない。
#   ノイズの内訳は NATS を直接購読して確認できる。
kubectl exec -n edr-system "${NATS_POD}" -- \
  timeout 15 nats sub 'events.>' --server nats://localhost:4222 \
  | grep -oE 'events\.[a-f0-9-]+\.[a-z]+' | sed -E 's/.*\.//' | sort | uniq -c | sort -rn
#   特定の種別 (credential / file 等) が支配的なら、その発生源フィルタを見直す
```

### EDRBackupStale

（`EDRBackupNeverSucceeded` — 一度も成功していない場合 — と
`EDRBackupFailing` — 直近に失敗がある場合 — も、調べ方はこの手順と同じです。

**意味**: 自動 DB バックアップがサイレントに失敗しています。`edr_backup_last_success_timestamp_seconds` は**整合性検証に通った**バックアップのみを記録するため、pg_dump が exit 0 でも切り詰め/空ダンプは成功として数えません。復旧が必要になった時=災害時に初めて壊れたバックアップに気づく事態を防ぐ先行指標です。詳細は [バックアップ・リストア.md](バックアップ・リストア.md)。

```bash
# Step 4: 復旧後、次サイクルで edr_backup_last_success_timestamp_seconds が
```

### EDRBackupNeverSucceeded

**ありません。** 調べ方は EDRBackupStale と同じですが、まず
`backup_scheduler` が起動しているか（`edr_scheduler_runs_total{scheduler="backup"}`）を
見てください。0 なら、失敗しているのではなく走っていません。

### EDRBackupFailing

直近に失敗がある状態です。古い成功が残っていても、新しいものは
取れていません。`edr_backup_failures_total` の増分と、
backup コンテナのログを併せて見てください。

### 重要パネルの見方

**EDR Overview ダッシュボード**:
- **Agent Online Rate**: 90% 以上が正常。急落はネットワーク障害 or Ingestion 障害を示す
- **API Error Rate**: 0.1% 以下が正常。スパイクは DB 障害 or デプロイ失敗を示す
- **Active Alerts / Pending Alerts**: Pending が急増は Detection エンジンの遅延を示す

**EDR Database ダッシュボード**:
- **Connection Count**: `max_connections` の 80% 超は要注意 (デフォルト 100)
- **TimescaleDB Chunk Size**: 日次で増加する。90日超のチャンクは圧縮 or 削除を検討
- **WAL Archiving Lag**: 0 が正常。増加は S3 接続問題 or ディスク不足を示す

**NATS ダッシュボード**:
- **Stream Pending Messages**: ALERTS が 0 付近を維持していれば正常
- **Consumer Ack Rate vs Publish Rate**: 消費速度が生産速度を下回ると要注意

### EDRHashIOCHasNothingToMatch

**何が起きているか**

直近1時間のイベントの半分以上が、ハッシュを1つも持たずにハッシュ IOC
照合に届いています。既知マルウェアのハッシュ照合は、その分だけ**動いて
いません。**

**なぜ静かに見えるか**

一致0件は「安全」と「確かめられていない」の両方に見えます。この
アラートは、その2つを分けるためだけにあります
（`edr_ioc_hash_absent_total`）。

**確認する順序**

1. どの端末か

   ```promql
   sum by (agent_id) (increase(edr_events_ingested_total[1h]))
   ```

   メトリクスに agent_id が無いので、まず DB で当たりを付けます:

   ```sql
   SELECT os_type, count(*) FROM agents WHERE status='online' GROUP BY 1;
   ```

2. エージェントのバージョン。**ハッシュを proto に載せるようになったのは
   途中からです。** それ以前のエージェントは計算だけして送りません。

   ```sql
   SELECT agent_version, count(*) FROM agents
   WHERE status='online' GROUP BY 1 ORDER BY 2 DESC;
   ```

3. Windows なら SeDebugPrivilege。取れていないと他ユーザーのプロセスの
   実行ファイルを開けず、ハッシュも取れません。

   ```sql
   SELECT telemetry_mode, count(*) FROM agents
   WHERE status='online' GROUP BY 1;
   ```

   `poll` が多ければ、エージェントのログに
   「SeDebugPrivilege を有効化できませんでした」が出ています。

4. それでも説明が付かないときは、実際のイベントを見ます:

   ```sql
   SELECT raw_data->>'process_name', raw_data ? 'sha256'
   FROM events WHERE event_type='process'
   ORDER BY time DESC LIMIT 20;
   ```

**やってはいけないこと**

閾値を上げて黙らせること。**このアラートは「検知が動いていない」と
言っています。** 鳴っているあいだ、ハッシュ IOC は実質無効です。

**正常に戻る条件**

比率が 50% を下回り、2時間続くこと。0 にはなりません —— 読めない
ファイルと権限不足は常にあります。
