# field サポート・フロンティアと curate 自己点検カナリアの恒久化 — 2026-07-02 セッション総括

前日(2026-07-01)のサイレント故障スプリント([検知率向上と隠れた故障の是正_20260701.md](検知率向上と隠れた故障の是正_20260701.md))で、
検知率を縛っていたのは「能力不足」ではなく「作ったのに壊れている/届いていない/有効化
されていない/計測されていない」の運用側であることが判明した。本セッションはその続きとして、
**「未有効化」の次のレバー=どの agent フィールドを emit すれば何ルールが息を吹き返すか** を
特定し、それを一度きりの手作業でなく **常時ランキングされる生きたロードマップ** に恒久化した。

並行セッションの [検知率向上_20260702_curate衛生とplatformゲート.md](検知率向上_20260702_curate衛生とplatformゲート.md)
(PR #354 隔離不変条件 / PR #356 platform ゲート)とは対象が異なり、本書は
**field サポートのフロンティア特定と curate の自己点検自動化**を扱う。

---

## 1. 発見: 有効なのに永久に発火しない「false green」ルール 132 件

検証EC2の `rules` テーブル(`source='sigmahq' AND enabled=true`)を、サーバの field
サポート判定(`SupportedSigmaFields()` × `RuleSelectedFields()` × `RuleFieldSupportWith()`)で
棚卸ししたところ、**有効化されているのに selection が参照するフィールドをテレメトリが emit
しておらず、構造的に一度も match し得ない**ルールが **132 件**あった。

curate の語彙では本来こうしたルールは `pending`(field 非対応)に留め置かれるべきだが、
curate ゲートの外(手動/API 有効化、あるいはテレメトリ被覆の退行)で有効化されると、
UI 上は緑(enabled)なのに実体は inert=**false green** になる。「有効化数」は増えても
検知率は 1mm も動かない。

### 欠落フィールド別に集計 → 次に足すべきフィールドのランキング

inert 132 件を「どのフィールドが欠けているせいか」で集計すると、明確な優先順位が出た:

| 欠落フィールド | これを emit すれば有効化されるルール数 |
|---|---|
| `OriginalFileName` | **74** |
| `Initiated` | **41** |
| (以下ロングテール) | … |

= **単一の agent フィールドを 1 つ emit するだけで数十のルールが一斉に息を吹き返す**。
新規ルールを書くより桁違いに ROI が高い、検知 recall の最大レバーがここにあった。

## 2. `Initiated` の解消 — direction→Initiated エイリアス(PR #367, マージ済)

ランキング 2 位の `Initiated`(ネットワーク接続の「発信/着信」を表す Sysmon フィールド)は、
agent 側の新規 emit を待たずに **サーバ側の別名導出だけで解消できた**。agent は既に
`direction`(`"outbound"`/`"inbound"`)を送っており、これを Sigma の `Initiated`
(`"true"`/`"false"`)へ写像すればよい。

- `alert_pipeline.go` の `addPipelineSigmaAliases()` 末尾に `direction`→`Initiated`
  変換を追加(`outbound`→`true`, `inbound`→`false`)。
- 回帰テスト `initiated_alias_test.go`(変換 + field サポート判定)を新設。

結果: inert **132 → 93**(ネットワーク 41 ルールのうち大半が有効化)。field フロンティアの
「サーバ側の別名で解決できる分」と「agent の新規 emit が要る分」の切り分けは
[検知率向上_20260703_fieldsupportロングテール消化.md](検知率向上_20260703_fieldsupportロングテール消化.md)
へ続き、最終的に false green は 93→0 まで消化された。

`OriginalFileName`(74 ルール、ランキング 1 位)は PE VERSIONINFO の agent 側 emit が必要で、
follow-up タスクへ(agent の PE バージョン情報抽出)。

## 3. 一度きりの棚卸しを「常時ランキング」に恒久化 — 2 段の自己点検カナリア

上記の 132 件監査は手作業だった。同じ穴が二度と黙って開かないよう、curate スケジューラの
毎 tick(発火 0 / 隔離整合の自己点検)に **field サポート契約の常時監視**を組み込んだ。
性質の異なる 2 つのカナリアが相補的に働く:

### 3a. 発火 0(inert)カナリア + 隔離整合の自動是正(PR #357, マージ済)

- **`InertRules(ctx, minAge, window)`** — 有効化から 7 日超が経過してなお 7 日間 1 度も
  発火していないルールを列挙。「**DIDN'T fire**(発火実績が無い)」の観点。grace period で
  有効化直後のルールは除外。`metrics.CurateInertRules`(Gauge)に露出。
- **`ReconcileQuarantined(ctx)`** — FP で `quarantined` にしたはずが、後続の手動/API 一括
  有効化で `enabled=true` に戻って鳴り続けるルールを再無効化(`quarantined ⟹ disabled`
  不変条件の自己修復)。`metrics.CurateQuarantineReconciled`(Counter)。

### 3b. false-green カナリア(PR #387, マージ済)

- **`FalseGreenRules(ctx)`** — §1 の静的 field 契約チェックそのもの。inert カナリアが
  「1 週間ゼロ発火」を待つのに対し、これは **有効なのに field 非対応のルールを即座に**
  検出する(curate ゲート外の有効化・テレメトリ被覆の退行を待たずに捕捉)。2026-07-03 に
  0 まで駆動済み。値が上がったら enabled 集合の field 契約が腐り始めた合図。

### 3c. field-gap カナリア = 「次に足すべきフィールド」の生きたランキング(PR #371)

false-green を「何件あるか」で見るだけでなく、**「どのフィールドを足せば何ルール有効化するか」**
まで踏み込んだのが本カナリア(本セッションの中核成果):

- **`FieldGapReport(ctx) (inert int, gaps []FieldGap, err error)`** — 有効 sigmahq ルールを
  走査し、field 非対応のものを **欠落フィールド別に集計して most-rules-first でソート**。
  `FieldGap{Field, Rules}`。
- **`metrics.CurateFieldGap{field}`**(GaugeVec)に露出 → Grafana で
  `OriginalFileName → 74, Initiated → 41, …` が常時ランキング表示される。
- `CurateScheduler` が約 6h 毎(スロー信号のため毎 tick ではない)に top を WARN ログ + メトリクス化。

**位置づけの整理**:
`FieldGap` は「そのルールは **CANNOT fire**(構造的に発火不能)+ 欠けているフィールド名」を提示する
`InertRules`(発火ベース=DIDN'T fire)の**根本原因版**。前者は「何を直せば良いか」を名指しし、
後者は「結果として鳴っていない」を拾う。両輪で「作ったのに検知率に効いていないルール」を
黙って放置させない。

## 4. 併せて直したサイレント故障: Prometheus ルール未マウント(PR #360, マージ済)

検知率とは別軸だが、本セッション中に **Prometheus のアラートが全て inert** であることを発見。
`docker-compose.yml` で `deploy/prometheus/rules` がコンテナにマウントされておらず
`/etc/prometheus/rules/` が空 → 全 EDR アラートルールが読み込まれず沈黙していた。
マウント追加 + `deploy/prometheus.yml` の死んだ `rule_files` 参照(`alerts.yml`)撤去で
9 アラートのロードを実証。§3 の curate カナリア用アラート(`EDRCurateInertRules`,
`EDRCurateQuarantineReenabled`)もこれで初めて実際に評価されるようになった。

「作ったのに壊れている」の Prometheus 版であり、0701 スプリントと同じ教訓
(**静的被覆 ≠ 実際に評価されている**)の再演。

---

## 5. 結論: 検知率は今や「agent テレメトリの被覆幅」で律速される

サーバ側の検知能力・ルール資産は飽和に近い。検知 recall の次のレバーは、
**agent がどれだけ多様なフィールドを emit するか**に移った。そしてその「次に足すべき最高の
フィールド」は、もはや手作業の棚卸しでなく **field-gap カナリアが Grafana に常時ランキング
表示する**。運用者は数字の一番大きいフィールドから順に agent の emit を足していけばよい。

- **現時点の最大レバー**: `OriginalFileName`(74 ルール)= agent の PE VERSIONINFO 抽出。
  → follow-up タスクへ。
- **恒久ガード**: false-green(即時)/ inert(1 週間ゼロ発火)/ field-gap(欠落フィールド
  ランキング)の 3 カナリアが、有効化集合の field 契約の腐敗を継続監視する。
