# フロントエンド全域監査と実データ化

**実施日:** 2026-06-11 〜 2026-06-12
**対象:** 検証環境（EC2, `https://203-0-113-10.nip.io`）上の全フロントエンド画面
**関連PR:** #93〜#108

---

## 1. 背景と目的

管理画面の一部（セキュリティスコアカード等）で「値が正しく表示されない」報告を起点に調査したところ、
**個別の不具合ではなく、フロントエンド全体に共通する構造的な問題**が複数のパターンで存在することが判明した。
そこで全画面を体系的に監査し、実害のある箇所から順に修正した。

## 2. 発見された問題のパターン

| # | パターン | 例 | 危険度 |
|---|---------|----|--------|
| P1 | **偽データの捏造表示** — エラーや空データ時に架空の値を表示 | メトリクスのモック値（50/60/70…）、インシデントパターン分析の `Math.random()` 件数、ネットワーク分離の固定3件コンプライアンス指摘、パッチ自動化の架空CVE、**ログインで使えない偽のMFA復旧コード** | 高 |
| P2 | **バックエンド未実装（404）** — フロントだけ実装され API が存在しない | 敵対的エミュレーション、ネットワーク分離、データ保持、エンドポイントグループ ほか約70ページ | 高 |
| P3 | **レスポンスキー不一致** — API は正常だがフロントが違うキーを読む | `{kpis:[...]}` `{deployments:[...]}` `{jobs:[...]}` を `apiFetchList` の `ARRAY_KEYS` 未登録キーや誤フィールドで読み常に空 | 中 |
| P4 | **エラー握りつぶし** — `.catch(() => body)` 等で失敗を成功と偽装 | データ保持の purge「404でも成功扱い」、各種保存ミューテーション | 中 |
| P5 | **サーバー側バグ** | forensics-automation のテーブル名衝突による 500、TimescaleDB hypertable のサイズ0表示 | 中 |

> **原則（本プロジェクトの方針）:** セキュリティ製品のダッシュボードに**架空の値を表示しない**。
> データが無ければ「データがありません」、未実装なら「準備中」と正直に表示する。

## 3. 監査の方法（再現手順）

1. フロントエンドが参照する**静的 API パスを全抽出**:
   ```bash
   grep -rhoE "(apiFetch|apiFetchList)(<[^>]*>)?\('/api/v1/[a-zA-Z0-9/_-]+'" \
     frontend/app frontend/components frontend/lib --include='*.tsx' --include='*.ts' \
     | grep -oE "/api/v1/[a-zA-Z0-9/_-]+" | sort -u
   ```
   → 568 エンドポイント
2. 検証環境へ **admin トークン付き GET で実プローブ**（読み取りのみ。429 は `sleep 0.4` でリトライ）
3. 404 を「GET（表示用）/ WRITE（操作用）」に分類（ソース上の `method:` 文脈で判定）
4. 404 エンドポイント → ページの対応表を作成し、未実装ページ一覧を確定

| HTTP | 件数 | 意味 |
|------|------|------|
| 200 | 314 | 正常 |
| 402 | 31 | プランゲート（Lite制限・正常動作） |

- **chaos run のドライラン化（#130）** — 「`inconclusive` 固定・空メトリクス」から、実行時に**実環境の定常状態メトリクス**（CPU/メモリ/ディスク% ＋ オンラインエージェント数・未対応アラート数）を before/after で実測して記録する**ドライラン**に。実障害注入は安全のため行わず、結果は誠実に `inconclusive`（検証環境を壊さない方針。`hostResources` を再利用）。
- **phishing 実メール送信＋追跡（#131）** — `phishing_recipients`（受信者ごとの追跡トークン、migration 265）＋ campaigns に `landing_page` 追加。`notification.SendHTMLMail`（実績ある DHE 安全 SMTP 経路 `smtpSendWithFallback` の公開ラッパー）で、テンプレ HTML に**開封ピクセル＋クリック追跡 URL を注入して SMTP 送信**（バックグラウンド・最大200件、SMTP 未設定なら未送信＝偽の送信はしない）。**公開追跡エンドポイント**（認証不要・128bit トークンで保護）`/api/v1/phishing/track/{open,click,report}/:token` で開封・クリック・報告を記録。click は landing へ302、無ければ訓練啓発ページを表示。一覧・stats は recipients から実集計。SMTP 設定は `notification_channels`(type email) を使用。

## 6. 開発上の教訓（再発防止）

- **`apiFetchList` は `ARRAY_KEYS` に列挙されたラッパーキーしか剥がせない。** 新しいキー（`{kpis:...}` 等）で返すハンドラを作ったら `frontend/lib/api.ts` に追加するか、既存キー（`data`/`items`）に統一する
- **`INSERT ... SELECT $1 ... WHERE col=$1` は 42P08 で静かに全失敗する。** 同一プレースホルダを複数箇所で使う場合は全出現箇所に明示キャスト（`$1::varchar` 等）。`PREPARE` で事前検証できる
- **TimescaleDB hypertable のサイズは `pg_total_relation_size` では取れない**（チャンクに格納されるため親は≈0）。`hypertable_size()` を先に試しフォールバックする
- **モックは `lib/mock.ts` の `m()`/`USE_MOCK` 経由で**（本番では自動的に空になる）。`.catch(() => 固定値)` での直接埋め込みは禁止
- **EXISTS によるテーブル存在チェックは名前衝突に弱い。** 新機能のテーブルは機能名プレフィックスで命名し、migration とハンドラのテーブル名を一致させる（forensics の教訓）
- **GitHub Actions の予算（Budget/Stop設定）は集中的な CI 実行で枯渇し、全ジョブが「Actions budget is preventing further use」で即失敗する。** 全チェックが数秒で同時失敗したら、コードではなくまず予算を疑う
- **新規テーブルの migration は旧 migration との同名テーブル衝突を疑う。** `CREATE TABLE IF NOT EXISTS` は既存テーブルがあると**無音でスキップ**し、後続の index/seed が欠落カラムで失敗→api が migration リトライループで unhealthy になる（pentest 263 と旧 115 の衝突）。新規テーブルでも `CREATE TABLE` の後に冪等な `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` / `ALTER COLUMN ... TYPE` を続けて既存スキーマを吸収する
- **`/admin` 外のページは `admin/layout.tsx` のプランゲート（routeFeatureMap）が効かない。** 有料機能ページは該当サブツリーに `layout.tsx` を置き `<PlanGate feature={...}>` でラップする（forensics / threat-hunting / yara の教訓）。402 を `.catch(() => [])` で握り潰すと「プラン制限」か「0件」か判別不能な空表示になる
- **「画面が空＝バグ」とは限らない。** プランゲート済みページは未契約プランで意図的に空/アップグレード案内になる（MDM は Lite で正常にゲート表示。誤って二重ゲートを足さないこと）。まず該当 API を実プローブし 402(plan_required) かを確認する
