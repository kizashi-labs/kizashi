# 相関レイヤ（api-server `internal/correlation`）不発の是正 — 2026-07-20 セッション総括

[検知率向上サマリ_20260711.md](検知率向上サマリ_20260711.md) の続報。前スプリントで
「出荷される5つのビルトイン相関ルールを end-to-end 固定した」と記録した相関層
（3系統目 `internal/correlation`）を再監査したところ、**その固定が実は end-to-end に
なっておらず、本番の AlertPipeline 経路では5ルールすべてが永久 inert**（一度も
インシデントを生成し得ない）だったことが判明した。本セッションはその P0 を是正する。

対象ブランチ: `claude/edr-product-comparison-dev8e0`（PR #446）。

> **故障クラスは既知のものと同一**: [検知率向上と隠れた故障の是正_20260701.md](検知率向上と隠れた故障の是正_20260701.md)
> の故障 #10（auth `eventName`/`4625` 参照でブルートフォース検知が黙って不発）・#11
> （network ルールが camelCase 参照で永久 inert）と全く同じ ——
> **消費側（ルール）が、テレメトリ/パイプラインの出さないトークンを参照する** ため
> 検知が発火しない。今回はそれが相関層で起きていた。

## 0. 要約（TL;DR）

- **P0 バグ**: ビルトイン相関ルール（`corr-001`〜`corr-005`）は Sysmon 風の *サブタイプ*
  （`auth_failure` / `credential_dump` / `file_encrypted` / `network_connection` …）で
  `EventTypes` フィルタを掛けるが、AlertPipeline は *ベースカテゴリ*（`auth` / `process` /
  `file` / `network`）しか `ProcessAlert` に渡していなかった。完全一致フィルタのため
  **どのベースカテゴリもどのサブタイプにも一致せず、5ルール全てが inert**（横展開/
  資格情報ダンプ/ランサム/永続化/C2 ビーコンの相関インシデントが生成不能）。
- **修正**（commit `3e1ab87`）: ベースカテゴリ + MITRE テクニックからサブタイプ集合を導出する
  `DeriveEventSubtypes()`（新規 `classify.go`）を追加し、ルールフィルタをベース *または*
  導出サブタイプへのマッチに変更。高 severity・低閾値ルール（ランサム/資格情報ダンプ）は
  **MITRE テクニックでゲート**し、良性の file/process アラートが誤ってインシデント化しないようにした。
- **回帰保護の是正**: 既存テストは `ProcessAlert` に *サブタイプを直接* 与えていたため
  バグを隠蔽していた。**本番パイプラインと同じベースカテゴリ + テクニック**を投入する
  発火テスト（`builtins_fire_test.go`）と誤検知ゲートテストを新設し、既存テスト群も
  実経路に合わせて修正。
- **CI lint 修正**（commit `60462ea`）: リファクタで新設した `matchOp` の未チェック
  `fmt.Sscanf` 戻り値2箇所を、`--new-from-merge-base` の errcheck が新規コードとして検出。
  戻り値を明示破棄（挙動維持）して解消。
- **CI 全 green 確定**: run `29727591234`（head `60462ea`）で Server Tests / Frontend /
  Agent build ×3 / govulncheck / Backup&Restore / E2E Playwright すべて success。
- **副次発見（未修正・フォローアップ要）**: パリティ移行 318–356 が挿入する
  `source = 'builtin-parity'` は `rules_source_check` 制約に列挙されておらず、DB seed 時に
  制約違反で **無言で全行 drop** される（§4）。同じ「サイレント故障」クラス。

## 1. P0 バグ：相関ルールが本番経路で永久 inert

### 症状
`internal/correlation` の Engine は、受信アラートを `eventMatchesRule` でルールの
`EventTypes` と突き合わせて相関バッファに積む。出荷ルール（`builtins.go`）の
`EventTypes` は次のような **Sysmon 風サブタイプ**で書かれている:

| ルール | 監視サブタイプ（例） |
|---|---|
| `corr-001` 横展開（ブルートフォース） | `auth_failure`, `failed_login` |
| `corr-002` 資格情報ダンプ campaign | `credential_dump`, `lsass_access` |
| `corr-003` ランサム outbreak | `file_encrypted`, `ransomware_detected` |
| `corr-004` 永続化確立 | `registry_modified`, `scheduled_task_created` |
| `corr-005` C2 ビーコン | `network_connection`, `outbound_connection` |

一方、実際に相関エンジンを呼ぶ `internal/detection/alert_pipeline.go` は、Sigma/IOC
マッチ時に **アラートのベースカテゴリ**（`auth` / `process` / `file` / `network` /
`registry` / `dns`）を `eventType` として渡していた。`eventMatchesRule` は完全一致
（`strings.EqualFold`）のため、`"auth"` は `"auth_failure"` に決して一致しない
→ **5ルールとも `MinEvents` に到達しようがなく、インシデントは1件も生成されない**。

### なぜ気づかれなかったか
既存の回帰テスト（`builtins_coverage_test.go` 等）は `ProcessAlert(..., "auth_failure", ...)`
のように **サブタイプを直接** 与えてルールを発火させていた。テストは緑だが、それは
**本番 AlertPipeline が決して渡さない入力**で駆動していたため。前スプリントの
「相関5ルールを end-to-end 固定」は、この意味で end-to-end になっていなかった。

## 2. 修正：ベースカテゴリ + MITRE テクニック → サブタイプ導出（`classify.go`）

相関エンジンに届くのは *アラート*（生テレメトリではない）である以上、
**アラートの MITRE テクニックが最も確度の高い判別子**になる。そこで
`DeriveEventSubtypes(baseType, mitreTech, severity, data)` を新設し、
ベースカテゴリと（サブテクニックを親に畳んだ）テクニックからサブタイプ集合を導出する:

- `auth` + `T1110`（ブルートフォース）→ `{auth, auth_failure, failed_login}`
  （`data.success=false` 等のアウトカムからも失敗トークンを付与）
- `T1003/T1555/T1552/...`（資格情報アクセス）または `data` の LSASS ターゲット
  → `{credential_dump, lsass_access, mimikatz_detected}`
- `T1486/T1485/T1490/...`（impact 暗号化/破壊）→ `{file_encrypted, ransomware_detected, ...}`
- `registry` / `T1053`(スケジュールタスク) / `T1543`(サービス) / `T1547`(自動起動)
  → 永続化サブタイプ
- `network` / `T1071/T1095/...` → `{network_connection, outbound_connection}`

ベースカテゴリは常に集合に含めるので、ベース型を直接キーにするルールも従来通り動く。

### 誤検知ゲート（重要）
高 severity・低閾値の `corr-002`（資格情報ダンプ, `MinEvents=3`）と `corr-003`
（ランサム, `MinEvents=5`）は、**MITRE テクニックが無い限りサブタイプを付与しない**
設計にした。これにより「テクニック未タグの良性 file/process アラートが大量に来ても
ランサム/LSASS 窃取インシデントに化けない」ことを保証する。回帰テスト
`TestBuiltinRulesNoFalsePositive` で固定。

### Engine 側の変更（`engine.go`）
- `alertEvent` に `Subtypes []string` を追加、`ProcessAlert` シグネチャに `mitreTech` を追加し
  `DeriveEventSubtypes` の結果を格納。
- `eventMatchesRule`: ルール `EventTypes` を **ベースカテゴリ OR 導出サブタイプ**にマッチ。
- `evalCondition`: `event_type` 条件はベース + 全サブタイプ候補に対して評価
  （`event_type contains "credential"` が `credential_dump` に当たる）。

### Pipeline 側の変更（`alert_pipeline.go`）
- Sigma マッチ経路: `ProcessAlert(ctx, alertID, agentID, eventType, tech, severity, corrData)`
  ——ルールの MITRE テクニックを相関エンジンへ伝播。
- IOC マッチ経路: テクニック不明のため空文字を渡す（サブタイプはベース由来のみ）。

## 3. 回帰保護：本番と同じ入力で駆動する発火テスト

**`builtins_fire_test.go`（新規）**:
- `TestBuiltinRulesFire`: 5ルールそれぞれを、**AlertPipeline が実際に stamp するのと同じ
  ベースカテゴリ + テクニック**（例: `"auth"` + `"T1110"`）で `MinEvents` 分駆動し、
  対応インシデントの生成を assert。これがバグ再発の恒久ガード。
- `TestBuiltinRulesNoFalsePositive`: テクニック無しの良性 file/process アラートが
  ランサム/資格情報ダンプを誘発しないことを assert。

既存テスト（`correlation_test.go`, `builtins_coverage_test.go`）も、サブタイプ直接投入から
**ベースカテゴリ + テクニック投入**へ全面修正し、実経路との乖離を解消した。

ローカル: `go test ./internal/correlation/...` 全緑（相関 + 発火 + 誤検知ゲート）、
detection スイートも回帰なし。

## 4. 副次発見（未修正・フォローアップ要）：`builtin-parity` が DB seed で無言 drop

CI ログ調査中に、Server Tests の「Run migrations」ステップで大量の
`ERROR: new row for relation "rules" violates check constraint "rules_source_check"`
が出ていることを確認した。原因:

- パリティ移行 **318–356**（Two-engine parity ルール群）は `source = 'builtin-parity'` で
  `rules` テーブルへ INSERT する。
- しかし `rules_source_check` 制約を定義する唯一の移行 **276** は
  `community / custom / threat-intel / ai-generated / builtin / sigmahq` しか許可しておらず、
  **`builtin-parity` を含まない**（`sigmahq` を追加した時と同種の「ソース値の追加漏れ」）。
- 結果、これらパリティルールは **DB へ一切挿入されず**、detection-server の DB RuleEngine が
  本番で読み込めない = 死蔵。

**なぜテストで捕捉されないか**: `migration_parity_test.go` は `extractMigrationRules()` で
移行 SQL を **直接パースしてインメモリ RuleEngine にロード**するだけで、制約付き DB
テーブルへは挿入しない。CI の「Run migrations」も `psql ... 2>/dev/null || true` で
**エラーを握り潰す**ため、seed 失敗は緑のまま素通りする。§1 と同じ「テストは緑・本番は不発」
のサイレント故障クラス。

**推奨修正（本セッションでは未実施）**: 移行 276 に倣い、`rules_source_check` に
`'builtin-parity'` を追加する新規移行を1本入れる（例: `357_allow_builtin_parity_source.sql`）。
併せて、`migration_parity_test.go` 系がインメモリだけでなく **実制約付き DB への seed 可否**も
1ケース検証すれば、この故障クラスの再発を構造的に防げる。

> 本項はスコープ外（今回の依頼は相関 P0 の是正）のため未着手。フォローアップ課題として記録する。

## 5. CI lint 修正（errcheck）

初回 CI（head `3e1ab87`）は Server Tests の **golangci-lint** ステップのみ失敗し、以降の
Unit tests / E2E は skip された。真因は §2 のリファクタで新設した `matchOp` ヘルパー内の
**未チェック `fmt.Sscanf` 戻り値2箇所**。CI の golangci-lint は
`--new-from-merge-base=origin/main` で **新規・変更コードのみ**をゲートするため、
移動前は既存バックログ扱いで非ゲートだった同一処理が、新関数へ移した瞬間に「新規コード」
として errcheck に捕まった。

修正（`60462ea`）は戻り値を明示破棄:

```go
case "gte":
    var fv, cv int
    _, _ = fmt.Sscanf(fieldVal, "%d", &fv)
    _, _ = fmt.Sscanf(want, "%d", &cv)
    return fv >= cv
```

パース失敗時に int が 0 のまま = **挙動完全維持**。ローカルで CI と同一ツール
（go1.26.5 ビルドの golangci-lint）にて `--new-from-merge-base=origin/main` → `0 issues` を確認。

> **注記**: postgres の `builtin-parity` 制約 ERROR（§4）は `psql ... || true` で無視される
> **非致命ノイズ**であり、CI 失敗の原因ではない。ログ末尾を埋めていたため切り分けを要した。
