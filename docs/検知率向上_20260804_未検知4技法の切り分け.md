# 未検知4技法(T1069/T1087/T1486/T1110)の切り分け — 2026-08-04

`docs/results/live-20260726-windows-scorecard.csv` で rank=0 (None) だった4技法について、
2つの検知経路それぞれを実装まで辿って真因を切り分けた。結論として **4件は1つの共通要因と
4つの個別要因の重ね合わせ**であり、うち「どの経路にもルールが存在しない」という真の被覆
欠落は T1069/T1087 と T1110 だった。本 PR はその2件を塞ぐ。

## 共通要因 — 07-26 の実行では server-detect 経路が1件もアラートを出していない

計測時のアラート実体が `docs/results/fixtures/alerts-WIN-ENDPOINT-01-20260726.json` に
残っている。窓内のアラートは **6件のみ、すべて `[Sigma]` 接頭辞**だった。

接頭辞は経路の指紋である:

| 接頭辞 | 生成元 | 経路 |
|---|---|---|
| `[Sigma]` | `alert_pipeline.go:357` | server-api / Go builtin |
| `[SIGMA]` | `rules/rule_engine.go:223` (`strings.ToUpper(rule.Type)`) | server-detect / DB `rules` テーブル |
| `[BEHAVIORAL]` / `[HEURISTIC]` / `[DISCOVERY]` | `engine.go` 配下の `*Scorer` | server-detect |

`[SIGMA]`・`[BEHAVIORAL]`・`[HEURISTIC]`・`[DISCOVERY]` が **1件も無い**。DB ルールと
状態付き検知器9種はすべて `Engine`(server-detect)にしか実体が無い(`newDiscoveryScorer` /
`newFileBurstScorer` / `newAuthAttackScorer` の呼び出しは `engine.go:265-267` の1箇所のみ)ため、
この実行では **server-detect が生む検知はすべて欠落していた**。

裏付け: 実行窓には discovery コマンドが7種(T1033/T1082/T1057/T1016/T1049/T1069/T1087)
走っており、`DiscoveryScorer` の閾値は「5分窓で4種以上」。本来は確実に発火する条件だった。

これは既知の観測(detection-engine の NATS consumer が慢性的にラグ、
`project_live_measurement_fim_gap_20260713`)と符合する。**ただし当時のデプロイ状態は
リポジトリからは確定できない**ため、共通要因の断定には再計測時の `nats jsz` 確認が要る。

比較対象の 07-02 計測が `[SIGMA]`/`[BEHAVIORAL]` 主体だったのは、そちらでは server-detect
が生きていたからで、**検知能力が落ちたのではなく経路が落ちていた**。

## 個別要因

### T1069 / T1087 — builtin 側に「ローカル版」が存在しない ★本 PR で修正

07-26 のランナーが実行したのは `net localgroup administrators` と `net user`
(`deploy/validation/atomic-runner.ps1:55-56`)。

**builtin(server-api)**: 該当ルール無し。近いものは3つあるが、いずれも条件が外れる。

| builtin | 条件 | `net localgroup administrators` / `net user` が外れる理由 |
|---|---|---|
| `Domain Account Discovery` | `"net"` **かつ** `" user "` **かつ** `"/domain"` | `/domain` 不在。加えて `" user "` は末尾が `user` で終わるコマンドラインに一致しない |
| `Domain Group Discovery` | `"net group"`+`"/domain"`、または `"domain admins"` 等 | `net localgroup` は `net group` を部分文字列として含まない。`administrators` は特権グループ名リストに無い |
| `Local Administrators Group Addition via net.exe` | `localgroup` **かつ** `/add` | `/add` 不在(読み取り専用の列挙) |

**DB(server-detect)**: `Network Discovery via net.exe` (migration 019, `a1b2c3d4-...-017`,
`enabled=true`, `mitre_tags={T1087.001,T1069.001}`) が `' localgroup'` / `' user'` に一致し、
**被覆はしている**。07-02 に発火したのはこれ。

つまり **T1069/T1087 の被覆は server-detect 単一障害点だった**。他の8技法は builtin が
拾ったので、経路が落ちても部分点が残った。この2件だけ 0点になったのはそのためである。

#### ユーザ提起の2仮説の検証結果

- **サブテクニック表記の差(T1069 vs T1069.001)は原因ではない**。`attack-scorer` の
  `sameTechnique` (`tactics.go:216`) は基底テクニックまで畳んで比較し、
  片方が基底のみなら Technique 一致とする。`T1069.001` vs `T1069` は一致する。
- **プラットフォーム・ゲートも原因ではない**。07-02 に Windows ホストで
  `Local System Accounts Discovery - Linux` が発火した理由は別にあり、
  **ゲートが本番で機能していない**ためである:
  `RuleEngine` は `flatMap["platform"]` で判定するが、この値の出所は
  `EventBatch.Platform` (`ingestion/handler.go:503`) で、**エージェントはこのフィールドを
  一度も設定していない**(`agent/` 配下に `Platform_PLATFORM_*` の代入が皆無)。
  結果 `platformString` は `"unknown"` を返し、`platformMatchesEvent` の
  fail-open 分岐(`ep == ""`)で全ルールが通る。ゲートは実質 no-op。
  → 本 PR の範囲外だが、**独立した潜在課題として台帳に登録すべき**。

### T1110 — 認証テレメトリが Sigma から不可視 ★本 PR で修正

3段重ねだった。

1. **入力欠落(修正済・main)**: Windows Security ログの XPath が時刻比較にリテラルを
   使っており `EvtQuery` が常に失敗、`auth` イベントが恒久的に0件だった。
   `timediff()` ベースへの修正は main に入っている
   (`agent/internal/platform/windows/auth_query.go`)。**エージェント差し替え待ち**。
2. **builtin が構造的に一致し得ない(本 PR)**: 唯一の T1110 builtin は
   `EventID: 4625` を選択していたが、ingestion が `auth` イベントに対して emit するのは
   `username/action/success/source_ip/auth_method/logon_type` のみで、
   **`EventID` は registry イベントにしか導出されていなかった**
   (`alert_pipeline.go` の Sysmon registry EventID ブロック)。
   つまりこのルールは製品が生成し得るどのイベントにも一致できない死蔵ルールだった。
   2026-07-20 の field 監査が本ルールを "resolved" と記録しているのは、
   `EventID` が(registry 経路で)supported 集合に入っていたためで、**監査が偽陰性だった**。
3. **一致してもテクニックを取り違える(本 PR)**: タグが `attack.t1078` 始まりで、
   アラートの `mitre_technique` は先頭タグ(`parseMITRETechFromTags`)。
   T1078 と T1110 は tactic を共有しないため、`shareTactic` も効かず、
   **発火しても T1110 としては rank=0 のまま**だった。
   `TestBuiltinSigmaPrimaryTechnique` は許可リスト方式のため本ルールを見ていなかった。

#### ★到達可能にするのは修正ではなかった — FP ソークが捕まえた

当初 ②③ を「ルールを実在フィールドでも選択できるようにし、タグ順を直す」形で修正した。
CI の FP ソークが即座に落ちた:

```
❌ 新たに誤検知を出すルールです "[Sigma] Failed Logon Attempt (Brute Force Indicator)":
   9599.93 /1000ホスト/日 (16件)
```

原因は明白で、**単発の認証失敗に鳴るルールは純粋な誤検知**だからである。
これは推測ではなく、ソークの良性プロファイルに**そう明記されている**:

```toml
# tests/fpsoak/profiles/dev-machine.toml
# タイプミスによるパスワード失敗。単発では鳴ってはならない
# (auth_attack.go はレート現象でのみ判定する) ことの確認材料。
[[auth]]
actions = ["failed"]
```

`auth_attack.go` の冒頭コメントも同じことを述べている——
「builtin の Multiple Failed Login ルールは単一の 4625 で発火するため、
打ち間違いと攻撃を区別できず、ただ全ての失敗に鳴る」。

**つまりコードベースはこのルールが無価値であることを最初から知っていた。
無害だったのは、たまたま死蔵していたからにすぎない。**
到達可能にした瞬間に、設計が予告していた誤検知がそのまま出た。

→ **per-event ルールを削除**した。T1110 はレート現象であり `AuthAttackScorer` の担当である。
結果として **api 経路の T1110 被覆はゼロのまま**だが、これは per-event Sigma では埋められない。
状態付き検知器が server-detect にしか無いという構造の問題であり、別課題として扱う。

エイリアス側も見直した。`EventID` / `TargetUserName` の導出は**入れていない**。
`SupportedSigmaFields()` は説明的な集合ではなく、**curate サービスが
「どの SigmaHQ ルールを `rules` テーブルに有効化するか」を判定するゲート**である
(`curate_service.go`)。有効化されたルールを評価するのは server-detect の `RuleEngine` だが、
その `FieldMappings` には `EventID` も `TargetUserName` も無い。api 側だけで導出すると、
**解決できないルールを field-supported として有効化する**ことになり、P5-7 が扱った
false-green そのものを再生産する。復活させるなら両エンジンに入れる必要がある。

入れたのは `logon_type` → `LogonType` の1件のみ。こちらは `RuleEngine` 側に
**既にマッピングがある**ので、curate が有効化したルールが実際に解決できる。

なお計測シナリオ側の注意点として、ランナーの `failed-logon-burst` は
**7個の異なるアカウントに1回ずつ**失敗させる(`atomic-runner.ps1:88-92`)。
`AuthAttackScorer` の `bruteMinFails=6` は**単一アカウント**基準なので原理的に到達せず、
実際に成立するのは**パスワードスプレー経路**(`sprayMinAccounts=6`、要 `source_ip` 非空)である。
`parseAuthEvent` は `IpAddress` が `-` のときに `WorkstationName` へフォールバックするため
ローカル `ValidateCredentials` でも `source_ip` は埋まる。`T1110.003` は
`sameTechnique` で `T1110` に一致するので採点は通る。

### T1486 — 修正済。ただし Windows での再計測が未了

07-26 レポート(`live-20260726-windows-independent-validation.md`)が特定した
①③④⑥⑦(FileBurstScorer のホスト単位退化、壁時計採点、ファイルイベントの
サイレント破棄、timeframe ルールのパース失敗、inotify 非再帰)は**すべて main に入っている**。
2026-08-01 に **Linux 実機で MTTD 6秒での初検知を確認済み**。

Windows 側で残る懸念はコード上は見当たらない:

- 監視ルート既定は `System32` / `SysWOW64` / `C:\ProgramData` / `C:\Users` / `C:\Temp` で
  `bWatchSubtree=true` (`agent/internal/platform/windows/file_collector.go:82-88,137`)。
  テストが書く `$env:TEMP` (= `C:\Users\<user>\AppData\Local\Temp\...`) は `C:\Users` 配下で被覆される
- 送出は `collector.EmitFile` 経由で非ブロッキング→250ms待機→取りこぼし計上の三段構え
- `FileBurstScorer` はプロセス特定不可時に 5秒窓/60ファイルへ切り替わる。
  テストは 140 ファイルに 280 操作を1〜2秒で実施するため十分超える

→ **コード修正は不要。Windows 実機での再計測のみが残作業。**

ただし throughput 上の潜在リスクとして、`watchDirectory` が
`ReadDirectoryChangesW` の排出ループ内で create/modify ごとに MD5+SHA1+SHA256 を
**同期的に**計算しており、バースト中はカーネル側の通知バッファ溢れを招き得る。
実測で確認されたわけではないので本 PR では触らない。

### ★2周目の是正 — 追加ルールが良性コーパスに当たっていた

初版の2ルールはセレクタが広すぎ、FP ソークの `it-admin` プロファイルが**正常業務として
流している**コマンドに当たっていた:

| 良性コマンド (`tests/fpsoak/profiles/it-admin.toml`) | 当たっていたセレクタ |
|---|---|
| `whoami /groups` | `Local Permission Groups Discovery` / `whoami_groups` |
| `query user` | `Local Account Discovery` / `session_enum` |

初回ソークで個別に報告されなかったのは **new-rule floor (3000/1000ホスト/日) 未満**
だったためで、FP を出していなかったからではない。**floor 未満は「無害」ではなく
「報告されないだけ」**で、ベースラインの総量は押し上がる。

→ 両セレクタを削除した。どちらも `classifyDiscoveryCommand` (discovery.go) が既に
T1069/T1033 として分類しており、**単発では鳴らさずバースト相関の材料にする**という
この種のコマンドの正しい扱いは既に実装されている。計測対象の
`net localgroup administrators` / `net user` には影響しない。

あわせて `TestLocalDiscoveryRulesAreQuietOnFPSoakCorpus` を追加した。ソークの良性
コマンド列を直接テストに持ち込み、**追加した2ルールがそのどれにも発火しないこと**を固定する。
ソークは15分かかるうえグローバルな concurrency グループを3セッションで奪い合っており
実行機会が不安定なので、discovery 系に関しては同じ問いをミリ秒で答えられるようにした。

## 本 PR の変更

1. `sigma_builtins.go` に builtin を2件追加
   - `Local Account Discovery` (T1087.001) — `net user` / `net accounts` /
     `Get-LocalUser` / `wmic useraccount` / `query user`。`/domain` を含む形は除外し、
     ドメイン版ルールとの二重発火を避ける
   - `Local Permission Groups Discovery` (T1069.001) — `net localgroup` /
     `Get-LocalGroupMember` / `whoami /groups` / `wmic group get`。
     `/add` `/delete` を除外し、T1098 の書き込み系ルールと棲み分ける
   - どちらも `level: low`。discovery 単発は管理者操作と区別できないため、
     severity を上げず相関の材料に留める(`sigmaLevelToInt(low)` = 3、
     自動隔離の閾値には届かない)
2. `sigma_builtins.go` の T1110 per-event builtin を**削除**
   (`Multiple Failed Login Attempts (Brute Force Indicator)`)。到達不能かつ形が誤っていた。
   削除理由と「再追加してはいけない理由」を同じ位置にコメントとして残している
3. `alert_pipeline.go` の `addPipelineSigmaAliases` に `logon_type` → `LogonType` を追加。
   **RuleEngine 側には既にあり api 側だけ欠けていた**パリティ欠落で、ingestion のコメントが
   主張する「Sigma LogonType ルールに供給」は api 経路では成立していなかった。
   `EventID` / `TargetUserName` は**意図的に導出しない**(理由は上記およびコード内コメント)
4. テスト
   - `builtin_local_discovery_auth_fire_test.go` (新規) — 07-26 のコマンドライン実物での発火、
     ドメイン版/書き込み版との棲み分け、**単発の認証失敗で builtin が1件も発火しないこと**の固定、
     `LogonType` エイリアスと `TargetUserName` が supported に入らないことの固定
   - `TestBuiltinSigmaPrimaryTechnique` にローカル版2ルールを追加
   - `field_support_reachability_test.go` の emit ミラーに `logon_type` を追加
     (ingestion は emit していたのにミラーから漏れていた)
