# 隠れた故障の是正 — Wazuh 取込経路のサイレントドロップ（2026-08-03）

対象 PR: **#574**（migration `357_agents_os_type_unknown.sql`）

Wazuh 連携の取込経路に **4 件**の欠陥があった。3 件は「例外が上がらず静かにデータが消える」種類で、
ログを追っていても気付けない。いずれも**実 DB で再現を確認**してから修正している。

共通する構造は P5-10（`status='inactive'` の読み出し側未追随）と同じく **DB 制約とコードの語彙のずれ**だが、
今回は過剰発火ではなく**全損**として出た。Wazuh 連携は「設定したのに何も入ってこない」状態が
長期間続いていたことになる。

---

## 1. `23514` — 未登録ホスト由来の Wazuh アラートが 1 件も保存されていなかった

`server/internal/api/handlers/ingest_handler.go` の `upsertAgent` が、未登録ホストのエージェント行を
`os_type` にリテラル `'unknown'` を入れて INSERT していた。

```sql
INSERT INTO agents (hostname, ip_addresses, os_type, status, last_seen, source)
VALUES ($1, ARRAY[$2::inet], 'unknown', 'online', NOW(), 'wazuh')
```

しかし `agents_os_type_check` は migration 001 以来 `('windows','linux','darwin')` のみを許可しており、
以降どのマイグレーションも緩和していなかった。

```
ERROR:  new row for relation "agents" violates check constraint "agents_os_type_check"
DETAIL:  Failing row contains (..., wazuh-repro-1, unknown, ...)
```

`upsertAgent` が失敗すると `WazuhAlert` は 500 を返して打ち切るため、**未登録ホスト由来の Wazuh アラートは
1 件も保存されていなかった**。webhook 送信側から見れば 500 が返るだけで、原因は分からない。

## 2. `42P10` — エージェント同期が完全な no-op だった

`server/internal/sync/wazuh.go` の `SyncAgents` が `ON CONFLICT (hostname)` を使っていたが、
**`agents.hostname` に UNIQUE 制約は存在しない**。

```
ERROR:  there is no unique or exclusion constraint matching the ON CONFLICT specification
```

全行がこのエラーで失敗し、`slog.Warn` を出して `continue` するだけだった。ループは最後まで回り
関数はエラーを返さないので、**同期は「成功した」ように見えて 1 件も反映されない**。

UNIQUE を張って解決することはできない。マルチテナント構成では同名ホストが別テナントに並存しうるためで、
`UPDATE` → 0 行なら `INSERT` の二段 upsert に置き換えた。

## 3. `23514` — Wazuh の `os.platform` を素通ししていた

同じ `SyncAgents` が `wa.OS.Platform` をそのまま `os_type` に書いていた。Wazuh の `os.platform` は
**ディストリビューション ID**（`ubuntu` / `centos` / `amzn` / `debian` …）であって OS ファミリではない。
2 を直しても Linux ホストは全て CHECK で弾かれる。

## 4. Wazuh アラート 1 件で隔離が解除される

`agents.status` の `'isolated'` は**ネットワーク隔離中を示す封じ込め状態**であって死活状態ではない。
隔離中のホストは「隔離されたまま報告し続ける」のが正しい挙動である。しかし Wazuh 由来の 2 経路が
`status` を無条件に代入していた。

| 経路 | 内容 |
|---|---|
| `ingest_handler.upsertAgent` | 既存行に `status = 'online'` を無条件代入。webhook にアラートが**1 件届くだけ**で隔離が解除される |
| `sync.SyncAgents` | `status = $6`（`mapWazuhStatus` の online/offline）を無条件代入。Wazuh は当社の隔離状態を関知しないため、**定期同期のたびに**解除される |

ハートビート経路（`store.AgentStore.UpdateLastSeen`）は既に
`CASE WHEN agents.status = 'isolated' THEN 'isolated' ELSE 'online' END` のガードを持っていた。
同じガードを Wazuh の 2 経路にも適用した。明示的な解除（`UnisolateAgent`）は従来どおり効く。

## 設計判断 — なぜ CHECK を緩め、かつ OS 導出も行うのか

`'unknown'` を `os_type` の正規値に昇格させるのは辻褄合わせではない。**読み出し側が既に `'unknown'` を
想定値として扱っていた**からである。

- `store/agents.go` の `ProtectionModeByOS` — `COALESCE(NULLIF(os_type,''), 'unknown')`
- `compliance/evaluator.go` の `loadAgentData` — `COALESCE(os_type, 'unknown')`

つまり「不明」は既にドメイン上の正当な状態で、CHECK だけが追随していなかった。

> **判断基準**: CHECK を緩めるか独立したカラムを足すかは「**読み出し側が既にその値を想定値として
> 扱っているか**」で決める。YES なら緩和、NO なら別カラム。P5-10 の `status='inactive'` は NO 側の
> 事例に見えたが、実際には main が先に緩和方式を採っていた（後述の教訓 2）。

加えて **Wazuh の webhook ペイロードには OS フィールドが一切ない**（`agent` は id / name / ip のみ）。
推定は best-effort にしかならず、また Wazuh は AIX / Solaris / HP-UX も管理できる。それらに
windows / linux / darwin を当てるのは誤ラベルで、`autoupdate` の `platform = a.os_type` 突合や
`agent_config_profiles` の一致を静かに誤爆させる。

→ **推定できれば正規値、できなければ正直に `unknown` を永続化し、後から昇格させる。**

## 追加した導出層 `server/internal/sync/ostype.go`

| 関数 | 役割 |
|---|---|
| `NormalizeOSType(platform, osName)` | ディストリ ID → OS ファミリ。`platform` 優先、無ければ `os.name` を走査、未知は `unknown` |
| `OSTypeFromAlert(payload)` | webhook から best-effort 導出（`data.win` / `location` / `rule.groups`） |
| `SanitizeIP(ip)` | Wazuh の `"any"` と CIDR 付きを吸収 |

`NormalizeOSType` で注意した点: 短い曖昧なコード（`ol` = Oracle Linux、`alma`）は**完全一致のみ**にした。
部分一致にすると `"Solaris"` が `"ol"` を含むため AIX/Solaris が Linux に化ける。

`SanitizeIP` は 5 件目に近い欠陥の予防である。Wazuh は固定アドレスを持たないエージェントに `"any"` を返し、
`$1::inet` は `22P02` で失敗する。同期は行単位で `continue` するため、これも静かに 1 行落ちる。

既存行の `os_type` は **`'unknown'` のときだけ昇格**させ、既知値を `'unknown'` へ降格させない（両経路）。

## 教訓

### 1. CHECK 制約バグは例外を握り潰されて静かに消える

3 件とも、アプリ側が失敗を握り潰していた（`slog.Warn` + `continue`、または 500 で打ち切り）。
そのため「機能が一度も動いていない」状態が長期間表面化しない。

> **新機能が本当に動いているかは、ログではなく DB に行が入っているかで確かめる。**
> `SELECT count(*) FROM agents WHERE source='wazuh'` が 0 なら、それが答えである。

`ON CONFLICT` の 42P10 は特に危険で、**構文的には正しく、テーブルに UNIQUE を足すまで永久に失敗する**。
`ON CONFLICT (col)` を書くときは、その列の UNIQUE 制約が実在するかを `\d <table>` で確認する。

### 2. 「実 DB で再現できた」は「現在の main にバグがある」を意味しない

本件の作業中、同じ調査手法で `dead_agent_cleanup` の `status='inactive'` 問題（P5-10）も
「未修正」と判定したが、これは**ローカル dev DB が古かったことによる誤判定を疑う必要があった**。

- ローカル dev DB は**イメージに焼き込まれた migration までしか進まない**。
  `kizashi-api` イメージは 2026-04-16 ビルドで migrations は 227 件までしか含まず、
  `server/migrations` はコンテナにマウントされていない。`RUN_MIGRATIONS=true` があっても
  再起動で 1 件も増えない（DB が遅れているのではなく、イメージと同期している）。
- したがって**バグの実在判定は ①実 DB での再現 ②その時点の `origin/main` の migration 群とソース の両方**で取る。
- さらに main は数十分〜数時間で進むため、②は水物である。**提出直前にも `git fetch origin` を単独実行**して
  先端を取り直す（複合コマンド内で fetch が静かに失敗すると、古い ref のまま誤判定する）。
- 「既に main にあるか」は日付ではなく `git merge-base --is-ancestor <commit> <base>` で判定する。
  author date が古くても main への着地が後、というケースは普通にある。

現在の main のスキーマを確認したいだけなら、稼働環境に触らず参照 DB を作るのが速い（数分）。

```bash
git archive origin/main server/migrations | tar -x -C <scratch>
docker cp <scratch>/server/migrations kizashi-postgres:/tmp/refmig
# CREATE DATABASE edrplatform_ref → schema_migrations 作成 →
# ls *.sql | sort の順に psql -v ON_ERROR_STOP=1 --single-transaction -f each
# （実行器 internal/store/migrate.go と同じ sort.Strings 辞書順・ファイル単位トランザクション）
docker exec kizashi-postgres psql -U edr -d edrplatform_ref -c "\d agents"
```

2026-08-03 実施で 385 件全成功。ただし**参照 DB も作った時点で固定される**ので、
一次情報は常に `origin/main` の migration ファイルそのものである。

> 参照 DB を作り直す操作では **`DROP DATABASE` を書かない**。「既に存在したら中断」にしておく。
> 本番 DB 名 `edrplatform` と参照 DB 名 `edrplatform_ref` は 1 文字違いで、タイプミスが致命傷になる。

### 3. 状態列は「死活」と「封じ込め」を混同しない

`agents.status` は `'online'` / `'offline'` / `'inactive'`（死活）と `'isolated'`（封じ込め）という
**性質の異なる 2 種類の状態を 1 列に載せている**。そのため「報告を受けた」を理由に `'online'` を
無条件代入すると、封じ込め状態が巻き添えで消える。

エージェント行の `status` を書くコードは、**`'isolated'` を保護しているか**を必ず確認する。
既存の正しい実装は `store.AgentStore.UpdateLastSeen`（`CASE WHEN ... 'isolated' ...`）。
