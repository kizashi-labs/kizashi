## 1. インシデント対応フレームワーク

本 SOP は **NIST SP 800-61** および **SANS Institute** のインシデント対応ライフサイクルに基づいています。

```
┌─────────────────────────────────────────────┐
│              インシデント対応ライフサイクル              │
│                                             │
│  準備 → 識別 → 封じ込め → 根絶 → 復旧 → 事後対応    │
│                     ↑                       │
│              フィードバックループ                    │
└─────────────────────────────────────────────┘
```

### 対応時間目標（RTO）

| 重大度 | 分類 | 初動開始 | 封じ込め完了 | 復旧完了 |
|--------|------|---------|------------|---------|
| P1 | Critical（重大度 9〜10） | 15 分以内 | 1 時間以内 | 4 時間以内 |
| P2 | High（重大度 7〜8） | 1 時間以内 | 4 時間以内 | 24 時間以内 |
| P3 | Medium（重大度 5〜6） | 4 時間以内 | 翌営業日 | 72 時間以内 |
| P4 | Low（重大度 1〜4） | 翌営業日 | 1 週間以内 | 2 週間以内 |

## 2. フェーズ 1 — 準備

### 2-1. 必要なアクセス権の確認

対応前に以下のアクセス権が付与されていることを確認してください：

| リソース | 必要なロール |
|---------|------------|
| Kizashi Web UI | `analyst` 以上 |
| ライブレスポンス | `analyst` 以上 |
| エンドポイント隔離 | `analyst` 以上 |
| インシデント作成・更新 | `analyst` 以上 |

### 2-2. 連絡先リストの更新

チームの連絡先リストを最新の状態に維持してください（[エスカレーション・通知フロー](#10-エスカレーション通知フロー) 参照）。

### 2-3. ツールの確認

対応開始前に以下のツールが利用可能であることを確認してください：

- [ ] Kizashi Web UI にアクセスできる
- [ ] ライブレスポンスのセッション開始が可能
- [ ] 証拠収集先の安全な共有ストレージにアクセスできる
- [ ] 社内チャット・ビデオ会議ツールが利用可能

## 3. フェーズ 2 — 識別・トリアージ

### 3-1. アラートの確認

アラートを受信したら以下を確認します：

1. **SOCワークキューを確認**（`/soc-queue`）
2. 対象アラートをクリックして詳細を確認
3. **AI分析結果**（右パネル）を確認して初期判断の参考にする

### 3-2. 重大度の評価

以下の観点からインシデントの重大度を評価します：

| 評価観点 | 質問 |
|---------|------|
| **影響範囲** | 何台のエンドポイントが影響を受けているか？ |
| **データ影響** | 機密データや個人情報へのアクセス・流出の可能性はあるか？ |
| **業務影響** | 重要業務システムへの影響はあるか？ |
| **拡大リスク** | 感染の拡大・横展開の可能性はあるか？ |

### 3-3. インシデントの作成

P1 / P2 と判断した場合、即座にインシデントを作成します：

1. アラート詳細 → **インシデントに昇格** ボタンをクリック
2. タイトルに以下の形式で入力：`[YYYY-MM-DD] [脅威種別] [影響エンドポイント名]`
   - 例：`[2026-06-03] Ransomware WIN-SALES-042`
3. 重大度・担当者を設定して **作成**

### 3-4. 初期記録

インシデントの調査メモ（コメント）に以下を記録します：

```
【初期確認】
検知日時: YYYY-MM-DD HH:MM UTC
検知ルール: <ルール名>
対象エンドポイント: <ホスト名> (<IPアドレス>)
重大度: <重大度>
AI分析結果概要: <AIの判定内容>
初期対応者: <名前>
```

## 4. フェーズ 3 — 封じ込め

### 4-1. 短期封じ込め（即時実施）

**目的**: 被害の拡大を防止する

| アクション | 手順 | 条件 |
|-----------|------|------|
| エンドポイント隔離 | 対象エンドポイント詳細 → **隔離** ボタン | ランサムウェア・バックドア・C2通信が確認された場合 |
| プロセス強制終了 | ライブレスポンス → プロセス終了コマンド | 悪意あるプロセスが特定された場合 |
| ファイル検疫 | ライブレスポンス → ファイル検疫 | 悪意あるファイルが特定された場合 |

**隔離実施のコマンド（API）:**

```http
POST /api/v1/agents/{agent_id}/isolate
Authorization: Bearer <APIキー>
```

### 4-2. 隔離対象エンドポイントへの継続アクセス

隔離中もライブレスポンスによる調査継続が可能です：

1. **エンドポイント → ライブレスポンス** を開く
2. 隔離中の端末をクリックしてセッション開始
3. 調査コマンドを実行（ネットワーク通信は遮断されているが管理接続は維持）

### 4-3. 長期封じ込め

短期封じ込め後、以下を検討します：

- **認証情報のリセット**: 侵害された可能性のあるアカウントのパスワードをリセット
- **ルール追加**: 検出された IOC（IP/ドメイン/ハッシュ）を IOC管理に追加
- **アラート抑制の解除**: 封じ込め中は過剰な抑制をかけないよう注意

## 5. フェーズ 4 — 根絶

### 5-1. 証拠収集（フォレンジクス）

根絶前に証拠を収集します。証拠は法的要件に対応するために改ざん不可能な形で保存してください。

1. **エンドポイント → フォレンジクス** を開く
2. 以下を収集して安全なストレージに保存：
   - メモリダンプ
   - プロセス一覧（実行時の状態）
   - ネットワーク接続状態
   - 疑わしいファイル

3. ライブレスポンスで追加収集：

```bash
# プロセス一覧
ps aux > /tmp/processes_$(date +%Y%m%d%H%M%S).txt

# ネットワーク接続
netstat -anp > /tmp/network_$(date +%Y%m%d%H%M%S).txt

# 最近変更されたファイル（過去24時間）
find / -newer /tmp -mtime -1 -type f 2>/dev/null | head -100
```

### 5-2. マルウェアの除去

| 手順 | 操作 |
|------|------|
| 1. 悪意あるプロセスの確認 | ライブレスポンス → `ps aux` でプロセスを確認 |
| 2. プロセスの終了 | 対象プロセスを右クリック → **プロセス終了** |
| 3. マルウェアファイルの検疫 | ライブレスポンス → 対象ファイルを **検疫** |
| 4. 永続化メカニズムの除去 | スタートアップ・スケジュールタスク・レジストリを確認 |
| 5. スキャンの実行 | エンドポイント詳細 → **スキャン実行** |

### 5-3. 侵害された認証情報の処理

- 影響を受けたアカウントの **パスワードを全サービスで変更**
- APIキー・シークレットが侵害された可能性がある場合は **即時ローテーション**
- セッショントークンの無効化（ユーザーを強制ログアウト）

## 6. フェーズ 5 — 復旧

### 6-1. 復旧前の確認

| 確認項目 | 方法 |
|---------|------|
| マルウェアが完全に除去されていること | スキャン結果でクリーンを確認 |
| 脆弱性が修正されていること | 侵入経路を特定・パッチ適用済みを確認 |
| 認証情報がリセットされていること | 影響を受けた全アカウントで変更済みを確認 |
| ログが正常に収集されていること | エンドポイント詳細でイベント取得を確認 |

### 6-2. 隔離解除

```http
POST /api/v1/agents/{agent_id}/unisolate
Authorization: Bearer <APIキー>
```

または Web UI: エンドポイント詳細 → **隔離解除** ボタン

### 6-3. 監視の強化

復旧後 72 時間は通常より厳重に監視します：

1. **検知 → アラート** で対象エンドポイントをフィルターして集中監視
2. 必要に応じてアラートの通知チャンネルを追加
3. 72 時間後に異常がなければ通常監視に戻す

## 7. フェーズ 6 — 事後対応

### 7-1. インシデントレポートの作成

インシデントクローズ後 5 営業日以内にレポートを作成します：

**必須記載事項:**

```
【インシデントレポート】

インシデントID: INC-YYYY-XXXX
作成日: YYYY-MM-DD
作成者: <名前>

1. 概要
   - 発生日時・発見日時
   - 影響を受けたシステム・ユーザー数
   - インシデントの種類

2. タイムライン
   - 発生〜検知〜対応完了の時系列

3. 根本原因
   - 攻撃の侵入経路
   - 利用された脆弱性・弱点

4. 対応内容
   - 実施したアクションと結果

5. 影響範囲
   - データ・システムへの影響
   - 業務への影響

6. 再発防止策
   - 短期対策（実施済み）
   - 中長期対策（計画中）
```

### 7-2. ポストモーテム（事後検討会）

P1 / P2 インシデントでは、対応完了後 2 週間以内にポストモーテムを開催します：

**議題:**

1. タイムラインの振り返り（何が起き、いつ誰が何をしたか）
2. 対応の評価（うまくいったこと・改善が必要なこと）
3. 再発防止策の決定（オーナー・期限を設定）
4. 検知ルール・プレイブックの更新有無の判断

### 7-3. 検知・対応の改善

| 改善アクション | 担当 | 期限 |
|-------------|------|------|
| IOC をインテリジェンスデータベースに追加 | SOCアナリスト | 即時 |
| 検知ルールの追加・修正 | SOCチームリード | 1 週間 |
| プレイブックのアップデート | SOCチームリード | 2 週間 |
| インフラ・設定の脆弱性修正 | インフラチーム | 優先度による |

## 8. インシデント分類と重大度定義

### 8-1. インシデント種別

| 種別コード | 説明 | 例 |
|-----------|------|-----|
| `MAL` | マルウェア感染 | ランサムウェア・トロイの木馬・スパイウェア |
| `PHI` | フィッシング | 認証情報詐取・BEC |
| `UNA` | 不正アクセス | アカウント乗っ取り・内部不正 |
| `DLP` | データ漏洩 | 機密情報の外部送信・USBコピー |
| `DOS` | サービス妨害 | DDoS・リソース枯渇攻撃 |
| `VUL` | 脆弱性悪用 | CVE悪用・ゼロデイ攻撃 |
| `INS` | 内部脅威 | 内部者による不正行為 |
| `APT` | 標的型攻撃 | APTグループ・持続的侵入 |

### 8-2. 重大度基準

| レベル | 基準 |
|--------|------|
| **P1 Critical** | データ流出・ランサムウェア展開・重要システム停止・複数ホストへの横展開 |
| **P2 High** | 単一ホストへのマルウェア侵入・権限昇格成功・内部不正が疑われる |
| **P3 Medium** | 不審な通信・異常なファイルアクセス・フィッシング試行 |
| **P4 Low** | 誤設定・ポリシー違反・情報収集活動の痕跡 |

## 9. シナリオ別対応チェックリスト

### ランサムウェア

- [ ] 感染端末をネットワーク隔離
- [ ] ドメインコントローラー・バックアップサーバーの安全を確認
- [ ] 感染拡大の有無を確認（他エンドポイントのアラートを確認）
- [ ] バックアップの無事を確認
- [ ] `vssadmin`・`bcdedit` の実行履歴を確認
- [ ] 身代金メモファイルを証拠として収集
- [ ] マルウェアのサンドボックス解析（`/malware-analysis`）
- [ ] 外部通報（NISC / 警察 / 顧客）の要否を判断

### アカウント侵害

- [ ] 侵害されたアカウントを即時無効化
- [ ] 全サービスのパスワードをリセット
- [ ] MFA の再登録を強制
- [ ] 侵害期間中のアクティビティログを確認
- [ ] 他アカウントへの侵害拡大を確認
- [ ] 侵入経路（フィッシングメール・脆弱なパスワード等）を特定

### 不審な外部通信（C2通信疑い）

- [ ] 対象端末を隔離
- [ ] 通信先 IP/ドメインを IOC として登録
- [ ] VirusTotal で通信先を確認
- [ ] 通信先が既知の C2 フレームワーク（Cobalt Strike 等）であるか確認
- [ ] プロセスツリーで通信元プロセスを特定
- [ ] バックドアの永続化メカニズムを確認（スタートアップ・タスクスケジューラ等）

### 内部者脅威

- [ ] 対象ユーザーのアクティビティをUEBA（`/ueba`）で確認
- [ ] アクセスログを保全（改ざん防止のため外部へ退避）
- [ ] 対象ユーザーへの通知前に法務・HR部門に相談
- [ ] 証拠収集は法的手続きに従って実施
- [ ] 必要に応じてアカウントを無効化（強制ログアウト）

## 10. エスカレーション・通知フロー

### 10-1. 内部エスカレーション

```
SOCアナリスト
    │  P1/P2 検知または判断に迷う場合
    ▼
SOCチームリード（即時連絡）
    │  重大インシデント（データ流出・重要システム停止）
    ▼
CISO / セキュリティマネージャー（30分以内）
    │  法的影響・顧客影響がある場合
    ▼
法務 / 経営層 / PR担当（1時間以内）
```

### 10-2. 外部通報の判断基準

| 状況 | 通報先 | 期限 |
|------|--------|------|
| 個人情報漏洩（500人以上） | 個人情報保護委員会 | 72 時間以内（速報）|
| 重要インフラへの攻撃 | NISC / IPA | 即時 |
| 金融機関・証券会社 | 金融庁 / 財務局 | 業法に従う |
| 顧客データ漏洩 | 影響顧客 | 合理的な期間内 |

### 10-3. Kizashi での通知設定

重大インシデント時に自動通知を飛ばすには：

1. **管理 → 管理 & 設定 → 通知チャンネル** で Slack / Email を設定
2. **管理 → 対応 → プレイブック** でインシデント作成時に通知を送るプレイブックを設定
