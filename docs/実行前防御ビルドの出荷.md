# 実行前防御ビルドの出荷（Linux eBPF LSM / macOS ESF）

エージェントの実行前防御が「実装はあるが誰にも届かない」状態だった原因と、その配線をまとめる。
設計そのものは [design/Linux改ざん防止と実行前防御設計.md](design/Linux改ざん防止と実行前防御設計.md) を参照。

## 何が問題だったか

防御コードは `prevention` ビルドタグの向こう側にあり、これを有効にした唯一のビルドが
`edr-agent-linux-amd64-ebpf`。ここまでは設計どおりだが、その先が繋がっていなかった。

| 段 | 状態（是正前） |
|---|---|
| CI ゲート | **無し**。`ci.yml` は `-tags ebpf` までしか見ず、staticcheck も `prevention` を明示的に対象外にしていた |
| ビルド頻度 | `agent-ebpf.yml` が `workflow_dispatch` のみ。`downloads/` のバイナリは **3週間停止**していた |
| インストーラ | `install.sh` は常に既定ビルドを取得。防御版を選ぶ経路が存在しない |
| 自動更新 | `update-check` が常に既定ビルドを提示。**防御版を入れても初回更新で防御が消える** |

つまり防御は「ビルドすれば存在するが、誰も選べず、選んでも次の更新で消える」状態だった。

## 是正後の経路

```
ci.yml (全PR)
  ├─ bpf2go: PreventionLSM / TamperLSM / CredAccessLSM を生成
  ├─ staticcheck -tags "ebpf prevention"
  ├─ go build + go test -tags "ebpf prevention"
  └─ GOOS=windows go vet -tags prevention      ← Windowsドライバ側も同時に型検査

agent-ebpf.yml (週次 ※暫定。本来は main への agent/ 変更で自動)
  └─ edr-agent-linux-amd64-ebpf を downloads/ へ

install.sh
  └─ /sys/kernel/security/lsm に bpf があれば variant=ebpf を自動選択
       └─ /etc/edr/agent-variant に記録

update.sh / エージェント自己更新
  └─ 記録された variant を引き継ぐ（防御版は防御版のまま更新）
```

## variant パラメータ

`GET /api/v1/agents/download?...&variant=ebpf` と
`GET /api/v1/agents/:id/update-check?...&variant=ebpf`。値は `""`（既定）か `ebpf` のみの
許可リスト方式（ファイル名に入るため）。

**フェイルセーフの向き**が重要で、`variant=ebpf` に対応するバイナリがサーバに無い場合は
**アップデートを一切提示しない**。既定ビルドで代替すると、防御を意図して入れた端末から
prevention が黙って剥がれる——このパラメータが防ごうとしているまさにその事故になる。
少し古い防御版に留まるほうが、新しい無防備版に移されるより安全。

インストーラ側も同じ向きで、防御版が未公開のサーバでは警告を出して既定ビルドに落ちる
（インストール自体は失敗させない）。

## 運用

```bash
# 防御版を強制（カーネル判定をスキップ）
EDR_AGENT_VARIANT=ebpf ./install.sh

# 既定ビルドに固定（BPF LSM 対応ホストでも防御版を入れない）
EDR_AGENT_VARIANT=none ./install.sh
```

BPF LSM が無効なホストで防御版を有効にするには、カーネル起動パラメータに `bpf` を足す:

```
lsm=lockdown,capability,landlock,yama,apparmor,bpf
```

## macOS（ESF）

Linux と同じ構図が macOS にもあった。しかもこちらは**ビルドすら通らない**状態だった。

`-tags esf` の実装は cgo ファイル（`import "C"` / `EndpointSecurity.h`）なので、
`CGO_ENABLED=0` だと Go がファイルごとビルド対象から外す。フォールバックの ps ポーリング実装は
`darwin && !esf` で除外される。結果、**両方消えて `NewDarwinProcessCollector` が未定義**になる。

CI がこれを検出できなかった理由は「vet の範囲が `./internal/platform/darwin/...` だけだったから」。
未定義が現れるのは使用側の `cmd/agent` で、当該パッケージ内には参照が無い。

### 対応

- ビルド制約を cgo 込みに揃えた。`process_collector.go` は `darwin && (!esf || !cgo)`、
  ESF 実装と ESF 防御は `&& cgo`。これで `-tags esf` + `CGO_ENABLED=0` は
  **ポーリング実装に安全に縮退**する（コンパイルエラーではなく、機能が落ちるだけ）。
- `ci.yml` の darwin vet を `./...` に拡大。同じ穴が二度開かない。
- `agent-macos-esf.yml` を新設。macOS ランナーで `CGO_ENABLED=1` のネイティブ ESF ビルド
  （arm64 / amd64 / `esf prevention` 組み合わせ）と `go test` を回す。
  macOS ランナーは課金単価が高いので darwin 関連パスに限定。

### 署名と公証

ESF は **Apple の entitlement 承認が律速**（`com.apple.developer.endpoint-security.client`、
数週間）。申請一式は [macOS-ESF-entitlement申請キット.md](macOS-ESF-entitlement申請キット.md) にある。

ワークフローは署名シークレット（`APPLE_DEVELOPER_ID_P12` / `APPLE_TEAM_ID` /
`APPLE_SIGN_IDENTITY` / `APPLE_NOTARY_*`）が設定されていればそれを使い、無ければ
**未署名のまま artifact に上げるだけで `downloads/` には公開しない**。

未署名 ESF バイナリは `es_new_client` が `ES_NEW_CLIENT_RESULT_ERR_NOT_ENTITLED` で失敗するため、
既定ビルドより明確に劣る（防御版の見た目で ESF テレメトリが出ない）。承認前の段階でこのジョブが
生む価値は**コンパイルゲート**であって配布ではない、という線引き。

同じ理由で `install.sh` は macOS で ESF を自動選択しない。署名済みかどうかは外から判定できないので、
`EDR_AGENT_VARIANT=esf` の明示が要る。

## ⚠️ 暫定措置（2026-08-10 — Actions 予算枯渇）

リポジトリの Actions 予算が上限に達しており（`The job was not started because an
Actions budget is preventing further use`、main 自体も全ジョブ赤）、コストの大きい
2つのトリガを**一時的に落としてある**。

| ワークフロー | 本来 | 暫定 | 失うもの |
|---|---|---|---|
| `agent-ebpf.yml` | main への agent/proto 変更で自動 | **週次**（月 03:00 UTC） | バイナリの陳腐化が「1マージ以内」→「7日以内」に緩む |
| `agent-macos-esf.yml` | main push **＋ PR** | **main push のみ** | ESF ビルドの破損が PR 時点で捕まらない（マージ後まで気づかない） |

**予算は 2026年9月に復旧予定。その時点で戻すこと。**

**復帰手順**は各ワークフローのヘッダに枠囲みで書いてある（`schedule:` を消して
`push:` のコメントを外す／`pull_request:` のコメントを外す）。それ以外は変更していない。

戻し忘れを検出する仕組みは無い——ので、**両ワークフローが実行のたびに
`::warning::` で自己申告する**ようにしてある（週次実行時／main push 時）。
Actions の画面を見た人には必ず目に入り、トリガを戻せば警告も消える。

> この暫定措置は、**本ドキュメントが直そうとしている欠陥そのものを部分的に戻している**。
> 「防御版バイナリが静かに古くなる」のが元の問題で、週次はそれを7日に抑えているだけである。
> 予算が回復したら戻すこと。戻し忘れを検出する仕組みは無い。
>
> なお `ci.yml` 側の `-tags "ebpf prevention"` のビルド・テストと
> `GOOS=darwin go vet -tags esf ./...` は**据え置き**。既存ジョブに相乗りしていて追加コストが
> 小さく、かつ実際にバグを検出した箇所なので、ここを削ると PR 単位の検査が空になる。

## enforce はまだ既定 off

防御版を入れても、既定では **audit（fail-open: 何も拒否せず報告のみ）**。
実際に `-EPERM` で拒否するのは `EDR_PREVENTION_ENFORCE=1` を明示したときだけで、
これは `agent/cmd/agent/prevention_linux.go` の設計どおり。本ドキュメントの範囲は
「防御ビルドが端末に届き、更新で消えないこと」までで、enforce の既定化は別判断。
