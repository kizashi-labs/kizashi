# インストーラ・バイナリ配信経路アーキテクチャ

エージェントのインストーラとバイナリ配信には複数の経路が併存しています。混乱を避けるため、現状を正確にマップ化します。**本ドキュメントは現状の整理であり、各経路の統廃合は別途の設計判断が必要です（安易に削除しないこと）。**

> このマップは 2026-06-10 のコード調査に基づきます。実機エンドポイントの更新作業中に「どの経路が実体か」で混乱が生じたため作成しました。

---

## 1. インストーラ（3系統）

| 経路 | サービス名/構成 | 用途・状態 |
|------|----------------|-----------|
| **A. 動的生成（installer_handler）** | `EDRAgent`（watchdog なし、`config\config.toml`） | **本番・正統**。ダッシュボードのエンロール経路。トークン制 |
| B. 手動スクリプト（`deploy/install/`） | `EDRWatchdog`（watchdog あり、`agent.toml`） | 手動/エアギャップ用。README・[エージェントインストール手順](エージェントインストール手順.md) が参照 |
| C. 静的スクリプト（`agent/deploy/`） | `EDRAgent` | **孤立（非推奨）**。どこからも参照されない旧静的ファイル |

### A. 動的生成（`server/internal/api/handlers/installer_handler.go`）
ダッシュボードからのエンロールで使う**本番の正統経路**。サーバーがインストールスクリプトを動的生成して配信します。

- `GET /api/v1/installer/linux/:arch` → Linux 用スクリプト生成（ワンライナー: `curl -fsSL <server>/api/v1/installer/linux/amd64 | sudo bash`）
- `GET /api/v1/installer/windows/:arch` → `Install-EDRAgent.ps1` 生成（サービス名 `EDRAgent`）
- `GET /api/v1/installer/download/:os/:arch` → バイナリ配信（**この経路専用**）
- `GET /api/v1/installer/script[/:os/:arch]` → スクリプトのみ
- `/api/v1/admin/installer/tokens`（admin）でエンロールトークンを管理
- **実機エンドポイント（検証 EC2 の Windows `EDRAgent` 構成・Linux `edr-agent.service`）はこの経路で導入されたとみられる**

### B. 手動スクリプト（`deploy/install/install.{sh,ps1}`）
手動・エアギャップ環境向け。サービス名 `EDRWatchdog`（watchdog が agent を監督）、設定 `agent.toml`。README・docs が「インストーラ」として参照する。**A とはサービス名・レイアウトが異なる**点に注意。

### C. 静的スクリプト（`agent/deploy/windows/Install-EDRAgent.ps1`, `agent/deploy/linux/install.sh`）
**孤立・非推奨**。リポジトリのどこからも参照されず（installer_handler は自前でスクリプトを生成するため、これらの静的ファイルは読まない）。A の `EDRAgent` モデルと同系だが別実装の旧コピー。参照・編集しないこと。新規は A（本番）または B（手動）を使う。

> **★ レイアウト分岐に注意**: A・C は `EDRAgent`（watchdog なし）、B は `EDRWatchdog`（watchdog あり）を生成します。既存端末の更新時は `sc.exe qc <svc>` / `systemctl cat <svc>` で実構成を必ず確認してください（[エージェントインストール手順](エージェントインストール手順.md) の「エージェントバイナリの更新」参照）。

## 2. バイナリ配信（3系統）

| 経路 | 配信元 | 利用者 |
|------|--------|--------|
| **a. `/api/v1/agents/download`** | サーバーイメージ同梱（Dockerfile が `agent-builder` でコンパイル → `/downloads`） | `update.sh`/`update.ps1`、エージェント自己更新(updater)、install.sh |
| b. `/api/v1/installer/download/:os/:arch` | 同上（installer_handler 経由） | 上記インストーラ A |
| c. Caddy 静的 `/downloads/` ← `/srv/downloads` | CI が SCP した artifacts | HTTPS ドメイン経由のアクセス |

- **a/b** はどちらもサーバーイメージにビルド時コンパイルされたバイナリを配信（`AGENT_BIN_DIR=/downloads`、ボリュームマウントなし）。ビルド時に `.sha256` sidecar も生成され、checksum エンドポイントはこれを読む。
- **c** は ci.yml が `artifacts/*` を EC2 の `/srv/downloads` へ SCP→`docker cp` で edr-caddy に投入（[Caddyfile](../deploy/docker/Caddyfile) `root * /srv/downloads`）。**a/b とは別ソースのバイナリを配り得る**ため、理論上は不整合の余地がある（両方とも実働）。
- **注**: 直接 `http://IP:8080`（api コンテナ）アクセスでは a/b のみ有効。Caddy(HTTPS ドメイン)経由では c も有効。

---

## 3. 推奨・指針

- **新規インストール**: 本番はダッシュボードのエンロール（A）、手動は `deploy/install/`（B）。
- **既存端末の更新**: `update.ps1`/`update.sh`（配信 a）。旧型構成は実構成を確認のうえバイナリ差し替え。
- **`agent/deploy/`（C）は使わない**（非推奨・孤立）。
- **統廃合について**: インストーラの `EDRAgent` vs `EDRWatchdog` 統一、配信 a/b/c の集約は、本番エンロール経路（installer_handler）と Caddy 配信に関わる**設計判断**であり、混乱が実害化したときにスコープを切って実施する。安易な削除は本番を壊す恐れがある。
