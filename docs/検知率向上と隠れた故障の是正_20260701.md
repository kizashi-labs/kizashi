# 検知率向上と隠れた故障の是正 — 2026-07-01 セッション総括

「他社EDRと比べて検知率をどう上げるか」への取り組みを、実コード確認と検証EC2の
live 実測に基づいてまとめる。★**核心的な発見＝当製品の検知能力は既に包括的に
構築済みで、検知率を制限していたのは「サイレント故障・未デプロイ・未有効化・
未計測」という運用/整合の問題だった。**

## 1. 一貫パターン: 「新機能の追加」の依頼のたびに"既存だが壊れている検知"が出た

「検知を追加して」という要望を掘るたびに、**追加すべき能力は既にあり、壊れているか
無効化されているだけ**という構図が繰り返し現れた。実コードを確認した結果:

| 「新規」として検討した能力 | 実際の状態 |
|---|---|
| image_load 署名検証(DLLサイドロード) | ✅ 実装済(`imageload_etw.go`, WinVerifyTrust) |
| LSASS / process_access(認証情報窃取 T1003) | ✅ 実装済(`cred_windows.go` + prevention ドライバ ObRegisterCallbacks) |
| AMSI(難読化スクリプト T1027/T1059) | ✅ 実装済(`script_etw.go` が AMSI プロバイダ購読・Content/AppName/hex解除まで) |
| クラウド/ID 検知(Azure AD/CloudTrail) | ✅ 実装済(`cloud_siem`/`cloud_identity`/CSPM/`azure_auth`/`gcp_auth`) |

センサ面(process/network/dns/registry/image_load/script/AMSI/auth/eBPF LSM/
カーネルドライバ W0/LSASS/クラウド)は**包括的に構築済み**。**検知能力に未実装の
空白は残っていない**（実コード確認済み）。

## 2. サイレント故障カタログ(このセッションで発見・修正した12件超)

いずれも「検知は発火するのに実際には機能しない」= 気づかれず検知率を毀損していた。
**故障クラスの大半は同一: ルール/消費側が、テレメトリの出さないフィールドや、
DBに無い列を参照する。**

| # | 故障 | 症状 | 修正 |
|---|---|---|---|
| 1 | IOC `ioc_type` 全 NULL | 23,379件のIOCが照合対象外 | 既修正(migration277) |
| 2 | basename バグ | SigmaHQ 約39ルールが本番で全死 | 既修正(#319) |
| 3 | image_load 署名が常に unknown | dbghelp 正規DLLをFP、image_load curate不可 | 全DLL WinVerifyTrust(#c5073400) |
| 4 | UEBA ベースライン空 | プロセス異常検知が土台不在 | UpdateBaselines 復旧([#342]) |
| 5-9 | 5検知器のアラート保存失敗 | anomaly/heartbeat/risk/remediation が 22P02(非UUID RuleID)/42703(存在しない rule_name・type 列)で保存不可=「検知したのに記録されない」 | RuleID空化+列是正([#345]) |
| 10 | auth `eventName`/`4625` 参照 | 正規化auth eventは `action=failed`。**T1110 ブルートフォース検知が黙って一度も発火せず** | field:action へ([#346]) |
| 11 | network 3ルール camelCase 参照 | RDPブルートフォース/ポートスキャン/内部偵察が `dstPort/srcIp/dstIp`(flatは snake_case)で永久 inert(ever_fired=0で実証) | snake_case へ([#349]/migration291) |
| 12 | ライブ IOCMatcher 死蔵テーブル | `process_events`(不在)/`network_connections`(空)を照合、実データは `events` | retro は events を照合([#347]) |
| 13 | UpdateBaselines 除算/encode 型 | `/$1` の text 推論(42883)+int 7 の text encode 不可 | `$1::float`+`make_interval`([#345]/[#350]) |
| 14 | retro hunter `id` 列 | events の識別列は `event_id`(42703) | event_id へ([#351]) |

### 根本対策: フィールド契約 CI ゲート([#349])
故障の大半は「テレメトリが出さないフィールドを参照するルール = 永久 inert」。
既存の Sigma 向け field-support ゲートを **behavioral(SequenceEngine)ルールへ拡張**
(`BehavioralRuleReferencedFields`/`BehavioralRuleFieldSupportWith`)。SequenceEngine は
Sigma 評価と同じ aliased flat map を見るため `SupportedSigmaFields()` が共通契約集合。
出荷 behavioral ルール全形をコーパス化し、未対応フィールド参照を CI で落とす
(`behavioral_field_contract_test.go`)。**この故障クラスの再発を構造的に防止。**

## 3. 検知 recall/precision の実増(このセッションで実施)

- **precision**: PsExec FP 293→0([#339]) / dbghelp 署名FP根治
- **recall**: ThreatFox +4,169 IOC([#344]) / レトロIOCハンティング=**過去12件の侵害を新規検出**([#347]) / 相関キルチェーン2種([#348]) / inert 5ルール復活(auth×2, network×3) / curate 段階有効化 **+103ルール**(process_creation 80 + 低FP 23、compiled 1049→1152)
- **eBPF既定化**([#337]): Linux 短命プロセス検知の盲点(polling版 8% vs eBPF 53.8%)を解消

## 4. live 検知率 実測(定点観測ベースライン)

検証EC2・eBPF エージェント・本番同等パイプライン貫通の live 採点(`attack-scorer`)。
詳細は [results/live-20260701-linux-scorecard.md](results/live-20260701-linux-scorecard.md)。

| KPI | 値 |
|---|---|
| 可視性率 | **100%** |
| 検知率(Tactic+) | **80%** |
| 解析検知(Technique) | **30%** |
| MTTD | **1s** |

★**計測上の学び**: 技術を2秒間隔で撃つと窓の重なりで 92.3%/15.4%/152s と底上げ・
誤帰属される。50秒間隔に分離すると 80%/30%/1s に収束=各技術が自分の検知器へ
正しく帰属。**定点観測は分離 run を基準にする。**

## 5. 計測中に自己解決したインフラ障害(運用知見)

計測中に agent テレメトリ全断(last_seen 停止・events 0)。切り分け=agent→server
8080/9091/443 全遮断・SSH22のみ疎通・一般internet到達可・DNATカウンタは外部SYN
到達を示す → **AWS SG でなくサーバホストの docker FORWARD チェーン破損**(コンテナ
`up -d` 再作成後、外部→コンテナDNATの戻り経路が drop)。**`systemctl restart docker`
で iptables/nft 再構築し復旧**(AWS変更不要)。検証EC2の egress 全断は「docker FORWARD
破損」か「オーファン隔離 `table inet edr_isolate`」の2系統があり、どちらも agent
テレメトリを黙って全ドロップさせる。

## 6. 結論: 検知率を上げる本当のレバーは「運用規律」

検知能力は完成しており、検知率は**能力不足でなく以下で制限されていた**:

1. **サイレント故障**(作ったのに壊れている) → 12件超修正 + CI ゲートで再発防止
2. **未デプロイ**(端末に届いていない) → デプロイ済
3. **未有効化**(ルールが off) → curate +103
4. **未計測**(数値がない) → live 実測 + ベースライン記録

**残る検知率レバーは全て運用**: process_creation curate ソークの長期反復(残571、要
24-72h FP soak)/より多くの端末へのデプロイ/FP チューニング(FP自動隔離の
`quarantined⟹disabled` 不変条件の破れ是正 等)。いずれも腰を据えた運用ループが適切で、
新規検知コードの追加余地は無い(実コード確認済み)。
