# PR #542 ブランチの棚卸しと、クロスイベント型キルチェーンの取り込み（2026-08-01）

**対象**: `claude/detection-rate-deep-dive-gux8ck`（PR #542、クローズ済み・ブランチは保全）
**状態**: 棚卸し完了。第1弾（クロスイベント型 SequenceEngine + 早期キルチェーン4件）を取り込み

---

## 0. 要約（TL;DR）

長期ブランチ #542 の内容を main へ戻すにあたり全ファイルを棚卸しした。結論は
**「そのまま戻せるものは1つも無い」**。main は merge-base から **244コミット**進んでおり、

- **57ファイルは両方で編集済み** — ブランチ側は244コミット分古く、**再適用すると main が退行する**
- **マイグレーション11件は全番号が衝突**（main 側 315〜325 は別内容で使用済み）
- **うち5件は機能ごと不要** — main の `322_host_integrity_event_type_and_rules.sql` が
  `named_pipe` / `wmi_activity` / `ps_classic` / `device_event` / `resource_usage` の
  event_type をすべて既に追加済み
- キルチェーン6件のうち **4件のみが今 main で機能する**（残り2件は入力センサーが未着地）

長期ブランチを走らせている間に同じ領域が別PRで進むと、**重複と再作業が指数的に増える**。
検知率改善のような広範囲の作業は、テーマ単位で小さく main へ入れ続けるべきだった。

## 2. 【重要】キルチェーン6件のうち4件しか機能しない

ブランチの killchain マイグレーションが要求する `event_type` を、main が実際に生成できるか
全数照合した。**入力が来ないルールを入れても「不活性ルール」になるだけ**で、これは本セッションで
繰り返し直してきた問題そのもの（[検知率向上_20260726_prevention誤ゲートによるeBPF死角.md](検知率向上_20260726_prevention誤ゲートによるeBPF死角.md)）。

| キルチェーン | 必要な event_type | main で生成可能か | 判定 |
|---|---|---|---|
| WMI永続化 + 名前付きパイプ横展開 | `named_pipe`, **`wmi_activity`** | ❌ WMI-Activity ETW センサー未着地 | **保留** |
| LSASS creddump + インジェクション | **`create_remote_thread`**, **`credential_access`** | ~~❌ 両センサーとも未着地~~ → **✅ 誤り。両方着地済み** | **取り込み（365）** |
| フィッシング実行 → 初動偵察 | `process` | ✅ | 取り込み（358） |
| ポートスキャン → 横展開 | `process` | ✅ | 取り込み（359） |
| 資格情報探索 → 持ち出し | `process` | ✅ | 取り込み（360） |
| RDP接続 → 即時偵察 | `network`, `process` | ✅ | 取り込み（361） |

> ### ⚠️ 上表の「未着地」判定は片方が誤りだった（2026-08-02 訂正）
>
> LSASS creddump キルチェーンを保留した根拠「`create_remote_thread` / `credential_access` の

## 3. 第1弾で取り込んだもの

### SequenceEngine のクロスイベント型対応（main に無かった）

staged キルチェーンの各ステージが**異なる `event_type` / `field`** を読めるようにする
`stage_N_event_type` / `stage_N_field` 拡張。これが無いとルール全体で単一フィールドしか
読めず、`process` の commandline → `network` の dstPort のような**イベント型をまたぐ連鎖が
そもそも表現できない**。

適用は merge-base からの差分を抽出して main 現行版へ 3-way で当てており、ブランチ側の
古い内容で main を上書きしていない。

### フィールドサポート監査の追従

`BehavioralRuleReferencedFields` が `stage_N_field` も拾うようにした。これが無いと、
**別フィールドを読むステージ（＝テレメトリに存在しない名前を書いてしまう可能性が最も高い箇所）が
不活性ルール検査をすり抜ける**。

> **意図的に見送ったもの**: ブランチは `field_support.go` の kitchen-sink に `wmi_consumer_type`
> や `ps_classic` 系のフィールドも追加していたが、**対応センサーが main に無い状態でこれを入れると
> 「何も生成しないのにサポート済み」という false green** になる（P5-7 と同じ型）。
> センサー着地時に併せて入れる。
>
> テスト `TestBehavioralRuleFieldSupport_StageOverrideWithoutSensorIsUnsupported` は
> この状態を**明示的に固定**している。WMI センサーが着地すると期待値が反転し、それが
> 保留中のキルチェーンを有効化してよい合図になる。

## 5. 第3弾で「ファイルを戻さなかった」理由（T1110→T1078）

ブランチには `rules/auth_bruteforce_success.go` という**独立した検知器**があった（自前の
5分スライディングウィンドウ、自前のキー体系 `agent|user`、自前の上限 `bfsMaxKeys`）。
これをそのまま戻すのは誤りだった。

main には既に `detection/auth_attack.go`（`AuthAttackScorer`、PR #486）があり、
**まったく同じ失敗タイムスタンプ列を既に保持している**。しかも:

```go
if success {
    if username != "" {
        delete(a.brute, acctKey)   // ← 状態が最も価値を持つ瞬間に捨てていた
    }
    return nil
}
```

つまり**探していたシグナルは、既存コードが意図的に破棄している一行の中にあった**。
別検知器を足せば、同じイベント列に対して**二重のウィンドウ・二重の退避処理・二重の配線**を
持ち、さらに閾値が2箇所（ブランチ版10 / main版6）に分かれて時間とともにずれていく。

そこで**削除の直前に窓内失敗数を数えて発火する**形で既存検知器に統合した。結果:

| | ブランチ版 | 採用した形 |
|---|---|---|
| 状態 | 新規に持つ（重複） | 既存の `bruteState` を再利用 |
| engine.go の配線 | 追加が必要 | **不要**（`Observe` は既に success を受け取っている） |
| 閾値 | 独立した 10 | `bruteMinFails=6` との関係を明示した `bruteSuccessMinFails=10` |
| 窓外失敗の扱い | 剪定あり | 剪定あり（success 経路は従来剪定していなかったため明示的に追加） |

**教訓**: 長期ブランチの成果物は「機能」であって「ファイル」ではない。main が同じ問題領域を
別の形で進めていた場合、ファイル単位で戻すと構造が二重化する。第4弾以降も同じ基準で判定する。

## 6. 第4弾：テスト20本は「無料のカバレッジ」ではなかった

第4弾の前提は「main はカバレッジゲートを上げ続けているので、ブランチのテスト20本を戻せば
そのまま得になる」だった。**これは誤りだった。**

ブランチ固有のテスト18本を main の上に置いて実測した結果:

| 結果 | 件数 | 内訳 |
|---|---|---|
| **コンパイルすら通らない** | 3 | `reassembleFormatString` / `normalizeTechnique` / `applyPreventionEscalation` がいずれも main に無い |
| **コンパイルは通るが FAIL** | 13 | 未着地センサー・未着地ルールの仕様書 |
| **そのまま PASS** | 2 | `alert_dedup_test.go`, `untested_rules_coverage_test.go` の一部 |

つまり **20本の大半は「テスト」ではなく「まだ書かれていない機能の仕様書」**だった。
そのまま戻せば CI が赤くなるだけで、カバレッジは1%も上がらない。**対応する実装と同じPRで
着地させるべきもの**であり、単独で先行させる意味がない。

### ただし、その中に main の実バグが3系統あった

失敗の理由を1本ずつ分類したところ、「ブランチ機能が無いから落ちる」ではなく
**「main の挙動が実際に間違っているから落ちる」**ものが混じっていた。

1. **`pipeline_subjects_test.go` → P5-10（本PRで根治）**
   `AlertPipeline`（本番でビルトインSigmaを評価する唯一の経路）が **4イベント型しか購読していない**。
   `script` / `image_load` / `dns` / `auth` ほか10型のルールが**構造的に到達不能**だった。
   → [技術的負債と改善計画.md P5-10](技術的負債と改善計画.md)

   > **この調査は3週間前に一度行われていた。** PR #469（2026-07-15）が、実機計測で
   > `Process Hollowing`(T1055.012) の恒久未発火を確定させ、**同じ購読フィルタの問題に加えて
   > もう一段（`AlertPipeline` の `SigmaEvaluator` が `rules` テーブルを一切読まない）**を
   > 突き止めていた。それが main に入らないまま3週間滞留し、同じ経路を別角度から再発見したのが本件である。
   > **長期滞留PRのコストが、§0 で書いた「重複と再作業」としてそのまま現れた**——
   > 今回は#542だけの話ではなかった。両者は #582 に統合し、#469 はクローズした。

2. **`certutil_fp_test.go` / `lolbin_condition_fp_test.go` → ルール内容のFP**
   `certutil -decode`（ローカル復号）が「CertUtil Used for File Download」として発火し、
   本来の「Local Base64 Decode」は発火しない。`InstallUtil.exe /u`（通常のアンインストール）と
   定型の `odbcconf CONFIGSYSDSN` も誤検知する。**別PRで是正予定**。

3. **`ftp_upload_fp_test.go` → 取りこぼし**
   `ftp -s:`（スクリプト実行）と `curl -T` / `curl --upload-file` が FTP アップロード規則に
   引っかからない（T1048 の穴）。**別PRで是正予定**。

### 判定

| ファイル | 判定 |
|---|---|
| `alert_dedup_test.go` | ✅ 本PRで取り込み（main の現行挙動を固定） |
| `pipeline_subjects_test.go` | ✅ 本PRで取り込み（**導出関係を固定する形に書き換え**、下記） |
| `certutil_fp` / `lolbin_condition_fp` / `ftp_upload_fp` | 🟡 実バグ。ルール修正と同じPRで |
| `untested_rules_coverage` | 🟡 一部は main に無いビルトインルール（C2既定ポート）の仕様書 |
| WMI / ps_classic / remote_thread / device_event / lsass 系 9本 | ⏸ 第5弾（センサー）と同時に着地 |
| `commandline_normalize_extra` / `killchain_credit` / `prevention_escalation` | ⏸ 対応する実装ごと移植が必要 |

`pipeline_subjects_test.go` はブランチ版の**リテラル配列を突き合わせる形をやめた**。
手書きリストが乖離したことが P5-10 の原因そのものであり、手書きリストをもう1本増やす形の
テストでは同じ乖離を再生産するだけだからで、`eventTypeCategories` からの**導出関係**を固定している。

### 教訓

長期ブランチのテストは、**そのブランチの実装とセットで初めて意味を持つ**。
「テストだけ先に戻す」は、カバレッジ目的には効かず、CI を赤くするか、
（もっと悪いことに）期待値を main の現状に合わせて書き換えれば**バグを仕様として固定する**。
一方で、**落ちたテストの理由を1本ずつ読む**のは非常に価値が高かった——
P5-10 はそれ以外の方法では見つからなかった。
