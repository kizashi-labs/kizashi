# アンインストール保護

エージェントの削除に、端末利用者が持っていない秘密を要求する。

## なぜ必要か

自己防護には二段ある。

| 段 | できること | 本リポジトリの状態 |
|---|---|---|
| 検知 | 消されたことを**後から**知らせる | 実装あり（改ざんテレメトリ／`internal/integrity`） |
| 防止 | そもそも**消させない** | ← 本ドキュメント |

攻撃者が端末のローカル管理者を取った直後にやることはセンサの除去で、ここが通ると
以降の可視性がまるごと消える。検知だけだと「アラートが届いた頃にはもう見えていない」。
中堅以上の商用EDRが例外なくアンインストールパスワードを持っているのはこのため。

## 仕組み

```
管理コンソール                サーバ                     エンドポイント
  パスワード設定  ──POST──▶  PBKDF2 で digest 化
                              （平文は保存しない）
                                    │
                                    ├── heartbeat 応答に salt+digest を添付
                                    ▼
                                              /etc/edr/uninstall.guard (0600)

  uninstall.sh / uninstall.ps1
        │
        └─▶ edr-agent -verify-uninstall  ──▶ ローカルの guard と照合
                  exit 0 = 許可 / 2 = 拒否 / 3 = 判定不能
                                    │
                                    └── best-effort でサーバに通報
```

平文パスワードはサーバにもエージェントにも保存しない。存在するのは、管理者が設定した
瞬間のコンソール上だけ。DB が丸ごと流出してもフリートのアンインストールパスワードは得られない。

## 設計上の判断

### オフラインで完結する

検証はローカルの `uninstall.guard` だけで行い、サーバへの問い合わせをしない。
ネットワークを切るのは無料で、しかもアンインストール試行より**先**に起きる。
サーバ確認を必須にすると、攻撃者はケーブルを抜くだけで保護を無効化できる。

そのため guard は「必要になる前に」端末上に無ければならない。だから配布経路は
専用のフェッチではなく **heartbeat 応答**にした。既に全エージェントが短い間隔で
叩いている経路で、必要な配布特性をそのまま満たす。

### root は突破できる。それでも意味がある

`uninstall.guard` は root/SYSTEM から読める。digest を読み出してオフラインで
総当たりすることも、スクリプトを無視して手でバイナリを消すこともできる。
これは隠蔽の仕組みではないので、そう装わない。

この保護が実際に買っているのは3つ:

1. **正規の削除手順が秘密を要求する**（運用上、これが大半の経路）
2. **digest のオフライン攻撃が高価**（PBKDF2-HMAC-SHA256 600,000 回）
3. **失敗した試行が必ず可視化される**

root にとって本当に不可能にするにはカーネル側（Linux LSM / Windows ドライバ）が要る。
それは別の層で、[実行前防御ビルドの出荷](実行前防御ビルドの出荷.md) の延長線上にある。

### フェイルセーフの向き

| 状況 | 挙動 | 理由 |
|---|---|---|
| guard 未設定 | **許可** | 機能導入前に登録された端末を全部ロックしてしまう。解錠できるパスワードがそもそも存在しない |
| guard が壊れている | **拒否** | ファイルを壊すのはパスワードを当てるより遥かに安い。破損を「未保護」と同義にすると、それが最短の迂回路になる |
| パスワード不一致 | **拒否＋通報** | 本命の検知イベント |
| サーバへの通報が失敗 | **判断は変えない** | 誰にも聞こえない拒否でも、拒否は拒否 |

### 通報経路は認証しない

`POST /api/v1/agents/:id/uninstall-attempt` は JWT を要求しない。通報元は
「まさに削除されようとしているエージェント」で、攻撃者が先に資格情報を無効化している
場合が多い。認証を要求すると、**最も見たい通報だけが届かなくなる**。

代わりに、この経路は追記専用でエージェントの状態を一切変更しない。到達できる者は
一覧にノイズを入れられるが、それ以上のことはできない。この境界は広げてはいけない。

## 運用

### 設定

管理コンソール → 管理 → アンインストール保護（管理者のみ）。12文字以上。
設定後に平文を表示することはできない（サーバが持っていない）。

配布は各端末の次回ハートビート時（既定30秒間隔）。ローテート直後は、まだ配布が
済んでいない端末が直前のパスワードで動く時間帯がある。

### 正規の削除

```bash
sudo EDR_UNINSTALL_PASSWORD='<password>' ./uninstall.sh
```

```powershell
$env:EDR_UNINSTALL_PASSWORD = '<password>'; .\uninstall.ps1
```

パスワードは環境変数か標準入力で渡す。コマンドライン引数にはしない——引数は
鍵導出が走っている間ずっとプロセス一覧から読める。

### 拒否された試行を見る

管理コンソールの同じ画面に一覧がある。`authorised=false` が調査対象で、
「センサを消そうとして SOC の秘密を持っていなかった」という事実そのものが所見になる。

### 保護を解除する

コンソールから解除できるが、**既に配布済みの端末では従来のパスワードが有効なまま**になる。
heartbeat には「忘れろ」という指示が無く、サーバが配布を止めるだけだからである。
即時に解除したい端末は `uninstall.guard` を手で消す。

## 実装の所在

| 層 | 場所 |
|---|---|
| KDF・guard ファイル | `agent/internal/uninstallguard/` |
| CLI（`-verify-uninstall`） | `agent/cmd/agent/uninstallauth.go` |
| 配布（heartbeat） | `agent/internal/heartbeat/`, `server/internal/api/handlers/agents_handler.go` |
| サーバ API・KDF | `server/internal/api/handlers/uninstall_protection_handler.go` |
| 永続化 | `server/internal/store/uninstall_protection.go`, `server/migrations/379_uninstall_protection.sql` |
| スクリプト | `deploy/install/uninstall.sh`, `deploy/install/uninstall.ps1` |
| コンソール | `frontend/app/admin/uninstall-protection/page.tsx` |

サーバとエージェントは**別モジュールで、KDF のコードを共有していない**。ずれると
「正しいパスワードが全端末で拒否される」という形で現場に出るので、両側のテストに
同一の既知応答ベクタ（KAT）を埋めてある。片方でも変えれば、そちら側のテストが赤くなる。
