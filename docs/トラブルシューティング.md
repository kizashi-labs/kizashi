## 1. エージェントの接続問題

### 症状
- ダッシュボード上でエージェントのステータスが `offline` または `unknown` と表示される
- エージェントが登録後もイベントを送信しない
- `agent heartbeat timeout` エラーがサーバーログに記録される

### 原因と対処

**ネットワーク疎通の確認**

エージェントホストからサーバーへの疎通を確認します。

```bash
# エージェント側から実行
curl -v https://<server-host>:8443/api/v1/health

# NATS ポートの疎通確認
nc -zv <server-host> 4222
```

**エージェントサービスの状態確認**

```bash
# Linux (systemd)
sudo systemctl status edr-agent
sudo journalctl -u edr-agent -n 100 --no-pager

# Windows (PowerShell)
Get-Service -Name EDRAgent
sc.exe query EDRAgent
```

**よくあるエラーと対処**

| エラーメッセージ | 原因 | 対処 |
|---|---|---|
| `connection refused: 4222` | NATS サーバー未起動またはポート閉塞 | サーバー側の NATS 起動確認、ファイアウォール設定確認 |
| `TLS certificate verify failed` | 証明書の不一致または期限切れ | サーバー証明書を更新し、エージェントに再配布 |
| `agent token invalid` | 登録トークンの期限切れまたは無効 | 管理コンソールで新しい登録トークンを発行 |
| `heartbeat timeout after 30s` | ネットワーク遅延またはエージェントのフリーズ | エージェントプロセスの再起動 |

**エージェント設定ファイルの確認**

```bash
# Linux
cat /etc/edr/agent.toml

# Windows
type "C:\ProgramData\EDRAgent\config\config.toml"
```

設定ファイルに `server.url` と gRPC用ポート（9091）への疎通が正しく設定されていることを確認してください。

## 2. アラートが発生しない

### 症状
- 不審な操作を行ってもアラートがダッシュボードに表示されない
- `alert` テーブルにレコードが挿入されない
- イベントは収集されているがルール評価が行われていない

### 原因と対処

**Detection Engine の動作確認**

```bash
# detection-engine コンテナのログを確認
docker logs kizashi-detection-engine --tail 100

# ルールのロード状態を確認
curl -s http://localhost:8081/internal/rules/status | jq .
```

**NATS JetStream のコンシューマー確認**

```bash
# NATS CLI で JetStream コンシューマーの状態を確認
nats consumer info EVENTS agent-events-consumer

# メッセージが溜まっていないか確認
nats stream info EVENTS
```

**ルール設定の確認**

管理コンソール → 「検知ルール」から、対象ルールが **有効 (enabled)** になっているか確認してください。ルールが無効化されている場合、そのルールに該当するイベントはアラートを生成しません。

**Suppression rule が catch-all 化していないか確認** (v1.3.9 以前で発生確認済)

検知エンジンは「アラート構築 → suppression matcher で抑制チェック → suppression に当たらなければ DB 保存」の順で処理する。`suppression_rules.conditions` JSONB が `{}` (= 全フィールド空) の rule が存在すると、すべてのアラートを silently drop する catch-all として機能してしまう挙動が v1.3.9 までの実装にあった (commit `beb402d` でガード追加)。本番で「detection は events を消費しているのにアラートが出ない」「特定タイプだけ消える」現象が出たら、以下を確認:

```sql
-- conditions が空のままの suppression rule を列挙
SELECT id, name, hit_count, is_active
FROM suppression_rules
WHERE conditions::text = '{}';
```

`hit_count` が異常に大きい (数千〜数十万) かつ `is_active = true` なら catch-all として全アラートを抹消している可能性が高い。**応急対処**は該当 rule を `is_active = false` に倒してから detection 再起動:

```sql
UPDATE suppression_rules SET is_active = false WHERE conditions::text = '{}';
```
```bash
docker restart kizashi-detection
```

恒久対処はバージョンを `beb402d` 以降に上げること (matcher 側に「全フィールド空なら false」のガードが入っており、データ側に空 rule が残っていても catch-all 化しない)。

**よくあるエラーと対処**

| 状況 | 対処 |
|---|---|
| ルールファイルが読み込まれていない | `docker restart kizashi-detection-engine` を実行後、ログを再確認 |
| NATS コンシューマーが停止している | `nats consumer resume EVENTS agent-events-consumer` で再開 |
| events は届くが alert 0 件 / 特定タイプだけ消える | 上記「Suppression rule が catch-all 化していないか確認」を参照 |
| IOC マッチが 0 件 (DNS C2 ドメイン等で alerts 出ない) | `engine.go` の IOC アラート構築で `RuleID` に文字列 sentinel を渡していると `alerts.rule_id` (uuid 型) で INSERT が silently 失敗する。v1.3.9 以前の `RuleID:"ioc-match"` パターンが該当 (`beb402d` で修正済) |
| PostgreSQL への書き込みエラー | DB 接続設定と `alerts` テーブルの権限を確認 |

## 3. パフォーマンス問題

### 症状
- エージェントホストの CPU 使用率が常時 30% 以上
- サーバー側コンテナのメモリ使用量が増加し続ける (memory leak の疑い)
- ダッシュボードのレスポンスが遅い

### エージェント側の CPU 高負荷

```bash
# エージェントプロセスのリソース使用量を確認 (Linux)
top -p $(pgrep kizashi-agent)

# スキャン除外設定を確認
cat /etc/kizashi-agent/config.yaml | grep -A 20 exclusions
```

エージェントの設定で `scan_interval` が短すぎる場合（例: 1秒未満）、スキャン頻度を下げることで CPU 負荷を軽減できます。

```yaml
# config.yaml の推奨設定
scan_interval: 5s
file_monitor_buffer_size: 1024
excluded_paths:
  - /proc
  - /sys
  - /tmp/swap
```

### サーバー側のメモリ問題

```bash
# 各コンテナのメモリ使用量を確認
docker stats --no-stream

# Go ランタイムの heap 情報を取得 (pprof が有効な場合)
curl http://localhost:8080/debug/pprof/heap > heap.prof
go tool pprof heap.prof
```

### データベースのスロークエリ確認

```sql
-- PostgreSQL スロークエリログの確認
SELECT query, mean_exec_time, calls
FROM pg_stat_statements
ORDER BY mean_exec_time DESC
LIMIT 20;
```

## 4. 認証・ログイン問題

### 症状
- ログイン時に `401 Unauthorized` が返る
- JWT トークンが期限切れになるのが早すぎる
- SSO (SAML/OIDC) 連携が機能しない

### 診断手順

```bash
# API サーバーの認証ログを確認
docker logs kizashi-api-server 2>&1 | grep -i "auth\|jwt\|login"

# JWT の有効期限設定を確認
docker exec kizashi-api-server env | grep JWT
```

**よくあるエラーと対処**

| エラーメッセージ | 原因 | 対処 |
|---|---|---|
| `token signature invalid` | JWT_SECRET の不一致 | 全サービスで同じシークレットが使われているか確認 |
| `token expired` | アクセストークンの期限切れ | フロントエンドのリフレッシュトークン処理を確認 |
| `user not found` | ユーザーが DB に存在しない | 管理コンソールでユーザー作成を確認 |
| `account locked` | ログイン試行回数の超過 | DB で `users.locked_until` フィールドを確認・リセット |

**アカウントのロック解除**

```sql
-- PostgreSQL でロックされたアカウントを解除
UPDATE users SET locked_until = NULL, failed_login_count = 0
WHERE email = 'user@example.com';
```

## 5. データベース接続エラー

### 症状
- サーバー起動時に `failed to connect to database` エラー
- `too many connections` エラーが PostgreSQL ログに記録される
- 突然 API が `500 Internal Server Error` を返すようになる

### 診断コマンド

```bash
# PostgreSQL の接続状況を確認
psql -U kizashi_user -d kizashi_db -c "SELECT count(*) FROM pg_stat_activity;"

# 接続上限の確認
psql -U kizashi_user -d kizashi_db -c "SHOW max_connections;"

# 環境変数の確認
docker exec kizashi-api-server env | grep -i "db\|postgres\|dsn"
```

**よくあるエラーと対処**

| エラーメッセージ | 原因 | 対処 |
|---|---|---|
| `connection refused: 5432` | PostgreSQL 未起動 | `docker compose up -d postgres` で起動 |
| `too many connections` | コネクションプールの枯渇 | `DB_MAX_OPEN_CONNS` 環境変数を調整、または PgBouncer を導入 |
| `password authentication failed` | 認証情報の不一致 | `.env` ファイルの `DB_PASSWORD` を確認 |
| `database does not exist` | DB 未作成 | マイグレーションコマンドを実行: `make db-migrate` |

**コネクションプールの調整**

```bash
# docker-compose.yml または .env ファイルで設定
DB_MAX_OPEN_CONNS=25
DB_MAX_IDLE_CONNS=10
DB_CONN_MAX_LIFETIME=300s
```

## 6. NATS JetStream の問題

### 症状
- エージェントからイベントが届かない
- `nats: no responders available for request` エラー
- JetStream のストリームにメッセージが蓄積し続ける (consumer が遅延)

### 診断コマンド

```bash
# NATS サーバーの状態確認
docker logs kizashi-nats --tail 50

# NATS CLI でサーバー情報を確認
nats server info

# JetStream ストリーム一覧
nats stream list

# ストリームの詳細 (未処理メッセージ数など)
nats stream info EVENTS

# コンシューマーの詳細
nats consumer list EVENTS
nats consumer info EVENTS <consumer-name>
```

**よくあるエラーと対処**

| エラーメッセージ | 原因 | 対処 |
|---|---|---|
| `nats: no responders` | NATS サーバー未起動またはサブジェクト不一致 | NATS コンテナの再起動と設定確認 |
| `maximum consumers limit reached` | コンシューマー数が上限に達した | 不要なコンシューマーを削除: `nats consumer rm` |
| `storage limit exceeded` | JetStream のストレージ上限 | `nats stream edit` でストレージ上限を拡張 |
| `stream not found` | ストリームが削除または未作成 | アプリケーションを再起動してストリームを再作成 |

**JetStream ストリームのリセット（注意: データ消失）**

```bash
# 緊急時のみ実行。全メッセージが削除されます。
nats stream purge EVENTS
```

## 7. Docker/コンテナ起動問題

### 症状
- `docker compose up` 実行時にコンテナが起動しない
- コンテナが起動後すぐに `Exit 1` または `Exit 137` で終了する
- ヘルスチェックが `unhealthy` になる

### 診断コマンド

```bash
# 全コンテナの状態確認
docker compose ps

# 停止したコンテナのログを確認
docker compose logs --tail 100 <service-name>

# コンテナの終了コードと原因を確認
docker inspect <container-id> | jq '.[0].State'

# ヘルスチェックの詳細
docker inspect <container-id> | jq '.[0].State.Health'
```

**Exit コードの意味**

| Exit コード | 原因 | 対処 |
|---|---|---|
| `Exit 1` | アプリケーションエラー（設定不備など） | コンテナログで詳細を確認 |
| `Exit 137` | OOM Killer によるメモリ不足強制終了 | `docker stats` でメモリ使用量を確認し、制限を引き上げ |
| `Exit 143` | `SIGTERM` による正常シャットダウン（通常は問題なし） | 依存サービスの起動順序を確認 |

**依存関係の起動順序**

Kizashi の推奨起動順序:

```
1. postgres
2. nats
3. api-server
4. detection-engine
5. frontend
```

`docker-compose.yml` の `depends_on` と `healthcheck` が正しく設定されているか確認してください。

**ボリュームの権限エラー**

```bash
# ボリュームの権限を修正
docker compose down
sudo chown -R 1000:1000 ./data/
docker compose up -d
```

## 8. エンドポイント情報が正しく表示されない

### 症状A: OS版数が「Windows」または空欄のまま

エンドポイント一覧でOS列が空白、または "Windows" のみ表示される。

**原因と対処**

1. **エージェントバイナリが古い** — v0.1.157dc77 より前のバイナリは `os_version` をgRPC経由で送信しない。
   最新バイナリに更新してエージェントを再起動してください（下記「エージェントの手動更新」参照）。

2. **DBの `os_version` が空のまま** — エージェント更新後も表示されない場合、DBを直接確認します：
   ```bash
   docker exec kizashi-postgres psql -U edr -d edrplatform \
     -c "SELECT hostname, os_version, last_seen FROM agents ORDER BY last_seen DESC LIMIT 10;"
   ```
   `last_seen` が更新されているのに `os_version` が空の場合、サービスが古いままです。
   ingestionサービスを再起動してください：
   ```bash
   docker compose restart kizashi-ingestion
   ```

### 症状B: エンドポイント一覧に重複エージェントが表示される

同一マシンを複数回エンロールした場合などに発生します。
削除したいエージェント行の右端にあるゴミ箱アイコンをクリックして削除できます。

---

### エージェントの手動更新（Windows）

```powershell
# 1. サービス停止
sc.exe stop EDRAgent

# 2. 新しいバイナリをダウンロード（バイナリパスはsc.exe qc EDRAgentで確認）
Invoke-WebRequest -Uri "http://【サーバーIP】:8080/api/v1/agents/download?platform=windows&arch=amd64" `
  -OutFile "C:\ProgramData\EDRAgent\bin\edr-agent.exe"

# 3. サービス起動
sc.exe start EDRAgent

# 4. 現在のバイナリパスの確認（必要な場合）
sc.exe qc EDRAgent
```

**注意**: バイナリの実際のパスはインストール方法によって異なります。
`sc.exe qc EDRAgent` の `BINARY_PATH_NAME` で確認してください。

## 9. MDM（モバイルデバイス管理）の問題

### 症状A: コマンドが `sent` のまま終わらない

MDM コマンド（ロック / ワイプ / 紛失モード など）がキュー履歴で `sent` のまま長時間停留する状況。

#### 原因と対処

| プラットフォーム | 典型原因 | 対処 |
|---|---|---|
| Android | 端末がオフライン / 機内モード → Google FCM 到達失敗 | 端末の通信復帰を待つ。自動更新は 30 秒ごとに AMAPI を poll しているため、到達後は自動で `acknowledged` になる |
| Android | AMAPI 側で operation が error 終了 | コマンド履歴の「更新」ボタンを押して強制 poll → `failed` に遷移すると理由が DB の `result.amapi_poll_error` に保存される |
| iOS | 端末が次回 `/ios/server` にアクセスするまで未応答 | iOS は device-driven reconcile のため server-side poll は no-op。端末のネットワーク復帰を待つしかない |
| iOS | APNs push が未送信 | コマンド詳細の「Push」ボタンから APNs wake を手動実行 |

**ヒント**: ヘッダーの「自動更新 N 件」バッジは `sent` 行数と一致します。0 件にならない場合、上記対処を試してください。

### 症状B: 「Re-evaluate」ボタンを押しても compliance status が変わらない

`/admin/mobile-device-management` のデバイス行「Re-evaluate」ボタンは、3 つの signal 列（`jailbroken` / `encryption_enabled` / `screen_lock_enabled`）から status を自動計算します。

#### 判定ルール

```
jailbroken == true  OR
encryption_enabled == false  OR
screen_lock_enabled == false
  → non_compliant
それ以外
  → compliant
```

status が期待と違う場合、signal 列の値自体が正しく取り込まれていない可能性があります。以下を確認してください：

- **Android**: AMAPI の `devicePolicyPolicy.encryptionStatus` / `strongAuthRequired` が Sync で `mobile_devices.metadata` に書き込まれているか
- **iOS**: `/ios/checkin` の DeviceInformation クエリで返る `PasscodePresent` / `DataEncryptionEnabled` が取れているか

signal 列自体を手動 override したい場合は、API 経由で `PATCH /api/v1/admin/mobile-devices/:id/compliance` に `{"compliance_status":"compliant"}` のように明示値を送ってください（UI からの空 body PATCH は自動再評価として扱われます）。

### 症状C: 「MDM資格情報がまもなく期限切れ」アラートが出た

ABM トークン / AE SA キー / APNs p12 のいずれかが期限 30 日を切るとバックグラウンドスケジューラが `/alerts` にアラートを作成します（残り 30 日 = severity 3 / 7 日 = severity 7 / 1 日 = severity 9）。

#### 対処

| 統合タイプ | 更新手順 |
|---|---|
| APNs Push Certificate | Apple Developer Portal で新しい p12 を発行 → **統合設定** → APNs カード → 「アップロード」 |
| Apple Business Manager | ABM 管理画面で Server Token を再発行 → ABM カード → 「アップロード」 |

## 12. Windows プロセスチェーン検知が発火しない

### 症状
- T1547.001（PowerShell → reg.exe）、T1055（explorer → cmd → PowerShell）など、短命プロセスを含むチェーンルールが一切アラートを生成しない
- detection ログに `chain analysis` は出力されるが、`chain=reg.exe<-powershell.exe` のように 2 ホップ以上がつながらない
- `ppid=0` で reg.exe / certutil.exe 等が記録されている
- `cache_size` が 3〜6 程度で停滞している

---

### 原因 A: Toolhelp32 の PPID=0 問題（v1.3.10 以前）

Windows の `CreateToolhelp32Snapshot` / `Process32NextW` は、スナップショット取得時にプロセスが終了しかけている場合 `Th32ParentProcessID=0` を返す。reg.exe・certutil.exe のような LOLBin は実行時間が 100ms〜500ms と短いため、500ms ポーリング間隔と競合し PPID=0 のまま記録されやすい。PPID=0 ではチェーンをさかのぼれないため、ProcessChainEngine のキャッシュ上で祖先リンクが切れる。

**ログで確認**

```bash
docker compose logs detection --tail 200 | grep "chain analysis" | grep "reg.exe\|certutil\|vssadmin"
```

`ppid=0` が出ていれば PPID 解決に失敗している。

**修正内容（v1.3.10〜v1.3.12）**

| バージョン | 修正内容 |
|---|---|
| v1.3.10 | `buildEvent()` 内で `PPID=0` のとき `NtQueryInformationProcess` (ProcessBasicInformation, offset 40) で PPID を再取得 |
| v1.3.11 | `takeSnapshot()` ループ内でも同様の PPID フォールバックを追加（スナップショット段階での解決） |
| v1.3.12 | ポーリングループで `ppid が 0→non-0 に変化したプロセス` を再 emit し、プロセスがまだ生きているうちに cmdline 取得できるウィンドウを確保 |

**対処**: エージェントを v1.3.12 以降に更新してください。

```powershell
# GitHub Releases から最新バイナリを取得する場合
$headers = @{ Authorization = "token <GITHUB_PAT>"; Accept = "application/vnd.github.v3+json" }
$release = Invoke-RestMethod "https://api.github.com/repos/<org>/edr-platform/releases/latest" -Headers $headers
$asset = $release.assets | Where-Object { $_.name -eq "edr-agent-windows-amd64.exe" }
$dlHeaders = @{ Authorization = "token <GITHUB_PAT>"; Accept = "application/octet-stream" }
Invoke-WebRequest $asset.url -Headers $dlHeaders -OutFile "C:\ProgramData\EDRAgent\bin\edr-agent.exe"

sc.exe stop EDRAgent
sc.exe start EDRAgent
```

---

### 原因 B: Detection サービス再起動によるシード欠損

エージェントは起動時のみ既存の全プロセスを "existing" イベントとして emit し、サーバー側の ProcessChainEngine キャッシュを温める（seeding）。Detection サービスがエージェントの seeding 完了後に再起動すると、キャッシュが空のまま稼働し始めるため、既存プロセスの祖先チェーンが切れる。

**症状の確認**

```bash
# detection ログで cache_size を確認 — 起動後も一桁のまま変化しない
docker compose logs detection --tail 300 | grep "chain analysis" | grep "cache_size=[0-9],"
```

**対処**

detection サービスが健全であることを確認してから、対象 Windows エンドポイントの EDRAgent を再起動する:

```powershell
# Windows エンドポイントで実行
sc.exe stop EDRAgent
sc.exe start EDRAgent
```

再起動後 30 秒以内に `cache_size` が増加し始めることを確認してください。エージェントが持つプロセス数（通常 50〜200 件）が cache に流れ込みます。

```bash
# detection ログで seeding が届いているか確認
docker compose logs detection --tail 100 | grep "existing" | head -10
```

---

### 原因 C: `alerts.rule_id` UUID 型エラー（v1.3.11 以前）

`alerts.rule_id` カラムは PostgreSQL の `uuid` 型。v1.3.11 以前の ML チェーン検知は `RuleID` フィールドに `"ml-process-chain-chain-T1547.001"` のような文字列を渡しており、`SQLSTATE 22P02` (invalid input syntax for type uuid) でサイレントに INSERT が失敗していた。detection ログにチェーン検知ログは出るのにアラートが DB に残らない場合に疑う。

**確認方法**

```bash
docker compose logs detection 2>&1 | grep "22P02\|invalid input syntax for type uuid"
```

**対処（v1.3.12 以降修正済み）**

チェーンルール検知の `RuleID` フィールドを空にし、ルール識別情報は `RuleName` / `Description` に格納するよう修正。バージョンを v1.3.12 以降に上げてください。

---

### 総合チェックリスト

```bash
# 1. エージェントバージョン確認 (Windows)
# sc.exe query EDRAgent → BinaryPathName から確認、または GitHub Releases タグと照合

# 2. detection ログで PPID 状況を確認
docker compose logs detection --tail 500 | grep "chain analysis" | grep -E "reg\.exe|certutil|vssadmin" | tail -20

# 3. UUID エラーが出ていないか確認
docker compose logs detection 2>&1 | grep "22P02" | wc -l

# 4. alerts テーブルにチェーン検知が入っているか確認
docker exec <postgres-container> psql -U edr -d edrplatform \
  -c "SELECT rule_name, severity, created_at FROM alerts WHERE description LIKE '%chain%' ORDER BY created_at DESC LIMIT 10;"
```

## 13. 検疫ファイル機能の問題

### 症状

- エージェントが検疫を完了したにもかかわらず、管理コンソールの「検疫ファイル」一覧にレコードが表示されない
- エージェントログに `reportQuarantineToServer: server returned 500` が記録される
- `POST /api/v1/agents/:id/quarantine-result` が `{"error": "検疫レコードの保存に失敗しました"}` を返す

### 原因 A: `alert_id` FK 違反（v1.3.12 以前）

検疫コマンドを発行した時点では有効だったアラートが、エージェントの検疫完了報告が届くまでの間に削除されると、`quarantined_files.alert_id` の外部キー制約違反 (`SQLSTATE 23503`) が発生して INSERT が失敗する。

**確認方法**

```bash
# kizashi-api ログで FK 違反を確認
docker logs kizashi-api 2>&1 | grep "quarantine_files_alert_id_fkey\|23503"
```

**対処（v1.3.12 以降修正済み）**

`server/internal/store/quarantine.go` の `Record()` が alert_id FK 失敗時に `alert_id = NULL` で自動リトライするよう修正済み。サーバーを v1.3.12 以降に更新してください:

```bash
cd ~/edr-platform && git pull
docker compose up -d --build --no-deps api
```

更新後は `alert_id` が NULL のレコードとして保存されます（検疫自体は成功、アラートとのリンクのみ失われます）。

**運用ログでの確認**

v1.3.12 以降では、alert_id フォールバックが発生した際に以下の Warn ログが出力されます:

```
WARN quarantine.Record: alert_id FK violation; retrying with NULL agent=<id> alert_id=<uuid>
```

---

### 原因 B: agent_id が存在しない

エージェントが削除・再登録されて UUID が変わった場合、旧 UUID では `agents.id` FK も違反となり INSERT が失敗します。

**確認方法**

```bash
# エージェントが DB に存在するか確認
docker exec kizashi-postgres psql -U edr -d edrplatform \
  -c "SELECT id, hostname, last_seen FROM agents WHERE id = '<agent-uuid>';"
```

**対処**

エージェントを正しい UUID で再登録するか、エージェント側の設定ファイル (`agent.toml` の `id` フィールド) を DB の UUID と一致させてください。Linux では:

```bash
cat /etc/edr-agent/agent.toml | grep "^id"
```

---

### 原因 C: `--build` なしで API コンテナを再起動した

ソースを修正して `git pull` しても、`docker compose up -d api`（`--build` なし）では既存イメージが再利用され、コード変更が反映されません。

**対処**

```bash
# 必ず --build を付ける
cd ~/edr-platform
docker compose up -d --build --no-deps api
```

---

### 検疫レコードが一覧に出るが「復元」ボタンが機能しない

エージェント側の検疫IDが記録されていない古いレコード（`agent_quarantine_id = NULL`）は、サーバーからの復元コマンドを発行できません。

```bash
# 該当レコードの確認
docker exec kizashi-postgres psql -U edr -d edrplatform \
  -c "SELECT id, original_path, agent_quarantine_id FROM quarantined_files WHERE agent_quarantine_id IS NULL;"
```

`agent_quarantine_id` が NULL のレコードは、エンドポイント上で手動復元が必要です。

---

### 原因 D: シンボリックリンクの検疫が拒否される（v1.3.49 以降）

**v1.3.49 以降の仕様変更**: 検疫対象がシンボリックリンクの場合、エージェントはファイルを開いた時点でエラーを返し処理を中断します。

**エージェントログ**

```
ERROR ファイル隔離に失敗しました path=<path> error="ファイルオープン失敗: シンボリックリンクの操作は許可されていません: <path>"
```

**対処**

シンボリックリンクではなく実体ファイルのパスを指定してください。シンボリックリンク先のパスは以下で確認できます:

```bash
readlink -f <symlink_path>
```

---

### 原因 E: 検疫ファイルの権限設定に失敗した（非致命的）

ファイルの移動は成功しているが権限変更が失敗した場合、以下の警告が出力されます。検疫自体は完了しています。

```
WARN 検疫ファイルのパーミッション設定失敗 path=<quarantine_path> error=<error>
```

ファイルシステムが `chmod` を制限している場合（一部のコンテナ環境）に発生します。検疫ディレクトリ自体のパーミッション（0700）で保護されているため、通常は問題ありません。

## 14. グローバル検索・コマンドパレットの問題

### 症状A: 日本語（カタカナ）で検索しても結果が出ない

`Ctrl+K` のコマンドパレットや `/search` ページで「アラート」「インシデント」などカタカナを入力しても、ナビゲーション候補が表示されず「結果が見つかりません」となる。

#### 原因

**v1.3.20 未満**のバージョンに以下の2つの問題が存在していた。

1. **ページ候補が英語ラベルのみだった** — コマンドパレット（`Ctrl+K`）の内部候補リストが英語ラベル（`"Alerts"`, `"Incidents"` など）のみで構成されており、日本語クエリに一致しなかった。

#### 対処

**v1.3.20 以降では修正済み**のため、コンテナを最新版に更新するだけで解消します。

```bash
docker compose up -d --build --no-deps frontend
```

#### 手動診断（古いバージョンが稼働中の場合）

ブラウザのコンソールで入力値の確認：

```javascript
// コマンドパレット（Ctrl+K）を開いた状態で実行
```

### 症状B: エージェント検索で 500 エラーが発生する

エンドポイント一覧 (`/endpoints`) やグローバル検索で IP アドレスを含む検索をすると、サーバーが `500 Internal Server Error` を返す。

```
GET /api/v1/agents?search=192.168.1.1&limit=5  →  500
{"error":"エージェント一覧の取得に失敗しました"}
```

#### 原因

**v1.3.20 未満**のバージョンで、`agents` テーブルの `ip_addresses` カラムが `inet[]` 型（PostgreSQL のネットワークアドレス型の配列）であるにもかかわらず、`ILIKE` 演算子を直接適用しようとしていた。`inet` 型には `ILIKE` が使えないためエラーとなっていた。

```sql
-- NG（旧コード）
WHERE ip ILIKE $1          -- ip は inet 型 → エラー

-- OK（修正後）
WHERE ip::text ILIKE $1    -- text にキャストしてから比較
```

#### 対処

**v1.3.20 以降では修正済み**。API コンテナを更新してください。


```bash

  "https://<server>/api/v1/agents?search=192.168&limit=5" | jq .total
```

## 16. コンプライアンスページのスコアが0%になる

### 症状

`/compliance` ページを開くと MITRE ATT&CK スコアが 0% と表示される（CIS/NIST/ISO は正常）。

### 原因

**v1.3.30 未満**のバージョンで、コンプライアンスハンドラーが存在しないカラム `mitre_tags` を参照していた（正しいカラム名は `mitre_technique`）。クエリがエラーになり常に 0 件として計算されていた。

### 対処

**v1.3.30 以降では修正済み**。APIを最新版に更新してください：

```bash
cd ~/edr-platform && git pull origin main && docker compose up -d --build --no-deps api
```

### MITRE スコアの見方

修正後、MITRE ATT&CK スコアは以下の基準で算出されます：

- **0%**: アラートが0件、またはMITREテクニックが付与されていない
- **37%**: 約15種類のMITREテクニックを検知（例: T1059, T1003 など）
- **100%**: 40種類以上のMITREテクニックを検知

スコアはエンドポイントで検知されたアラートのMITREテクニックIDの種類数で決まります。アラートが増えるほどスコアが上昇します。

## 17. SIEMへの転送が意図しないアラートを含む

### 症状

- 特定のサーバーのアラートのみをSIEMに転送したいが、全端末のアラートが転送される
- 特定のルールのアラートだけをSIEMに送りたい
- MITRE ATT&CKの特定テクニックのみを転送したい

### 対処

**v1.3.29 以降**で詳細フィルターが利用可能です。`/settings/siem` の各SIEMターゲット設定に以下のフィルター欄があります：

| フィルター | 設定例 |
|---|---|
| ルール名フィルター | `Mimikatz_Strings, PowerShell_Empire` |
| 端末ホスト名フィルター | `server01, db-primary` |
| MITREテクニックフィルター | `T1059, T1003, T1078` |

**重要**: 空欄のままにすると全件転送します。ホワイトリスト方式のため、入力した値に**一致するもののみ**転送されます。

フィルター設定後は「テスト送信」で動作を確認してください。

## 23. v1.3.49 変更点に関するトラブルシューティング

### 自動隔離が期待した severity で発火しない

自動隔離は「ルールの `auto_isolate=true`」かつ「アラートの severity が閾値以上」の両方を満たした場合に実行されます。

閾値は `AUTO_ISOLATE_MIN_SEVERITY` 環境変数で制御できます（デフォルト: 9、有効範囲: 1〜10）。

```env
# docker-compose.yml または .env
AUTO_ISOLATE_MIN_SEVERITY=7   # severity 7 以上で自動隔離
```

設定変更後は detection コンテナを再起動してください:

```bash
docker compose restart detection
```

> **注意**: 閾値を下げると自動隔離の発火頻度が上がります。誤検知による意図しない隔離を防ぐため、まず低閾値を検証環境でテストすることを推奨します。

---

### アラートAPI: `severity=0` で 400 Bad Request が返る

**v1.3.49 以降の仕様変更**: `GET /api/v1/alerts?severity=0` は 400 を返します。

```json
{"error": "severityは1〜10の整数で指定してください"}
```

`severity` / `severity_max` パラメータを省略すると全件取得（フィルタなし）になります。フィルタを使用する場合は `1〜10` を指定してください。

---

### ネットワーク隔離解除ログに警告が出る

隔離を一度も実行していないエンドポイントで解除コマンドを発行した場合、以下のログが出ることがあります（**エラーではありません**）:

```
WARN iptables解除コマンド失敗 args=[iptables -F] error=...
WARN nftables解除コマンド失敗 table=edr_isolate error=...
```

`nft delete table` が `"No such file"` を返した場合や `pfctl -d` が `"pf not enabled"` を返した場合はエラーとして記録されず無視されます。上記ログが出ても隔離ルールが適用されていない状態であれば正常です。

## 24. スキャン・コマンド配信・エージェント更新の問題

### フルスキャンの結果が返らない / スキャンが永久に「実行中」

**症状:** エンドポイント詳細でフルスキャンを実行しても「対応アクション履歴」に結果（`scan_result`）が記録されず、行が「実行中」のまま。エージェントは online 表示。隔離・プロセス終了など他のコマンドも届かない。

**原因:** エージェントのコマンド受信用 gRPC EventStream が「半開き」状態になり、コマンドが永久に不達になる既知バグ（修正済み）。サーバー再起動時にストリームのみ EOF クローズされ、HTTP/2 接続は維持されたまま再接続がトリガーされないケース。エージェントログに `"stream send failed, buffering","error":"EOF"` が 0.5 秒ごとに無限ループで出力されるのが典型的な兆候。heartbeat は別経路（REST）のため online 表示は維持される。

**即時復旧:** エージェントサービスを再起動すると、死んだストリームが破棄されて再接続し、滞留コマンドが配信されます。

```powershell
# Windows（サービス名は実構成に合わせる。旧型は EDRAgent、新型は EDRWatchdog）
Restart-Service EDRAgent
```
```bash
# Linux
sudo systemctl restart edr-agent
```

**恒久対策:** 再接続バグ修正を含む新バイナリへ更新（[エージェントインストール手順](エージェントインストール手順.md) の「エージェントバイナリの更新」参照）。更新後、ログの `stream send failed, buffering`（EOF）ループが消え、`connected to EDR server` が出れば解消です。

---

### スキャン履歴が「タイムアウト」と表示される

スキャン中にエージェントが再起動（例: バイナリ更新）すると実行中スキャンは消滅し、結果が返りません。ペアリング窓（10分）を超えても結果が無いスキャンは「実行中」のまま残らず「**タイムアウト**」と表示されます。これは取り残された記録で、停止ボタンの対象ではありません（停止コマンドを送っても対応する実行中スキャンが無いため何も起きません）。新しくフルスキャンを実行し直せば正常に結果が返ります。

---

### エージェントログに `[updater] update-check: server returned 401`

**症状:** エージェントが起動時・1時間ごとに以下の WARN を出力する。

```json
{"level":"WARN","msg":"[updater] バージョンチェックに失敗しました","error":"update-check: server returned 401"}
```

**原因:** `GET /api/v1/agents/:id/update-check` はエージェントが JWT なしで呼ぶ公開エンドポイントだが、過去に認証必須グループへ誤登録されていたため 401 を返していた（修正済み）。

**対処:** サーバーを修正版イメージへ更新すれば解消します。確認方法:

```bash
# サーバー上または到達可能な場所から（JWTなし）
curl -s -w "\nHTTP %{http_code}\n" "http://【サーバーIP】:8080/api/v1/agents/【任意のagent-id】/update-check?version=0.1.0"
# 期待: HTTP 200 / {"up_to_date":true}（AGENT_LATEST_* 未設定時）
```

> **補足（自動更新の広告について）:** サーバーの `AGENT_LATEST_VERSION` が設定されていると update-check は更新情報を返します。**現在は update-check が実配信バイナリから checksum を動的算出するため、`AGENT_LATEST_CHECKSUM` のドリフトによる `checksum mismatch` は解消済み**です（以前は静的 checksum が `docker.yml` の再ビルドでずれ、`[updater] アップデートの適用に失敗しました ... checksum mismatch` を起こしていました）。なお、エージェントが watchdog 無し構成の場合は更新の適用自体が完結しないため、自動更新を使わない環境では `AGENT_LATEST_*` を空にしてください（update-check が `{"up_to_date":true}` を返す）。詳細は [運用ランブック](運用ランブック.md) のエージェント更新手順を参照。

### 更新後に「エージェントバイナリの改ざんを検知しました」

**症状:** バイナリ手動更新後、起動時に以下の ERROR が出る（起動自体は継続）。

```json
{"level":"ERROR","msg":"エージェントバイナリの改ざんを検知しました","stored_hash":"...","current_hash":"..."}
{"level":"ERROR","msg":"バイナリ整合性チェックに失敗しました"}
```

**原因:** エージェントは自身のバイナリ SHA-256 を `<config-dir>/agent.sha256` の保存値と照合します。バイナリだけ差し替えて保存ハッシュを更新しなかったため、改ざんと誤検知しています。放置するとサーバーへ偽の改ざんアラートを上げる恐れがあります。

**対処:** 保存ハッシュを新バイナリの値（bare hex・改行なし）へ更新して再起動します。更新スクリプト（`update.ps1` / `update.sh`）はこれを自動で行います。手動の場合:

```bash
# Linux 例
sudo sh -c 'printf "%s" "$(sha256sum /opt/edr-agent/edr-agent | awk "{print \$1}")" > /etc/edr-agent/agent.sha256'
sudo systemctl restart edr-agent
```
