# 疑似マルウェア検知 E2E 検証計画書

本書は Kizashi プラットフォームの検知・対応機能を実エンドポイントで End-to-End 検証するための手順書である。すべてのテストは **隔離された検証用 VM** で実施すること。本番ホストや業務端末では絶対に実行しないこと。

---

## 0. 前提条件

### テスト VM の要件

| OS | 推奨バージョン | 用途 |
|----|---------------|------|
| Windows 10/11 Pro | 22H2 以降 | プロセス/レジストリ/ETW 検知テスト |
| Ubuntu 22.04 LTS | - | proc/eBPF 検知テスト |
| macOS 14+ | - | オプション (低優先度) |

### 事前作業

1. **Windows Defender を無効化** (EDR と競合するため)
   ```powershell
   Set-MpPreference -DisableRealtimeMonitoring $true
   ```
2. **エージェント配布**: `https://203-0-113-10.nip.io/admin/enrollment` から enrollment token を発行し、エージェントインストーラを VM に転送してインストール
3. **管理 UI 監視準備**:
   - アラート画面: https://203-0-113-10.nip.io/alerts
   - イベントログ: https://203-0-113-10.nip.io/events
   - インシデント: https://203-0-113-10.nip.io/incidents
   - ダッシュボード: https://203-0-113-10.nip.io/dashboard

### 合格基準の定義

各シナリオについて以下 4 観点を確認する:

1. **検知**: アラートが管理 UI に出現 (severity, name, host)
2. **可視性**: イベントログに関連プロセス/ファイル/ネットワーク情報が記録
3. **MITRE マッピング**: ATT&CK technique ID が正しく付与されている
4. **対応**: Playbook/Auto-remediation/手動アクションが機能 (isolate/quarantine/kill)

## 1. シナリオ A: ファイルベース検知 (YARA) — EICAR

### 目的
- YARA scanner の動作確認
- ファイルスキャン API (`CmdScan`) の確認
- ファイルハッシュ IOC ブロックリストの照合確認

### 手順

#### A-1. EICAR テストファイル配置 (Windows)

```powershell
# 管理者権限 PowerShell で実行
$eicar = 'X5O!P%@AP[4\PZX54(P^)7CC)7}$EICAR-STANDARD-ANTIVIRUS-TEST-FILE!$H+H*'
New-Item -ItemType Directory -Force -Path C:\MalwareTest
$eicar | Out-File -NoNewline -Encoding ASCII -FilePath C:\MalwareTest\eicar.com

# 公式 EICAR もダウンロード
Invoke-WebRequest -Uri 'https://secure.eicar.org/eicar.com.txt' -OutFile C:\MalwareTest\eicar.com.txt
```

#### A-2. EICAR テストファイル配置 (Linux)

```bash
# 非 root でも可
mkdir -p ~/malware-test
cat > ~/malware-test/eicar.com <<'EOF'
X5O!P%@AP[4\PZX54(P^)7CC)7}$EICAR-STANDARD-ANTIVIRUS-TEST-FILE!$H+H*
EOF
curl -o ~/malware-test/eicar.com.txt https://secure.eicar.org/eicar.com.txt
```

#### A-3. 管理 UI からスキャン実行

1. `/agents` ページで対象エージェントを選択
2. 「アクション」→「YARAスキャン」→ ターゲットパス指定: `C:\MalwareTest` or `~/malware-test`
3. 実行

#### A-4. 期待結果

- [ ] `/alerts` に `EICAR_Test` / `Malware_Test_Content` ルール発火のアラート出現
- [ ] 重要度: `HIGH` 以上
- [ ] アラート詳細にファイルパス、ハッシュ、ルール名記録
- [ ] `/admin/file-hashes` のブロックリスト (`44d88612fea8a8f36de82e1278abb02f`) と MD5 照合
- [ ] ファイル検疫 API 実行 → ファイル移動確認

## 2. シナリオ B: プロセス連鎖検知 (Sigma + Lineage)

### 目的
- Sigma ルール発火 (Suspicious PowerShell / LOLBins)
- プロセスツリー相関 (17 MITRE ATT&CK ルール)

### 手順

#### B-1. エンコード PowerShell コマンド

```powershell
# T1059.001: Command and Scripting Interpreter: PowerShell
$cmd = 'Get-Process | Select-Object -First 5'
$enc = [Convert]::ToBase64String([Text.Encoding]::Unicode.GetBytes($cmd))
cmd.exe /c "powershell.exe -NoProfile -EncodedCommand $enc"
```

#### B-2. LOLBins 利用 (Mshta)

```cmd
REM T1218.005: Signed Binary Proxy Execution — Mshta
mshta.exe javascript:alert('test');close();
```

#### B-3. レジストリ永続化

```powershell
# T1547.001: Registry Run Keys
New-ItemProperty -Path 'HKCU:\Software\Microsoft\Windows\CurrentVersion\Run' `
  -Name 'KizashiTest' -Value 'notepad.exe' -PropertyType String -Force
```

#### B-4. 期待結果

- [ ] B-1 → Sigma: `Encoded PowerShell Command` 検知
- [ ] B-1 → Process lineage: `cmd.exe → powershell.exe -enc` が相関エンジンで繋がる
- [ ] B-2 → MITRE T1218.005 マッピング付きアラート
- [ ] B-3 → Registry monitor + T1547.001 アラート
- [ ] `/incidents` で自動インシデント化されるか (correlation rule 発火で複数アラート束ね)

## 3. シナリオ C: ランサムウェア振る舞い

### 目的

- 大量ファイル操作の UEBA 検知

### 手順

#### C-1. 安全な暗号化シミュレーション

```powershell
# 100 個のダミーファイル作成 → 全て拡張子変更
$testDir = "C:\MalwareTest\ransomware-sim"
New-Item -ItemType Directory -Force -Path $testDir
1..100 | ForEach-Object {
  "dummy content $_" | Out-File "$testDir\file$_.txt"
}
# 30 秒以内に全部を .locked に rename
Start-Sleep -Seconds 1
Get-ChildItem $testDir -Filter *.txt | Rename-Item -NewName { $_.Name + ".locked" }
```

#### C-2. 期待結果

- [ ] Behavioral Baseline が「異常な拡張子変更率」を検知
- [ ] Auto-remediation rule 発火 → エージェント自動隔離 (network isolation)
- [ ] `/admin/xdr` ダッシュボードに cross-domain 相関イベント

## 9. 危険行為禁止事項

以下は**検証環境であっても絶対に実行しないこと**:

- 実マルウェア検体のダウンロード・実行 (VirusTotal/MalwareBazaar サンプルも含む)
- 外部ネットワークへの攻撃通信 (DoS, スキャン, brute-force)
- 他人の管理するシステムへの接続テスト
- ランサムウェア本物 / wiper 系本物の実行
- 認証情報 dump ツール本物 (mimikatz.exe本体) の検証 VM 外への持ち出し

## 11. 検証結果記録 (Linux)

検証環境: EC2 endpoint `ip-10-0-15-11.ap-northeast-1.compute.internal` (RHEL 10.1 Coughlan)、agent 9ed28fec-3e61-4f7f-8626-d1a782e6ae9c、サーバ `https://203-0-113-10.nip.io`。

### §1 シナリオ A: ファイルベース検知 (EICAR) — Linux

- **2026-04-26 PASS** — EICAR を `/tmp/eicar.txt` 配置 → エージェント YARA scan が `EICAR_TEST` ルールで検知 → アラート / scan_result UI で発火確認、SHA-256 + size も記録 (commit `20bff70` 由来)。
- 検証中の修復: agent v1.3.1-3 へのアップグレード、ingestion heartbeat fix、scan→alert 配線修復、UI scan grouping (詳細はこのセッションでは扱わず、メモリ `project_edr_platform.md` 参照)。

### §4 シナリオ D: ネットワーク C2 beacon 検知 (DNS IOC) — Linux

- **2026-04-27 PASS** (修復後) — `dig malware-c2.example` → events.dns に届く → IOC matcher が exact match (cached domain) → アラート 4件発火 (`既知IOC検出: malware-c2.example` × 2 + `sub.malware-c2.example` × 2)。MITRE T1071 Application Layer Protocol タグ付け、correlation engine がインシデント自動作成、playbook (notify アクション) 実行まで連鎖確認。
- **修復が必要だった内容**:
  1. agent 側 DNS collector が AF_INET/SOCK_RAW/IPPROTO_UDP を使っていたため outbound パケット (= endpoint 自身が発するクエリ) を観測できなかった → AF_PACKET に切り替え、outbound 観測可能に (commit `e1a7300`)。
  2. ingestion 側で NATS publish payload が proto union (`{Payload: {Dns: ...}}`) 形式だったため detection 側の `mergeProtoEvent` が `flat["query"]` を取り出せていなかった → `normalizeEventData` の flat key/value 形式に統一 (commit `309a958`)。
  3. detection 側 IOC アラート構築で `RuleID: "ioc-match"` を sentinel として渡していたが `alerts.rule_id` は uuid 型のため INSERT が silently 失敗 → 空文字に倒し RuleID は NULL で保存、rule identity は RuleName/Title 側で保持 (commit `beb402d`)。
  4. 本番 DB に conditions 空の suppression rule が 3 件残っており catch-all として全アラートを抹消していた (hit_count 48k/130k/15k) → `matches()` 冒頭に「全フィールド空なら false」ガードを追加 (commit `beb402d`)、当該 3 件は `is_active=false` で残置。

### §6 シナリオ F: エージェント応答アクション 5/5 PASS — Linux

- **2026-04-27 PASS** — `/endpoints/{agent-id}` ページから 5 アクション全部を end-to-end 検証完了。

| Action | API | DB | Endpoint 効果 | Agent ログ |
|--------|-----|----|---|---|
| isolate | POST `/api/v1/agents/{id}/isolate` → 200 | `agents.status='isolated'`, `isolated_at`, `isolated_reason='手動隔離'`, `isolated_by` | nftables `edr_isolate` テーブル作成 (lo + mgmt server + SSH + DNS のみ accept、外部 ping 100% loss) | (実行) |
| unisolate | POST `/unisolate` → 200 | `agents.status='online'`, `isolated_at=NULL` | nftables `edr_isolate` テーブル削除、外部 ping 復活 | (実行) |
| kill_process | POST `/kill-process` body `{"pid":N,"reason":"..."}` → 202 | `response_actions` 行追加 | 対象 PID 終了 | `⚠️ プロセス終了を実行中 pid=200711 reason="手動によるプロセス終了"` |
| quarantine_file | POST `/quarantine-file` body `{"path":"...","alert_id":"..."}` → 202 | `quarantined_files` 行追加 (agent_quarantine_id 含む) | 元 path 削除、`/var/lib/edr-agent/quarantine/<uuid>.quarantine` (mode 000) として保存 | `✓ ファイルを隔離しました quarantine_id=2d95cb89-...` + `✓ server に検疫結果を報告しました` |
| restore_file | (UI) | `quarantined_files.restored_at` 更新 (`response_actions` 側には行が入らない、後述 #3) | 元 path 復活 (mtime 含めて元のまま)、quarantine dir から削除 | `ファイルを復元中 quarantine_id=...` → `✓ ファイルを復元しました` |

- **副次バグ 3 件** (検証中に判明):
  1. **`/agents/{id}` ページのダミー UI** (commit `beb402d` で修正済) — 旧実装は確認ダイアログの「実行する」が API を呼ばず `setActionDone` のみで silent failure。`/endpoints/{id}` への redirect に置換。**運用上の教訓**: 新規エンドポイント詳細を開くときは `/endpoints/{agent-id}` を使うこと (`/agents/{id}` は redirect 経由で同じページに到達)。
  2. **kill のスナップショット遅延** — UI のプロセス一覧 (`agent-processes` query) はスナップショットなので、短命プロセスは選んでから kill 実行までに消えていることがある (`No such process` エラー)。回避策: 検索ボックスに正確な PID を入れて確実に同定する。改善余地: kill ボタンに「実行直前にプロセス再確認」オプション。
  3. **`response_actions` テーブルに `restore_file` 行が入らない** — 他 4 アクションは記録されるが restore のみ抜ける。`quarantined_files.restored_at` 側で track はされている。仕様か bug か未確定 (次セッション課題)。
