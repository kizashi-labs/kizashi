# Free プラン カウントダウン UX 設計検討

> **ステータス:** 設計検討（実装未着手）
> **対象読者:** 開発チーム / プロダクトマネージャー / カスタマーサクセス
> **最終更新日:** 2026年4月22日
> **背景:** 2026-04-22 早朝の `8256cb6 fix(license): treat Free plan as truly unlimited` を同日中に revert した経緯（`7abf94b`）を受け、Free 顧客の有効期限 UX を別の形で改善する案を検討する

---

## 1. 課題

現状の Free プランの挙動:

- DB には `expires_at = now + 365 day` が書き込まれる
- 管理画面 `/admin/license` で「有効期限：YYYY-MM-DD（残り 364 日）」と表示
- 期限到達時、`IsExpired = true` になり、エージェントが新規登録できない（`ResetLicense` で再度 365 日付与可能）

**UX 上の問題:**

1. **「無料プランなのに期限がある」という違和感** — 顧客が「お金を払わないと使えなくなる」と誤解しやすい
2. **365 日 → 30 日 → 7 日と減るだけで、何もアクションを取らない**ので、長期間サポートに「期限切れになりますか？」という問い合わせが頻発する可能性
3. **期限切れ後のリカバリパスが UI 上に明示されていない** — `ResetLicense` 機能は存在するが、Free 顧客が自分で見つけにくい

**ARR 上の意図（残したい）:**

- 年に 1 回、Free 顧客との接点が生まれる（更新通知 → アップセル機会）
- 「無償だが永久に保証はしない」という legal posture を維持
- 万一の濫用（5 EP 以上で運用しようとする攻撃的回避）に対する手動介入のフック

---

## 2. 設計案の比較

### 案 A: 表示文言を「ライセンス有効期限」→「評価期間」にリネーム

最小変更案。`/admin/license` の Free プラン時の文言だけ変える。

```diff
- ライセンス有効期限：2027-04-22（残り 365 日）
+ 評価期間：2027-04-22 まで（残り 365 日）— 期限到達後は自動でリセットできます
```

**Pros:**
- 1 行のフロントエンド差分
- 顧客の不安を「期限切れ → 評価延長可」という明確なメッセージで緩和
- ARR フック（年次接点）はそのまま維持

**Cons:**
- 期限到達時に `IsExpired = true` でエージェント登録が止まる挙動は変わらない（顧客自身が「リセット」ボタンを押す必要あり）
- 「自動でリセットできます」の文言と実装（手動操作必要）が乖離する場合は誤情報リスク

**実装工数:** 0.5 日

### 案 B: 「365 日後に期限切れ」を表示するが、30 日前まで通知バナーを抑制

長期間の不安を消し、近付いてきたら通知。

- 残り 31 日以上 → カウントダウン表示なし、「Free プラン」バッジのみ
- 残り 30 日以下 → バナー表示「評価期間が残り XX 日です。継続には更新ボタンを押すか有償プランへアップグレードしてください」
- 残り 0 日 → 「評価期間終了。エージェント停止前に更新するか有償プランへ」

**Pros:**
- 通常時は UI クリーン（顧客にストレスを与えない）
- 期限間近で適切にアクション促進
- ARR フックタイミングが明確（30 日前）

**Cons:**
- 「期限が見えない」と不安に思う顧客も一定数いる
- バナーの実装ロジックが少し複雑（しきい値分岐）

**実装工数:** 1 日

### 案 C: 「無料更新」ボタン追加 + 30 日前から表示

案 B + 更新フローを 1 クリック化。

- ライセンス画面に常時「無料延長」ボタン（クリックで `ResetLicense` 呼び出し → 365 日延長）
- 通知バナー（残り 30 日）に「今すぐ無料更新」ボタンを inline 配置
- バックエンド: `ResetLicense` を Free プラン顧客のみセルフサービスで叩ける API として切り出し（`POST /api/v1/license/extend-free`）

**Pros:**
- 顧客が「困った時にどうすればいいか」が UI 上で完結
- サポート問い合わせ削減
- 1 クリック更新により「年次接点」が顧客アクション化される（メールでなく UI で）

**Cons:**
- 「永久に無料更新できる」と顧客が認識すると、ARR への転換動機が弱まる
- セルフサービス更新を制限する場合、別途レート制限ロジック必要（年 1 回まで等）

**実装工数:** 2 日

### 案 D: 期限を 365 日から 90 日に短縮 + 自動更新

Free プランをトライアル的に位置付け直す。

- Free 顧客の `expires_at = now + 90 day`（評価フェーズ）
- 期限到達時、自動的に `ResetLicense` を内部実行（顧客介入不要）
- 90 日ごとにメール通知「Kizashi Free を継続利用中です。アップグレード検討しませんか？」

**Pros:**
- 法的・営業的に明確（「90 日評価ライセンス、自動継続」）
- 短いサイクルで ARR フックが頻繁に発火
- 顧客は何もしなくても継続利用可能

**Cons:**
- 自動更新の安全装置（暴走防止）が必要
- 90 日に区切ることで「評価」感が強まり、本番運用顧客が離れる可能性
- バックエンドに自動更新ワーカー新設が必要（`BillingGraceWorker` パターン流用可）

**実装工数:** 3 日

### 案 E: そのまま（現状維持）

何もしない。365 日カウントダウンを表示し、期限到達時は手動 reset 必須。

**Pros:**
- 工数 0
- ARR フックとして最も強い（顧客が必ず接点を持つ）

**Cons:**
- UX 課題は未解決（顧客の不安・サポート問い合わせ）
- 元々の `8256cb6` が解決しようとした問題が残ったまま

**実装工数:** 0 日

## 4. 推奨

**案 B（30 日前まで通知抑制）+ 案 A の文言リネーム** の組み合わせを推奨します。

**理由:**
1. **顧客 UX 改善の効果が大きい**（通常時はクリーン、期限間近のみ通知）
2. **ARR フックは維持**（30 日前のバナーが営業接点）
3. **実装工数 1 日程度**（フロントエンドのみ、バックエンド変更なし）
4. **将来 case C/D に拡張する余地を残す**（バナーから「今すぐ更新」ボタンへの拡張は容易）

**実装後の状態:**
- Free 顧客は通常時「Free プラン（5 EP まで）」バッジのみ見える
- 残り 30 日になると `/admin/license` ページにバナー「評価期間が残り XX 日です」表示
- 残り 7 日で重要度を上げて通知（赤色バナー）
- 期限到達時はエージェント登録が止まり、「ライセンスをリセット」ボタン or 有償プラン誘導画面へ
