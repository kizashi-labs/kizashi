> **ステータス:** 実装済み (v1.3.13)
> **対象読者:** 開発チーム / SRE
> **最終更新日:** 2026年4月30日
> **関連:**
> - `docs/ops/database-schema.md` — `agents` テーブルの証明書カラム
> - `docs/runbook.md` — Agent mTLS 証明書更新ランブック

---

## 概要

各エージェントは gRPC 接続を mTLS で保護しており、エージェントごとの TLS 証明書を保持する。
証明書の有効期限切れはエージェントの通信断に直結するため、有効期限 30 日前にサーバ主導で自動更新を行う。

本機能は以下の 3 つのコンポーネントで構成される:

| コンポーネント | 役割 |
|---|---|
| `AgentCertRenewer` スケジューラ | 毎 24h 期限切れ近いエージェントを検出し NATS へ更新命令を発行 |
| NATS ブリッジ + ingestion ハンドラ | 命令を gRPC ストリームに変換してエージェントへ届ける |
| エージェント `RenewCertificate()` | CSR 生成 → 新証明書取得 → アトミック書き込み → 再接続 |

```
│ API サービス                                          │

│ Ingestion サービス                                     │

│  startNATSCommandBridge                                │

│    → relay() → dispatcher.EnqueueCertRenew()          │
│    → commandToProto("cert_renew")                      │
│       CollectArtifactCommand{Type=UNSPECIFIED,         │
│                              Target=<token JSON>}      │

│  RenewCertificate(ctx, renewalToken)                   │
│    1. RSA-2048 鍵ペアを生成                            │

└────────────────────────────────────────────────────────┘
```

## サーバ側 — スケジューラ

### `server/internal/scheduler/agent_cert_renewer.go`

```
AgentCertRenewer
  ├── agentStore *store.AgentStore
  └── nc         *nats.Conn

Run(ctx):
  初回 2 分後 → 以後 24 時間ごとに checkAndRenew() を呼ぶ

checkAndRenew():
  agents := ListExpiringAgents(30)
  for each agent: renewAgent(agent)

renewAgent(agent):
  token = uuid.New().String()   // ランダム 1 回限りのトークン
  SetRenewalToken(agentID, token, 7 * 24h)
  nats.Publish("commands.<agentID>.cert_renew", {"renewal_token": token})
```

起動は `server/cmd/api/main.go` で `go scheduler.NewAgentCertRenewer(agentStore, nc).Run(ctx)` により行われる。

## サーバ側 — DB スキーマ

`agents` テーブルに 3 カラムを追加 (Migration 246):

| カラム | 型 | 用途 |
|---|---|---|
| `cert_not_after` | `TIMESTAMPTZ` | 証明書有効期限。エンロール時に更新 |
| `cert_renewal_token` | `TEXT` | 更新用ワンタイムトークン |
| `cert_renewal_expires` | `TIMESTAMPTZ` | トークン TTL (7 日) |

```sql
ALTER TABLE agents
    ADD COLUMN IF NOT EXISTS cert_not_after       TIMESTAMPTZ,
    ADD COLUMN IF NOT EXISTS cert_renewal_token   TEXT,
    ADD COLUMN IF NOT EXISTS cert_renewal_expires TIMESTAMPTZ;

CREATE INDEX IF NOT EXISTS agents_cert_not_after_idx
    ON agents (cert_not_after) WHERE cert_not_after IS NOT NULL;
```

`cert_not_after` はエンロール (`Enroll` / `Enroll("renew:...")`) 完了時に `parseCertNotAfter()` で署名済み証明書の `NotAfter` をパースして保存する。

## サーバ側 — `SignCSR` 内のトークン検証

```
Enroll(enrollToken):
  if strings.HasPrefix(enrollToken, "renew:"):
    token = strings.TrimPrefix(enrollToken, "renew:")
    consumeRenewalToken(agentID, token)  // アトミック検証 & 削除
    → 既存 agentID に対して新証明書を発行
  else:
    静的 ENROLL_TOKEN と照合
    → 新規 agentID を割り当て
```

`consumeRenewalToken` は以下を 1 回のクエリでアトミックに行う:
1. `cert_renewal_token = $token AND cert_renewal_expires > NOW()` で行を取得
2. `cert_renewal_token = NULL, cert_renewal_expires = NULL` にリセット

これによりトークンの再利用が不可能になる。

## エージェント側 — `RenewCertificate()`

```go
func (c *GRPCClient) RenewCertificate(ctx context.Context, renewalToken string) error {
    // 1. 新しい RSA-2048 鍵ペアを生成
    key, _ := rsa.GenerateKey(rand.Reader, 2048)

    // 2. CSR 生成 (CN = agentID)
    csr, _ := x509.CreateCertificateRequest(rand.Reader, &x509.CertificateRequest{
        Subject: pkix.Name{CommonName: c.agentID},
    }, key)

    // 3. サーバへ署名依頼 (renewalToken を使用)
    resp, _ := c.enrollClient.Enroll(ctx, &pb.EnrollRequest{
        EnrollToken: "renew:" + renewalToken,
        Csr:         pem.EncodeToMemory(&pem.Block{Type: "CERTIFICATE REQUEST", Bytes: csr}),
        AgentId:     c.agentID,
    })

    // 4. アトミック書き込み (temp → chmod 600 → rename)
    atomicWrite(c.certPath, resp.SignedCert, 0600)
    atomicWrite(c.keyPath,  keyPEM,          0600)

    return nil
}
```

### アトミック書き込みの重要性

証明書と秘密鍵は 2 つのファイルに分かれている。非アトミックな書き込み中にプロセスが落ちると、新しい証明書と古い秘密鍵が混在して gRPC 接続が永続的に不能になる。

`atomicWrite` は `{file}.tmp` に書いてから `os.Rename()` することで、ファイルシステムレベルの原子性を保証する。

## エージェント側 — `Reconnect()` と再接続ループ

証明書更新後も既存 gRPC コネクションは古い証明書で確立されている。新証明書を有効にするには再接続が必要。

```go
func (c *GRPCClient) Reconnect() {
    c.conn.Close()  // SHUTDOWN → RunWithReconnect が検知して再ダイヤル
}
```

`RunWithReconnect` は接続状態の変化 (`TRANSIENT_FAILURE` or `SHUTDOWN`) を監視しており、`conn.Close()` による切断を検知すると最大 3 回の指数バックオフで再接続する。再接続時は `tls.LoadX509KeyPair(certPath, keyPath)` でディスク上の新証明書を読み込む。

## 失敗ケースと対応

| ケース | 挙動 | 対応 |
|---|---|---|
| トークン期限切れ (7日超過) | `SignCSR` がエラー返却 | 翌日のスケジューラが新トークンを発行 |
| ネットワーク断で `Enroll` 失敗 | `RenewCertificate` がエラー返却 | エージェントはエラーログを出力。翌日再試行 |
| `atomicWrite` 失敗 | 既存ファイルは変更されない | gRPC 接続は旧証明書で継続。翌日再試行 |
| `Reconnect` 後の接続失敗 | `RunWithReconnect` が指数バックオフ | ネットワーク復旧後に自動再接続 |
| サーバ再起動で更新命令がロスト | NATS JetStream durable consumer で配信保証 | 最大 1 日の遅延で再配信 |

## 設計上の判断事項

### なぜ `CollectArtifactCommand` をキャリアに使うか

gRPC の `ServerCommand` oneof に新フィールドを追加するとプロトコルバッファの後方互換性問題が生じる。
`CollectArtifactCommand{Type=ARTIFACT_TYPE_UNSPECIFIED}` は既存の `apply_policy`・`forensics_job` コマンドと同じキャリアパターンで実績があり、エージェントとサーバのバージョン非対称環境でも安全。

### なぜサーバ主導 (pull-based) ではなくサーバ発火 (push-based) か

エージェントはエンドポイント上で動作するため、証明書期限を自己監視して CSR をサーバに送る pull-based 設計も可能。しかし pull-based はエージェント側に証明書管理ロジックが必要で、オフライン期間中は更新が行われない。サーバ主導なら DB のスキャンで期限切れを一元管理でき、オフラインエージェントは再接続時に命令を受信できる (NATS durable consumer)。

### なぜ RSA-2048 か

既存のエンロールフローと同じ鍵長・アルゴリズムを踏襲して互換性を維持する。将来 ECDSA P-256 への移行が必要な場合は `RenewCertificate` 内の鍵生成部分のみ変更すればよい。
