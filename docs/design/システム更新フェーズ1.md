## 1. Phase 1 のスコープ

### やること
- DB schema 追加（`system_updates` / `system_update_settings` 2 テーブル）
- 7 つの REST API エンドポイント実装
- 管理画面 `/admin/system-updates` ページ追加
- 「現在版」「履歴一覧」「設定」の表示・操作 UI
- ハンドラ単体テスト
- OpenAPI 仕様への追加

### やらないこと（Phase 2 以降）
- ❌ updater コンテナの実装（Go バイナリ、Docker socket、image pull）
- ❌ GitHub Releases API の自動ポーリング
- ❌ 実際の `docker compose pull/up` 実行
- ❌ ロールバック自動化
- ❌ Patch Management UI への通知バナー（Phase 5 で実装）

### Phase 1 完了時点での挙動
- 管理画面を開くと「最新版チェック未実施」と表示
- 「今すぐチェック」ボタンを押すと **スタブ実装** が「現在最新です」と返す（実際の Releases API は叩かない）
- 「適用」ボタンは UI 上存在するが、押すと **承認 record だけ作って実際は何もしない**（Phase 3 で実装）
- 設定画面で auto_apply_* / 通知メール / channel が変更できる（Phase 2/3 で実際に使われる）

→ **Phase 1 単体で本番デプロイ可能**。営業デモには物足りないが、UI ウォークスルーは可能。Phase 2 完了後に「実装の続き」として実演可能になる。

## 3. DB スキーマ（最終形）

`server/migrations/236_system_updates.sql`:

```sql
-- 236_system_updates.sql
-- System auto-update tracking (Phase 1: schema + API + UI only)

CREATE TABLE IF NOT EXISTS system_updates (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    current_version TEXT NOT NULL,
    available_version TEXT NOT NULL,
    release_notes_url TEXT NOT NULL DEFAULT '',
    release_notes_md TEXT NOT NULL DEFAULT '',
    channel TEXT NOT NULL DEFAULT 'stable' CHECK (channel IN ('stable', 'beta')),
    detected_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    status TEXT NOT NULL DEFAULT 'available'
        CHECK (status IN ('available', 'approved', 'applying', 'success', 'failed', 'rolled_back', 'cancelled')),
    approved_by UUID REFERENCES users(id) ON DELETE SET NULL,
    approved_at TIMESTAMPTZ,
    applied_at TIMESTAMPTZ,
    failed_reason TEXT NOT NULL DEFAULT '',
    rollback_from_version TEXT NOT NULL DEFAULT '',
    UNIQUE(available_version)
);

CREATE INDEX IF NOT EXISTS idx_system_updates_status ON system_updates(status);
CREATE INDEX IF NOT EXISTS idx_system_updates_detected_at ON system_updates(detected_at DESC);

CREATE TABLE IF NOT EXISTS system_update_settings (
    id INT PRIMARY KEY DEFAULT 1 CHECK (id = 1),  -- single-row pattern
    auto_apply_patch BOOL NOT NULL DEFAULT FALSE,
    auto_apply_minor BOOL NOT NULL DEFAULT FALSE,
    maintenance_window_start TIME,
    maintenance_window_end TIME,
    notify_email TEXT NOT NULL DEFAULT '',
    channel TEXT NOT NULL DEFAULT 'stable' CHECK (channel IN ('stable', 'beta')),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

INSERT INTO system_update_settings (id) VALUES (1) ON CONFLICT DO NOTHING;
```

**設計上の注意:**
- `status = 'cancelled'` を CHECK に追加（親設計書には未記載だったが、UI から「承認取消」が呼ばれた場合に使用）
- `approved_by` を `users(id)` への FK にし、ユーザ削除時は SET NULL（履歴保持）
- 単行パターンの `system_update_settings.updated_at` を追加（変更履歴監査用、Phase 1 では INSERT/UPDATE トリガー不要、Go 側で SET）
- `idx_system_updates_detected_at DESC` を追加（一覧表示の ORDER BY 高速化）

## 4. API エンドポイント仕様（最終形）

### 共通
- 全エンドポイント `RequireAdmin` ミドルウェアで保護（admin role 必須）
- レスポンスは `application/json`
- エラー時は `{"error": "...", "code": 400}` 形式（既存パターン踏襲）

### `GET /api/v1/admin/system-updates`

更新履歴一覧。

**Response:**
```json
{
  "items": [
    {
      "id": "uuid",
      "current_version": "1.0.0",
      "available_version": "1.0.1",
      "release_notes_url": "https://github.com/.../releases/tag/v1.0.1",
      "release_notes_md": "## What's Changed\n- Fix XX\n- Improve YY",
      "channel": "stable",
      "detected_at": "2026-04-22T08:00:00Z",
      "status": "available",
      "approved_by": null,
      "approved_at": null,
      "applied_at": null,
      "failed_reason": "",
      "rollback_from_version": ""
    }
  ],
  "total": 1
}
```

### `GET /api/v1/admin/system-updates/current`

現在動いているバージョン + 最新の available（あれば）。

**Response:**
```json
{
  "current_version": "1.0.0",
  "latest_available": {
    "id": "uuid",
    "available_version": "1.0.1",
    "status": "available",
    "release_notes_url": "..."
  }
}
```

最新が無い（または現在版以下）の場合は `latest_available: null`。

### `POST /api/v1/admin/system-updates/{id}/approve`

承認。**Phase 1 では DB ステータスを `approved` に更新するだけ。実際の適用は Phase 3。**

**Response:** 更新後の `SystemUpdate` 全フィールド

**バリデーション:**
- `id` 存在チェック
- `status == 'available'` でなければ 409 Conflict
- 承認者を `c.GetUint("user_id")` から取得して `approved_by` にセット、`approved_at = NOW()`

### `POST /api/v1/admin/system-updates/{id}/cancel`

承認取消。**Phase 1 では `status` を `available` に戻すだけ。**

**バリデーション:** `status == 'approved'` でなければ 409 Conflict

### `POST /api/v1/admin/system-updates/check`

即時チェック。**Phase 1 ではスタブ実装で「現在最新です」を返すだけ。Phase 2 で GitHub Releases API を叩く実装に置き換える。**

**Response:**
```json
{
  "checked_at": "2026-04-22T08:00:00Z",
  "result": "up_to_date",
  "latest_available": null
}
```

`result` は `up_to_date` | `update_available` の 2 値（Phase 1 はほぼ常に `up_to_date`）。

### `GET /api/v1/admin/system-updates/settings`

**Response:**
```json
{
  "auto_apply_patch": false,
  "auto_apply_minor": false,
  "maintenance_window_start": "02:00",
  "maintenance_window_end": "04:00",
  "notify_email": "ops@example.com",
  "channel": "stable",
  "updated_at": "2026-04-22T08:00:00Z"
}
```

### `PUT /api/v1/admin/system-updates/settings`

**Request:** GET レスポンスから `updated_at` を除いた形（部分更新は許可しない、全フィールド送信）

**バリデーション:**
- `channel ∈ {'stable', 'beta'}`
- `notify_email` が非空なら email 形式チェック
- `maintenance_window_*` が片方だけ NULL は不可

## 7. 受け入れ基準（acceptance criteria）

Phase 1 完了の判定:

### 機能面
1. ローカル `docker compose up` で起動し、migration 236 が auto-apply される
2. 管理者ユーザーで `/admin/system-updates` を開けて UI が表示される
3. 「今すぐチェック」を押すと「現在最新です」が表示される
4. DB に手動で `INSERT INTO system_updates ...` を入れると、UI に「v1.0.1 利用可能」バナーが出る
5. 「適用」を押すと status が `approved` に変わる（DB 確認）
6. 「キャンセル」を押すと status が `available` に戻る
7. 設定変更が DB に永続化される
8. 非 admin ユーザーは `/admin/system-updates` にアクセスできない（403 or リダイレクト）

### 品質面
9. `go test ./...` 全 PASS
10. `npm run vitest` 全 PASS
11. `npm run build` 成功
12. `tsc --noEmit` エラー 0
13. OpenAPI 仕様の lint（`docs/openapi.yaml`）が通る
14. 新規追加コードに基本的な error handling（DB エラー → slog.Error + HTTP 500）

### ドキュメント面
15. CHANGELOG `[Unreleased]` に追記
16. 本書（`system-updates-phase1.md`）の Acceptance criteria を全チェック
17. README に新機能のスクリーンショットは Phase 5 で対応（Phase 1 では不要）

## 8. Phase 2 への引き継ぎ事項

Phase 1 完了時点で Phase 2 着手のために以下が整備されている必要あり:

- `system_updates` テーブルへの insert 経路が API 経由 + 手動 SQL の 2 通り（Phase 2 では updater コンテナが直接 insert する経路を追加）
- `POST /api/v1/admin/system-updates/check` がスタブ実装（Phase 2 で GitHub Releases API 呼び出しに置き換え）
- 設定の `channel = 'stable' | 'beta'` を Phase 2 の Releases フィルタリングに使う
- `system_update_settings.notify_email` を Phase 2 の通知送信先として使う

これらは Phase 1 で interface だけ整えて、Phase 2 で実装を追加する（既存コード変更は最小限）。

## 9. リスクと緩和策

| リスク | 緩和策 |

| フロントエンドの `apiFetchList` が新エンドポイントで動かない | Day 3 開始前に既存の admin ページの API 呼び出しコードを読む |
