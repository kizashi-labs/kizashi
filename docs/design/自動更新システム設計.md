# 自動アップデート機構 設計提案 (Auto-Update System Design)

> **ステータス:** 設計提案 (未実装)
> **対象読者:** 開発チーム / プロダクトマネージャー
> **最終更新日:** 2026年4月22日
> **関連:** `docs/ops/customer-upgrade-procedure.md` (現行の手動アップデート手順)

---

## 背景

現状、顧客環境のバージョンアップは手動 (`docker compose pull && up -d`) です。Patch リリースのたびに各顧客が個別操作を必要とし、適用遅延 = セキュリティリスク になります。

本書は「顧客環境への自動アップデート機構」の2つの設計案を比較し、推奨案を示します。

---

## 設計案の概要

| 案 | 一言で言うと | 工数目安 |
|---|---|---|
| (A) Watchtower 同梱 | OSS 既製品をそのまま | 1日 (検討除外: タグ固定運用と相性悪い) |
| **(B) 自社製 updater コンテナ** | 専用 updater + 専用 UI | 約18日 |
| **(C) Patch Management 拡張** | 既存 Patch 機能の対象に「サーバ自体」を追加 | 約15日 |

(A) は `IMAGE_TAG` 固定運用と相容れない (Watchtower は基本的に latest を pull する) ため、本書では (B) と (C) を詳細検討します。

---

# (B) 自社製 Updater コンテナ

## アーキテクチャ

```
┌──────────────────────────────────────────────────────────────┐
│ 顧客環境 (docker compose stack)                              │
│                                                              │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌────────────┐  │
│  │ postgres │  │ api      │  │ frontend │  │ updater ★  │  │
│  └──────────┘  └──────────┘  └──────────┘  └─────┬──────┘  │
│                                                  │          │
│                                       /var/run/docker.sock  │
└──────────────────────────────────────────────────┼──────────┘
                                                   │
                            ┌──────────────────────┼──────────┐
                            ▼                      ▼          ▼
                    GitHub Releases API    GHCR registry   api/v1/updater/*
                    (manifest.json)       (image pull)    (DB状態同期)
```

## コンポーネント

### updater コンテナ (新規 Go バイナリ `server/cmd/updater/main.go`)

責務:
1. 定期的に GitHub Releases API をポーリング (デフォルト 6h ごと)
2. 自身の `current_version` と最新 `available_version` を比較
3. アップデート可能な場合、DB の `system_updates` テーブルに記録
4. 管理画面からの「適用」承認を待機
5. 承認後:
   - `docker compose pull` (Docker socket 経由 SDK)
   - `docker compose up -d --no-deps api frontend agent`
   - ヘルスチェック → 失敗時自動ロールバック

### Docker socket マウント (セキュリティ境界)

```yaml
updater:
  image: ghcr.io/.../updater:${VERSION:-latest}
  volumes:
    - /var/run/docker.sock:/var/run/docker.sock
    - ./docker-compose.yml:/workspace/docker-compose.yml:ro
    - ./.env:/workspace/.env:ro
  environment:
    UPDATER_CHECK_INTERVAL: 6h
    UPDATER_AUTO_APPLY: "false"        # 手動承認必須 (デフォルト)
    UPDATER_CHANNEL: stable             # stable | beta
    UPDATER_RELEASES_URL: https://api.github.com/repos/.../releases
    DATABASE_URL: ${DATABASE_URL}
  depends_on:
    api:
      condition: service_healthy
```

## DB スキーマ (新規 migration `236_system_updates.sql`)

```sql
CREATE TABLE IF NOT EXISTS system_updates (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  current_version TEXT NOT NULL,
  available_version TEXT NOT NULL,
  release_notes_url TEXT NOT NULL DEFAULT '',
  release_notes_md TEXT NOT NULL DEFAULT '',
  channel TEXT NOT NULL DEFAULT 'stable',
  detected_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  status TEXT NOT NULL DEFAULT 'available',
    -- available | approved | applying | success | failed | rolled_back
  approved_by UUID,
  approved_at TIMESTAMPTZ,
  applied_at TIMESTAMPTZ,
  failed_reason TEXT NOT NULL DEFAULT '',
  rollback_from_version TEXT NOT NULL DEFAULT '',
  UNIQUE(available_version)
);
CREATE INDEX idx_system_updates_status ON system_updates(status);

CREATE TABLE IF NOT EXISTS system_update_settings (
  id INT PRIMARY KEY DEFAULT 1 CHECK (id = 1),
  auto_apply_patch BOOL NOT NULL DEFAULT FALSE,
  auto_apply_minor BOOL NOT NULL DEFAULT FALSE,
  maintenance_window_start TIME,
  maintenance_window_end TIME,
  notify_email TEXT NOT NULL DEFAULT '',
  channel TEXT NOT NULL DEFAULT 'stable'
);
INSERT INTO system_update_settings (id) VALUES (1) ON CONFLICT DO NOTHING;
```

## API エンドポイント (新規)

| Method | Path | 用途 |
|---|---|---|
| GET | `/api/v1/admin/system-updates` | 一覧 (履歴含む) |
| GET | `/api/v1/admin/system-updates/current` | 現在版 + 最新可用版 |
| POST | `/api/v1/admin/system-updates/{id}/approve` | 適用承認 |
| POST | `/api/v1/admin/system-updates/{id}/cancel` | 承認取消 |
| POST | `/api/v1/admin/system-updates/check` | 即時チェック (手動) |
| GET | `/api/v1/admin/system-updates/settings` | 設定取得 |
| PUT | `/api/v1/admin/system-updates/settings` | 設定更新 |

## State Machine

```
[available] ──(approve)──▶ [approved]
                             │
                             ▼ updater がポーリング検知
                          [applying] ──┬─(成功)─▶ [success]
                                       └─(失敗)─▶ [failed]
                                                    │
                                                    ▼ 自動ロールバック
                                                 [rolled_back]
```

## UI 設計 (`/admin/system-updates/page.tsx` 新規)

- 上部: 現在版バッジ + 「最新版あり (v1.0.2)」通知バナー
- 中央: リリースノート Markdown レンダリング
- 下部: 「メンテナンスウィンドウで適用」「今すぐ適用」「スキップ」ボタン
- 履歴テーブル: 過去の適用結果 (success / failed / rolled_back)

| **計** | | **約 18日** |

## Pros / Cons

**Pros**
- 顧客の管理画面に統合 (運用一元化)
- 承認フロー組み込みで安全
- ロールバック自動化が可能
- セルフホスト顧客にも提供可能 (依存サービスなし)

**Cons**
- Docker socket マウントが必須 = privileged 級権限
- compose ファイルの構造に強く依存 (顧客カスタマイズに弱い)
- updater 自身のアップデートをどうするか (circular update 問題)

# (C) Patch Management 拡張

既存の `patch_deployments` テーブル (`server/migrations/102_patch_management.sql`) + UI (`frontend/app/admin/patch-management/page.tsx`) を再利用し、「サーバ自体」を patch target として追加する案。

## アーキテクチャ

```
既存:
  patch_deployments → target_agents → エージェント側 patcher が適用

拡張:
  patch_deployments → target_type='server' → サーバ側 self-patcher が適用
                                            (ServerSelfPatcher worker)
```

## DB スキーマ拡張 (migration `236_patch_target_server.sql`)

既存テーブルに最小変更:

```sql
ALTER TABLE patch_deployments
  ADD COLUMN IF NOT EXISTS target_type TEXT NOT NULL DEFAULT 'agent';
  -- 'agent' | 'server' | 'both'

ALTER TABLE patch_deployments
  ADD COLUMN IF NOT EXISTS server_components JSONB NOT NULL DEFAULT '[]';
  -- ["api", "frontend", "agent_image"] など

ALTER TABLE patch_deployment_results
  ALTER COLUMN agent_id DROP NOT NULL;

ALTER TABLE patch_deployment_results
  ADD COLUMN IF NOT EXISTS target_kind TEXT NOT NULL DEFAULT 'agent';
  -- 'agent' | 'server'

ALTER TABLE patch_deployment_results
  ADD COLUMN IF NOT EXISTS server_component TEXT NOT NULL DEFAULT '';
```

## バックエンド変更

### 1. 既存 `patch_handler.go` に分岐追加

`Deploy` ハンドラ内:

```go
switch deployment.TargetType {
case "agent":
    // 既存ロジック (NATS 経由でエージェントへ配信)
case "server":
    h.serverPatcher.Enqueue(deployment)  // 新規
case "both":
    // 両方
}
```

### 2. 新規 `server/internal/scheduler/server_self_patcher.go`

役割: サーバ自身の更新を実行する worker (api コンテナ内に内蔵 = updater コンテナ不要)

```go
type ServerSelfPatcher struct {
    db          *sql.DB
    docker      *client.Client  // /var/run/docker.sock 経由
    composeFile string
}

func (p *ServerSelfPatcher) ApplyDeployment(ctx context.Context, dep PatchDeployment) error {
    // 1. result を 'in_progress' に
    // 2. docker compose pull
    // 3. docker compose up -d --no-deps <components>
    // 4. ヘルスチェック → 成否で result 更新
    // 5. 失敗時ロールバック
}
```

### 3. main.go に worker 登録

```go
serverPatcher := scheduler.NewServerSelfPatcher(db, dockerClient, "/workspace/docker-compose.yml")
go serverPatcher.Run(ctx, 30*time.Second)
```

```
対象:  ◯ エージェント   ◯ サーバ   ◯ 両方

    ☑ api

```

## 適用フロー

```
管理者が UI で「v1.0.2 をサーバに適用」作成
    ↓
patch_deployments に INSERT (status='scheduled', target_type='server')
    ↓
ServerSelfPatcher が 30秒ごとに poll → 検知
    ↓
docker compose pull → up -d → ヘルスチェック
    ↓
patch_deployment_results を status='success' で更新
```

## Pros / Cons

**Pros**
- 既存 UI / API / DB を最大限再利用 (実装量小)
- Patch Management の文脈で「OS パッチもサーバ更新も一元管理」というメッセージング
- スケジューリング / 段階展開 / レポート機能が即座に流用可能

**Cons**
- `patch_deployments` テーブルに無関係なカラムが増える (関心の混在)
- target_type の分岐が UI/API/Worker で3層になり複雑化
- ロールバック設計が既存パッチとは別物なので、共通化しきれない
- 顧客視点で「OS パッチと EDR 自身の更新は別物」という mental model のずれ

# 比較と推奨

| 観点 | (B) Updater コンテナ | (C) Patch Management 拡張 |
|---|---|---|
| 実装量 | 約18日 | 約15日 |
| 既存コード再利用度 | 低 (新規多数) | 高 |
| ユーザの mental model | クリア (専用画面) | やや混在 |
| 関心の分離 | ◎ 独立コンテナ | △ 既存テーブルに混在 |
| ロールバック設計 | 専用設計可能 | 既存設計と整合必要 |
| セルフホスト適合性 | ◎ | ◎ |
| Docker socket 露出 | あり (updater) | あり (api コンテナ経由) |
| 商用印象 | 「Auto-Update」として宣伝可 | 「OS と EDR を一元管理」として宣伝可 |

## 推奨: (B) を採用

理由:
1. **関心の分離が明確** — エージェント OS パッチと、サーバ自身のバージョン更新は本質的に別ドメイン。混ぜるとテーブル設計と UI が時間とともに悪化する
2. **専用 UI** の方が承認フロー / リリースノート表示と相性がよい
3. updater コンテナを切り離せるため、有効化/無効化を顧客側で選択できる (セキュリティポリシー上 Docker socket 不可の顧客がいる場合に外せる)
4. 工数差はわずか3日

## ハイブリッド案 (最終提案)

完全な (B) ではなく、**(B) のコア機能 + Patch Management UI への通知バナー追加**:

- アップデート検知 / 承認 / 適用 = 専用 `/admin/system-updates` 画面 (= B)
- Patch Management ダッシュボードに「サーバ更新あり」バナーをリンク表示

これで「探しに行かなくても気づける」+「専用画面で詳細管理」の両立。

---

## 着手判断

設計を実装に進める場合は、Phase 1 (DB schema + API + 手動チェック UI) から段階着手するのが安全です。実装着手の意思決定は以下の条件で:

- 顧客数 5社以上 (手動運用がスケールしなくなる目安)
- Patch リリース頻度 月1回以上
- 顧客側からの自動化要望が出始めた段階
