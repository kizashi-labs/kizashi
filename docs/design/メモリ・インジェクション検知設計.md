# メモリ／インジェクション検知 設計（検知深化 ④）

**位置づけ**: 検知深化スプリント（①UEBAリスクボード／②per-agentベースライン／③ML誘導AIトリアージ は実装済み）の最終・最大項目。①〜③が「死蔵コードの活性化」だったのに対し、④は**純新規**。
**狙い**: ファイル/プロセス名/Sigma では捉えられない**インメモリ脅威（プロセスインジェクション・シェルコード・反射型DLL・プロセスホロウィング）**を検知する。これは商用 EDR との検知差で最も大きい「メモリ可視性」の核。
**現状**: Sigma で痕跡の一部のみ（rundll32 MiniDump / mavinject / `LD_PRELOAD` 等）。メモリそのものは見ていない。

T1055（Process Injection）に焦点を絞り、**impact-to-effort 順にフェーズ化**する。

---

## スコープとフェーズ

### M1: RWX/非バック実行メモリのスキャン（クロスOS・最優先）— ✅ Linux/Windows 実装済み・既定ON（2026-08-01）
**シグナル**: インジェクション/シェルコードの王道指標 ＝ **書込可能かつ実行可能(RWX)な private メモリ**、および**ディスク上のファイルにバックされていない実行可能領域（unbacked/floating code）**。正規のコードは通常 RX かつ image-backed。
- **Linux**: `/proc/<pid>/maps` を走査し `rwxp` 領域、`(deleted)`/匿名の実行可能マッピングを抽出。カーネル不要・**手元の Linux EC2 で即検証可能**。
- **Windows**: `VirtualQueryEx` で `MEM_PRIVATE` かつ `PAGE_EXECUTE*`、image にバックされない実行領域を列挙。
- **macOS**: `mach_vm_region` で同等（最後・難度高）。
- **出力**: 新規テレメトリ型 `memory`（後述）で「該当プロセス＋領域（addr/size/perm/unbacked/エントロピー）」を申告 → サーバ検知器がアラート化。
- **誤検知対策**: JIT を多用する正規プロセス（ブラウザ/.NET/Java/Node）の RWX は正常 → **allowlist** ＋ per-process ベースライン（②の基盤を流用）。「unbacked かつ RWX かつ高エントロピー」を高信頼トリガに。

### M2: Windows クロスプロセス・インジェクション・テレメトリ（✅ 実装済み・agent ビルド済 / ドライバは EC2 再ビルド要）
**シグナル**: 他プロセスへの注入操作そのもの。
- **W4a の `ObRegisterCallbacks` を拡張**: 保護PID への剥奪に加え、**任意プロセス**への `PROCESS_VM_WRITE | PROCESS_CREATE_THREAD | PROCESS_VM_OPERATION` を伴うハンドルオープンを**監査（audit）**して申告。
- `PsSetCreateThreadNotifyRoutine` でリモートスレッド生成（古典的 CreateRemoteThread）を検知。
- 既存ドライバ（W0/W4a 実機実証済み）に追記するだけ＝**低工数・高価値**、Windows。

### M3: 対象プロセスのインメモリ YARA スキャン（既存 YARA 流用）
- M1/M2 で疑わしいプロセスを特定したら、その**プロセスメモリに対して YARA**（agent 側 YARA を memory スキャンへ拡張）→ 既知シェルコード/パッカー/インプラント署名に照合。
- 全プロセス常時ではなく**疑わしい対象だけ**スキャンして負荷を抑制。

### M4: 範囲外（将来）
- エクスプロイト防御（ROP/ヒープスプレー＝CET/CFG・ハードウェア/カーネル依存）、ランサムのファイルロールバック（VSS/シャドウコピー＝別トラック）。本設計の対象外。

## アーキテクチャ

新規テレメトリ型 **`memory`** を**確立済みパターン（buf→proto→server→agent）**で追加：
- **proto**: `MemoryEvent{ pid, process_name, image_path, regions[]{ base, size, prot(rwx), backed(bool), unbacked_exec(bool), entropy }, reason }`。
- **agent**: `memory_collector`（M1 スキャナ）。OS 別実装（`/proc/pid/maps` / `VirtualQueryEx` / `mach_vm_region`）。**opt-in タグ/環境変数**（負荷管理）。Windows M2 はドライバ申告。
- **server**: `internal/detection/memory_detector.go`。判定＝「unbacked-exec ∧ RWX ∧ (高エントロピー ∨ 既知injector親) ∧ ¬allowlist」。Sigma でも条件化できるようフィールドをフラット化。重大度高（7-8）。`process_block`/event 配管とイベント型 CHECK 制約（migration）に `memory` を追加。
- **可視化/相関**: 既存アラート/インシデント/相関エンジン・②ベースライン・UEBAスコアに自然合流（インジェクション元プロセスの anomaly が上がる）。

EVENT_TYPE 追加・CHECK 制約・buf 生成・ETW/collector 追加は、image_load/script 追加（#212-215）と同じ手順を踏襲。

## 検知ロジック（M1 の核）

疑わしさスコア（誤検知を抑えるため複合条件）:
- `unbacked_exec`（ディスクにバックされない実行領域）= 強（floating code/反射型DLL）
- `rwx private` = 中〜強
- 領域エントロピー > 7.0（暗号化/圧縮シェルコード）= 加点
- 親/生成元が LOLBin・Office・スクリプトホスト = 加点（②/プロセスチェーンと相関）
- allowlist（既知 JIT: chrome/firefox/dotnet/java/node/wine 等）該当 = 減点/除外

「unbacked_exec ∧ rwx」または「rwx ∧ entropy>7 ∧ ¬allowlist」で高信頼アラート。

## M1 の運用設計（2026-08-01 追記・実機検証を反映）

M1 を既定ON（`EDR_MEMORY_SCAN=0/false/no/off` で opt-out、#511）にするにあたり、Windows 実機での計測から得た設計要件を記録する。詳細な経緯は [検知率向上_20260720_死んだ配線の復活と既定センサ有効化.md](../検知率向上_20260720_死んだ配線の復活と既定センサ有効化.md) §2.1。

### 1. 抑制機構が必須（`memFindingSuppressor`）

**周期スキャナは状態を持たないと、存在し続ける領域を毎周期そのまま再送する。** 実測では、稼働中の powershell.exe 1つ（.NET CLR の JIT が確保した RWX 領域10個）だけで **10件/分 ＝ 約14,400件/日/台**の重複イベントを生んでいた。実検知が1件も無い状態でである。

対処は「状態のダンプ」から「**変化の検知**」への転換:

- 領域を**初回検出時に1度だけ報告**し、存在し続ける間は沈黙する。
- 同一性のキーは `(pid, プロセス名, アドレス, サイズ, 権限, YARA判定)`。**領域の拡大・権限変更・ルール一致の開始はいずれも新情報**であり、重複として抑制してはならない。プロセス名を含めるのは、PID 再利用時に前プロセスの抑制状態を継承して領域が隠れるのを防ぐため。
- 追跡集合は**毎周期そのとき存在する領域から再構築**する。消えた領域と終了プロセスは自然に刈られ、集合は「今生きているもの」に有界化される。消滅後の再出現は再びアラートする（確保→解放→再確保は実際の攻撃パターン）。

**検知能力は低下しない。** インジェクションは「直前まで存在しなかった領域」として現れるため、抑制を通過する側に残る。むしろ新規領域の出現がシグナルとして際立つ。

### 2. allowlist は検知対象を盲目にしうる（本設計「誤検知対策」への重要な但し書き）

上記のノイズ源は powershell.exe だったが、**`powershell.exe` を allowlist に追加してはならない**。本スキャナが検知対象とするもの（T1059.001 ファイルレス PowerShell、T1055、T1620）が、まさに powershell.exe の RWX メモリ上に存在するためである。JIT の RWX と実装の RWX が同じ場所に同居しているのが、この検知の本質的な難しさ。

allowlist（`memoryScanAllowlist`）は「そのプロセスを丸ごと走査対象から外す」措置であり、**最もノイズの多いプロセスが最も攻撃者に狙われるプロセスである場合、FP 対策が検知の穴になる**。ノイズ低減はまず抑制機構とサイズ床（`minRWXAlertBytes` / `minUnbackedAlertBytes`）で行い、allowlist は「そのプロセスでの検知を放棄してよい」と判断できる場合に限る。

### 3. 実測コスト（Windows Server / 105-109プロセス / SeDebugPrivilege 有効）

| 項目 | 実測 |
|---|---|
| 1周の所要時間 | avg 565-593ms |
| **60秒周期の占有率** | **0.94 - 0.99%** |
| 走査プロセス | 94-98（未オープン 11-12 = SeDebugPrivilege でも開けないもの） |
| 検査領域 | 約56,000 |
| 最遅プロセス | SearchApp.exe 59-66ms（単独支配なし） |
| 定常イベント量（抑制後） | **0件/日/台** |

SeDebugPrivilege の有無で占有率は変わらない。**未検証**: 多セッションの RDS/ターミナルサーバ（プロセス数が数倍〜十数倍）。計測手順は [ops/メモリスキャン負荷計測ランブック.md](../ops/メモリスキャン負荷計測ランブック.md)。

### 4. 計測基盤（常設）

- `collector.MemoryScanStats` / `ScanSuspiciousMemoryWithYARAStats`（linux/windows/スタブ）が1周分のコストを返す。既存の `ScanSuspiciousMemory` / `ScanSuspiciousMemoryWithYARA` は薄いラッパで**シグネチャ・挙動は不変**。
- `edr-agent -memscan-bench N` : 設定・登録・サーバ接続いずれも不要、イベント送信なし。稼働中エージェントと並行実行できる。
- 周期ごとの負荷ログは **Debug 級**（60秒周期では1台あたり約1,440行/日になるため）。`logging.level=debug` で有効化。

### 5. メモリ内 YARA の内容スキャン（Linux / Windows 実装済み）

RWX 領域の**バイト列を実際に読んでキュレート済みルールと照合**する。Linux は `/proc/<pid>/mem`、Windows は `ReadProcessMemory`（いずれも1領域あたり最大 `maxRegionScanBytes`=4MiB）。列挙だけでは「構造的に不審な領域がある」までしか言えず、**「これは既知の実装である」とは言えない** — Cobalt Strike / Meterpreter / Mimikatz / Havoc のマーカーが機能するのはこの経路があるときだけ。

対象の絞り込みは共有述語 `shouldContentScan(rwx, guarded)` に集約している:

- **RWX 領域のみ読む。** 非バック read-execute 領域は通常のプロセスにも多数存在するため、これも読むとスキャンコストが跳ね上がる割に信号が薄い。
- **ガードページ（Windows `PAGE_GUARD`）は読まない。** ガードは所有プロセスにアクセスを通知するために存在し、スタック伸長がこれに依存しているため、読むこと自体が中立な観測ではない。列挙対象からは外さない（領域の存在は報告する）。

Windows では `PROCESS_VM_READ` を付けて `OpenProcess` し、**拒否された場合は query-only にフォールバック**する。1プロセスの内容スキャンを失う方が、そのプロセスを列挙から丸ごと落とすより遥かに軽微なため。内容スキャンは領域ウォークと同じハンドル内で行う（領域ごとに再オープンするコストを避けるため、かつガードページ判定に必要な `MEMORY_BASIC_INFORMATION` がそこにしか無いため）。

**YARA 一致はサイズ床を無条件に上書きする**（`shouldEmitMemoryFinding`）。小さくとも特徴的な実装は報告される。

## フェーズ計画と検証粒度

| Phase | 内容 | OS | 工数 | 実機検証 |
|---|---|---|---|---|
| **M1-Linux** | `/proc/pid/maps` RWX/unbacked スキャン → memory テレメトリ → server 検知 | Linux | 中 | **手元 Linux EC2 で即可**（mmap RWX のテストペイロードで実証） |
| M1-Windows | `VirtualQueryEx` RWX/unbacked | Windows | 中 | Win EC2 |
| M2 | ドライバ拡張（注入ハンドル/リモートスレッド audit） | Windows | 低（W4a流用） | Win EC2（テストモード） |
| M3 | 対象プロセスのインメモリ YARA | 全 | 中 | 既知シェルコード署名で |
| M1-macOS | `mach_vm_region` | macOS | 高 | 要 entitlement 検討 |

**推奨着手スライス = M1-Linux**：カーネル不要・クロスOS へ拡張容易・**手元の Linux EC2 で実ペイロード（RWX mmap + シェルコード様バイト）を使って即実証**できる。最初に「メモリを実際に見て検知する」骨格（テレメトリ型＋スキャナ＋サーバ検知器）を通し、以降 Windows(M1/M2)・YARA(M3) を載せる。
