# ネットワーク C2 振る舞い検知の多信号フュージョン設計

**目的**: ATT&CK 検知カバレッジ監査で「真の穴＝プロセス署名を持たないビーコン検知（通信周期性/JA3/DNS
エントロピー）」「別軸＝新検知クラス（コード規模大）」とされた領域を、**既存資産を土台に段階実装**する設計。
Sigma ルール追加では届かない、ネットワーク振る舞い軸の検知を拡張する。

**位置づけ**: `docs/EDR競争力向上ロードマップ` の「C. 構造的な新検知クラス」の設計版。
`docs/ATT&CK検知カバレッジ監査.md` §12(C2)・§13(Exfil) の残穴に対応。

---

## 0. 前提の再確認 — まず既存を精査した（新規実装ではなく差分設計）

本プロジェクトの規律に従い、着手前に既存実装をコード精査した。**ビーコン検知の中核は既に存在し、
ライブ配線済み**である。設計は「新規作成」ではなく **既存への信号追加とフュージョン** になる。

### 既にあるもの（再利用する土台）

### 本当に無いもの（＝この設計で埋める差分）
1. **JA3/JA3S TLS フィンガープリント** — コードベースに皆無。**agent 側テレメトリ実装が必須**（TLS ClientHello から JA3 算出）。既知マルウェア（Cobalt Strike/Sliver/Metasploit）の TLS 指紋を、周期性が無くても捕捉できる。
2. **DGA/DNS エントロピースコアリング** — ファイル用 `shannonEntropy` はあるが **DNS クエリ用の per-query エントロピー/n-gram DGA スコアが無い**。`compliance/scorer.go` の「DGA patterns」はコンプラチェックであって検知エンジンではない。
3. **多信号フュージョン** — ★最大の穴。ビーコン検知は **周期性単独**で sev7 を出す。宛先レピュテーション(TI)・JA3 一致・宛先新規性・生 IP 直結(no-DNS)・データ量非対称と**融合していない**。これが誤検知(正規ハートビートも周期的)の主因であり、アナリストの最大の痛点。

## 1. 設計の核 — 多信号 C2 スコアフュージョン

単一信号（周期性だけ、JA3 だけ）は FP か FN のどちらかに倒れる。**複数の弱い信号を宛先(agent,dstIP/domain)
単位で合成し、合成スコアで重大度を段階化**する。周期性単独は今のまま medium で残し、他信号が重なった時だけ
high/critical に昇格させる（＝FP を増やさず true positive の確信度を上げる）。

### 信号カタログ（各々が 0.0–1.0 の部分スコア）
| # | 信号 | ソース | 新規/再利用 | 検出対象 |
|---|---|---|---|---|
| S1 | **周期性**（調和折り畳み CV/clean-frac） | `beacon_detector.go` | ♻️再利用 | 定期 call-home |
| S2 | **宛先レピュテーション**（TI 一致・confidence） | `engine.go` TI 照合 | ♻️再利用 | 既知 C2 IP/domain |
| S3 | **JA3/JA3S 既知不良一致** | agent JA3 + server 既知不良 DB | 🆕新規 | 署名なし implant の TLS 指紋 |
| S4 | **DGA/DNS エントロピー** | server（`shannonEntropy` 転用+n-gram） | 🆕新規（一部転用） | DGA ドメイン・DNS トンネル |
| S5 | **宛先新規性/希少性**（fleet 全体で稀・初観測） | server（network events 集計） | 🆕新規 | 新しい C2 インフラ |
| S6 | **生 IP 直結(no-DNS)** | server（DNS 解決履歴と突合） | 🆕新規 | ドメイン無しの直 IP beacon |

### フュージョン式（宛先キー = agent|dstIP または agent|domain）
```
score = wS1·S1 + wS2·S2 + wS3·S3 + wS4·S4 + wS5·S5 + wS6·S6      (Σw = 1)
severity:
  S2 or S3 が確定一致(既知C2/既知不良JA3)         → critical(9)   即時（他信号不問）
  score ≥ 0.75 かつ 2信号以上が寄与               → high(8)
  score ≥ 0.50（周期性含む）                        → medium(7)   ← 現状のビーコン相当
  それ未満                                          → 発火せず（テレメトリのみ）
```
- **周期性単独（S1 のみ）は今と同じ medium**。回帰を起こさない（既存挙動を包含）。
- S2/S3 の確定一致は単独で critical（既知 C2/既知不良指紋は周期性を待たない）。
- 重み `w*` は env で調整可能（`C2_FUSION_W_*`）、初期値は S1=0.30/S2=0.25/S3=0.20/S4=0.10/S5=0.10/S6=0.05。

### FP 制御（curate と同じ規律）
- **allowlist**: 正規の周期通信（OS更新・NTP・監視SaaS・テレメトリ）を宛先/JA3/ドメインで抑制。既存 suppression 基盤を再利用。
- **信頼度露出**: アラートに「寄与信号 N/6・score X.XX」を明示（IOC の confidence 露出と同型）。
- **FP 自動隔離**: curate と同型に、window 内で閾値超の FP を出す融合ルールは自動デチューン（重み低下 or 抑制）。

## 2. 各新規信号の設計

### S3: JA3/JA3S フィンガープリント（★agent テレメトリ必須＝センサ深度）
- **agent 側（新規）**: 送信 TLS ClientHello をパースし JA3（version,ciphers,extensions,curves,formats の MD5）を算出。応答 ServerHello から JA3S も。Linux は eBPF もしくは接続時のパケット先頭スニフ、Windows は ETW-TI/WFP。**最小実装**: 平文で観測可能な ClientHello の JA3 のみ（フルパケットキャプチャ不要）。
- **network event に `ja3`/`ja3s` フィールド追加**（`field_support.go` の kitchen に追加＝Sigma からも参照可能に）。
- **server 側（新規）**: 既知不良 JA3 DB（Cobalt Strike/Sliver/Metasploit/Meterpreter のデフォルト指紋、公開 abuse.ch JA3 フィード）を `feed_scheduler` と同型で同期。S3 = 一致で 1.0、fleet 内希少 JA3 で 0.5。
- **段階**: Ph3（agent 実装＋実機検証が要る＝最重量）。**先に S1/S2/S4/S5/S6 のサーバ完結分を出す**。
- FP: 正規アプリの JA3 は多様。**既知不良一致のみ高スコア**、希少性は補助信号に留める。

### S4: DGA/DNS エントロピースコア（サーバ完結）
- `dnsAgg` に per-query スコアラを追加。**`shannonEntropy` を DNS ラベルへ転用** + 英語 bigram 尤度（DGA は低尤度）。
- 指標: ①ラベルの Shannon エントロピー ②bigram 改良度（辞書外連続） ③長さ ④数字比率 ⑤同一 agent の NXDOMAIN 率（DGA は失敗照会が多い）。
- S4 = これらの合成。閾値超で「DGA 疑いドメイン」。既存 T1568.002(DGA) の静的ルールを**振る舞いスコアで補完**。
- FP: CDN/クラウドのランダム風 FQDN（`d1a2b3c4.cloudfront.net` 等）を既知サフィックス allowlist で除外。

### S5/S6: 宛先新規性・生 IP 直結（サーバ完結・既存データのみ）
- **S5 新規性**: `network events` を fleet 全体で集計し、その (dstIP/domain) が「初観測 or N台未満でしか見ない」を希少度に。C2 インフラは新規で希少。
- **S6 no-DNS**: 同 agent の直近 DNS 解決履歴に無い dstIP への直結＝ドメインを介さない生 IP beacon（implant によくある）。`dnsAgg` の解決記録と network events を突合。
- どちらも**既存テレメトリのみ**で実装可＝Ph1 で先行導入可能。

## 5. Ph4 詳細設計（JA3/JA3S）— agent テレメトリ実装計画

Ph1–3（S2/S4/S5/S6）はサーバ完結で実装済み。**残る Ph4 だけが agent 改修＋実機検証を要する重量級**。
着手前の精査で、JA3 が必要とする**生パケット捕捉の機構は既に agent に存在**することが判明した
（`dns_collector.go` の AF_PACKET）。Ph4 はこれを TLS ClientHello に拡張する差分実装である。

### 7.1 何を捕捉するか（復号しない）
- **JA3** = TLS **ClientHello** の (TLSVersion, CipherSuites, Extensions, EllipticCurves, ECPointFormats) を
  順序保存で連結し MD5。**JA3S** = ServerHello 版。implant（Cobalt Strike / Sliver / Metasploit / Meterpreter）は
  TLS スタックのデフォルト構成を使うため**特徴的な JA3 指紋**を残す。プロセス署名・コマンドラインが無くても
  TLS 指紋で捕捉できる＝**署名なしビーコンの本丸（S3）**。
- ClientHello は**平文**。復号（MITM）はしない。メタデータのみ。GREASE 値は除外（RFC 8701）。

### 7.2 捕捉点 — 既存 AF_PACKET を再利用（★Linux 先行・最短）
- ★`agent/internal/platform/linux/dns_collector.go` が既に `AF_PACKET/SOCK_RAW/ETH_P_ALL` で**送出パケットを
  L2 で捕捉**している（DNS 用）。**JA3 は同じ機構を TLS ClientHello に拡張するだけ**。
- **カーネル側 BPF フィルタで絞る**（性能必須）: TCP かつ payload 先頭が TLS record `0x16`(handshake) かつ
  handshake type `0x01`(ClientHello)。ServerHello=`0x02`→JA3S。**接続の最初の1パケットのみ**を対象。
- ClientHello をパースし JA3 算出 → 5-tuple に紐付けて `NetworkEvent.ja3` に載せる（または軽量 `TlsEvent` を
  emit し server 側で connect と相関）。先頭 ≤~1500B のみ読み、ClientHello 以外は即破棄。CAP_NET_RAW（agent は root）。
- 既存 DNS collector と同居（同一 AF_PACKET を共有 or 2枚目ソケット＋別 BPF フィルタ）。

### 7.3 OS 別の捕捉戦略（サブフェーズ）
| サブPh | OS | 手法 | 依存・リスク |
|---|---|---|---|
| **Ph4a** | Linux | **AF_PACKET**（既存 `dns_collector` パターン再利用）＋BPFフィルタ | 最短。root/CAP_NET_RAW のみ |
| Ph4b | Windows | ① **ETW Schannel**(Microsoft-Windows-Schannel、署名不要)を優先検証 → ClientHello 生バイトが取れなければ ② **WFP callout** ドライバ | WFP は**ドライバ署名(W5 EV+WHQL)依存**＝[調達ランブック](../ops/Windowsドライバ本番署名%20調達ランブック.md) のリードタイム大。ETW 経路を先に検証 |
| Ph4c | macOS | `/dev/bpf`(BPF device=AF_PACKET 相当) | entitlement 制約。ESF では TLS payload 不可。最劣後 |

JA3S（ServerHello）は各 OS で ClientHello と同経路の追加。

### 7.4 proto / テレメトリ拡張
- `proto/agent/v1/events.proto` の `NetworkEvent` に `string ja3 = 15;` `string ja3s = 16;` を追加（新フィールド＝
  後方互換）。`bytes_sent`/`is_encrypted` 等の既存フィールドと同居。
- `server/internal/detection/field_support.go` の kitchen に `ja3`/`ja3s` を追加 → **Sigma からも参照可能**に
  （既知不良 JA3 の Sigma ルールも書ける＝二経路で活用）。
- agent→server 正規化で ja3 を network event flatMap に載せる（既存の network フィールド正規化に追記）。

### 7.5 server 側 — 既知不良 JA3 DB とフィード同期
- **migration** で `known_ja3`(ja3 hash, label, source, severity, added_at) を追加。**seed**: Cobalt Strike /
  Sliver / Metasploit / Meterpreter のデフォルト JA3（公開値）。
- **`feed_scheduler` と同型**で abuse.ch **SSLBL JA3** フィードを定期同期（既存 P4-1 のフィード同型スケジューラを
  踏襲＝新規スケジューラ最小）。
- 照合: network event の `ja3` が `known_ja3` に一致 → **S3=1.0（確定）**。fleet 内**希少 JA3** → S3=0.5（補助信号）。

### 7.6 フュージョン S3 配線（既存 `C2FusionScorer` に加算）
- `ObserveTLS(agentID, dstIP, ja3 string, knownBad bool)` を追加（Ph1–3 の `Observe*` と同型）。宛先キー単位で
  ja3/knownBad を保持。
- `Fuse` で S3 を評価。段階化を更新（**既存 Ph1–3 挙動は不変＝S3 は加算のみ**）:
  ```
  S2(TI) or S3(既知不良JA3)                 → critical(9)   確定・単独昇格
  S4(DGA) or (S5&&S6) or (希少JA3 + 他1信号) → high(8)
  それ以外（周期性単独・単一弱信号）          → medium(7)     現状維持
  ```
- **既知不良 JA3 は S2(TI) と同格**（既知 implant 指紋への周期通信は周期性を待たず critical）。

### 7.7 FP 制御（JA3 は衝突する）
- JA3 は正規アプリと implant が**同一 TLS ライブラリなら衝突**する。→ **単独の「希少 JA3」では発火させない**。
  **既知不良（キュレートされた implant デフォルト）一致のみ高スコア**。
- **既知不良 DB の質がすべて**＝キュレーション必須（curate と同じ規律。誤登録 JA3 は FP フラッド源）。
- 企業内正規アプリの JA3 を suppression allowlist に登録（既存抑制基盤を再利用）。

### 7.8 計測・回帰固定
- **JA3 算出のユニットテスト**: 既知 ClientHello バイト列（テストベクタ）→ 期待 JA3 ハッシュ（GREASE 除外含む）。
  決定的・agent/実機不要。
- **フュージョン S3 テスト**: 既知不良 JA3→critical / 希少 JA3 単独→非昇格 / JA3+周期性→適切段階。`c2_fusion_test.go` に追加。
- **ライブ計測**: `attack-live-measure.yml`（本 PR で追加）に C2 シナリオ（隔離環境で Sliver/Mythic のデフォルト
  TLS beacon）を足し、JA3 捕捉→`known_ja3` 一致→critical を実機実証。`attack-scorer` の C2 戦術で before/after。

### 7.9 Ph4 内の推奨実装順
1. ✅**Ph4a-1 実装済（2026-07-09）: JA3 算出ライブラリ（純ロジック・パケット非依存）＋ユニットテスト**。
   `agent/internal/ja3/ja3.go`＝`ParseTLSRecord`/`ParseHandshake`(ClientHello を JA3 関連フィールドへ)、
   `JA3String`/`JA3`(md5)、`FromTLSRecord`(one-shot)。GREASE 除外(RFC 8701)。★**攻撃者由来パケットを
   パースするため全読み取りを境界チェックし、malformed/truncated は panic せずエラー**。テスト
   `ja3_test.go`＝既知ベクタ(GREASE 除去含む JA3 文字列/ハッシュ一致)・拡張なし・GREASE 判定・
   malformed 9 ケース非 panic。agent 全体ビルド緑。**Ph4a-2 以降（AF_PACKET 捕捉）が残**。
2. Ph4a-2: Linux AF_PACKET で ClientHello 捕捉 ＋ proto `ja3` ＋ 実機検証。
3. Ph4a-3: server `known_ja3` DB ＋ フィード同期 ＋ フュージョン S3 配線。
4. Ph4b: Windows（ETW Schannel 検証 → 不可なら WFP＋署名調達）。
5. Ph4c: macOS ＋ JA3S。

> ★**最小の第一歩**: Ph4a-1（JA3 算出の純関数＋テストベクタ）は、Ph1–3 と同じ「サーバ完結・低リスク」枠で
> この場でも実装可能。パケット捕捉(Ph4a-2)と OS 差(Ph4b/c)の重量級を後段に分離できる。

## 6. スコープ外（本設計に含めない）
- フルパケットキャプチャ/DPI（プライバシー・容量・性能の別問題）。JA3 は ClientHello 先頭のみで足りる。
- 復号（MITM）: しない。JA3 は平文メタデータのみ。
- 独自グローバル TI ネットワーク（別ロードマップ項目）。S2/S3 は外部公開フィード（abuse.ch JA3/OTX）に依存。

## 7. まとめ
- **周期性ビーコン検知は既に存在・ライブ稼働**（#441 調和折り畳み）。真の穴は **①JA3 ②DGA/DNSエントロピー
  ③多信号フュージョン**。
- 最大レバレッジは **③フュージョン**：既存の周期性＋TI を宛先単位で合成するだけで（新規テレメトリ不要）、
  確信度を上げ FP を下げられる＝Ph1 で即効。
- **JA3(Ph4) だけが agent 改修＋実機を要する重量級**。サーバ完結の Ph1–3 を先に出し、JA3 はセンサ深度の
  別トラックで進めるのが最短。
- 全 Ph を **合成 E2E＋ライブ計測＋FP ソーク**で回帰固定し、検知率スプリントの規律（作る→有効化→計測→維持）に乗せる。
