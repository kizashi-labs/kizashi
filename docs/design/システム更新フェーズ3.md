## 1. Phase 3 のスコープ

### やること
- Phase 2 の poller を **api container から独立した `updater` コンテナに extract**
- updater が `docker compose pull / up -d --no-deps` を **shell out** で実行
- 適用前に `pg_dump` を自動取得（リストアは手動）
- 適用後に **ヘルスチェック → 失敗時に image tag を自動 revert**
- `system_updates.status` を `approved → applying → success/failed/rolled_back` に正しく遷移
- 失敗時の運用ガイド（リストア手順）を docs 化

### やらないこと（Phase 4 以降）
- ❌ 無人自動適用（メンテナンスウィンドウ、auto_apply_patch/minor フラグ honoring）
- ❌ 段階的ロールアウト（カナリア、A/B）
- ❌ DB スキーマ自動ロールバック

### Phase 3 完了時点の挙動

1. UI で「承認して適用」を押す
2. `system_updates.status = approved`
3. updater コンテナが 30 秒ごとに DB をポーリング、`approved` 行を検出
4. `applying` に遷移、`pg_dump` を `/var/backups/edr/<timestamp>.sql.gz` に出力
5. `docker compose pull api frontend` 実行
6. `docker compose up -d --force-recreate --no-deps api frontend`
7. 30 秒間 `https://localhost/healthz` を polling
8. 成功 → `success`、失敗 → `IMAGE_TAG` を旧版に戻して再 `up`、`rolled_back` 記録
9. UI 上で履歴に状態が反映される

### セキュリティ境界
- updater コンテナのみが Docker socket をマウント
- api / frontend / postgres には Docker socket 不要（Phase 2 と同じ）
- updater コンテナは **read-only filesystem** + `cap_drop: ALL`（Phase 5 で追加検討）
- updater イメージには `docker-cli` + `docker-compose-plugin` + `postgresql-client` を含める

## 5. セキュリティ境界（pen test 対応）

### updater コンテナの権限スコープ
- ✅ Docker socket: read-write（必須）
- ✅ /workspace/docker-compose.yml: read-only
- ✅ /workspace/.env: read-only
- ✅ /var/backups/edr: read-write（dump 出力先）
- ❌ /workspace/server/: マウントしない
- ❌ /var/log/: マウントしない

### updater コンテナの脅威モデル
- 攻撃者が updater を侵害 → ホスト上の任意のコンテナを起動・破棄できる（root 相当）
- 緩和策:
  - イメージ署名検証（Phase 5 で cosign 統合検討、Phase 3 では未実装）
  - GitHub Releases から取得する image tag を strict allow-list でフィルタ（`^[0-9]+\.[0-9]+\.[0-9]+$` のみ許可）
  - audit log: image pull / up 操作を全て `system_updates` テーブルに記録（既存）
- pen test で必ず指摘される点:
  - Docker socket 権限の範囲
  - updater 侵害時の blast radius
  - image 署名検証の有無

## 6. ロールバック設計

### Image rollback（Phase 3 自動）
1. apply 開始時: 現在の `IMAGE_TAG` を `system_updates.rollback_from_version` に保存
2. 適用後 health check 失敗:
   - `IMAGE_TAG=<rollback_from_version>` で `docker compose up -d --force-recreate --no-deps api frontend`
   - 再度 health check
   - 成功 → `status=rolled_back`、`failed_reason='health check timeout'`
   - 失敗 → `status=failed`、`failed_reason='rollback also failed: ...'`（手動介入必須）

### DB rollback（Phase 3 では手動）
1. apply 開始時: `pg_dump | gzip > /var/backups/edr/<id>-<timestamp>.sql.gz`
2. 適用後 migration 失敗:
   - `status=failed`、`failed_reason='migration <number> failed'`
   - **管理者は `docs/ops/system-update-rollback.md` に従い手動でリストア**
3. リストア手順は別ドキュメントに記載（Day 6）

## 9. リスクと緩和策

| リスク | 緩和策 |
|---|---|
| Docker socket 経由の権限昇格 | ペネトレ前に updater イメージを最小化、cap_drop ALL を Phase 5 で追加 |
| updater 自身のアップデート（recursive 問題） | Phase 3 では updater は手動 pull/up（`docker compose pull updater && up -d`）と明記 |
| pg_dump がストレージを圧迫 | デフォルト 3 世代保持、cron で古い dump を削除（Phase 5） |
| compose CLI のバージョン依存 | updater イメージで CLI を fix（`docker:24-cli`）、ホストの CLI バージョンに依存しない |
| 顧客 compose カスタマイズで service 名が違う | 環境変数 `UPDATER_TARGET_SERVICES=api,frontend` で override 可能に |
| health check が 30 秒で足りない（DB migration 重い） | `UPDATER_HEALTH_TIMEOUT` を環境変数で延長可能に（デフォルト 30s、最大 5min） |
