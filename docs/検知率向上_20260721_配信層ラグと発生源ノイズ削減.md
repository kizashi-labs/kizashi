# 検知率向上 2026-07-21 — 配信層ラグの根治と発生源ノイズ削減

このセッションの主題は、**「静的解析・unit test・コードカバレッジがすべて緑でも、publish/配信層（JetStream
consumer）で検知が死ぬ」層を能動計測でのみ特定・実証・恒久修正する**こと。当初の仮説（consumer を
水平スケールすれば直る）は、計測を重ねるたびに真因が入れ替わり、最終的に別の恒久対応へ到達した。

本番稼働サーバ（EC2 2コア・ネイティブ postgres16 + nats3ノード + `go build` した detection、Linux eBPF
agent）に対し、各修正を **NATS 直接購読・JetStream consumer メトリクス・agent CPU の実測**で検証した。

関連: consumer 設定の指針は [ops/パフォーマンスチューニング.md](ops/パフォーマンスチューニング.md) §3.2、
ラグ対応ランブックは [ops/監視ランブック.md](ops/監視ランブック.md#edrdetectionconsumerlag)、
CI 側の是正は [ops/CI負債_調査と是正.md](ops/CI負債_調査と是正.md) に反映済み。

---

## 0. なぜ能動計測でしか捕まらなかったか

検知パイプラインは `NATS(events.>) → detection consumer → ルール評価 → アラート`。
静的解析・unit test・カバレッジは**コードの正しさ**を見るが、この障害は**配信層の実行時挙動**
（プリフェッチ／再配信／ホスト CPU／流入イベントの内訳）に宿っていた。コードは正しく、テストも緑で、
それでも本番では検知がリアルタイムに動いていなかった。

決定的だった計測手法:

- **`ack_floor.consumer_seq` の前進速度**＝真の消化量。`delivered` は再配信で水増しされるので当てにならない。
- **`num_redelivered` の増加率**＝再配信ストームの判定。Delivered にほぼ等しければ黒。
- **`nats sub 'events.>'` の直接購読**＝発生源が今この瞬間に何を送っているか（subject 別内訳）。
- **agent プロセスの CPU**＝発生源フィルタが効いているかの傍証。

---

## 1. 真因①: 再配信ストーム（`MaxAckPending` ≫ 実 worker 並列）

### 症状
detection の pending が 66k→133k と増加し続け、`ack_floor` が特定シーケンスで**完全停止**していた。
台数を増やしても `ack_floor` は 0 のまま。

### 真因
consumer 設定が `MaxAckPending=1024`（実装当時の既定 1000 相当）に対し、実 worker 並列は 20
（`sem := make(chan struct{}, 20)`）、`AckWait` は未設定（既定 30 秒）だった。JetStream は 1024 件まで
クライアントへプリフェッチするが、処理は 20 並列なので残り約 1000 件はバッファに滞留し **AckWait タイマー
だけが進む**。1 件約 1.25 秒 × 1024 = 末尾は約 64 秒待ちで、**処理前に AckWait を超過して再配信**される。
これが繰り返され worker が重複処理に空転、**正味消化がほぼゼロ**になっていた。

### 修正（[PR #468](https://github.com/kizashi-labs/kizashi/pull/468)）
`server/internal/detection/engine.go` の consumer 設定を env 化し、既定を実並列に整合させた。

- `MaxAckPending` 既定を **`concurrency*3`** に（プリフェッチ滞留が必ず `AckWait` 内に捌ける範囲）。
- `AckWait` を**明示**（`DETECTION_ACK_WAIT_SEC` 既定 60 秒）。
- `DETECTION_CONCURRENCY` / `DETECTION_MAX_ACK_PENDING` で調整可能。共有 durable なので全レプリカで一致必須。

### 実測（単一レプリカ）
| 指標 | 是正前 | 是正後 |
|---|---|---|
| Redelivered | 約 8/s（Delivered とほぼ同値） | **0/s** |
| Outstanding Acks | 350〜600（無制限滞留） | 上限で頭打ち（飽和） |
| pending | **+11/s（増加）** | **-7/s（ドレイン）** |
| ack_floor | **完全停止** | 正常前進 |

> `ack_floor` の「完全停止」は poison message ではなく**ストーム期のアーティファクト**で、ストーム停止＋
> 追いつきにより自動解消した（履歴 backlog 126k も完全ドレイン）。

## 2. 否定された仮説: 同一ホストへの水平スケール

ストーム是正後、単一レプリカは処理 ~19/s で飽和した。ここで detection-2 レプリカを起動して検証したが:

- 本番 EC2 は **2 コア・load average 5.84（コア数の約3倍＝過飽和）**、detection-1 単体で **CPU 109%**。
- detection-2 は durable が分散せず **CPU 6% で飢餓**、しかも throughput が **19/s → 10/s に低下**。

**検知は CPU 律速**であり、同一 2 コアホストへのレプリカ追加は overhead だけ増えて逆効果と実証された
（[PR #465](https://github.com/kizashi-labs/kizashi/pull/465) のスケール土台は温存するが、
この instance では detection-2 を起動しない）。→ 真のレバーは**発生源のイベント量削減**。

## 3. 真因②: 発生源のテレメトリ・ノイズ（発生源フィルタ）

`nats sub 'events.>'` の直接購読で流入内訳を測ったところ、支配的なのは process イベントではなかった。

| subject | 割合（15秒サンプル） |
|---|---|
| credential（credaccess） | **52%** |
| file | 35% |
| process | 11% |
| network | 2% |

[#461](https://github.com/kizashi-labs/kizashi/pull/461) が file の runtime ノイズ
（`/tmp/runc-*`）を除去した路線を、process と credaccess に拡張した。設計原則は #461 と同じ
**「発生源で落とす」**（agent の emit 前）で、agent 自身の CPU・帯域・detection 負荷を同時に下げる。

### 3-1. process runtime ノイズ（[PR #470](https://github.com/kizashi-labs/kizashi/pull/470)）
`isRuntimeNoiseProc` で、コンテナ exec 毎に create+terminate を撒く runtime scaffolding
（`runc` / `runc:[N:INIT]` / `containerd-shim` / `crun` / `conmon`）を eBPF fast-path と procfs fallback の
双方で除外。**コンテナ内の実ワークロード（`bash`/`wget`/`xmrig` 等）は別 comm なので温存**し、
検知可視性を保つ。加えて `isRuntimeNoiseCmd` で `runc init`（kernel comm が `6` になり comm 一致で漏れる）を
command_line で捕捉。

- 実測: process イベント中の runtime-noise comm が **51% → 0%**（live 購読で確認）。
- agent CPU: **35% → 11.7%**。

### 3-2. credaccess の誤検知（[PR #471](https://github.com/kizashi-labs/kizashi/pull/471) / [#472](https://github.com/kizashi-labs/kizashi/pull/472)）
credaccess（`ptrace_access_check` の T1003/T1055 検知）の tracer 内訳は、**/proc を読むだけの良性プロセス**が
支配していた: `ps`=2039 / `runc`=712 / `landscape-sysinfo`=375 / `needrestart` / `systemctl` / … 。
これらは認証情報窃取ではなく、単なるプロセス一覧・コンテナ起動・システム点検である。

`isBenignCredTracer` で良性 tracer を emit 前に allowlist 除外。#471 で主成分（ps/runc/landscape 等）、
#472 で 22 時間の実測に基づき残タ尾（needrestart/systemctl/systemd-detect-virt/cloud-id、約 1150 件/日の
偽 T1003）を追加。

> **⚠️ セキュリティ・トレードオフ**: これは comm allowlist なので、`ps` 等に名前を偽装した悪性プロセスは
> **この credaccess センサーの検知を回避しうる**。誤検知氾濫（ストームの過半＋偽アラート）の停止と引き換えに
> 受容した判断（ユーザー承認済み）。偽装されたバイナリの実挙動は process / behavioral パイプラインで
> 引き続き可視。allowlist は**実測した comm のみの厳密一致**とし、broad な `systemd-*` prefix は使わない
> （証拠ベースを維持）。

### 能動テスト
`systemctl`×3・`ps aux`×3・`pgrep`×3・`needrestart` を実際に実行しても **credaccess 検知 0 件**を確認
（修正前は `ps aux` だけで大量発火）。lookalike（`systemd-evil` / `needrestarter` / `systemctl-x`）が
**非除外**であることも unit test で担保。

## 4. 最終状態（本番実測）

| 指標 | 調査開始時 | 現在 |
|---|---|---|
| detection pending | 66k〜133k（増加継続） | **0〜32（実質リアルタイム）** |
| 再配信 | 約 8/s（ストーム） | **≈0** |
| ack_floor 前進 | **0（完全停止）** | 正常追従 |
| inflow（agent 送信） | 約 27/s | **5/s** |
| box load（2 コア） | **5.84** | **0.78** |
| agent CPU | 35% | 11.5% |
| 偽 T1003/日 | 約 1,150 件 | **0** |

**恒久解消の核心**: inflow 5/s ≪ detection 処理能力 12〜19/s。供給が処理能力を大きく下回ったので、
検知はリアルタイムに追従し、二度と配信層で滞留しない。

## 6. 教訓

1. **`delivered` を消化量と誤読しない**。再配信で水増しされる。真の前進は `ack_floor`。
2. **`MaxAckPending` は「並列度の調整つまみ」ではない**。実 worker 並列と揃えないと再配信ストームを招く。
3. **水平スケールは万能ではない**。ホストが CPU 律速なら逆効果。「台数を増やす」前に律速を測る。
4. **配信層の障害は発生源から潰すのが最も効く**。消化側を増やすより流入を減らす方が、CPU も帯域も同時に下がる。
5. **静的な緑は配信層の健全性を保証しない**。この層は能動計測（メトリクス実測・直接購読・実プロセス実行）でのみ見える。

## 7. 稼働中の consumer が「修正版」かを確認する（2026-07-23 追記）

修正が**今この瞬間に本番で効いているか**は、コードや PR ではなく**稼働中の consumer 設定**で確認する。
detection は GHCR `:main` イメージから updater 経由で再デプロイされるため、`DETECTION_*` env を明示していなくても
**コード既定（`concurrency*3=60` / `AckWait 60s`）が修正値そのもの**として適用される（＝一度きりの手動ビルドに
依存せず、通常のデプロイ経路で恒久的に配信される）。2026-07-23 に `:main` からの自動再デプロイでこれを確認済み。

```bash
# ① 起動ログ（最も確実。値をそのまま出力している）
docker logs kizashi-detection 2>&1 | grep "検知consumerを起動" | tail -1
#   → concurrency=20 max_ack_pending=60 ack_wait=1m0s  なら修正版

# ② JetStream 側の権威ある consumer 設定
docker exec kizashi-nats-1 wget -qO- "http://localhost:8222/jsz?consumers=true&config=true" \
  | python3 -c 'import sys,json; d=json.load(sys.stdin); c=[c for a in d["account_details"] for s in a["stream_detail"] if s["name"]=="EVENTS" for c in s["consumer_detail"] if c["name"]=="detection-engine"][0]["config"]; print("max_ack_pending=%s ack_wait=%ss"%(c["max_ack_pending"], c["ack_wait"]//10**9))'
#   → max_ack_pending=60 ack_wait=60s  なら修正版
#   → max_ack_pending=1000 ack_wait=30s なら未修正（プリフェッチ滞留＝ストーム再発リスク）
```

> **⚠️ 再起動中の一過性に注意**: detection の再デプロイ直後は、`②` が**旧コンテナ由来の値（例 `1000/30s`）を
> 一瞬返す**ことがある。新インスタンスの `CreateOrUpdateConsumer` が durable を上書きするまでの窓。数十秒後に
> 再確認するか、`①` の**新インスタンスの起動ログ**（タイムスタンプで判別）を正とすること。2026-07-23 の調査で
> 実際にこの一過性の `1000/30s` を観測し、回帰と誤認しかけた。**権威は「最新インスタンスの起動ログ」**。
