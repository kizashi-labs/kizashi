## 0. baseline 未知プロセス検出の FP 根治（カーネルスレッド）

検証EC2 のインシデント相関実測中に、baseline 検出器（`server/internal/detection/engine.go` の baseline 経路 →
`behavioral.CheckProcessAnomaly`）が Linux カーネルワーカースレッドを
「このエンドポイントで通常見られないプロセス: kworker/u4:1」等として誤検知しているのを発見。

- **真因**: `kworker/u4:1`・`kworker/0:0-events`・`kworker/dying` 等は接尾辞（CPU/worker/workqueue 名）が
  動的に変わる。`BuildBaseline` の `TypicalProcesses`（上位50件・完全一致）に定着せず、毎回「初見」として
  sev4 アラートを量産していた。
- **実測（検証EC2）**: baseline 未知プロセスアラート **3,582件中611件（約17%）がカーネルスレッド**由来。
- **修正**: `isLinuxKernelThread()`（kworker/・ksoftirqd/・migration/・rcu_・kthreadd・jbd2/・irq/ 等30プレフィックス、
  `[kworker/...]` 括弧・前後空白許容）で `CheckProcessAnomaly` の源流除外＋`BuildBaseline` の上位50枠浪費防止。

本修正（[#419](https://github.com/kizashi-labs/kizashi/pull/419)）は、並行セッションが同時に実装していた
**上位互換の [#420](https://github.com/kizashi-labs/kizashi/pull/420)** に統合されてマージされた。#420 は
`isLinuxKernelThread` をそのまま取り込んだ上で、残り約2,971件の短命良性ユーザーランドツール
（chmod/rm/cron・motd 断片等）を **プロセス名でなく実行元ディレクトリ**で判定する `isSuspiciousExecPath` を追加した
再設計（未知プロセスが `/tmp`・`/dev/shm`・`/home` 等の疑わしい先から実行された時のみ発火、system 配下は抑制）。
#419 は差分が空になり自動クローズ。詳細は [[project_baseline_unknown_process_fp_20260707]] / [[project_fp_hardening_dedup_20260706]]。

## 1.「検知率を上げる次のレバー」分析

Windows は既に飽和（可視性/検知/Technique ~100%、容易な recall レバーは枯渇＝

[docs/results/live-20260702-windows-discovery.md](results/live-20260702-windows-discovery.md)）。
伸びしろは Linux 側にある。推奨順①〜④を精査した結果は次のとおり。

| # | レバー | 判定 | 根拠 |
|---|---|---|---|
| ① | /home FIM 可視性 | **真のギャップ**（並行 #423 が先取り実装） | FIM は /tmp・/etc・/root のみ監視で /home 不監視だった |

| ④ | ThreatFox フィード | **既に実装済み** | migration 287＋`parseThreatFoxCSV` |

### ③ が既に埋まっていたことの確認

`server/internal/detection/sigma_builtins.go` と `migrations/*.sql` を grep した結果、横展開/実行/C2 の候補技法は

**→ 投機的なルール追加は重複と FP を生むだけ**で、真の残ギャップの特定にはライブ再計測が必要（「実測ファースト」）。

### ④ が既に実装済みだったことの確認

abuse.ch ThreatFox は migration 287 でフィード登録（`is_active=TRUE`）済みで、`internal/intel/feed_importer.go` に

## 2. ① センサー可視性 — FIM /home 拡張（並行 #423）＋ server 側補完（本 PR #426）

### 発見: migration 309 の注記は不正確だった

migration 309 は authorized_keys（T1098.004）/.bashrc（T1546.004）を
**「file テレメトリが /home 未監視の『センサー欠落』ゆえルールでは不可（eBPF file probe 拡張が別途必要）」** と注記していた。

しかし FIM コレクタ（`agent/internal/collector/fim_collector.go`）は **eBPF ではなく SHA-256 ポーリング**であり、
**ポーリングの監視パスに /home を足すだけで足りる**（eBPF 拡張は不要）。この点を実証・修正した。

- 並行セッションが [#423](https://github.com/kizashi-labs/kizashi/pull/423) で FIM に glob 対応
  （`expandGlob`）と /home/*/.ssh・.bashrc・.config/systemd/user・autostart 監視を実装（センサー側）。
- 本 PR #426 が **server 側の欠けたピースと追加パス**を補完（下記 §4）。

### file_event ルーティングの確認

FIM イベントは `handler.go` で `path`→`TargetFilename`/`FilePath`、`change_type`→`Operation` に alias され、
`category: file_event` の Sigma ルールにフィールドで一致する。**`rule_engine` は logsource.category を
マッチのゲートには使わず**（`product` による platform ゲートのみ）、フィールド一致で判定する。
authorized_keys の file_event builtin ルールが FILE イベントで発火することをユニットテストで固定した
（`home_persistence_file_event_test.go`）。

## 3. ② テレメトリ信頼性 — プロセスイベントの silent drop 根絶

### 真因

`agent/internal/platform/linux/process_ebpf.go` の **procfs フォールバック経路**（`pollProcFS`）が、
プロセスイベント送信を全て次の形で行っていた:

```go
select {
case out <- evt:
default:      // ← チャネル(buf 1000)満杯時にイベントを黙って捨てる
}
```

バーストや下流（アップローダ）の一時的な詰まりで、**背圧なく・メトリクスなく検知対象イベントが消える**。
これが「Linux process telemetry の間欠 drop（検知率の隠れ天井）」の正体。
一方、eBPF 主経路（`ebpf_loader.go`）は `case <-ctx.Done()` の**背圧**で正しくドロップしない
＝経路で挙動が非対称だった（#423 は FIM のみでこの経路は未修正）。

> ※ P4-2 で過去に決着した eBPF ドロップ（stale `.o` / `needBytes` 不整合）とは**別の**問題。
> こちらは procfs フォールバック経路の silent drop。

### 修正

eBPF 主経路と同じ**背圧（blocking + ctx 対応）**に統一する `sendProcEvent` を導入し、`select default:` を撤去。

```go
func sendProcEvent(ctx context.Context, out chan<- collector.ProcessEvent, evt collector.ProcessEvent) bool {
	select {
	case out <- evt:
		return true
	case <-ctx.Done():
		return false
	}
}
```

通常時はバッファ（1000）が吸収し、過負荷時のみブロック（ctx で shutdown 可）。EDR は検知イベントを
黙って捨てないのが正しい不変条件。dns/file/network collector も同じ `default:` ドロップを持つが、本 PR は
名指しのギャップである **process 経路に限定**（他テレメトリ型は volume 特性が異なるため別途判断）。

## 5. 教訓

- **migration の注記を鵜呑みにしない**: 309 の「eBPF file probe 拡張が必要」は不正確で、ポーリング FIM の
  パス拡張で足りた。実装機構（eBPF か polling か）を確認してから難易度を見積もる。
- **silent drop は検知率の隠れ天井**: 「ルールが無い」より前に「テレメトリが届いているか／捨てていないか」を疑う。
  経路間で挙動（背圧の有無）が非対称だと、片方だけノイズなく劣化する。
- **共有リポで並行セッションが同じ推奨を実装中**: 本日、baseline FP（#420）・FIM /home（#423）・migration 番号
  （310→311 に採番し直し）で計3度先取りされた。**着手前に `git grep origin/main` / `ls-tree origin/main` で
  重複と番号衝突を確認する**と手戻りが減る。
- **真の残ギャップはライブ再計測で特定する**: ③④のように、推測での「欠けている」判断は実装済みと衝突しがち。
  次アクションは Linux 能動計測バッテリの再走で、PR#416/#420/#423/#426 反映後の Tactic 止まり/MISS を実測すること。
