## 1. エスカレーション組織構造と各ロールの責任範囲

### 1.1 組織階層

```
[CEO]
  └── [CTO（最高技術責任者）]
        ├── [Engineering（開発チーム）]
        │     ├── バックエンドエンジニア
        │     ├── セキュリティリサーチチーム
        │     └── インフラ/SREチーム
        └── [サポート組織]
              ├── L3: テクニカルサポートマネージャー（TSM）
              │     └── 製品スペシャリスト（製品ドメインごと）
              ├── L2: シニアサポートエンジニア（SSE）
              └── L1: フロントラインサポートエンジニア（FSE）
```

### 1.2 各ロールの責任範囲

#### L1 — フロントラインサポートエンジニア（FSE）

| 項目 | 内容 |
|------|------|
| **主な業務** | お客様からの問い合わせ・障害報告の受付、初期トリアージ、基本的なトラブルシューティング |
| **意思決定権限** | P3/P4の障害対応、一般的な操作・設定に関する回答 |
| **エスカレーション条件** | P1/P2障害の受付時、初期対応で解決しない場合、お客様からのエスカレーション要求時 |
| **SLA責任** | 初期応答時間の遵守 |
| **勤務時間** | Starter: 平日9:00〜17:00 JST / Professional: 月〜土 8:00〜20:00 JST / Enterprise P1: 24×7×365（ローテーション） |

#### L2 — シニアサポートエンジニア（SSE）

| 項目 | 内容 |
|------|------|
| **主な業務** | L1からエスカレーションされた複雑な技術問題の調査・解決、根本原因分析 |
| **意思決定権限** | P1/P2障害の技術的対応方針決定、ワークアラウンドの承認、緊急設定変更の承認 |
| **エスカレーション条件** | P1障害で2時間以内に解決の見通しが立たない場合、製品バグ・データ問題が疑われる場合、複数顧客への同時影響が確認された場合 |
| **SLA責任** | 解決目標時間の管理、重大障害の進捗報告 |
| **勤務時間** | 24時間365日（ローテーション、P1/P2対応） |

#### L3 — テクニカルサポートマネージャー（TSM）/ 製品スペシャリスト

| 項目 | 内容 |
|------|------|
| **主な業務** | 重大障害の指揮・調整、開発チームとのブリッジ、SLAパフォーマンス管理、再発防止策の決定 |
| **意思決定権限** | 開発チームへのエスカレーション承認、外部機関への報告判断（JPCERT等）、お客様への補償提案 |
| **エスカレーション条件** | P1障害で4時間以上解決しない場合、広域障害（複数顧客影響）の発生、セキュリティインシデント（データ漏洩疑い）の発生 |
| **SLA責任** | サポート組織全体のSLA遵守状況の監督 |
| **勤務時間** | 通常営業時間 + オンコール（P1重大障害時の呼び出しあり） |

#### 開発チーム（Engineering）

| 項目 | 内容 |
|------|------|
| **主な業務** | 製品バグの修正、緊急パッチのリリース、インフラ障害の復旧、セキュリティ脆弱性の修正 |
| **意思決定権限** | コード変更・緊急デプロイの実施、インフラ構成の変更 |
| **エスカレーション条件** | 製品バグ・インフラ障害が確認された場合（L3からのエスカレーション） |
| **SLA責任** | 緊急パッチのリリース時間目標（P1バグ: 24時間以内にHotfixリリース目標） |
| **勤務時間** | 通常営業時間 + オンコール（P1インフラ障害時） |

#### CTO（最高技術責任者）

| 項目 | 内容 |
|------|------|
| **主な業務** | 技術的な重大事案の最終判断、外部機関・報道機関への技術的声明、大規模インシデント時の指揮 |
| **意思決定権限** | サービス全停止・緊急シャットダウンの決定、外部セキュリティ専門機関への依頼承認 |
| **エスカレーション条件** | P1障害が8時間以上継続する場合、セキュリティインシデント（データ漏洩確定）、法的対応が必要な事案 |

#### CEO

| 項目 | 内容 |
|------|------|
| **主な業務** | 経営上の重大意思決定、規制当局・法執行機関対応、主要顧客への説明責任 |
| **意思決定権限** | 事業継続・サービス停止の最終決定、法的手続きへの対応方針 |
| **エスカレーション条件** | 広域データ漏洩の確定、規制当局による調査開始、主要顧客（Enterprise）からの契約解除通告 |

## 2. 障害レベル別エスカレーションフロー

### 2.1 P1（重大障害）— 全サービス停止 / セキュリティ緊急事態

```
【発生・検知】
お客様からの報告 or 当社監視システムによる自動検知
          ↓ 即時（分単位）
【初期受付 — L1 FSE】
- チケット作成・障害レベルをP1に設定
- お客様へ受付確認通知（SLA応答時間内）
- 内部エスカレーション通知（Slackの #incident-p1 チャンネルに投稿）
          ↓ 受付即時
【L2 SSE 対応開始】
- 技術的調査の開始
- ウォーブリッジ（電話会議ブリッジ）のセットアップ（Enterprise）
- 影響範囲の特定（単一テナント / 複数テナント）
          ↓ 30分経過・解決の見通しが立たない場合
【L3 TSM エスカレーション】
- TSMに状況報告・対応方針の協議
- 開発チームへの協力要請判断
- 広域障害の場合: ステータスページの更新
- お客様へ進捗報告（30〜60分ごと）
          ↓ 2時間経過・解決しない場合（P1 インフラ/バグ起因）
【開発チーム（Engineering）参加】
- SREチームによるインフラ調査・復旧作業
- バグ確認の場合: 緊急Hotfix対応開始
          ↓ 4時間経過（Enterprise）/ 8時間経過（全体）
【CTO 通知・指揮】
- CTO がインシデントコマンダーとして指揮を執る
- 必要に応じて外部セキュリティ専門機関への依頼
- 対外コミュニケーション方針の決定
          ↓ データ漏洩確定 / 法的対応必要
【CEO 報告・対応】
- CEO 判断による事業対応
- 規制当局（個人情報保護委員会等）への報告判断
- JPCERT/CC への報告（必要な場合）

【解決・クローズ】
- 復旧確認・お客様への復旧通知
- 事後報告書（PIR）作成（72時間以内）
- SLAクレジット算定・適用
```

---

### 2.2 P2（主要機能障害）— 一部主要機能の喪失

```
【発生・検知】
お客様からの報告 or 当社監視システムによる自動検知
          ↓
【初期受付 — L1 FSE】
- チケット作成・障害レベルをP2に設定
- お客様へ受付確認通知（SLA応答時間内）
- 内部通知（Slackの #incident-p2 チャンネルに投稿）
          ↓ SLA応答時間内 / L1で解決不可の場合
【L2 SSE 対応開始】
- 根本原因調査
- お客様への調査状況報告（2〜4時間ごと）
- ワークアラウンドの検討・提供
          ↓ 解決目標時間の50%経過・解決しない場合
【L3 TSM 関与】
- 対応方針の見直し
- 必要に応じて開発チームへエスカレーション
          ↓ 解決目標時間超過
【開発チーム参加（必要な場合）】
- 製品バグ確認の場合: 優先度付きバグ修正対応

【解決・クローズ】
- 復旧確認・お客様への復旧通知
- 事後報告書（PIR）作成（72時間以内）
```

---

### 2.3 P3（軽微な障害）— 軽微な機能不具合

```
【発生・検知】
お客様からの報告
          ↓
【初期受付 — L1 FSE】
- チケット作成・障害レベルをP3に設定
- お客様へ受付確認通知（SLA応答時間内）
          ↓
【L1 FSE による対応】
- 基本的なトラブルシューティング
- FAQ・ナレッジベースを活用した回答
- 必要に応じてL2へエスカレーション
          ↓ L1で解決不可
【L2 SSE 対応（必要時）】
- 技術的調査・対応

【解決・クローズ】
- 復旧確認・チケットクローズ
- 製品バグの場合: バックログに登録し次回リリースで対応
```

---

### 2.4 P4（問い合わせ・改善要望）

```
【受付 — L1 FSE】
- チケット作成・P4に設定
- ナレッジベース・ドキュメントで回答可能な場合: 即時回答
- 機能改善要望の場合: 製品チームのバックログに登録・お客様に通知

【クローズ】
- 回答完了後にチケットクローズ
- 機能要望の場合: 製品ロードマップ反映可否を追って通知
```

## 4. ウォーブリッジ / コールブリッジ手順

ウォーブリッジ（War Bridge）とは、P1重大障害発生時に当社内部の関係者が常時接続する音声/ビデオ会議ブリッジのことです。コールブリッジは、お客様も含めて参加する音声会議のことです。

### 4.1 ウォーブリッジ（内部）

#### 開催条件

- P1障害発生時（自動的に開催）
- P2障害で広域影響が確認された場合

#### 手順

```
Step 1: L2 SSE がインシデント検知・受付後、即時にウォーブリッジを開設
        - 会議URL: [社内インシデント管理ツールのURL] から自動生成
        - Slack #incident-p1 チャンネルに会議URLを投稿

Step 2: 参加必須メンバー
        - L2 SSE（インシデントコマンダー、解決まで）
        - L3 TSM（エスカレーション後、30分経過から参加）
        - Engineering SRE（2時間経過または技術的エスカレーション後）
        - TAM（Enterprise 顧客の場合、即時参加）

Step 3: ウォーブリッジ内でのロール分担
        - インシデントコマンダー（IC）: L2 SSE または L3 TSM
          → 全体の進捗管理・意思決定
        - テクニカルリード（TL）: Engineering SRE
          → 技術的調査・復旧作業の指揮
        - コミュニケーション担当（Comms）: FSE または TSM
          → お客様・ステータスページへの定期報告
        - スライブ担当（Scribe）: FSE
          → 対応タイムラインの記録（インシデント管理ツールに記録）

Step 4: 定期進捗確認（30分ごと）
        - 現在の状況
        - 実施中の対応内容
        - 次のアクションと担当者
        - 想定復旧時間（ETA）の更新

Step 5: 障害解消確認
        - 全コンポーネントの正常動作確認
        - お客様への復旧通知送付
        - ウォーブリッジの解散
        - PIR（事後報告書）作成担当の指名
```

### 4.2 コールブリッジ（お客様参加）

#### 開催条件

- Enterprise 顧客のP1障害で、TAMまたはお客様から音声会議参加の要求があった場合
- P1障害が2時間以上継続し、お客様への詳細説明が必要な場合

#### 手順

```
Step 1: TAM または L2 SSE がお客様に会議招待を送付
        - Google Meet / Microsoft Teams（お客様の希望に合わせて選択）
        - 招待メール記載事項: 障害概要・会議URL・参加方法

Step 2: 参加者
        [当社側]
        - L2 SSE または L3 TSM（技術説明担当）
        - TAM（Enterprise 顧客の場合、ファシリテーター）
        [お客様側]
        - セキュリティ担当者・システム管理者（担当者に一任）

Step 3: コールブリッジの進め方
        - 開始時: 障害状況の現況説明（5分）
        - 技術的調査状況の共有（質疑応答含む）
        - 想定復旧時間（ETA）の報告
        - 次回状況報告の時間を設定（例: 1時間後）
        - 終了時: アクションアイテムの確認

Step 4: コールブリッジ終了後
        - 議事録をお客様にメール送付（30分以内）
        - 次回コールまでの進捗は Slack または Email で随時報告
```

### 4.3 ウォーブリッジ記録の保管

- インシデント管理ツール（Jira / PagerDuty）にタイムラインとして記録
- 対応完了後にPIRとして正式な事後報告書に転記
- 保管期間: 3年間

## 5. 外部関係者連絡手順

### 5.1 JPCERT/CC への報告

#### 報告が必要なケース

- Kizashi の製品自体に重大なセキュリティ脆弱性が発見された場合
- お客様のシステムで発見された脅威が国内サイバーセキュリティ上の重大インシデントに該当する場合
- 当社のインフラに対する高度な標的型攻撃（APT）が確認された場合

#### 報告手順

```
Step 1: CTO または TSM が報告の必要性を判断
        → 判断基準: 当社単独で対処困難な規模・影響 / 業界横断的な脅威

Step 2: 報告担当者の指名（通常: TSM または CTO）

Step 3: JPCERT/CC への報告
        - 報告先: https://www.jpcert.or.jp/form/
        - 電話: 03-6271-8901（緊急の場合）
        - 報告内容: 事案の概要・発見日時・影響範囲・対応状況・連絡先

Step 4: 報告後の対応
        - JPCERT/CC との情報連携・対応協力
        - 必要に応じて顧客への JPCERT 報告の事実を通知
        - 対応状況の定期報告
```

### 5.2 顧客 CSIRT との連携

Enterprise プランのお客様のCSIRT（Computer Security Incident Response Team）との連携手順。

#### 連携の目的

- お客様環境内でのセキュリティインシデント発生時の役割分担明確化
- 脅威インテリジェンスの相互共有（当社からお客様へ）
- インシデント対応における技術的連携

#### 連携手順

```
Step 1: 契約締結時の連携体制確認
        - お客様CSIRT担当者・連絡先の登録（サポートポータルの組織設定）
        - 情報共有の範囲・方法の合意（NDA締結ステータスに応じる）

Step 2: インシデント発生時
        - TAM または L2 SSE が顧客CSIRTへ状況報告
        - 技術的情報（IoC、TTPs等）の共有（お客様の承認のもと）
        - 対応の役割分担確認（お客様側対応 / 当社側対応の切り分け）

Step 3: 情報共有ツール
        - 当社: Kizashi のアラート・テレメトリデータをCSIRTと共有
        - お客様: 自社ネットワーク情報・被害状況を当社と共有
        - 共有形式: STIX/TAXII（Enterprise プラン対応）または直接連絡
```

### 5.3 個人情報保護委員会（PPC）への報告

個人情報の漏洩・滅失等の事案（個人情報保護法第26条に基づく報告義務が生じる場合）。

#### 報告が必要なケース（法定基準に基づく）

- 要配慮個人情報が含まれる個人情報の漏洩
- 不正利用により財産的被害が生じるおそれのある漏洩
- 不正の目的をもって行われた漏洩
- 1,000件以上の個人情報が含まれる漏洩

#### 報告手順

```
Step 1: CTO が法務担当または外部法律顧問と協議（データ漏洩確認後、即時）

Step 2: 速報報告（3〜5日以内）
        - 報告先: https://www.ppc.go.jp/
        - 報告内容: 事案の概要・把握した日時・被害の状況等

Step 3: 確報報告（原則30日以内 / 不正アクセスは60日以内）
        - 詳細な事案内容・再発防止策を報告

Step 4: 関係するお客様への通知
        - お客様への漏洩事実の通知（可能な限り速やかに）
        - 被害拡大防止のための措置の説明
```
