## 1. はじめに

Kizashi は、1人のアナリストから大規模SOCまで幅広い運用体制に対応しています。本ガイドでは、SOCの規模ごとに **推奨プラン**・**運用フロー**・**自動化設定**・**スケールアップの判断基準** を解説します。

### 基本方針

組織のセキュリティ運用において最も重要なのは、**人的リソースの限界を技術で補完する** ことです。特に少人数チームでは、以下の優先順位で機能を活用してください。

1. **自動化を最優先** — Playbook・自動隔離・AI トリアージで人的作業を最小化
2. **アラート疲れの防止** — 抑制ルール・ML検知で誤検知を削減し、対処すべきアラートに集中
3. **AIを第二のアナリストとして活用** — AI調査機能で初期分析を委任し、人間は判断に専念

## 2. プラン選定フローチャート

```
開始
 │
 ├── エンドポイント数が5台以下で、まず試したい
 │    └─→ Free プラン（評価用、SLA保証なし）
 │
 ├── エンドポイント数が5〜45台、SMB（歯科医院・士業・地域チェーン等）
 │    ├── 専任セキュリティ担当者なし、メールサポートで OK
 │    │    └─→ Lite プラン ★ SMB 推奨（¥500/EP/月、5 台刻み）
 │    └── MDM が必要（モバイル端末も管理したい）
 │         └─→ Starter プランへ（Lite に MDM なし）
 │
 ├── エンドポイント数が50〜199台
 │    └── AI調査・Playbook自動化は不要
 │         └─→ Starter プラン（MDM 含む、平日サポート）
 │
 ├── エンドポイント数が200〜999台
 │    ├── SOC担当が1〜5名
 │    │    └─→ Professional プラン ★ 最も多いケース（AI 調査 + SIEM + 24h サポート）
 │    └── SOC担当が6名以上 or コンプライアンス要件あり
 │         └─→ Enterprise プラン
 │
 └── エンドポイント数が1,000台以上
      ├── 単一組織
      │    └─→ Enterprise プラン
      └── 複数組織を管理（MSP/グループ企業）
           └─→ Enterprise プラン（マルチテナント必須）
```

## 3. 1人SOC運用（Professional プラン推奨）

### 3-1. なぜ Professional か

1人SOCの最大の課題は **アラート疲れ** と **24/7対応の不可能性** です。Starter プランではアラートの確認しかできませんが、Professional プランでは以下の「1人の限界を補う機能」が利用可能です。

| 機能 | 1人SOCでの価値 |
|------|---------------|
| **SOCワークキュー** | 未対応アラート・インシデントを「今すぐ/今日中/今週中」に自動分類。始業時のダッシュボードウィジェットで件数を瞬時に把握 |
| **AIトリアージ自動化** | アラートの初期トリアージを自動化。誤検知を自動クローズし、侵害の可能性・推奨対応をAIが判定。1人では追いきれない知識領域を補完 |
| **デイリーブリーフィング** | 毎朝8時に前日サマリーを自動生成。Slack配信設定で出勤前にモバイルで確認可能 |
| **自動対応Playbook** | 「Criticalアラート → エージェント隔離 → インシデント作成 → 通知」を自動化。不在時の初動対応を確保 |
| **アラートグルーピング** | 相関エンジンが同一端末・同一テクニックのアラートを自動集約。個別対応ではなく攻撃全体像で把握 |
| **繰り返しアラート抑制候補** | ノイズアラートをAIが候補として提示し、ワンクリックで抑制ルール作成 |
| **ML異常検知** | 機械学習で誤検知を削減し、本当に対処すべきアラートに集中 |
| **脅威インテリジェンス** | IOCの自動照合により、手動OSINTの時間を大幅削減 |
| **SIEM連携** | 既存SIEMがある場合、アラートの統合管理で画面切り替えを削減 |

> **Enterprise は不要な理由:** マルチテナント管理、SOAR連携、コンプライアンス自動化は1人運用では活用しきれません。SOARに投資するよりも、Kizashi内蔵のPlaybookで十分カバーできます。

```
┌─ 始業時（〜15分）──────────────────────────────────┐
│                                                     │
│  1. ダッシュボードを開く                               │
│     └ SOCワークキューウィジェットで緊急件数を確認       │
│     └ 未対応Critical/Highアラートがあるか確認           │
│                                                     │
│  2. Slack のデイリーブリーフィングを確認（設定済みの場合）│
│     └ 夜間の新規アラート・緊急件数・AI自動クローズ数    │
│     └ 上位MITREテクニック・オフライン端末数            │
│                                                     │
│  3. /soc-queue を開いて「今すぐ対応」レーンを処理      │
│     └ 夜間のPlaybook実行履歴（自動隔離）を確認・検証   │
│     └ 誤隔離があれば解除                               │
│                                                     │
│  4. アラートグルーピングセクションを確認               │
│     └ 相関エンジンが新しいインシデントを作成していないか │
│                                                     │
├─ 日中（必要に応じて）────────────────────────────────┤
│                                                     │
│  5. 「今日中に対応」レーンを処理                        │
│     └ AI調査で概要把握 → 判断 → 対応実行              │
│                                                     │
│  6. Medium/Lowアラートの確認（まとめて処理）            │
│     └ 抑制候補セクションでノイズアラートを確認          │
│     └ 繰り返し発生する誤検知 → 「抑制ルール作成」クリック│
│                                                     │
├─ 週次（30分〜1時間）──────────────────────────────┤
│                                                     │
│  7. 脅威ハンティング                                   │
│     └ 最新の脅威情報に基づくプロアクティブ探索          │
│                                                     │
│  8. 相関エンジン閾値の見直し（必要に応じて）            │
│     └ インシデント過多 → CORRELATION_THRESHOLD を上げる │
│     └ 検知漏れ → CORRELATION_THRESHOLD を下げる        │
│                                                     │
│  9. Playbook・YARAルールの見直し                       │
│     └ 誤検知率の高いルールのチューニング               │
│     └ 新しいカテゴリのYARAルール有効化検討             │
│                                                     │
│  10. 週次レポート作成（レポート機能で自動生成）          │
│                                                     │
├─ 夜間・休日（自動運用）──────────────────────────────┤
│                                                     │
│  Playbookが24/7で稼働:                                │
│  ├ Critical → 自動隔離 + インシデント作成 + 即時通知   │
│  ├ High → インシデント作成 + 通知（隔離は手動判断）    │
│  └ Medium/Low → 蓄積のみ（翌朝まとめて確認）          │
│                                                     │
│  AIトリアージが5分ごとに稼働:                          │
│  └ 誤検知率高 → 自動でfalse_positiveにクローズ        │
│                                                     │
│  ※ Slackのデイリーブリーフィングで翌朝サマリーを受信   │
└─────────────────────────────────────────────────────┘
```

### 3-3. 必須の初期設定

#### Playbook（自動対応ルール）

以下の4つのPlaybookを初期設定として推奨します。

| Playbook名 | トリガー条件 | 自動アクション | 目的 |
|------------|-------------|--------------|------|
| **緊急自動隔離** | severity = critical | エージェント隔離 → インシデント作成 → 通知送信 | 深刻な脅威の即時封じ込め |
| **高リスク通知** | severity = high | インシデント作成 → 通知送信 | 高リスクアラートの見逃し防止 |
| **ランサムウェア即時対応** | rule_name に "ransomware" を含む | エージェント隔離 → インシデント作成 → 通知送信 | ランサムウェアの拡散防止 |
| **IOC一致対応** | IOCマッチ検知 | エージェント隔離 → 通知送信 | 既知の脅威指標への即時対応 |

> **設定場所:** 管理画面 → プレイブック（`/admin/playbooks`）

#### アラート抑制ルール

運用開始後1〜2週間で繰り返し発生する誤検知を特定し、以下のパターンで抑制ルールを作成します。

| 抑制対象例 | 条件 |
|-----------|------|
| Windows Update 関連の正常なプロセス実行 | hostname に "*" + rule_name = "suspicious_process" |
| バックアップソフトの大量ファイル操作 | rule_name = "mass_file_modification" + hostname = バックアップサーバー |
| 監視ツール自体の検知 | rule_name に "network_scan" + hostname = 監視サーバー |

> **設定場所:** 管理画面 → アラート抑制（`/suppressions`）

#### 通知設定

| 通知先 | 対象 | 目的 |
|--------|------|------|
| Slack（チャンネル） | Critical + High | リアルタイム通知 |
| メール | Critical のみ | 夜間・休日のフォールバック |
| Webhook（PagerDuty等） | Critical のみ | 電話呼び出し（オプション） |

> **設定場所:** 管理画面 → 通知設定（`/admin/notifications`）

### 3-4. エンドポイント規模別の適合度

| エンドポイント数 | 1人SOCでの管理 | 備考 |
|-----------------|---------------|------|
| 〜50台 | 余裕あり | Playbook最小構成でも対応可能 |
| 50〜100台 | 適切 | AI + Playbook活用が推奨 |
| 100〜200台 | 可能 | 抑制ルールの最適化が必須 |
| 200〜299台 | 限界付近 | 全自動化 + AI フル活用が前提 |
| 300台以上 | **増員を推奨** | 1人では対応が困難 |

## 4. 小規模SOC運用（2〜5名 / Professional プラン）

### 4-1. 推奨体制

| 役割 | 人数 | 担当 |
|------|------|------|
| Tier 1（初期トリアージ） | 1〜2名 | アラート確認・初期分類・既知パターンの対応 |
| Tier 2（詳細調査） | 1〜2名 | インシデント調査・フォレンジック・脅威ハンティング |
| マネージャー | 1名 | レポート・方針策定・エスカレーション判断 |

### 4-2. 運用フロー

```
┌─ Tier 1（常時）─────────────────────────────────────┐
│  ・ダッシュボードのアラート監視                         │
│  ・AI調査結果のレビューと初期分類                       │
│  ・既知パターン → Playbook/手動で対応完了               │
│  ・未知/複雑 → Tier 2 にエスカレーション                │
└─────────────────────────────────────────────────────┘
           │ エスカレーション
           ▼
┌─ Tier 2（必要時）────────────────────────────────────┐
│  ・インシデント詳細調査                                 │
│  ・ライブレスポンスによるリモート調査                    │
│  ・脅威ハンティング（週次）                             │
│  ・検知ルール・Playbookのチューニング                   │
│  ・IOC登録・脅威インテリジェンス管理                    │
└─────────────────────────────────────────────────────┘
           │ 報告
           ▼
┌─ マネージャー（週次/月次）────────────────────────────┐
│  ・週次レポートレビュー                                 │
│  ・KPIモニタリング（MTTD/MTTR）                        │
│  ・経営層への報告                                       │
│  ・抑制ルール・対応方針の承認                           │
└─────────────────────────────────────────────────────┘
```

### 4-3. Professional プランの追加活用

1人SOCの設定に加え、以下を活用します。

| 機能 | 活用方法 |
|------|---------|
| **RBAC（役割ベースアクセス制御）** | Tier 1 は閲覧+対応のみ、Tier 2 はルール編集権限、マネージャーはフル権限 |
| **SIEM連携** | 既存SIEMへのログ転送でセキュリティ基盤を統合 |
| **カスタム検知ルール（YARA/Sigma）** | Tier 2 が組織固有の脅威に対応するルールを作成 |
| **インシデントタイムライン** | エスカレーション時に Tier 1 → Tier 2 の情報引き継ぎをスムーズに |
| **脅威ハンティング** | Tier 2 の定例業務として週次でプロアクティブ探索 |

## 5. 中規模SOC運用（6〜15名 / Enterprise プラン）

### 5-1. Enterprise が必要な理由

| 要件 | Enterprise機能 |
|------|---------------|
| 複数チーム/拠点の管理 | マルチテナント（`/admin/organizations`） |
| ワークフロー自動化 | SOAR連携（`/admin/soar`） |
| 監査・規制対応 | コンプライアンス自動レポート（`/admin/compliance-auto`） |
| 高度な脅威検知 | XDR（クロスドメイン検知）、デセプション（ハニーポット） |
| APIによる外部連携 | APIキー管理、OAuth2クライアント |
| 300台超のエンドポイント | エージェント数無制限 |

### 5-2. 推奨体制

| 役割 | 人数 | 担当 |
|------|------|------|
| Tier 1 | 3〜5名 | 24/7シフト制アラート監視・初期対応 |
| Tier 2 | 2〜4名 | 詳細調査・フォレンジック |
| Tier 3（脅威リサーチ） | 1〜2名 | 脅威インテリジェンス・ハンティング・ルール開発 |
| SOCマネージャー | 1名 | チーム運営・レポート・経営層連携 |
| エンジニア | 1〜2名 | SOAR/SIEM連携開発・インフラ管理 |

### 5-3. SOAR活用例

Enterprise プランのSOAR機能で、チーム間のワークフローを自動化します。

| ワークフロー名 | トリガー | アクション |
|--------------|---------|-----------|
| Tier 1 自動アサイン | 新規アラート（High以上） | 当番アナリストに自動割り当て + チケット作成 |
| エスカレーション自動化 | アラート未対応（30分経過） | Tier 2 にエスカレーション + マネージャーに通知 |
| インシデント自動作成 | 同一ホストで3件以上のHighアラート | インシデント自動作成 + 関連アラートをリンク |
| コンプライアンス通知 | コンプライアンススコア低下 | マネージャーに通知 + レポート自動生成 |

## 8. 運用メトリクス（KPI）

SOCの運用品質を測定するための推奨KPIです。

### 8-1. 必須KPI

| メトリクス | 定義 | 目標値（参考） |
|-----------|------|---------------|
| **MTTD**（平均検知時間） | 脅威発生〜アラート生成までの時間 | < 5分（自動検知） |
| **MTTR**（平均対応時間） | アラート生成〜対応完了までの時間 | Critical: < 1時間 / High: < 4時間 |
| **誤検知率** | 全アラート中の誤検知の割合 | < 30%（継続的に改善） |
| **アラート対応率** | 対応済みアラート / 全アラート | > 95% |
| **Playbook実行成功率** | 成功した自動対応 / 全自動対応 | > 98% |

### 8-2. 改善KPI

| メトリクス | 定義 | 確認頻度 |
|-----------|------|---------|
| 未対応アラート数の推移 | 日次での未対応アラート残数 | 日次 |
| 抑制ルール適用数 | 抑制ルールで除外されたアラート数 | 週次 |
| AI調査活用率 | AI調査を実行したアラートの割合 | 月次 |
| インシデント解決時間 | インシデント作成〜クローズまでの時間 | 月次 |

> **確認場所:** ダッシュボード（`/dashboard`）、レポート生成（`/reports`）

## 9. スケールアップの判断基準

### 9-1. Starter → Professional へのアップグレード

以下のいずれかに該当する場合、Professional プランへのアップグレードを検討してください。

| 判断基準 | 兆候 |
|---------|------|
| アラート対応が追いつかない | 未対応アラートが毎日増加している |
| 誤検知が多い | Medium/Lowアラートの80%以上が誤検知 |
| 夜間/休日の脅威に対応できない | 翌朝に初めてCriticalアラートに気づく |
| 調査に時間がかかりすぎる | 1件のHighアラートの調査に2時間以上 |
| 既存SIEMとの統合が必要 | セキュリティツールが分散している |

### 9-2. Professional → Enterprise へのアップグレード

| 判断基準 | 兆候 |
|---------|------|
| SOCメンバーが6名以上 | ワークフロー管理が煩雑になってきた |
| エンドポイントが300台超 | Professional のエージェント上限に近づいている |
| コンプライアンス要件 | ISMS/PCI DSS等の監査レポートが必要 |
| 複数組織の管理 | グループ会社やクライアントごとの分離が必要 |
| 高度な脅威対応 | XDR/デセプション/フォレンジックが必要 |

### 9-3. 人員増員の判断基準

| 指標 | 1人SOCの限界 | 増員検討ライン |
|------|-------------|--------------|
| エンドポイント数 | 〜200台 | 200台超 |
| 1日のアラート数 | 〜50件 | 50件超（Playbook活用後） |
| Critical/Highアラート | 〜5件/日 | 5件超/日 |
| MTTR（Critical） | 1時間以内で対応可能 | 1時間を常時超過 |

## 10. 付録: ライセンス管理操作

### 10-1. プラン構成

| プラン | エンドポイント上限 | ユーザー上限 | 主要機能 |
|--------|-----------------|-------------|---------|
| Free | 5台 | 2名 | 基本検知 + アラート |
| Lite | 5〜45台（5 台刻み、Stripe 数量に従う） | 3名 | + レポート（MDM なし） |
| Starter | 49台 | 10名 | + MDM |
| Professional | 299台 | 50名 | + AI調査 / Playbook / SIEM / 脅威インテリジェンス / ML / YARA / ハンティング |
| Enterprise | 無制限 | 無制限 | + SOAR / XDR / マルチテナント / コンプライアンス / デセプション / フォレンジック / API |

> **Lite の `エンドポイント上限` の補足** (v1.3.2 以降): 表中の「45 台」は Lite tier の最大値。実際の各テナントの `agent_limit` は Stripe Subscription Quantity に従い、契約 EP 数 (5/10/15/.../45) と一致します。例: 10 EP 契約のテナントは `agent_limit=10`、それ以上のエージェント追加は HTTP 402。

### 10-2. ライセンスのアクティベート

1. 管理画面 → **ライセンス管理**（`/admin/license`）を開く
2. 「ライセンスキーのアクティベート」セクションにキーを貼り付け
3. 「アクティベート」をクリック
4. プラン・機能が即座に更新される

### 10-3. ライセンスのリセット

テスト目的やプラン変更前に、ライセンスを初期状態（Free プラン）に戻すことができます。

1. 管理画面 → **ライセンス管理**（`/admin/license`）を開く
2. ページ下部の「ライセンスのリセット」セクションで「リセット」をクリック
3. 確認ダイアログで「リセット実行」をクリック
4. Free プランに即座にリセットされる

> **注意:** リセット後は有料プランのすべての機能（AI調査、Playbook、SIEM連携等）が利用不可になります。再度ライセンスキーをアクティベートすることで有料プランに復帰できます。

### 10-4. FeatureGate（機能制限）

プランに含まれない機能のページにアクセスすると、「{プラン名}プランが必要です」というメッセージが表示されます。「プランをアップグレード」ボタンからライセンス管理ページに移動し、上位プランのキーをアクティベートしてください。
