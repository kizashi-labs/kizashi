## 1. 何が起きていたか

migration **315/330** で `agents.status` の CHECK に `'inactive'` が追加され、`DeadAgentCleanup` の

```sql
UPDATE agents SET status = 'inactive'
 WHERE status = 'offline' AND last_seen < NOW() - INTERVAL '30 days'
```

が通るようになった。**書き込み側はこれで直った。しかし読み出し側が追随していなかった。**

`agents.status` では **`'offline'` が「生きていない」の唯一のセンチネル**として使われている。
30 日死んだホストが `'offline'` から `'inactive'` へ移った瞬間、`status != 'offline'` と書かれた
すべての判定にとって、そのホストは**「生きている」側へ回り込む**。

これは P5-5 / P5-7 / P5-8 と同じ「語彙の片側だけ更新した」クラスの故障だが、
それらが *inert*（発火しない）に出たのに対し、今回は **過剰発火** に出た。

---

## 2. 最も重い退行 — オフラインアラートの無期限量産

`detection/heartbeat_monitor.go` の `checkOnce` は「落ちたばかりのホスト」を拾う意図のクエリ:

```sql
WHERE a.status NOT IN ('isolated', 'offline')   -- ← 'inactive' が無い
  AND a.last_seen < NOW() - $1::interval
  AND NOT EXISTS ( ...直近 10 分に「オフライン」アラートが無いこと... )
```

`'inactive'` が除外語彙に無いため、**30 日死んだ退役ホストが「たった今オフラインになった」と
再判定される**。実 DB で該当行が返ることを確認済み:

```
 hostname        | status   | last_seen
-----------------+----------+---------------------------
 DESKTOP-SQB1AJO | inactive | 2026-03-22 05:19:27+00
```

同クエリ内の重複抑止は**直近 10 分のみ**、既定チェック間隔は **2 分**。したがって
**退役ホスト 1 台につき severity 7 のアラートが約 10 分ごと（≒144 件/日）に無期限で生成される。**

そして自然解消しない。`scheduler.HeartbeatMonitor` は `status='online'` の行しか UPDATE しないため、
`'inactive'` が `'offline'` に戻ることはない。

## 3. 修正した読み出し側

`agents` の生存判定を持つ箇所を洗い出した（`status NOT IN` の全出現を確認し、
残りは alerts / incidents / vulnerabilities など無関係なテーブルであることも確認済み）。

**「生きている」判定（`status != 'offline'` / `NOT IN (...)`）— PR #608**

| 箇所 | 修正 | 直さないと |
|---|---|---|
| `detection/heartbeat_monitor.go` | `NOT IN ('isolated','offline','inactive')` | **アラート無期限量産**（上記） |
| `autoupdate/manager.go` `TriggerBulkUpdate` | `NOT IN ('offline','inactive')` | 一括アップデートの配信対象に退役ホストが混入 |
| `api/handlers/ueba_handler.go` | 同上 | UEBA のエンティティ異常に退役ホストが載る |
| `store/agents.go` `ListExpiringAgents` | 同上 | 退役ホストの証明書失効警告が出続ける |
| `frontend/types/api.ts` | `AgentStatus` に `'inactive'` 追加 | 型と実体の不一致（`badges.tsx` は既に対応済みだった） |

**#608 の分類から漏れていた 2 箇所 — 本 PR**

| 箇所 | 修正 | 直さないと |
|---|---|---|
| `api/handlers/alerts_handler.go` | 集計 switch に `inactive` バケット追加 | `total` は `ListAgents` の総数（inactive を含む）から取るのに内訳の switch がどのバケットにも入れず、**`total ≠ online+offline+isolated`** になる |
| `api/handlers/asset_criticality_handler.go` | `status == "offline" \|\| status == "inactive"` | 重要度スコアの -10 減点が `offline` のみを見ており、**より長く死んでいるホストほど減点されない**という反転が起きる（数時間落ちた `offline` は -10、30日死んだ `inactive` は減点なし） |

### 死活サマリの扱い（設計判断）

`COUNT(*) FILTER (WHERE status='offline')` 系（`router.go` / `ops_report_handler.go` /
`reports/generator.go`）は、PR #608 が **offline へ合算**する方針を採った。`total` と内訳の整合を
優先した判断で、固定形式のレポート項目では妥当。

一方、レスポンス形状を拡張できる箇所（`alerts_handler` の `agentSummary`、フロントのサマリタイル）
では**独立バケット**にした。migration 330 自身が「30日死んでいるホストと 2 時間前に落ちたホストを
同じ `offline` で束ねると、オフライン台数が退役済みホストで水増しされ続ける。**区別に意味がある**」と
書いており、合算はその区別を捨てる方向だからである。

どちらの場合も守るべき不変条件は **`total` と内訳の合計が一致すること**。
`daily_briefing_scheduler.go:139` は `status='offline' AND last_seen >= NOW()-'7 days'` と
期間で絞っているため、30日以上未確認の行はそもそも該当せず変更不要。

## 4. フロント表示側

4 画面すべてが**三項演算子の連鎖**でラベルを組み立てており、**該当しない状態が末尾の分岐に落ちる**
のが共通の原因だった。表引き＋フォールバックに置換した。

| 画面 | 症状 |
|---|---|
| `endpoints` | サマリタイルが online/offline/isolated のみ。`inactive` はどの内訳にも入らず総数とだけ合わない → タイルと絞り込みを追加 |
| `geo-map` | 末尾が `'オフライン'` のため `error` / `inactive` が「オフライン」と**誤ラベル** |
| `batch` | 末尾が生の `agent.status` のため `error` / `inactive` が**英語のまま**表示 |
| `network` | 凡例の末尾が `'エラー'` のため、`STATUS_COLOR` にキーを足すたびに未対応の状態が「エラー」と誤表示 |

## 7. 副次 — API ドキュメントの実装乖離

原因調査の過程で `admin/api-docs` と `docs/openapi.yaml` の Agents 記述が実装と乖離していると判明。
ハンドラのクエリ取得・リクエスト/レスポンス構造体・ルータ登録の 4 点と突合して是正した。

**黙って無視される類（利用者側から気づけない）:**

| 記載 | 実装 |
|---|---|
| `q` | `c.Query("search")` — `q` を渡しても無視され全件が返る |
| `offset`（openapi） | 実装に存在しない（`page` から算出） |
| `per_page` 最大 100 | 実際は 1000（範囲外は 20 にフォールバック） |
| `os=macos` | `os_type` の完全一致なので絶対にヒットしない（正は `darwin`） |

**エンドポイント自体の誤り:**

- `GET /api/v1/agents/stats` は**存在しない**。実在するのは `GET /api/v1/metrics/agent-stats` で、
  返るのは `{total, online, stale, offline}`。`by_os` / `by_version` も存在しない。
  なおこの集計は `status` ではなく **`last_seen` ベース**（online=5分以内 / stale=5分〜1時間 /
  offline=1時間超）で、`status='inactive'`（30日）とは**独立した別軸**である点を説明に明記した。
- `POST /agents/:id/commands` の body は `{command_type, command, args}`。記載の
  `{command:'isolate', params:{...}}` はそのまま送ると **400**。隔離は `POST /agents/:id/isolate` が正。

ID 表記も ULID → UUID に是正した（`information_schema` で agents / alerts / incidents / rules /
ioc_entries の `id` が全て `uuid` であることを実測）。

**その後（2026-08-04, PR #628 で解消）**: ここで「対応する実装を特定できないため据え置き」とした
`GET /api/v1/reports/:id/download` は、`router.go` のグループ定義を機械的に解決したことで実体が
`GET /api/v1/reports/:id` だと判明した。同時に **Agents 以外のセクションも全件突合し、60 件中 59 箇所の
乖離を是正**している（存在しないエンドポイント 12 件、メソッド違い 2 件、レスポンス形状 43 件ほか）。

## 8. 教訓

1. **状態列に値を足す変更は「書き込み側 1 箇所」では終わらない。** その列を**否定形**で読んでいる箇所
   （`status != 'X'` / `NOT IN (...)`）は、新しい値を**自動的に「該当する」側へ入れてしまう**。
   `status = 'X'` の追加は目に付くが、否定形は目に付かない。値を足す変更は、否定形の読み出しを
   全部数えるまで完了していない。
2. **「片側だけ更新した語彙」は inert にも過剰発火にも化ける。** P5-5 / P5-7 / P5-8 は発火しない側に
   出たが、本件は**アラートを無期限に量産する**側に出た。前者は気づかれず、後者は運用を溺れさせる。
3. **三項演算子の連鎖でラベルを組むと、状態が増えるたびに誤表示が増える。** 末尾の `else` が
   「その他ぜんぶ」を吸うため、新しい状態が既存のラベルを騙る。表引き＋フォールバックにすれば、
   未知の状態は生値で表示され「知らない」ことが見えるようになる。
4. **並行セッションが同じバグを直していることがある。** 本件は 2 セッションが別設計で同時に着手し、
   実 DB で対立案の退行を実測して決着させた後に、**そのどちらでもない第三の修正が main に着地**していた。
   着手前だけでなく**提出直前にも** `git fetch origin && git log -1 origin/main` を取り直す。
   「既に main にあるか」は日付でなく `git merge-base --is-ancestor` で判定する
   （author date が古くても main 着地はずっと後、というケースがある）。
5. **手書きの API ドキュメントは、実装と突き合わせない限り静かに嘘になる。** ハンドラのクエリ取得・
   リクエスト構造体・レスポンス構造体・ルータ登録の 4 点突合で機械的に検出できる。

## 9. CI 結果の読み方（本件のマージ作業で得た教訓）

本 PR は FP soak ゲートで一度落ちたが、原因は本 PR の外にあった。その切り分けと再確認の過程で
CI の読み方に関する落とし穴を 2 つ踏んだので記録する。

### 「失敗が無い」と「ゲートを通った」は別

rebase 後に `gh pr checks` を見ると全 20 件が SUCCESS / SKIPPED で、`gh pr view` も
`mergeable=MERGEABLE status=CLEAN` を返していた。しかし**チェック総数が 21 → 20 に減っており、
FP soak がリストから消えていた**。実行が `cancelled` で終わると結果が存在せず、
「ブロッキングな失敗が無い」状態として緑に見える。

- `gh pr checks` は**件数と項目名**まで見る。前回との差分で消えた項目がゲートの本体かもしれない。
- `mergeable=MERGEABLE` / `status=CLEAN` は「失敗していない」であって「通った」ではない。
- このリポジトリは並行ブランチが多く FP soak の `cancelled` が頻発する。
  結果が要るときは `gh run rerun <id>` で明示的に走らせる。

### CI 結果は「どのコミットに対する実行か」で判定する

「#604 はマージ済みなのに main の FP soak が赤い → 別要因が残っている」と一度誤結論した。実際には
その main 実行の対象 SHA が **#604 のマージコミットを含んでいなかった**だけだった。

```bash
git merge-base --is-ancestor <修正のコミット> <CI が走った SHA>
```

時刻の前後や「マージ済みかどうか」では判定できない。author date が古くても main への着地はずっと
後、というケースが普通にある（§7 の採番と同じ落とし穴）。**赤い CI を見たら、まずその実行の
対象コミットに期待する修正が入っているかを祖先関係で確かめる。**
