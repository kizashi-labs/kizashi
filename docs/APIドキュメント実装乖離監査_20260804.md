## 1. きっかけ

P5-10（`status='inactive'` の読み出し側未追随）の設計判断で、2 セッションが対立した。片方の根拠が
**「`admin/api-docs` が `'inactive'` を仕様として記載している」**だったが、その記述を実装と突合したところ
**API は `'inactive'` を受け付けなかった**。誤ったドキュメントが設計判断を誤らせかけた。

同じ箇所には `q`（実装は `search`）や、存在しない `GET /api/v1/agents/stats` も並んでいた。
Agents セクションだけ是正して「他セクションは未検証」と残課題にしていたが、それを消化したのが本作業。

## 3. 見つかった乖離の型

### 型 A: エンドポイントが存在しない / パスが違う（12 件）

| 記載 | 実装 |
|---|---|
| `GET /api/v1/auth/me` | `GET /api/v1/users/me` |
| `PUT /api/v1/alerts/batch` | `POST /api/v1/alerts/bulk-update` |
| `POST /api/v1/alerts/:id/suppress` | **存在しない**（抑制は条件で定義する別リソース `POST /api/v1/suppressions`） |
| `POST /api/v1/reports/generate` | `POST /api/v1/reports` |
| `GET /api/v1/reports/:id/download` | `GET /api/v1/reports/:id`（PDF は `/:id/pdf`） |
| `GET/POST/DELETE /api/v1/threat-intel/iocs` | `/api/v1/ioc` |
| `GET /api/v1/export/:job_id/download` | **存在しない** |
| `POST /api/v1/search/events` | `POST /api/v1/events/search` |
| `GET /api/v1/search/suggestions` | **存在しない** |
| `GET /api/v1/admin/audit` | `GET /api/v1/audit` |
| `GET /api/v1/admin/system/health` | `GET /health`（認証不要・`/api/v1` 配下ですらない） |
| `POST /api/v1/admin/api-keys` | `POST /api/v1/api-keys` |

### 型 B: メソッド違い（2 件）

- `GET /api/v1/rules/:id/test` → **POST**。しかも「過去のイベントに対してテスト実行」ではなく、
  リクエストボディで渡す**サンプルイベント 1 件に対する評価**だった。説明文ごと誤っていた。
- `POST /api/v1/threat-intel/search` → **GET**。`q` が必須で、省略すると 400。

### 型 C: レスポンス形状（43 件）

最多だったのは次の型。

> **実装は `{message}` か `{id, message}` しか返さないのに、docs は作成されたリソース全体を
> 返すかのように書かれていた。**

該当: suppressions 作成 / ioc 作成・削除 / incidents 作成・更新・アラート紐付け / rules 削除 /
reports スケジュール作成。

ほかに実務上の影響が大きいもの:

- **`POST /api/v1/auth/login` はリフレッシュトークンを返さない。** `token` 1 本と `expires_in` のみ。
  docs は `access_token` / `refresh_token` / `token_type` を返すと書いていた。
  MFA 有効時は `mfa_required` / `pre_auth_token` を含む**別形状**になる点も未記載だった。
- **配列キーの取り違え**: `rules` 一覧は `data` ではなく `rules`、`audit` は `logs`、
  `admin/users` は `users`、`reports` 一覧は `reports`。
- **`GET /api/v1/incidents/:id` は `incident` と `alerts` の 2 キー構成**で、インシデント本体は
  トップレベルに展開されない。
- **`PUT /api/v1/alerts/:id` は severity を更新できない**（`status` と `assigned_to` のみ）。
- **`POST /api/v1/export` はジョブキューではなく同期でファイル本体を返す。** ジョブ ID も後追いの
  ダウンロード URL も存在しない。`GET /export/status` も「ジョブの進行状況」ではなく、
  エクスポート可能な種別と件数の一覧だった。
- **`POST /api/v1/events/search` は KQL / Lucene 非対応。** `query` は `raw_data` への部分一致。
- ページング系の欠落（`has_more` / `total_capped`）。

### 型 D: 黙って無視されるパラメータ

**利用者側から気づけない**ため、型 A より質が悪い。

| 記載 | 実装 |
|---|---|
| `q` | `c.Query("search")` — `q` を渡しても無視され**全件が返る** |
| `offset`（openapi） | 実装に存在しない（`page` から算出） |
| `per_page` 最大 100 | 実際は 1000（範囲外は 20 にフォールバック） |
| `os=macos` | `os_type` の完全一致なので**絶対にヒットしない**（正は `darwin`） |
| `admin/audit` の `user_id` / `action` / `since` | 受け付けない（`user` / `method` / `errors` のみ） |

ID 表記も ULID → UUID に是正した（`information_schema` で agents / alerts / incidents / rules /
ioc_entries の `id` が全て `uuid` であることを実測）。

## 4. 進め方 — 計測してから着手する

全部を人手で読むと数十件規模になるため、**まず「どれだけ機械的に判定できるか」を計測**してから
方針を決めた。

| 段階 | 計測結果 | 判断 |
|---|---|---|
| パス/メソッド | 60 件すべて機械判定可能 | 自動化して一括是正 |
| レスポンス形状 | **31 件が判定可能 / 29 件は不能** | 31 件は自動突合、29 件は人手 |
| 判定可能 31 件の実態 | **20 件が不一致** | 想定より広範。手動分も潰す価値があると判断 |

判定可能の条件は「そのハンドラ内で成功ステータス(200/201/202)を返す `c.JSON` がちょうど 1 つで、
かつ第 2 引数が `gin.H{...}` リテラル」。実測すると `handlers` の `c.JSON` 4,285 箇所のうち
3,863 箇所（90%）が `gin.H` リテラルだが、エンドポイント単位では**成功レスポンスが複数ある**
（早期リターン等）ケースが効いて 31/60 に落ちる。

### 途中で見積もりを訂正した

判定不能 29 件のうち 16 件は「構造体/変数を返す」型で、当初は「同一パッケージ + `store` 限定の
型解決で軽く拾える」と見積もった。しかし実態は**全件が `x, err := h.Store.SomeMethod(...)` の形**で、
型を確定するには「ハンドラのフィールド型 → ストアのメソッドシグネチャ → 構造体定義 → json タグ」の
**4 段の解決**が必要だった。加えて `SupportHandler.ListTickets` は `[]*support.Ticket` を返しており、
**トップレベルがオブジェクトではなく配列**でキー突合の枠組みが当てはまらない。

4 段ホップの正規表現解決器は、途中 1 段の取り違えが**誤ったキー集合を「正解」として固定**する。
自動化を諦め、16 件は人手で読んで直した。

## 5. 再発防止: `server/internal/api/apidocs_routes_test.go`

**`TestAPIDocsEndpointsAreRegistered`** — 記載 60 件のパスとメソッドが登録されているかを突合。

**`TestAPIDocsResponseShapes`** — 判定可能な 31 件についてトップレベルのキー集合を突合。

### 安全側の作り込み

- **判定できなかった件数を必ずログに出す**（`31 件を判定 / 29 件は静的に判定不能`）。
  検証できなかった分が見えないと、緑が実態より良く見えてしまう。
- **抽出が壊れて「差分ゼロ＝緑」にならないよう下限を設ける**（ルート数 500 未満・記載数 40 未満・
  形状判定 25 件未満なら Fatal）。
- レスポンス例の JSON 内にも `method` / `path` というキーが現れるため、エンドポイント定義は
  **インデント 8 に固定**して取り違えを防ぐ（改行は CRLF チェックアウトも考慮）。

### ガード自身の欠陥を 1 件検出した

初版はグループ変数を**平坦に扱っていた**ため、同じ変数名が別ブロックで別プレフィックスに
再束縛されるケースを取り違えた。実例として `ak` が `/api-keys` と `/apikeys` の両方で使われており、
**22 経路を誤ったプレフィックスで「登録済み」と判定**していた。これは
**「存在しないパスを存在すると判定する」＝ガードが素通りする方向**の欠陥である。

ブレース深さでスコープを分ける実装に修正し、誤登録 22 件の解消・取りこぼしゼロを計測で確認した。

同じ欠陥が突合スクリプト側にもあり、`POST /api/v1/api-keys` を誤って「不一致」と判定していた
（実際は記載が正しかった）。**ツールの結果をそのまま信じて修正していたら、正しい記述を壊していた。**

## 6. 検証しないもの（既知の限界）

- リクエストボディの形状、パラメータ名、ネストした要素の中身
- 下記 13 件は構造的にキー突合の対象外
  - ファイル本体を返す（`POST /api/v1/export`、`GET /api/v1/reports/:id/pdf`）
  - 成功時に JSON を返さない（`/admin/tenants`、`/webhooks/stripe`）
  - ルータに無名関数で登録（`GET /api/v1/audit`、`POST /api/v1/search`、`GET /health`）
  - 成功レスポンスが複数あり、どれが「正」か機械的に決められないもの

**今回すべて人手で突合したが、以後の変更はガードで検出できない。**

## 7. 教訓

1. **ガードは「今の状態を固定する」道具であって「今ある誤りを見つける」道具ではない。**
   誤りを残したままガードを入れると、その誤りが正解として固定される。**直してから固定する**。
2. **ガードを入れる前に、意図的に壊して赤くなることを確認する。** 今回はパス・形状の両方で実施し、
   その過程で**自分のガードの欠陥を 1 件見つけた**。「緑だから正しい」は、赤くなることを
   確かめて初めて言える。
3. **「検証できなかった件数」を出力しないガードは、緑を過大に見せる。** 対象 60 件のうち 31 件しか
   判定していないのに「PASS」とだけ出れば、読み手は全件が保証されたと受け取る。
4. **着手前に「どれだけ機械化できるか」を計測する。** 今回は 31/60 という数字が出たことで
   「自動化 + 人手」の切り分けが決まり、さらに 20/31 が不一致と分かって手動分も潰す判断ができた。
   計測せずに全自動化を目指していたら、4 段ホップの脆い解決器を作っていた。
5. **手書き API ドキュメントの乖離は「黙って無視される」型が最も危険。** 存在しないパスは 404 で
   気づけるが、`q` のように無視されるパラメータは**成功レスポンスが返るのに結果が違う**。
   ハンドラのクエリ取得・リクエスト/レスポンス構造体・ルータ登録の 4 点突合で機械的に検出できる。
