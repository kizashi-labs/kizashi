## 1. WMI サブスクリプション永続化に観測面が無かった

WMI イベントサブスクリプションによる永続化（T1546.003）は、**wmic のコマンドラインでしか観測できていなかった**。

| 既存の検知 | logsource | 観測できるもの |
|---|---|---|
| builtin `WMIC Process Call Create` | `process_creation` | wmic の起動 |
| migration 329 `WMI Event Subscription Persistence (DB)` | `process_creation` | wmic のコマンドライン |

どちらも `process_creation` なので、wmic を経由しない登録経路が素通りする。

- PowerShell の `Set-WmiInstance`
- .NET の `ManagementClass`
- 任意のインプロセス WMI クライアント

これらはファイルレスで、再起動を跨いで生き残り、親プロセスが WMI を指さない。**まったく記録されないまま永続化が成立する**状態だった。

### 対応 — WMI サブシステム自身を観測面にする

`Microsoft-Windows-WMI-Activity` の ETW を直接購読する
（`agent/internal/platform/windows/wmi_etw.go`）。

**対象イベント ID を 2 つに絞った。**

| ID | 内容 | 採否 |
|---|---|---|
| 5861 | サブスクリプション登録（WQL フィルタ・コンシューマ・ネームスペースを 1 レコードで搬送） | ✅ T1546.003 |
| 5858 | WMI 操作（`ClientMachine` 付きはリモート WMI 実行） | ✅ T1047 |
| 5857 | プロバイダ ロード | ❌ 除外 |

5857 は通常の管理スクリプトや資産管理エージェントの WMI 利用で常時発火する、高レート・低弁別のストリームである。FP soak が測定したとおり、**非弁別セレクタこそが誤検知リストの大半を占める**（[P5-17](debt/P5.md) の LOLBin と同じ失敗）。「サブシステムに触れたか」ではなく「技術が使われたか」を符号化する。

### ルールはコンシューマの種別をキーにした

サブスクリプションの存在そのものには発火させない。SCCM や監視製品はサブスクリプションを日常的に登録するので、登録に発火させれば上記の非弁別セレクタ問題を再生産する。**コードを実行するコンシューマ**（`CommandLineEventConsumer` / `ActiveScriptEventConsumer`）であることが技術の要件である。

```yaml
detection:
  selection:
    event_type: WmiBindingEvent
  executing_consumer:
    consumer|contains:
      - "CommandLineEventConsumer"
      - "ActiveScriptEventConsumer"
  condition: selection and executing_consumer
```

### フィールド名は SigmaHQ の `wmi_event` のものを使う

ETW の生のプロパティ名ではなく、`event_type` / `operation` / `user` / `query` / `consumer` / `name` / `namespace` / `destination` を採用した。`sigma_category.go` が `wmi_activity` → `wmi_event` を既にマップしているため、**この語彙で出さないとコミュニティルールが一切マッチしない**。[P5-5](debt/P5.md) / [P5-10](debt/P5.md) と同じ「センサーは着地したがルールが発火しない」形になる。

`field_support.go` への登録も必須である。未登録のフィールドを選択するルールは「未対応」として評価前に退避され、**「WMI 活動が無かった」と見分けのつかない偽のグリーン**になる。

### 配線は既存経路に乗せた（proto 変更なし）

`ps_module` / `pipe_created` と同じ `"<type>:<uuid>:<json>"` の `EVENT_TYPE_LOG` 前置プロモーション。

`sigma_category.go` の `eventTypeCategories` には既に `"wmi_activity": {"wmi_event"}` があり、#582 で `AlertPipeline` の購読をここから導出するようにしてあったため、**センサーが着地した日からルールが動く**。#582 のコメントが予告していたとおりである。

> 「新しいセンサーのルールが、誰かが実機テストを走らせるまで静かに失敗するのではなく、センサーが着地した日から動く」

### ⚠️ ETW 側は実機未検証

この環境に Windows ホストが無く、`Microsoft-Windows-WMI-Activity` が実際にこれらのプロパティを配信するかは確認できていない。

- **証明済み**: ペイロード → 平坦化 → ルール一致（`wmi_activity_test.go`、shipped builtin セットを読み込んで検証）
- **未証明**: ETW → ペイロードの区間

プロパティ名は Windows ビルドによって綴りが揺れる（`Operation`/`OperationId`、`ClientMachine`/`ClientMachineFQDN` 等）ため、既知の綴りを順に試す `etwProp` で吸収してある。**綴りを外しても失敗はせず、空フィールドのイベントが出るだけ**＝静かに不活性になるので、無音のセンサーは「WMI 活動が無い」ではなく「未確認」として扱うこと。

### FP soak 実測（#636）

| 指標 | 値 |
|---|---|
| 着信イベント | 151,851 / 送信 151,851（100%） |
| 誤検知アラート | 439 件（99 ルール） |
| FP 率 | 263,397.53 /1000ホスト/日 |
| ベースライン | 266,999.13 → **263,397.53**（退行なし） |
| 窓の最後 90 秒のアラート | 0 件 |

最後の行が重要である。`detectionStillLagging` が 0 を報告した＝検知エンジンに遅延が無い＝**この値は下限ではなく実測**である。

WMI 関連ルールは 99 ルールの誤検知リストに **1 件も出ていない**。良性フリートは `wmi_activity` を生成しないので、新センサーは誤検知をゼロ件しか増やさなかった。

## 2. スキーマ不一致は 1 日で 6 件出た（[P5-21](debt/P5.md)）

Go のコードが「意図されたスキーマ」に対して書かれ、migration が別のものを作り、Postgres が実行時に文全体を拒否し、`ON CONFLICT DO NOTHING` や Debug レベルのログがそれを隠す — この形が 2026-08-03 の 1 日で 6 件見つかった。

ユニットテストは DB に触れないので、CI は何も検出しなかった。

### DB 不要の契約テストでゲート化した

`server/internal/store/schema_contract_test.go` は migration の SQL から列集合を導き、Go ソースの `INSERT` 列リストと突き合わせる。SQL パーサではなく契約テストであり、**確信を持って解析できないものは推測せずスキップする**（誤報を出す検査器は無効化されるため）。

### 抽出器の過剰近似（#638 で是正）

初版はコメントに書いた意味論とコードが食い違っていた。

> `CREATE TABLE IF NOT EXISTS` は既存テーブルに対して NO-OP なので最初の宣言が実体である

と説明しておきながら、実装は**2 回目以降の宣言の列も足し込む和集合モデル**だった。

和集合は「間違える方向」が悪い。DB に存在しない列を「ある」と報告するので、`audit_logs`（006 vs 173）や `yara_rules`（041 vs 174）を壊したのと**まさに同じバグに対して緑のまま**になる。

現在このツリーには、2 回目の `CREATE` でしか宣言されない「幻の列」を持つテーブルが 6 つある。

| テーブル | 初回 | 再宣言 |
|---|---|---|
| `response_actions` | 001 | 008 |
| `yara_rules` | 041 | 174 |
| `incident_playbooks` | 086 | 162 |
| `email_security_events` | 094 | 170 |
| `deception_events` | 116 | 165 |
| `api_endpoints` | 124 | 168 |

`migrate.go` と同じ順序（ファイル名順 → ファイル内はソース順）で migration を再生する厳密モデルに置き換えた。`DROP TABLE` も扱う。**Go の INSERT がこれら幻の列を使っている箇所は 0 件**だったので、厳密化のコストはゼロだった。

### 「B クラスは判定不能」は誤りだった

#630 の時点で「NOT NULL 列の書き漏れは、同じファイルに `CREATE TABLE IF NOT EXISTS`（NOT NULL）と `ALTER ADD COLUMN IF NOT EXISTS`（nullable）が併存するので判定不能」と報告した。**これは和集合モデルを前提にした結論で、順序を正しく再生すれば決定可能である。**

| 項目 | 値 |
|---|---|
| テーブル総数 | 367 |
| NOT NULL かつ DEFAULT 無しの列を持つテーブル | 326 |
| 解析した INSERT | 380 |
| 違反 | 0 件 |

0 件は #630 の修正がこのクラスを取りこぼしていなかったことの裏付けでもある。

主キーは「NOT NULL だが DEFAULT 無し」として扱う。`id UUID PRIMARY KEY` に DEFAULT が無ければ INSERT は本当に値を要求するので、主キーを常に「DEFAULT あり」とみなすとそれを隠す。両方の扱いで違反 0 件になることを確認したので、厳しい方を無償で採れた。

### 検査器自身が 2 回、偽陽性を出した

**1 回目（#630）**: `ALTER TABLE` の複数句のうち最初の 1 つしか読まず、migration 202 が確かに追加している `ioc_entries.source_feed` を「存在しない」と報告した（24 件の偽陽性）。

**2 回目（#638）**: `ALTER TABLE` が未知テーブルにエントリを作ってしまい、後続の `CREATE TABLE` が「再宣言＝NO-OP」と誤判定された。migration 179 は `DO` ブロックの ELSE 分岐で `CREATE` し、IF 分岐の `ALTER` がファイル上先に現れるため、`detection_rules` の 4 列を「存在しない」と報告した。

どちらも「検査器が、それが検出するために存在するバグのクラスを自分で再現した」形である。**誤報を出す検査器は無効化される**ので、この種の作業では検査器自身の正しさの検証が本体と同等に重要になる。

## 3. 台帳自身が事故を起こしていた（[P2-4](debt/P2.md)）

台帳（`docs/技術的負債と改善計画.md`）は 1084 行の単一ファイルで、ほぼ全ての PR が末尾に追記する構造だった。2026-08-03 の 1 日でこの構造に起因する事故が 5 件起きている。

| 種類 | 件数 |
|---|---|
| 番号衝突（`P5-11`、`P5-15`） | 3 |
| マージ解決時の節の消失（`P5-11` / `P5-12`） | 2 |

**分割だけでは足りない。** 分割が減らすのは git が競合として検出する noisy な事故だけで、上の 2 種類はどちらも競合を伴わずに起きる。別々の場所への追記どうしは git がクリーンにマージするので、**同じ番号の節が 2 つ並んだファイルが何事もなく main に入る**。消失の方も、消えたことを知らせるものが何も無い。

サイレントな失敗には規律ではなくチェッカーが要る、というのはこのセッションで繰り返し確認したことである。詳細は [P2-4](debt/P2.md)。

## 4. YAML 重複キーで弁別条件が消えていた（[P5-22](debt/P5.md)）

P4-6（DB Sigma ルールをリアルタイム経路でも評価する）の実現可能性を測るため、migration が投入する
Sigma を api-server の `SigmaEvaluator` に通したところ、**241 件中 237 件はそのままコンパイルできた**
（台帳の「2214 件」は SigmaHQ 同期分を含む数で、migration 由来はこの規模である）。

残る 4 件が全て同じ欠陥だった——同じ selection 内で `CommandLine|contains` を 2 回定義している。
YAML では重複キーは不正で、受け付けるパーサでは**後勝ち**になる。1 つ目のキーは**どの例でも
「どのバイナリか」を決める弁別条件**であり、それが黙って捨てられていた。

**2 つのエンジンで壊れ方が違う**のがこの欠陥の厄介なところである。

| エンジン | 挙動 | 結果 |
|---|---|---|
| api-server の `SigmaEvaluator`（yaml.v3） | パース拒否 | ルールが存在しないのと同じ |
| server-detect の sigma-go | 受け付けて後勝ち | 存在するが弁別条件を失う |

migration 371 で 4 件を修正し、`migration_sigma_parse_test.go` でゲート化した。穴の形は
**「`rules/sigma/**/*.yml` は `cmd/validate-rules` が本番の評価器で構文検証しているが、
migration SQL の中のルール本文は誰も同じ評価器に通していない」**というものだった。

### ★ 誤検知への効果はゼロだった（当初の見立ては誤り）

当初「この 2 件が誤検知 439 件のうち 29 件を出している」と報告したが、**測定がそれを否定した**。

| ルール | 修正前 | 修正後 |
|---|---|---|
| Archive Collected Data (Linux) | 17 件 | **17 件** |
| Suspicious chmod of Executable in /tmp | 12 件 | **12 件** |
| 総数 | 439 件 | 436 件（−3 は run 間ばらつき） |

実際の発火理由は測定後に特定した。

- **chmod**: `tests/fpsoak/profiles/dev-machine.toml:136` の `chmod +x /tmp/installer-{{rand}}.sh` が、
  **修正後の「意図どおりの」ルールに完全一致**する。これは YAML 欠陥ではなく**ルール設計そのものの
  非弁別性**である。
- **Archive**: `backup-server.toml:60` の `tar --zstd -cf /vault/...` が、本修正で触っていない
  `ziptools` 分岐（`zstd ` などが単独で十分）で発火している。

修正自体は正しく、**P4-6 の前提条件**でもある（パースできないルールはリアルタイム経路に載せられない）。
ただし誤検知削減の効果は無かった。上記 2 つの非弁別セレクタは別課題として残る。

> **教訓**: 「FP 一覧に載っているルールに欠陥が見つかった」から「その欠陥が FP の原因である」は
> **導けない**。発火経路を確認するか、修正前後で測るかのどちらかが要る。

## 4. このセッションで得た教訓

**サイレントな失敗には規律ではなくチェッカーが要る。** 番号衝突も、節の消失も、スキーマ不一致も、フィールド名の不一致も、すべて「気をつける」で防げないものだった。共通するのは *失敗が失敗として現れない* ことである。

**検査器の正しさは本体と同等に重要である。** 誤報を出す検査器は無効化され、無効化された検査器はゼロと同じ価値になる。今回入れた 7 つの検査はすべて変異テスト（意図的に壊して赤くなることを確認）を通してある。

**「間違える方向」を選ぶ。** 和集合モデルは「存在しない列をあると言う」向きに間違え、検出したいバグに対して緑になった。厳密モデルは「あるものを無いと言う」向きに間違え、それは赤として現れる。どちらも間違いうるなら、赤くなる方を選ぶ。

**観測面が無いことは、検知が弱いことより悪い。** WMI の件は「ルールの精度が足りない」のではなく「イベントがそもそも来ていない」だった。ルールを磨いても永久に発火しない。
