# 同期の受け側ガードと、本流へ反映すること

> **読む人**: 本流（生成器）側を触れる人。
> **要点**: 受け側のガードは「消されたことに気づく」までしかできません。
> **消されなくする**には、下の 3 件を生成器側に入れる必要があります。

---

## 1. 何が起きたか

このリポジトリは本流のスナップショットで、生成のたびに木がまるごと
差し替わります。**生成側が何かを落とすと、その PR は緑のまま入ります。**

実例が **3 度**あります。

| #70 | 同期がその全部を消し、**同時に検査そのものも消した** |
| #73 | 戻した |
| #74 | **また全部消えた。** 今度はガードが数えました（下記） |

PR は 22/22 緑で通りました。**検査が自分と一緒に消えるので、検査は自分を
守れません。**

## 2. いま守られていること —— と、守れないこと

#76 で受け側のガードを入れました（`scripts/sync_guard.py` と
`.github/workflows/sync-guard.yml`）。`pull_request_target` で走るので、
**PR が定義を消しても main の版が走ります。**

守っているもの:

| 対象 | 留め方 |
| --- | --- |
| ジョブの上限 | 欠落と 60 分超を落とす |
| step の上限 | **数**で留める（名前ではない。本流は step を改名するので、名前で留めると改名のたびに鳴る。**鳴る検査は消されます**） |
| `workflow-lint.yml` | ファイルの有無ではなく、**中の判定 2 本**を文字列で |
| `scripts/verify.sh` | 同じ 3 本 |
| ラチェット 16 本 | 一覧で |
| 較正の道具 3 本 | 一覧で |
| ガード自身 3 本 | 一覧で（**消えても、その回は止まりません** —— base 側で走るので。止まるのは次の PR で、そのときにはもう誰も見ていません。だから「消えた」ことが消えた回の画面に出る必要があります） |
| `agent-ebpf` の `mkdir` | 再試行ループの**内側**にあること |
| ラチェットの固定値 | **緩んだ向きだけ**を落とす（下記） |

### ラチェットの固定値 —— 「呼ばれたか」は見えないが、結果は見える

ここには以前「生成器が較正の道具を**呼んでいるか**は見えないので守れない」
と書いてありました。**呼んだかどうかは確かに見えませんが、呼ばれなかった
結果は見えます** —— 固定値が main と違う値で戻ってきます。

判定を実際に読んで 3 種類に分けました。守るのは 2 つだけです。

| 種類 | 判定の形 | 緩む向き | 守るか |
| --- | --- | --- | --- |
| 上限 | `if got > N` | **N が増える** | 落とす |
| 下限 | `if got < N` | **N が減る** | 落とす |
| 実数一致 | `if got != N` | **無い** | 見ない |

**実数一致を見ないのは手抜きではありません。** ずれた瞬間にその検査自身が
落ちるので、静かに退行できません。ここで鳴らすと、正当な更新のたびに
赤くなります —— **鳴る検査は消されます。**

現物は上限 14・下限 7・実数一致 14（＋ラチェットではない局所変数 2）で、
`sync_guard.py` の `RATCHET_LIMITS` に名前で並べてあります。
**表に無い固定値が出てきたら「分類してください」で落とします。** 既定を
「見逃す」にすると、新しいラチェットは黙って守られないままになります。

> **向きを名前から推測しないでください。** `min*` や `*_CEILING` は
> だいたい合っていますが、`floor = 2000` や `NAV_PENDING` のように
> 名前では決まらないものがあります。取り違えると、**捕まえるべき退行
> だけを黙って通します。**
> `sync_guard_test.py` が、実物にある固定値がすべて分類されていること
> と、表に実物に無い名前が残っていないことを**両方向**で留めます。

**守れないこと** —— ガードは受け取った木しか見えません:

- 較正の道具が**呼ばれたかどうか**そのものは見えません。上の検査が
  見るのは結果（値が緩んだか）だけなので、**値が動かない回は素通り
  します。** 呼ぶこと自体は生成器側にしか入れられません（§3-3）。
- 1 本ずつの改名や追加は捕まえません。捕まえるのは #70 で実際に起きた形
  （**まとめて全部消える**）です。
- **ガードより前に開かれた PR には、遡って走りません。**（下記）

### ガードは、自分より前に開かれた PR を見ていません

`pull_request_target` が走るのは PR の**イベント**（open / synchronize /
reopen）です。ガードが main に入る前に開かれ、その後 push されていない
PR には、**一度も走りません。**

実例がいま開いています。**#74（同期 PR、削除 21,088 行）は
`total_count: 0` —— チェックが 1 件もありません。** 06:48Z に開かれ、
ガードは #76 でそのあとに入りました。

つまり **`sync/main-20260820` は、ガードが見たことのない木です。**
required status check を入れても、**チェックが 0 件の PR は「必須の
チェックが完了していない」として止まる**ので入りませんが、止まっている
理由が「ガードが落ちた」ではなく「ガードが走っていない」であることを
読み違えないでください。

走らせるには、**その PR を閉じて開き直してください**（`reopened` で走ります）。
ブランチには何も push されません。空コミットを push するのでも走りますが、
同期ブランチの履歴に生成器が作っていないコミットが混ざります。

> **`workflow_dispatch` では走りません。** ここには以前「`workflow_dispatch`
> で回してください」と書いてありました。**間違いでした。**
> dispatch では `github.event.pull_request.head.sha` が空になり、
> **ref の無い tarball は既定ブランチを返します** —— ガードは main を見て
> 「配布物はすべて残っています」と**緑を返します。**
>
> **落ちるより悪い形です。** 手で回した人は確かめたつもりで、PR の木を
> 一度も見ていません。空 SHA を弾く枝を足して塞ぎました（#89 / #90）ので、
> いまは緑ではなく落ちます。

### ガード自身の `run:` は、1 つの PR では変えられません

`sync-guard.yml` の `run:` を書き換えると、**その PR は落ちます。**
この検査は base（main）の版で走るので、main の
`GUARD_ALLOWED_RUNS` に無い形は「許していない run:」になります。

**それは正しい挙動です。** この workflow は base の権限で走るので、
`run:` の書き換えが黙って入るほうが危ない。

変えるときは 2 つの PR に分けてください:

| | やること |
| --- | --- |
| 1 | 新しい形を**先に** `GUARD_ALLOWED_RUNS` へ足す。**workflow は触らない** |
| 2 | `sync-guard.yml` を新しい形にし、**古い形を一覧から消す** |

**2 で古い形を消し忘れないでください。** 両方許したままだと、新しい形が
持っている検査（いまなら空 SHA を弾く枝）を消しても落ちません ——
**塞いだはずの穴が、静かに開いたままになります。**
`sync_guard_test.py` の `test_dropping_the_empty_sha_branch_fires` が
そこを留めます（古い形を一覧に戻すと、この検査が落ちます）。

実例は #89（1 段目）と #90（2 段目）です。

## 3. 本流でやること（3 件）

### 3-1. `timeout-minutes` 49 件と、欠落検査と、ローカルの写し

生成器側で 49 件を残すか、`workflow-lint.yml` を**再生成の対象から外す**か、
どちらかを入れないと 3 度目が起きます。

現物は §4 の表です。数字は実測（直近 200 runs）の成功時最大に余裕を
足したもので、**遅い日を殺さず、ハングは早く切る**幅にしてあります。

欠落検査の本体:

- `.github/workflows/workflow-lint.yml`
  - `timeout-minutes` が無いジョブ → 落とす（既定が **6 時間**である
    説明つき）
  - `timeout-minutes > 60` → 落とす（「**ハングを上限の引き上げで
    直さないでください**」）
- `scripts/verify.sh` — 同じ判定の写しを、**領域に関係なく毎回**走らせる節

`workflow-lint.yml` を `ci.yml` の中に置いていないのは意図です。
**ci.yml が起動しないなら検査も動かない**ので、別ファイルにしてあります。

なぜ上限が要るのか（実測）:

| ジョブ | 中央 | 最悪 |
| --- | --- | --- |
| `agent-build (linux/amd64/ebpf)` | 1.7 分 | **360.3 分**（＝既定 6 時間の上限に当たって停止） |
| `rules-validate` | 1.2 分 | **111.2 分** |

どちらも `apt-get` の取得で止まっていました。**落ちないので誰も気づかず、
予算だけが減ります。**

### 3-2. `agent-ebpf.yml` の `mkdir -p downloads` の位置

再試行ループの**内側**に置いてください。`downloads/` は `.gitignore` に
入っているのでクローン直後には存在せず、**再試行の間に挟まる
`git reset --hard` が消します。**

この 1 行で、このワークフローはこのリポジトリで初めて成功しました
（それまで 4/4 失敗、すべて同じ位置）。

**この step は PR では走りません**（`if: github.ref == 'refs/heads/main'`）。
つまり**消えても PR は緑です。**

### 3-3. 生成器から較正の道具を呼ぶ

```
scripts/recalibrate_ratchets.py --apply
scripts/reanchor_mutations.py --apply
```

**順番が要ります。** 固定値を下げたあと、その値を参照している変異仕様書の
pattern も一緒に動かさないと、**下げた瞬間に仕様書が死にます。**

これを入れないと、ラチェット 16 本は「生成のたびに約 50 個の固定値を
測り直す負担」として、また配布から外されます（#70 がそうしました）。
道具は #75 で作ってあります —— **呼ばれていないだけです。**

受け側は §2 で**緩んだ結果**を落とすようにしましたが、それは事後です。
値が動かない回は素通りしますし、緩んだと分かっても受け側では直せません
（正しい値は生成器側でしか測れません）。**呼ぶこと自体は、ここでしか
入れられません。**

## 5. 数え直し方

```sh
cd .github/workflows
python3 - <<'PY'
import glob, yaml
job = step = 0
for f in sorted(glob.glob('*.yml')):
    for jn, j in (yaml.safe_load(open(f)).get('jobs') or {}).items():
        t = j.get('timeout-minutes')
        print(f"{f}\t{jn}\t{t if t is not None else 'MISSING'}")
        job += t is not None
        for s in (j.get('steps') or []):
            if 'timeout-minutes' in s:
                step += 1
                print(f"    ↳ {s.get('name') or s.get('uses')}\t{s['timeout-minutes']}")
print(f"job={job} step={step} total={job+step}")
PY
```

`MISSING` が 1 つでも出たら、`workflow-lint` と `sync-guard` の両方が
落ちます。

## 6. 関連

- `scripts/sync_guard.py` — 受け側のガード本体。**何を守っているかは
  ここのコメントが正**です
- `scripts/sync_guard_test.py` — ガード自身の判定。**確かめる道具が
  壊れていることが、いちばん高くつきます** —— 以後どの同期も
  「配布物はすべて残っています」と報告し、それは正しく見えます
- `.github/workflows/sync-guard.yml` — なぜ `pull_request_target` なのか、
  なぜ PR の木を展開しないのかの説明
- `scripts/verify.sh` — CI と 1:1 のローカル実行

> **`Sync Guard / The sync did not drop anything` は required status check に
> してください。** required でないと、同期 PR は「赤いが入れられる」状態に
> なります —— #70 は緑で入りましたが、次は赤で入ります。設定には admin
> 権限が要ります。
