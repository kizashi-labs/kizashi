# PR #447 マージ統合記録 2026-08-02 — JA3重複実装とSigmaルール大規模拡張の解消

`claude/detection-rate-methods-6mza2z`（PR #447、[検知率向上_20260715...](検知率向上_20260715_Windows横展開深化とクラウド永続化とランサム複合相関.md)・

mainへマージする過程で、**mainが同時期に独立して進めていた大規模な検知拡張作業**との統合が必要になった。
単純な「両方追加」では済まない規模・性質だったため、判断の記録として残す。

## 1. 何が並行して起きていたか

PR #447 は2026-07-09に作業開始し、複数回に分けてmainへマージを試みる間（約3週間）、mainは以下を独立に積み上げていた:

- **JA3/JA3S基礎ライブラリ**（`agent/internal/ja3/`）: TLS ClientHelloからのフィンガープリント計算のみ。
  **呼び出し元ゼロ**（`git grep` で確認）＝未配線の孤立コード。
- **`C2FusionScorer`**（`server/internal/detection/rules/c2_fusion.go`）: ビーコン周期性(S1)・脅威インテリ評価(S2)・
  ドメイン希少性(S5)等を融合するPh1-3実装。設計ドキュメント
  `docs/design/ネットワークC2振る舞い検知の多信号フュージョン設計.md` に基づく計画的な機能。
- **Sigmaビルトインルールの大規模拡張**: 160→254ルール（DBエンジンパリティ migration 318–329で56技法を
  api-server↔detection-server間で二重化、単一イベント被覆バッチ等）。
- **監査ドキュメントの独自更新**: 上記に対応する戦術別マトリクス・更新ログの大幅改訂。

一方、こちら（PR #447）は同時期に:

- JA3計算＋**Linux eBPF捕捉センサ＋Windows raw-socketセンサ＋サーバ側ブロックリスト＋engine.go配線＋E2Eテスト**の
  フルスタック実装。
- ビーコン検知へのペイロードサイズ均一性(CV)軸追加。
- Windows横展開の深化・クラウド永続化・ランサム複合相関・AD/ドメイン全体タンパリング等、44件の新規Sigmaルール。

## 2. 統合方針と判断根拠

### 2.1 JA3実装: こちらの完全実装を採用

`git grep -l "internal/ja3\"" origin/main -- '*.go'` が**空**（main側のJA3ライブラリを呼ぶコードが存在しない）
ことを確認。mainの実装は「将来のPh4aで使う予定の孤立ライブラリ」であり、こちらは捕捉→指紋→検知→アラートの
一気通貫が動作・テスト済み。両者は関数シグネチャも異なる（main: `FromTLSRecord` 単一関数でJA3/JA3S両対応、
こちら: `FromClientHello`/`FromServerHello`/`ServerName` を分離）ため、部分マージではなく**片方を選ぶ**必要
があった。呼び出し元の有無という客観的な基準で判断し、こちらの実装（`agent/internal/ja3/ja3.go`,
`ja3_test.go`）を採用。

### 2.2 C2相関: 両方を統合（アーキテクチャ的に補完関係）

`rule_engine.go` の同一箇所（`if eventType == "network"` ブロック）を両ブランチが別々に拡張していた:

```go
// 統合後
if eventType == "network" {
    dst := beaconDstIP(flatMap)
    e.c2fusion.ObserveTI(agentID, dst, tiSignalFromEvent(flatMap))
    e.c2fusion.ObserveNetwork(agentID, dst) // S5 fleet-rarity bookkeeping
    if bm := e.beacon.Observe(agentID, dst, beaconBytesSent(flatMap)); bm != nil {
        matches = append(matches, e.c2fusion.Fuse(bm))
    }
}
```

`BeaconDetector.Observe` の3引数シグネチャ（こちらが追加した `bytesSent`）と `C2FusionScorer.Fuse`
（mainが追加した多信号昇格）は競合しない直交する改良だったため、両方を残す形で自然に統合できた。
`C2FusionScorer`（ルールエンジン内、宛先単位のTI+周期性+希少性融合）と、こちらの `C2Correlator`
（detectionエンジン内、収集済みmatchesを跨いだ多軸相関）は**似て非なる別レイヤー**として共存している。
将来的な統合・整理の余地はあるが、今回はどちらも壊さず両立させることを優先した。

### 2.3 Sigmaルール: mainをベースに固有44件を追記（ユーザー承認済み方針）

Sigmaルールの近似タイトルの重複ペア（例:「Cloud Instance Metadata Service (IMDS) Credential Access」対
「Cloud Instance Metadata Service Access」、Rcloneエクスフィル検知の別バリエーション等）が複数存在し、
git の行単位マージでは正しく再構成できない規模の衝突（1ファイルに5,6箇所の絡み合ったコンフリクト、
双方の追加ルールが行レベルで交錯）だったため、以下の方針をユーザーに確認の上で採用:

1. `builtinSigmaRules` は**順不同のGoスライスリテラル**（`LoadBuiltinRules` が `for range` でロードするだけ）
   であることを利用し、行単位の差分解決ではなく**タイトル単位の集合演算**で再構成。
2. main側の完全なファイル（254ルール、うち1件は既存の重複タイトルあり＝main自身の既知の軽微な問題、
   今回は関知せず）をベースとして採用。
3. こちら固有のタイトル（main側に存在しないもの）44件を `git show <ref>:path` から正規表現で個別抽出し、
   ベースの末尾に追記。
4. 近似だが別タイトルのペア（IMDS/Rclone等）はタイトルが異なるため重複除去の対象にならず、**軽微な冗長性
   （同一攻撃に対し2つの類似ルールが発火しうる）が残る**。誤検知は増えないが、アラート件数がわずかに
   増える可能性がある既知のトレードオフとして許容。将来のクリーンアップ候補。

再構成後、`grep -c "^title:"` で件数照合（254+44=298、実測299=main自身の重複1件を含む）を行い、
欠落・重複が意図通りであることを検証した。

### 2.4 監査ドキュメント: mainをベースに更新ログのみ追記

`docs/ATT&CK検知カバレッジ監査.md` もmain側で大幅に独自更新（DBエンジンパリティの記述等、検知ルールの
拡張とは無関係な広範な内容）されていたため、Sigmaルールと同じ理由で行単位マージを断念。main全体を採用し、
こちらの更新ログエントリ（2026-07-15, 2026-07-22 分）を「更新ログ」セクション先頭に追記する形で統合した。
戦術別マトリクスの細部の食い違い（同じ技術IDの記載漏れ是正が両ブランチで独立に行われていた等）は
mainの記述を優先し、重複した記述の完全な整合は取っていない（実害はテキストの冗長性のみ）。

## 3. マージ過程で発見・修正した副次的な問題

いずれも本来のPR #447の作業範囲外だが、マージを完了させるために対処した:

| 問題 | 発見経緯 | 対応 |
|---|---|---|
| `TestBuiltinIOCs_WellFormed` が CIDR型IPを不正値として拒否 | main側の新規テスト（CIDR未対応時代に書かれた）と、こちらのCIDR対応機能（`ioc_matcher.go`）が前提レベルで矛盾 | `net.ParseCIDR` も許容するようテストのアサーションを更新 |
| `TestHandlers_AllFieldsPopulated` が `IPBlock` 未設定で失敗 | main単体でも再現することを確認（こちらの変更とは無関係な**main自身の既存バグ**、フィクスチャ更新漏れ） | フィクスチャに `IPBlock: &handlers.IPBlockHandler{}` を追加してCIを解消 |
| マージ後、mainで一時的に `IPBlock` の重複キーによるビルド破壊 | mainが同じ問題を別PR（#591）で並行に修正しており、こちらのマージでその修正と衝突（詳細未特定・タイミング起因） | main側の別コミット（#594）が数分以内に自動的に解消。こちらからの追加対応は不要だった |

## 4. マージの実際的な難しさ: 「動くターゲット」

mainは本セッション中も継続的にマージされ続けており（1回のマージ解消の合間に平均10〜30分でmainが
さらに1〜2コミット進む）、コンフリクト解消→ビルド→テスト→push→（mainがまた進む）→再解消、を
**6回**繰り返した。各回で `git worktree add --detach` による使い捨てワークツリーを使い、実ブランチを
汚さずに解決策を検証してから本番適用する運用を徹底した。最終確認として `mergeable_state` の
API値だけでなく、都度実際の `git merge --no-commit --no-ff` によるドライランで衝突の有無を検証した
（APIのキャッシュが数分遅延することがあったため）。
