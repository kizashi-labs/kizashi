## Service Overview

| Service    | Port  | Binary           | Health endpoint       |
|------------|-------|------------------|-----------------------|
| API        | 8080  | `edr-api`        | `GET /healthz`        |
| Ingestion  | 9000  | `edr-ingestion`  | `GET /healthz`        |
| Detection  | 9100  | `edr-detection`  | `GET /healthz`        |
| Frontend   | 3000  | Next.js          | `GET /`               |
| PostgreSQL | 5432  | TimescaleDB 16   | `pg_isready`          |
| NATS       | 4222  | NATS 2.10        | `nats server check`   |
| Redis      | 6379  | Redis 7          | `redis-cli ping`      |
| Nginx      | 443   | nginx            | `nginx -t`            |

## Architecture Quick Reference

```
Browser ──> Nginx (443) ──> Frontend (3000)
                       ──> API (8080)
                              ├── PostgreSQL (timescaledb)
                              ├── Redis (cache / rate-limit)
                              └── NATS (pub/sub)
                                     └── Ingestion ← Agents (gRPC)
                                     └── Detection engine
```

## On-Call Checklist

Before investigating any alert:

```bash
# 1. System health overview
curl -sf http://localhost:8080/healthz | jq .

# 2. Docker Compose status (production)
docker compose -f docker-compose.prod.yml ps

# 3. Recent error logs
docker compose -f docker-compose.prod.yml logs --tail=100 api | grep -i error
docker compose -f docker-compose.prod.yml logs --tail=100 ingestion | grep -i error

# 4. Database connectivity
psql "$DATABASE_URL" -c "SELECT pg_is_in_recovery(), now();"

# 5. NATS status
nats server check --server nats://localhost:4222
```

## Incident Response Process

1. **Acknowledge** the alert within SLA (P1: 5 min, P2: 15 min)
2. **Assess** — check health endpoints and error logs
3. **Communicate** — post in `#incidents` Slack channel with initial status
4. **Mitigate** — apply the relevant runbook below
5. **Resolve** — confirm service is healthy, close the alert
6. **Document** — fill in the post-incident review template

### API Down / 5xx Spike

**Symptoms**: `GET /healthz` returns non-200, or error rate > 1% in last 5 min.

```bash
# Check process
docker compose -f docker-compose.prod.yml ps api

# Tail recent logs
docker compose -f docker-compose.prod.yml logs --tail=200 api

# Check DB connection from inside the container
docker compose -f docker-compose.prod.yml exec api \
  sh -c 'pg_isready -h $DB_HOST -p $DB_PORT -U $DB_USER'

# Restart if process crashed
docker compose -f docker-compose.prod.yml restart api

# Check for OOM kill
dmesg | grep -i oom | tail -20
```

**Escalate to P1 if**: Restart does not resolve within 5 minutes.

### High Alert Queue Depth

**Symptoms**: NATS queue `alerts.ingest` depth > 10,000 messages.

```bash
# Check queue depth
nats stream info ALERTS --server nats://localhost:4222

# Check ingestion consumer lag
nats consumer info ALERTS detection-engine --server nats://localhost:4222

# Scale detection if needed (Kubernetes)
kubectl scale deployment edr-platform-api --replicas=4

# Or restart detection service
docker compose -f docker-compose.prod.yml restart detection
```

**Root cause investigation**:
```bash
# CPU / memory usage
docker stats edr-detection

# Check for stuck goroutines
curl -sf http://localhost:9100/debug/pprof/goroutine?debug=2 | head -100
```

### Database Slow / Connection Exhaustion

**Symptoms**: API latency p99 > 2s, or `FATAL: remaining connection slots reserved`.

```bash
# Active connections
psql "$DATABASE_URL" -c "
  SELECT count(*), state, wait_event_type, wait_event
  FROM pg_stat_activity
  GROUP BY state, wait_event_type, wait_event
  ORDER BY count DESC;"

# Long-running queries (> 30s)
psql "$DATABASE_URL" -c "
  SELECT pid, now() - query_start AS duration, query
  FROM pg_stat_activity
  WHERE state = 'active'
    AND now() - query_start > interval '30 seconds'
  ORDER BY duration DESC;"

# Kill a blocking query
psql "$DATABASE_URL" -c "SELECT pg_terminate_backend(<pid>);"

# Check pg_stat_statements for expensive queries
psql "$DATABASE_URL" -c "
  SELECT query, calls, mean_exec_time, total_exec_time
  FROM pg_stat_statements
  ORDER BY total_exec_time DESC
  LIMIT 10;"

# Reload pgbouncer / connection pool if applicable
docker compose -f docker-compose.prod.yml restart api
```

### NATS Disconnected

**Symptoms**: API logs `nats: no servers available`, or detection/ingestion services can't publish.

```bash
# NATS health
nats server check --server nats://localhost:4222

# Restart NATS
docker compose -f docker-compose.prod.yml restart nats

# Wait for reconnect (clients auto-reconnect by default)
sleep 10
curl -sf http://localhost:8080/healthz | jq .nats

# Verify JetStream streams still exist
nats stream ls --server nats://localhost:4222
```

**Data loss risk**: Events published during outage are lost unless the agent client queues them. Check agent logs for retried events.

### Disk Space Critical

**Symptoms**: Disk usage > 85% on data volumes.

```bash
# Find large directories
df -h
du -sh /var/lib/docker/volumes/* | sort -rh | head -20

# PostgreSQL WAL / dead tuples
psql "$DATABASE_URL" -c "
  SELECT schemaname, tablename,
         pg_size_pretty(pg_total_relation_size(schemaname||'.'||tablename)) AS size
  FROM pg_tables
  ORDER BY pg_total_relation_size(schemaname||'.'||tablename) DESC
  LIMIT 20;"

# Vacuum / autovacuum
psql "$DATABASE_URL" -c "VACUUM ANALYZE;"

# Rotate old Docker logs
docker compose -f docker-compose.prod.yml logs --no-log-prefix > /dev/null
# Or truncate: truncate -s 0 /var/lib/docker/containers/<id>/<id>-json.log

# Delete old TimescaleDB chunks (alerts older than 90 days)
psql "$DATABASE_URL" -c "
  SELECT drop_chunks('alerts', INTERVAL '90 days');"
```

### Windows Process Chain Detection Silent (cache_size Low)

**Symptoms**: ATT&CK chain rules (T1547.001, T1055, T1566.001, etc.) fire zero alerts even after confirmed suspicious process execution on a Windows endpoint. Detection logs show `chain analysis` lines but `cache_size` stays at 3–6 and ancestry chains do not extend past the current process.

**Triage**

```bash
# Step 1 — confirm chain events are flowing at all
docker compose -f docker-compose.prod.yml logs detection --tail 300 \
  | grep "chain analysis" | tail -20

# Step 2 — check for PPID=0 on short-lived processes
docker compose -f docker-compose.prod.yml logs detection --tail 300 \
  | grep "chain analysis" | grep -E "ppid=0.*reg\.exe|certutil|vssadmin"

# Step 3 — check for UUID INSERT errors (v1.3.11 and earlier only)
docker compose -f docker-compose.prod.yml logs detection 2>&1 \
  | grep "22P02\|invalid input syntax for type uuid" | wc -l

# Step 4 — confirm alerts reach the DB
docker compose -f docker-compose.prod.yml exec postgres \
  psql -U edr -d edrplatform \
  -c "SELECT rule_name, severity, created_at FROM alerts WHERE description LIKE '%chain%' ORDER BY created_at DESC LIMIT 5;"
```

**Fix A — cache_size low after detection restart (most common)**

The agent seeds the ProcessChainEngine cache only at startup. If detection is restarted after the agent has already sent seeding events, the cache is empty.

```powershell
# Run on the affected Windows endpoint
sc.exe stop EDRAgent
sc.exe start EDRAgent
```

Wait 30 seconds and re-check that `cache_size` climbs to 50+ in detection logs.

**Fix B — PPID=0 on short-lived LOLBins (agent < v1.3.12)**

Upgrade the Windows agent to v1.3.12+. The fix adds `NtQueryInformationProcess` PPID resolution in both `takeSnapshot()` and `buildEvent()`, plus re-emission of create events when ppid changes 0→non-0 between poll ticks.

**Fix C — UUID type error (agent server < v1.3.12)**

If step 3 above shows UUID errors, the detection service binary is pre-v1.3.12. Rebuild and redeploy:

```bash
docker compose -f docker-compose.prod.yml up -d --build detection
```

**Escalate to P2 if**: Cache size remains < 10 after EDRAgent restart and detection service is confirmed healthy.

### Quarantine Result 500 (検疫レコード保存失敗)

**Symptoms**: エージェントが検疫を完了したにもかかわらず管理コンソールの「検疫ファイル」一覧にレコードが出ない。エージェントログに `reportQuarantineToServer: server returned 500`。API ログに `quarantined_files_alert_id_fkey` FK 違反。

**Triage**

```bash
# Step 1 — API ログで FK 違反を確認
docker logs kizashi-api 2>&1 | grep "quarantine\|23503\|alert_id_fkey" | tail -20

# Step 2 — 検疫レコードの有無を確認
docker exec kizashi-postgres psql -U edr -d edrplatform \
  -c "SELECT id, agent_id, alert_id, original_path, quarantined_at FROM quarantined_files ORDER BY quarantined_at DESC LIMIT 10;"

# Step 3 — API のバージョンを確認（v1.3.12 以降かチェック）
docker exec kizashi-api /api-server --version 2>/dev/null || \
  docker logs kizashi-api 2>&1 | head -5
```

**Fix A — alert_id FK 違反 (most common, server < v1.3.12)**

アラートが検疫コマンド発行後に削除されると `quarantined_files_alert_id_fkey` 制約違反で INSERT が失敗する。v1.3.12 では `alert_id = NULL` で自動リトライするよう修正済み。

```bash
cd ~/edr-platform && git pull
docker compose up -d --build --no-deps api
```

修正後は Warn ログ (`quarantine.Record: alert_id FK violation; retrying with NULL`) が出て 201 が返るようになる。

**Fix B — agent_id FK 違反**

エージェントが削除・再登録されて UUID が変わっている場合。DB の UUID と agent.toml の id が一致しているか確認し、必要なら再登録する。

```bash
# DB 側の UUID 確認
docker exec kizashi-postgres psql -U edr -d edrplatform \
  -c "SELECT id, hostname FROM agents WHERE hostname = '<hostname>';"
```

**Fix C — コード変更が未反映（--build 省略）**

`git pull` 後に `docker compose up -d api` だけ実行すると既存イメージが再利用される。必ず `--build` を付ける:

```bash
cd ~/edr-platform
docker compose up -d --build --no-deps api
```

**Escalate to P2 if**: Fix A/B/C を試みても 500 が継続し、`quarantined_files` テーブルへの INSERT がすべて失敗している場合。

### Agent mTLS 証明書自動更新 (更新失敗時)

**Symptoms**: エージェントログに `[cert_renew] 証明書更新に失敗しました`、または証明書期限切れで gRPC 接続が断する。

**Triage**

```bash
# Step 1 — 証明書期限が 30 日以内のエージェントを確認
docker exec kizashi-postgres psql -U edr -d edrplatform \
  -c "SELECT id, hostname, cert_not_after,
             cert_renewal_token IS NOT NULL AS token_pending
      FROM agents
      WHERE cert_not_after < NOW() + INTERVAL '30 days'
        AND cert_not_after IS NOT NULL
      ORDER BY cert_not_after;"

# Step 2 — スケジューラのログを確認
docker logs kizashi-api 2>&1 | grep "cert_ren" | tail -30

# Step 3 — NATS に更新命令が届いているか確認
nats sub "commands.*.cert_renew" --server nats://localhost:4222 &
# 翌 2 分 (初回) または 24 時間後にメッセージが届くはず

# Step 4 — エージェントのログを確認
# (Linux エージェントの場合)
journalctl -u edr-agent --since "1 hour ago" | grep -i "cert_renew\|renew"
```

**Fix A — token は発行済みだが命令がエージェントに届かない**

NATS ブリッジが起動していないか、ingestion サービスが `commands.*.cert_renew` を購読していない。

```bash
# ingestion を再起動
docker compose -f docker-compose.prod.yml restart ingestion

# NATS の接続状態を確認
nats server check --server nats://localhost:4222
```

**Fix B — トークン期限切れ (7日超過) でエージェントが更新に失敗**

`cert_renewal_token` の TTL は 7 日。スケジューラは翌日の実行で新トークンを自動再発行する。手動で即座に再試行する場合:

```sql
-- トークンをリセット (スケジューラが次回実行時に新トークンを発行する)
UPDATE agents
SET cert_renewal_token = NULL, cert_renewal_expires = NULL
WHERE id = '<agent_id>';
```

その後、スケジューラを待つか API を再起動してスケジューラを即時起動する:

```bash
docker compose -f docker-compose.prod.yml restart api
# 起動 2 分後にスケジューラが初回チェックを実行する
```

**Fix C — 証明書が期限切れで gRPC 接続が切れた場合の手動更新**

完全に期限切れになった場合、エージェントは接続できないため自動更新も不可能になる。
手動でエージェントを再エンロールする:

```bash
# 1. DB 上の古いエージェントレコードを削除 (または cert_not_after を延長)
docker exec kizashi-postgres psql -U edr -d edrplatform \
  -c "DELETE FROM agents WHERE id = '<agent_id>';"

# 2. エージェントホストで証明書と鍵を削除し、再エンロール
# (エージェントの設定に応じて証明書パスを変更すること)
rm /etc/edr-agent/agent.crt /etc/edr-agent/agent.key
systemctl restart edr-agent  # 起動時に自動エンロールが実行される
```

**Escalate to P2 if**: 30 日以内に期限切れになるエージェントが複数あり、スケジューラの再起動後も更新命令が配信されない場合。

詳細は `docs/design/agent-cert-rotation.md` を参照。

### 抑制ルール キャッチオール検出・無効化

**Symptoms**: アラートが全く発生しない（または急激に減少した）にもかかわらず、エンドポイントでは怪しい挙動が継続している。検知ログには "suppression matched" が大量に表示される。

**Triage**

```bash
# Step 1 — conditions={} の is_active ルールを確認
docker exec kizashi-postgres psql -U edr -d edrplatform -c "
  SELECT id, name, is_active, conditions
  FROM suppression_rules
  WHERE conditions::text = '{}'
    AND is_active = true;"

# Step 2 — 直近 1 時間の suppression match 数を確認
docker logs kizashi-detection --since 1h 2>&1 | grep "suppression matched" | wc -l

# Step 3 — suppression_rules テーブル全体を確認
docker exec kizashi-postgres psql -U edr -d edrplatform -c "
  SELECT id, name, is_active, created_at, conditions::text
  FROM suppression_rules
  ORDER BY created_at DESC;"
```

**Fix A — キャッチオールルールを即座に無効化（ダウンタイムなし）**

```bash
# 該当ルールを無効化（<id> は Step 1 で特定した UUID）
docker exec kizashi-postgres psql -U edr -d edrplatform -c "
  UPDATE suppression_rules
  SET is_active = false
  WHERE conditions::text = '{}'
    AND is_active = true;"

# 無効化後、detection を再起動して suppression キャッシュをリセット
docker compose up -d --build --no-deps detection
```

**Fix B — ルールを完全削除（管理コンソール経由）**

管理コンソール → サイドバー **検知** → **アラート抑制** (`/suppressions`) →
対象ルールを選択 → **削除**

または API 経由:

```bash
curl -sf -X DELETE https://<host>/api/v1/suppressions/<id> \
  -H "Authorization: Bearer <admin-token>"
```

> **この手順は 2026-08-18 まで別の宛先を指していました。**
> `/api/v1/admin/suppression-rules/<id>` と書いてありましたが、それは
> `alert_suppression_rules` という**検知側が一度も読んだことのないテーブル**の
> CRUD で、**そこを消しても実際の抑制は何も変わりません**。「消したのに
> まだアラートが落ちる」を踏んだ場合は、この宛先違いを疑ってください。
> 死んでいた系統は migration 456（旧 450）で撤去済みです。

**Fix C — detection が古いバイナリを使用している（v1.3.13 未満）**

v1.3.13 より前のバージョンでは、条件が空のルールのガード処理がない。detection を最新ビルドへ更新する:

```bash
cd ~/edr-platform && git pull
docker compose up -d --build --no-deps detection
```

**Escalate to P1 if**: キャッチオールルールを無効化してもアラートが復帰しない場合（detection サービス自体の問題の可能性）。

### AI 利用ログ保持クリーナー障害

**Symptoms**: `ai_usage_logs` テーブルのサイズが無制限に増加している。API ログに `RetentionCleaner` のエラーが出ている。`called_at < NOW() - 1 year` のレコードが残存している。

**Triage**

```bash
# Step 1 — ai_usage_logs のサイズ・件数を確認
docker exec kizashi-postgres psql -U edr -d edrplatform -c "
  SELECT count(*),
         pg_size_pretty(pg_total_relation_size('ai_usage_logs')) AS table_size,
         min(called_at) AS oldest
  FROM ai_usage_logs;"

# Step 2 — 1 年超えのレコードを確認
docker exec kizashi-postgres psql -U edr -d edrplatform -c "
  SELECT count(*) AS expired_rows
  FROM ai_usage_logs
  WHERE called_at < NOW() - INTERVAL '1 year';"

# Step 3 — API ログで RetentionCleaner のエラーを確認
docker logs kizashi-api 2>&1 | grep -i "retention\|ai_usage_logs" | tail -30
```

**Fix A — クリーナーが一時的に失敗している（API を再起動して再スケジュール）**

RetentionCleaner は API 起動時に goroutine として起動し、1 分後に初回実行 → 以降 24 時間ごとに実行します。API を再起動するとクリーナーも再起動されます。

```bash
cd ~/edr-platform
docker compose up -d --build --no-deps api
# 1 分後に初回クリーンが実行されるのをログで確認
docker logs kizashi-api -f 2>&1 | grep -i "retention\|deleted.*ai_usage"
```

**Fix B — 期限超過レコードを手動削除**

```bash
docker exec kizashi-postgres psql -U edr -d edrplatform -c "
  DELETE FROM ai_usage_logs
  WHERE called_at < NOW() - INTERVAL '1 year';"
```

**Fix C — api サービスが v1.3.15 未満（クリーナー未実装）**

v1.3.15 より前のバイナリには `RetentionCleaner` が存在しない。最新版へ更新する:

```bash
cd ~/edr-platform && git pull
docker compose up -d --build --no-deps api
```

**Escalate to P2 if**: 手動削除後も `oldest` が 1 年超のままで、API ログに繰り返しエラーが出ている場合。

## Scaling Procedures

### Horizontal Scaling — API / Ingestion / Detection

All three services are stateless and can be scaled horizontally. Session state is stored in PostgreSQL; NATS handles pub/sub; no sticky sessions are required.

**Docker Compose (single host)**
```bash
# Scale API to 3 replicas
docker compose -f docker-compose.prod.yml up -d --scale api=3
```

## Disaster Recovery

### RPO / RTO Targets

| Component | RPO (data loss tolerance) | RTO (recovery time target) |
|---|---|---|
| PostgreSQL (events/alerts) | ≤ 1 hour | ≤ 2 hours |
| NATS JetStream (in-flight events) | ≤ 5 minutes | ≤ 30 minutes |
| Agent configuration/rules | 0 (recreatable from code) | ≤ 15 minutes |
| License/tenant data | 0 (critical — separate backup) | ≤ 1 hour |

### Failover — Primary Database Down

```bash
# 1. Confirm primary is unreachable
psql "$PRIMARY_DATABASE_URL" -c "SELECT 1;" || echo "PRIMARY DOWN"

# 2. Check replica lag before promoting
psql "$REPLICA_DATABASE_URL" -c "
  SELECT pg_is_in_recovery(), pg_last_wal_receive_lsn(), pg_last_wal_replay_lsn();"

# 3. Promote replica to primary (PostgreSQL 13+)
# On replica host:
pg_ctl promote -D /var/lib/postgresql/data

# 4. Update DATABASE_URL to point to new primary
# Docker Compose:
sed -i 's|DATABASE_URL=.*|DATABASE_URL=postgres://edr:<pass>@<replica-host>:5432/edrdb|' .env.prod
docker compose -f docker-compose.prod.yml up -d api ingestion detection

# 5. Verify API health
curl -sf http://localhost:8080/healthz | jq .
```

### Full Environment Restore

```bash
# 1. Restore PostgreSQL from latest backup (see Backup section)
pg_restore -h <new-host> -U postgres -d edrdb /backups/edrdb_latest.dump

# 2. Verify data completeness
psql "$DATABASE_URL" -c "
  SELECT 'agents' AS tbl, count(*) FROM agents
  UNION ALL SELECT 'alerts', count(*) FROM alerts
  UNION ALL SELECT 'rules', count(*) FROM rules;"

# 3. Run pending migrations
docker compose -f docker-compose.prod.yml run --rm \
  -e RUN_MIGRATIONS=true api sh -c 'sleep 0'

# 4. Start services
docker compose -f docker-compose.prod.yml up -d

# 5. Re-register NATS JetStream streams (they auto-create on startup)
curl -sf http://localhost:8080/healthz | jq .nats

# 6. Validate agent connectivity (check for heartbeats within 5 min)
psql "$DATABASE_URL" -c "
  SELECT count(*) FROM agents WHERE last_seen > NOW() - INTERVAL '10 minutes';"
```

### NATS JetStream Recovery

NATS JetStream stores data on disk. If the volume is lost, in-flight messages are lost but the system recovers automatically when streams are recreated at startup.

```bash
# Force stream recreation (destroys undelivered messages)
nats stream rm ALERTS --server nats://localhost:4222 --force
docker compose -f docker-compose.prod.yml restart api
# Streams are recreated automatically on API startup

# If JetStream storage is corrupted
docker compose -f docker-compose.prod.yml stop nats
docker volume rm edr-platform_nats_data
docker compose -f docker-compose.prod.yml up -d nats
```

## Backup Procedures

### PostgreSQL Backup — Automated Daily

Add to cron on the database host (`crontab -e`):

```bash
# Full logical backup at 02:00 daily — kept for 30 days
0 2 * * * /usr/local/bin/edr-backup.sh >> /var/log/edr-backup.log 2>&1
```

**`/usr/local/bin/edr-backup.sh`**:
```bash
#!/usr/bin/env bash
set -euo pipefail
DATE=$(date +%Y%m%d_%H%M%S)
BACKUP_DIR=/backups/postgresql
OFFSITE_BUCKET=s3://your-org-edr-backups/postgresql   # Edit this

mkdir -p "$BACKUP_DIR"

# Logical dump (parallel, 4 jobs)
pg_dump "$DATABASE_URL" \
  -Fc -j 4 \
  -f "$BACKUP_DIR/edrdb_${DATE}.dump"

# Upload to offsite object storage
aws s3 cp "$BACKUP_DIR/edrdb_${DATE}.dump" "$OFFSITE_BUCKET/edrdb_${DATE}.dump"

# Prune local backups older than 7 days
find "$BACKUP_DIR" -name "*.dump" -mtime +7 -delete

echo "Backup completed: edrdb_${DATE}.dump"
```

### Backup Verification (Weekly)

```bash
# Restore to a test database to verify backup integrity
DATE=$(ls -t /backups/postgresql/*.dump | head -1)
pg_restore --list "$DATE" | wc -l   # Should be > 100 objects

# Full test restore
psql "$DATABASE_URL" -c "CREATE DATABASE edrdb_verify;"
pg_restore -d postgres://edr:<pass>@localhost:5432/edrdb_verify "$DATE"
psql postgres://edr:<pass>@localhost:5432/edrdb_verify \
  -c "SELECT count(*) FROM alerts;"
psql "$DATABASE_URL" -c "DROP DATABASE edrdb_verify;"
```

### Point-in-Time Recovery (PITR)

Enable WAL archiving on the primary for PITR capability:

```bash
# postgresql.conf additions:
# wal_level = replica
# archive_mode = on
# archive_command = 'aws s3 cp %p s3://your-org-edr-backups/wal/%f'

# Verify archiving is working
psql "$DATABASE_URL" -c "
  SELECT archived_count, failed_count, last_archived_wal
  FROM pg_stat_archiver;"
```

**Recovering to a point in time**:
```bash
# 1. Stop the server
pg_ctl stop -D /var/lib/postgresql/data

# 2. Restore base backup
aws s3 cp s3://your-org-edr-backups/postgresql/edrdb_<date>.dump .
pg_restore -d postgres://postgres@localhost:5432/edrdb_new <dump-file>

# 3. Create recovery.conf (PostgreSQL < 12) or postgresql.conf entry:
# recovery_target_time = '2026-03-23 08:30:00 UTC'
# restore_command = 'aws s3 cp s3://your-org-edr-backups/wal/%f %p'

# 4. Start in recovery mode
pg_ctl start -D /var/lib/postgresql/data
```

### What to Back Up

| Data | Backup Method | Frequency | Retention |
|---|---|---|---|
| PostgreSQL (full) | `pg_dump -Fc` | Daily at 02:00 | 30 days local, 90 days S3 |
| PostgreSQL WAL | WAL archiving to S3 | Continuous | 7 days |
| Agent binaries | S3 / artifact registry | Per build | Last 10 releases |
| NATS JetStream data | Docker volume snapshot | Daily | 7 days (re-creatable) |
| Nginx TLS certs | Certbot auto-renew + backup | On renewal | 3 copies |
| `.env.prod` secrets | Encrypted vault (e.g. AWS SSM) | On change | Version history |

## エージェント更新・サーバー手動操作

### 稼働中エージェントの更新（フリート反映）

サーバーイメージを更新しても**稼働中エージェントは自動更新されません**（自動更新機構は未運用）。新しいエージェントビルドを反映するには各端末で更新が必要です。

- **方法:** `deploy/install/update.ps1`（Windows）/ `update.sh`（Linux・macOS）を各端末で実行（RMM・構成管理ツールで配布）。Agent ID・設定を保持しバイナリのみ差し替え（SHA-256検証・自動ロールバック・整合性サイドカー自動更新）。
- **フルインストーラを更新に使わない:** `install.ps1` / `install.sh` の再実行は新しい Agent ID を生成し、ダッシュボードに**重複エンドポイント**として登録されます。
- **旧型インストール端末に注意:** 一部端末は旧インストーラ構成（サービス `EDRAgent`、`config\config.toml` や `/etc/edr-agent/config.toml`、watchdog 無し）です。更新スクリプトの前提（`EDRWatchdog` / `agent.toml`）と異なるため、`sc.exe qc EDRAgent`（Windows）/ `systemctl cat edr-agent`（Linux）で実バイナリ・config パスを確認し、その構成に合わせて差し替えてください。整合性サイドカー（`<config-dir>/agent.sha256`）の更新も忘れずに。詳細は [エージェントインストール手順](エージェントインストール手順.md) の「エージェントバイナリの更新」。
- **コマンド不達（半開きストリーム）の即時復旧:** スキャン等のコマンドが届かない場合、`Restart-Service EDRAgent` / `systemctl restart edr-agent` で再接続し滞留コマンドが配信されます（[トラブルシューティング](トラブルシューティング.md) 24章）。

### サーバーでの手動 docker compose 操作（重要な注意）

検証/本番サーバーで手動 compose 操作を行う場合の必須事項:

- **必ず両方の compose ファイルを指定:** プロジェクトは `docker-compose.yml` + `docker-compose.prod.yml` の2ファイル構成です。`-f` を片方しか指定しないと prod override（image タグ等）が効きません。
  ```bash
  COMPOSE="docker compose -f docker-compose.yml -f docker-compose.prod.yml"
  ```
- **★ IMAGE_TAG を必ず明示:** prod override は `image: ...:${IMAGE_TAG:-main}`。CI/CD（`docker.yml`）は `export IMAGE_TAG=main` してデプロイしますが、**`.env` に古い `IMAGE_TAG`（例: 旧バージョン）が残っていると、手動 `docker compose up -d` でそのタグの古いイメージに巻き戻ります**。手動操作時は `IMAGE_TAG=main` を明示するか、`.env` の `IMAGE_TAG` を現行（`main`）に揃えてください。
  ```bash
  # 例: api のみ現行イメージで再作成（依存は触らない・ローカルイメージ使用）
  IMAGE_TAG=main $COMPOSE up -d --no-deps --pull never api
  ```
- 変更前に `.env` をバックアップ（`cp .env .env.bak-$(date +%s)`）。`docker compose restart` は環境変数を再読込しないため、`.env` 変更を反映するには `up -d` で再作成すること。

### エージェント自動更新の広告（`AGENT_LATEST_*`）

サーバーの `AGENT_LATEST_VERSION` / `AGENT_LATEST_URL` / `AGENT_LATEST_CHECKSUM`（`.env`）が設定されていると、`GET /api/v1/agents/:id/update-check` が更新情報を返し、エージェントが自己更新を試みます。

- **checksum ドリフトは解消済み:** 以前は静的 `AGENT_LATEST_CHECKSUM`（`deploy.sh` が注入）が `docker.yml` のイメージ再ビルドとドリフトし、エージェントが `checksum mismatch` で更新適用に失敗していました。**現在は update-check が実配信バイナリから checksum を動的算出するため、`AGENT_LATEST_CHECKSUM` を設定しなくても正しい checksum で広告されます**（設定しても、実体と一致するもので上書きされます）。`AGENT_LATEST_VERSION` のみ設定すれば、当該バージョン未満のエージェントに更新が広告されます。
- **自動更新を運用しない場合:** `AGENT_LATEST_VERSION`（および任意で URL/CHECKSUM）を空にしてください。`update-check` が `{"up_to_date":true}` を返し、エージェントは何もしません。
  ```bash
  sed -i 's|^AGENT_LATEST_VERSION=.*|AGENT_LATEST_VERSION=|; s|^AGENT_LATEST_URL=.*|AGENT_LATEST_URL=|; s|^AGENT_LATEST_CHECKSUM=.*|AGENT_LATEST_CHECKSUM=|' .env
  IMAGE_TAG=main docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --no-deps api
  ```
  > 注: エージェントのバージョンはビルド時に注入されるようになり（ダッシュボード表示・比較が正常化）、checksum ドリフトも解消されました。ただし **watchdog 無し構成の端末は更新の適用（`.update-pending`→差し替え）が完結しない**ため、その種の端末を含む環境では引き続き広告しない（空にする）か、`update.ps1`/`update.sh` での更新を使ってください。
