## 1. 発見された問題 (2026-07 監査)

EDR プラットフォームはマルチテナント分離を **PostgreSQL Row-Level Security (RLS)** で実装している。API リクエストは `tenantMiddleware` が `app.tenant_id` を接続にセットし、`agents` / `alerts` / `incidents` の RLS ポリシー(migration 027)が行を絞り込む設計。しかし監査で**分離が全く実効していない**ことが判明した。

### 根本原因(3つ、いずれもライブ DB で実証)

| # | 問題 | 実証 |
|---|---|---|
| 1 | **アプリが DB スーパーユーザ `edr`(rolsuper=t, rolbypassrls=t)で接続** | スーパーユーザ/BYPASSRLS ロールは FORCE の有無に関わらず**全 RLS を無条件素通り**。`SET app.tenant_id='<非マッチ>'; SELECT count(*) FROM agents;` が全 7 件を返した。 |
| 2 | **RLS が FORCE でない** | `relforcerowsecurity=f`。テーブル所有者(edr)も RLS を素通り。 |
| 3 | **`app.tenant_id` が実クエリに届かない** | `PrepareConn` の `set_config(..., true)`(トランザクション局所)は、その Exec の暗黙トランザクション終了時に破棄され、リクエストの後続クエリでは空。空だとポリシーのエスケープ節 `app.tenant_id IS NULL OR ''` が**全テナントアクセスを許可**する。 |

### 影響

認証済みの**非 viewer ユーザ**(analyst 等)は、URL の `:id` を差し替えるだけで:
- `POST /api/v1/agents/<他テナントの agent id>/isolate` — **他社の端末をネットワーク隔離**(業務停止)
- `POST .../kill-process` — **他社端末のプロセスを kill**
- `POST .../quarantine-file` — **他社端末のファイルを隔離**
- 他テナントの `agents` / `alerts` / `incidents` を**閲覧・改変**

= **クリティカルなクロステナント BOLA**。加えて、アプリが DB 全権(スーパーユーザ)で動くこと自体が重大なアンチパターン(SQLi/アプリ侵害 = DB 全権奪取)。

> 注: 検証環境はデフォルトテナント単一のため未検出だった。単一テナント運用では表面化しないが、マルチテナント本番では即座に悪用可能。

## 2. 是正手順

### 手順1: コード修正 (PR #539 で main 反映済み)

- **`internal/store/postgres.go`**: `PrepareConn` / `AfterRelease` の `set_config` 第3引数を `true`→**`false`**(セッションスコープ)に修正。これで `app.tenant_id` がリクエストの全クエリに届き、解放時にクリアされる(原因 #3)。
- **migration 324**: `agents` / `alerts` / `incidents` に **`FORCE ROW LEVEL SECURITY`**(原因 #2)。

> ★これら**だけでは是正されない**。原因 #1(スーパーユーザ接続)が残る限り RLS は素通りのまま。次の手順2が必須。

### 手順2: 非スーパーユーザ・アプリロールへの切替 (★オペレータが意図的に実施)

稼働中システムの DB ロール変更 + 接続差し替えは高リスク(GRANT 漏れ = アプリ停止)。**ステージングで検証してから**本番に適用すること。

ロール作成・GRANT・DEFAULT PRIVILEGES は **migration 325(`server/migrations/325_edr_app_role.sql`)がコード化済み**で、次回 migration 適用時に自動実行される。ただし `edr_app` は **`NOLOGIN`・パスワード未設定**で作られるため(Secret を git に載せないため)、**この段階では接続に使えず既存挙動は一切変わらない**(安全な準備段階)。切替を有効化するのは以下 2 ステップの意図的オペレーション:

**(1) パスワード付与 + ログイン許可**(値は Secret 管理から。git・シェル履歴に残さない):

```sql
-- edr(所有者/スーパーユーザ)で接続して実行
ALTER ROLE edr_app WITH LOGIN PASSWORD '<Secret の強力なパスワード>';
```

migration 325 が既に付与済みの権限(参考・冪等なので再実行も可):

```sql
GRANT USAGE ON SCHEMA public TO edr_app;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO edr_app;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO edr_app;
ALTER DEFAULT PRIVILEGES FOR ROLE edr IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO edr_app;
ALTER DEFAULT PRIVILEGES FOR ROLE edr IN SCHEMA public
  GRANT USAGE, SELECT ON SEQUENCES TO edr_app;
```

**(2) アプリ実行時接続を `edr_app` に切替**: 全サービス(api / detection / ingestion / updater)で **新 env `APP_DATABASE_URL`** を `edr_app` の DSN に設定する。`.env` に一行追加するだけでよい(compose は `APP_DATABASE_URL` をパススルー済み):

```dotenv
APP_DATABASE_URL=postgres://edr_app:<pass>@postgres:5432/edrplatform?sslmode=disable
```

- **`APP_DATABASE_URL` が空(未設定)の間は各サービスが `DATABASE_URL` にフォールバック**するため、migration 325 をマージ・適用しても挙動は変わらない。切替は `APP_DATABASE_URL` の設定で初めて有効化する。
- **migration は引き続き `DATABASE_URL`(所有者 `edr`)で実行**される(DDL に所有者権限が要るため)。api は `RUN_MIGRATIONS=true` のとき、`APP_DATABASE_URL` が別値なら migration 専用に `DATABASE_URL` で所有者接続を張り直す(コード対応済み)。RUN_MIGRATIONS 経路は `edr` のまま。
- バックグラウンドワーカ(検知エンジン/ingestion/updater)も `edr_app` で接続する。`app.tenant_id` を設定しないため RLS エスケープ節により全テナントにアクセスできる(検知エンジンが全テナントのイベントを処理する意図された挙動)。
- 秘密情報は Secret 管理(K8s Secret / SSM / Vault)経由で注入する。
- **★デプロイ順序の落とし穴**: `APP_DATABASE_URL` を**読み取るアプリコード**と compose のパススルーは migration 325 と同じ PR (#541) に含まれる。**#541 がマージ・デプロイされる前に `APP_DATABASE_URL` を設定しても、稼働中イメージはそれを読まず従来どおり `DATABASE_URL`(edr) で接続する**(＝切替が無言で効かない)。必ず **#541 のデプロイ後**に (2) を行うこと。

### 手順2.5: 切替前のステージング・ドライラン (★GRANT 完全性 + 分離の事前実証)

本番切替の**最大の事故要因は GRANT 漏れ**(切替後にアプリが権限不足で停止)。切替前に、**稼働中アプリを止めずに** `edr_app` の権限と分離を検証できる — `SET ROLE edr_app` は所有者/スーパーユーザ接続から可能で、`edr_app` のログイン/パスワードは不要。migration 325 適用済みの DB(ステージング)で以下を実行する:

```sql
-- 1) RLS 分離が edr_app で実効するか (非マッチ → 0、自テナント → 該当件数)
SET ROLE edr_app;
SET app.tenant_id = '<存在しないテナントUUID>';
SELECT count(*) FROM agents;            -- 期待: 0
SET app.tenant_id = '<自テナントUUID>';
SELECT count(*) FROM agents;            -- 期待: 該当件数
RESET ROLE;

-- 2) GRANT 完全性: 各 count が 0 でなければ切替でその機能(テーブル)が停止する
--    ★relkind は 'r'(通常テーブル)だけでなく 'p'(パーティション親)/'v'(ビュー)/
--      'm'(マテビュー)も見る。`GRANT ... ON ALL TABLES IN SCHEMA` は
--      **マテビューを対象に含まない**(PostgreSQL の仕様)ため、'r' だけを数えると
--      取りこぼす。
SELECT c.relkind,
  count(*)                                                                     AS total,
  count(*) FILTER (WHERE NOT has_table_privilege('edr_app', c.oid, 'SELECT')) AS missing_select,
  count(*) FILTER (WHERE NOT has_table_privilege('edr_app', c.oid, 'INSERT')) AS missing_insert,
  count(*) FILTER (WHERE NOT has_table_privilege('edr_app', c.oid, 'UPDATE')) AS missing_update,
  count(*) FILTER (WHERE NOT has_table_privilege('edr_app', c.oid, 'DELETE')) AS missing_delete
FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = 'public' AND c.relkind IN ('r','p','v','m')
GROUP BY 1 ORDER BY 1;

-- 2') ★TimescaleDB chunk の GRANT 完全性 (events / network_connections の実体)
--     chunk は `_timescaledb_internal` にあり public の走査対象外。ここが 0 で
--     ないと、切替後にイベント系の画面だけが permission denied で空になる。
--     migration 329 が hypertable へ明示 GRANT して伝播させる。
--
--     ★対象は実チャンク (_hyper_N_M_chunk / compress_hyper_N_M_chunk) のみ。
--     同じスキーマに bgw_job_stat / bgw_policy_chunk_stats / bgw_job_stat_history
--     といった TimescaleDB 内部カタログが同居しているが、これらは TimescaleDB の
--     バックグラウンドワーカ (所有者権限) だけが書き込むもので、edr_app に
--     INSERT が無いのが正常。スキーマ全体を数えると必ず missing_insert=3 が出て
--     誤検知になる (2026-07 検証EC2 で実際に踏んだ)。
SELECT count(*) AS chunks,
  count(*) FILTER (WHERE NOT has_table_privilege('edr_app', c.oid, 'SELECT')) AS missing_select,
  count(*) FILTER (WHERE NOT has_table_privilege('edr_app', c.oid, 'INSERT')) AS missing_insert
FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname LIKE '\_timescaledb\_internal%'
  AND c.relkind IN ('r','p')
  AND (c.relname LIKE '\_hyper\_%\_chunk' OR c.relname LIKE 'compress\_hyper\_%\_chunk');

-- 3) シーケンス USAGE (serial/identity 列への INSERT が通るか。0 を期待)
SELECT count(*) FILTER (WHERE NOT has_sequence_privilege('edr_app', c.oid, 'USAGE')) AS missing_seq_usage
FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = 'public' AND c.relkind = 'S';
```

いずれの `missing_*` も **0** であれば、切替後にアプリが権限不足で停止するリスクは無い。カタログ照合(`has_table_privilege`)なので、個別テーブルへのダミー INSERT より網羅的かつ安全(スキーマ推測による誤判定が無い)。

> **2026-07 追記 — ドライラン query の穴を是正**: 当初の query は `relkind = 'r' AND nspname = 'public'` のみを集計しており、**マテビュー(`ALL TABLES IN SCHEMA` の対象外)** と **TimescaleDB chunk(`_timescaledb_internal`)** を走査していなかった。この 2 つが漏れると「ドライランは `missing_* = 0` なのに、切替後にイベント系画面だけが空になる」という検知できない事故になる。上記 2) / 2') はその穴を塞いだもの。GRANT 側の予防は migration 329。
>
> **検証EC2 での実測 (2026-07-30)**: `edr_app` 切替後に 2') を実行したところ、実チャンク側の漏れは **0** だった(TimescaleDB が hypertable への GRANT を chunk へ伝播しており、migration 325 の `ALL TABLES IN SCHEMA` 経由でも届いていた)。当初 `missing_select=1 / missing_insert=3` が出たのは、query が `_timescaledb_internal` スキーマ全体を数えており `bgw_job_stat` / `bgw_policy_chunk_stats` / `bgw_job_stat_history` という **TimescaleDB 内部カタログ**を拾っていたため。これらに `edr_app` の INSERT が無いのは正常。上記のとおり実チャンクのみに絞り込んで是正した。migration 329 は「マテビューは `ALL TABLES` の対象外」という PostgreSQL 仕様への保険として残す(この環境にマテビューは無く、連続集計は `relkind='v'` のため実害は無かった)。

> **★検証EC2 (staging) での実測 (2026-07)**: 上記ドライランを実行し、①分離 = 非マッチ→**0** / 自テナント→**7**、②GRANT 完全性 = `missing_select/insert/update/delete` すべて **0**、③`missing_seq_usage` = **0** を確認済み。migration 325 の `GRANT ... ON ALL TABLES/SEQUENCES` により**漏れは無く、本番切替でアプリが停止するリスクは無い**ことを、稼働中アプリを止めずに事前実証した。

## 3. 追加の多層防御・強化候補

### 実装済み

- **対応アクション系エンドポイントのアプリ層テナントチェック(多層防御)**: agent に**コマンドを送出する 7 エンドポイント**(`Isolate` / `Unisolate` / `TriggerScan` / `TriggerScanCancel` / `KillProcess` / `QuarantineFile` / `RestoreFile`)で、対象 agent が呼び出し元テナントに属することをアプリ側でも検証する(`AgentHandler.ensureAgentInTenant` → `AgentStore.AgentBelongsToTenant` の明示 `AND tenant_id = $2`)。非マッチは**コマンド送出前に 404**。★これは **RLS に依存しない**ため、`edr_app` 切替前(スーパーユーザ接続で RLS 素通り)でもクロステナント BOLA を閉じる。Commander 経由のコマンド送出は RLS 保護テーブルを触らないため、RLS だけでは塞げない経路をここで塞ぐ。単一テナント運用(tenant_id 無し)では no-op。

- **`users` テーブルの RLS 追加(migration 326)**: `users` は tenant_id 列を持つが RLS 未設定で `List` 等がクロステナントにユーザを返していた。agents/alerts/incidents と同型の RLS(ENABLE+FORCE+エスケープ節ポリシー)を追加。★NULL テナント問題(Create/SeedAdminUser/管理API/LDAP JIT が tenant_id 未設定=NULL を残す→RLS で不可視化 + 認証済み INSERT が拒否される)を **Go コードを変えず**に解決するため、列 DEFAULT を `COALESCE(NULLIF(current_setting('app.tenant_id',true),'')::uuid, 既定テナント)` にした(認証済みリクエストは自テナント、バックグラウンド/起動時は既定テナントに自動フォールバック)。login は JWT 発行前=app.tenant_id 未設定=エスケープ節で全件可視のため壊れない。

### 精査の結果 RLS を見送ったテーブル

- **`rules` / `suppression_rules` は「全テナント共有(グローバル)」設計**: コードは完全にテナント非対応(`RuleRow`/`SuppressionRule` に TenantID フィールドなし、INSERT で tenant_id 未設定、組込ルールの大多数が `tenant_id=NULL`)。detection engine は app.tenant_id 未設定で全ルールをロードする前提。ここに素朴に RLS を付けると **API からグローバルルール(NULL テナント)が不可視化し、ルール/抑制管理 UI が破綻**する。ルールはプラットフォーム共通資産のため、テナント分離 RLS は**適用しない**(将来テナント固有ルールを導入する場合は `tenant_id IS NULL` をグローバルとして全テナント可視にするポリシー拡張が別途必要)。

- **alerts / incidents の tenant_id DEFAULT 付与(migration 328)**: `edr_app` 切替の前提整備。両テーブルは RLS 済みだが tenant_id の DEFAULT が無く、API プロセス内のアラート生成ワーカ(約15本)が tenant_id 未設定で INSERT する。`edr_app` 切替後は NULL テナントのアラート/インシデントが認証済み API から不可視化する(単一テナントでも既定テナント≠NULL)。users(326)と同型の動的 DEFAULT + バックフィルで是正。

### 残る強化候補 (別issue / 大規模なため専用設計)

- **★エスケープ節 `app.tenant_id IS NULL OR ''` の fail-closed 化(大規模・専用フェーズ推奨)**: エスケープ節があるため「`app.tenant_id` を設定し損ねた接続」は全テナントアクセスになる(fail-open)。理想は API 接続でエスケープ節を外し fail-closed 化することだが、**2026-07 の監査で単純実装は不可と判明**:
  - `app.tenant_id` をセットするのは HTTP リクエスト経路(tenantMiddleware)のみ。**cmd/api プロセス内の約35本のバックグラウンドワーカ**(HeartbeatMonitor / DeadAgentCleanup / DataRetentionCleaner / 各種アラート生成 detector・correlator / 集計 collector / IncidentEscalator / 通知系 / in-process 検知パイプライン等)と**認証前 HTTP 経路**(ログイン=`users`、heartbeat=`agents`/`alerts`、enrollment=`agents`、Wazuh/Mobile/Log ingest=`agents`/`alerts`)が、いずれも同一の `edr_app` プールを `app.tenant_id` 未設定で共有し、エスケープ節に依存して全テナント処理している。
  - よってエスケープ節を単純削除すると **ログイン全滅・agent 永久オフライン・アラート生成/保持削除/集計/通知の全停止**を招く。
  - 安全に fail-closed 化するには: ①**API プロセスに 2 本目のプール**を持たせ、バックグラウンドワーカ + 認証前経路だけ **all-tenant worker ロール**(または BYPASSRLS)で接続、②cmd/ingestion / cmd/detection は別プロセスなので各 `APP_DATABASE_URL` を worker ロールへ、③alerts/incidents への INSERT に **agent→tenant 解決 + 明示 tenant_id 設定**を追加、④ログイン/authMiddleware のユーザ検索はテナント確定前に走るため worker ロール経由に。= **フェーズ分割した専用設計・テストが必須**。PR #541 では実施せず、設計と破損インベントリを記録するに留めた(未着手の技術的負債として [技術的負債と改善計画.md](../技術的負債と改善計画.md) に登録)。
  - → 詳細なフェーズ分割設計: [RLS-fail-closed設計.md](RLS-fail-closed設計.md)。
- **ロール権限の追加最小化**: `edr_app` に不要なテーブルへの権限を更に精査(327 で schema_migrations は対処済)。
