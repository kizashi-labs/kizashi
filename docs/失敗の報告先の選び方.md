# 失敗の報告先の選び方

実測 (2026-08-12)。失敗を報告する綴りは3つあります。

| 綴り | 件数 | 答える問い |
|---|---|---|
| `fail(ctx, err, msg)` | 147 | この回が仕事を終えられなかった（`internal/scheduler` の中だけ。`tick.Fail` への委譲） |
| `metrics.BackgroundFailed(comp, …)` | 46 | **この部品が失敗した**（`edr_background_failures_total`） |
| `tick.Fail` / `tick.FailComponent` | — | この回が終えられなかった／その両方 |

**どれも「失敗を報告する」ですが、答える問いが違います。**

## 選び方

**「回」があるのは、周期的に回る仕事の中だけです。**

- `tick.Run` / `trackRun` で回している仕事の中 → **`tick.FailComponent`**
  部品ごとの件数を残したまま、その回を「終えられなかった」に落とします。
  `BackgroundFailed` だけだと、失敗は数えられるのに **`last_success` は
  動き続けます** —— 毎回失敗しているワーカーが、健全なワーカーと同じ姿に
  なります。
- それ以外 → **`metrics.BackgroundFailed`**
  「回」の単位が無いので、部品ごとの件数が正しい答えです。

`TestTrackedWorkersDoNotReportPastTheRun` が 0 件に留めています。
**この検査は3段たどります** —— 最初は `tick.Run` に直に渡している関数
しか見ておらず、そこから呼ばれる関数が漏れていました。広げて見つかった
のは 10 か所:

    detection/correlation.go:upsertCase        インシデントの自動作成
    shipper/elasticsearch.go:Flush ×2          ES への送信
    sync/wazuh.go:SyncAgents ×2                Wazuh 同期
    compliance/evaluator.go:EvaluateAll        エージェントごとの評価
    detection/heartbeat_monitor.go:createOfflineAlert
    enrichment/virustotal.go ×2                エンリッチメント
    threatintel/public_feeds.go ×2             公開フィードの取り込み

`shipper.Flush` は `tick.Run(ctx, "es", func(ctx){ s.Flush(ctx) })` の形で、
**クロージャに包まれていたので「直に渡している関数」としても見えて
いませんでした。**

**同じ到達判定で `slog.Error` を探すと、さらに 13 か所ありました**
（`TestTrackedWorkersDoNotReportOnlyToTheLog`）:

    alert_enrichment  テーブル確認の失敗
    cloud/poller      設定を読めない統合／イベントを組み立てられない
    shipper           **ES が受け取らなかった文書**（送信自体は成功なので、
                      ログ以外に跡が残りません）
    risk_action       **自動隔離の失敗** —— 成功時だけ severity 10 の
                      アラートが立つので、失敗は画面のどこにも出ません
    sync/wazuh        端末ごとの脆弱性取得（合計だけ見ると「脆弱性なし」）
    updater/applier   ロールバック記録の失敗（行が 'applying' のまま）
    detection/anomaly ベースライン更新／異常検知（古い土台の上で判定を続けます）

**さらに `slog.Warn` を同じ判定で探すと 30 か所**ありました
（`TestTrackedWorkersDoNotDowngradeToWarn`）。**`Warn` は運用の設定で
最初に切られる段です** —— このセッションでも「`Error` を `Warn` に落とす」
変更が検査を通ったことがありました。19 か所を `tick.Fail` に移し、
残り 9 は理由つきです（`return err` で呼び出し側が報告する／直後に
`FailComponent` を呼ぶ／回の話ではない）。

**最後に「error を受け取って何も言わない分岐」を測ると 4 か所**でした
（`TestTrackedWorkersDoNotSwallowErrorsSilently`）。どれも直後に
`rows.Err()` か `skipped` の件数でまとめて報告しています ——
**pgx は Scan が失敗した時点で結果セットを終える**ので、`continue` は
1行を飛ばすのではなく、そこで走査が終わります。理由つきで留めました。

**`internal/scheduler` も走査に入れました**
（2026-08-12）。入れると 13 か所あり、どれも「この回は仕事を終えられ
なかった」でした —— 証明書の状態更新、コンプライアンススコアの保存、
エスカレーション、レポート／ダイジェストのメール、フィード取得、
デッドエージェントの非アクティブ化、KPI 定義、ベースラインの除外ルール。
`fail` に移しました。

これで、`tick.Run` から届く失敗の報告は3つとも見張られています:

    slog.Error   0 件（＋到達判定の取り違え2）
    slog.Warn    22 件（すべて理由つき —— 検出の報告・設定の話・
                 テーブルがまだ無い配置）
    黙って捨てる 25 件（すべて理由つき —— `for rows.Next()` の中の
                 `rows.Scan` で、直後の `rows.Err()` が報告します）

**3つとも `server/internal` 全体を見ています**（除外はありません）。
`internal/scheduler` を最後に入れたとき、`Error` 13・`Warn` 45 が
`fail` に移りました —— **除外していた package は、除外していただけで
健全ではありませんでした。**

### 「渡す error が無い」は理由になりません

`Warn` に最後まで残っていた2件は `cert_expiry_checker.go:checkDomainCert`
で、**error 値を持たない失敗**でした —— TLS の型アサーション失敗と、
ピア証明書0件です。`fail(ctx, err, …)` は error を要るので、そこで
止まっていました。

行には `status='error'` を書いていたので**画面には出ていました**。
出ていなかったのは回の方です —— `last_success` が動き続け、**証明書を
1枚も読めていないチェッカーが、健全なチェッカーと同じ姿**でした。

名前のある error を2つ作って渡しました（`errNotATLSConn` /
`errNoPeerCertificate`）。**error が無いなら作ります。**

あわせて、この形の一般則を検査にしました
（`internal/scheduler/giving_up_on_a_domain_test.go`）——
**1つの対象を諦めた枝は、行と回の両方に出していること。** 片方だけだと、
画面と計測が食い違ったまま気づけません。

`slog.Error` に残る2件は**到達判定の取り違え**です —— `pool.Query(…)` が同じ package の
`Query` という名前のハンドラに当たります。到達判定は package までしか
見ないので消せず、理由を書いてあります。

## 「回」の外の 46 か所（実測）

| 分類 | 件数 | どういうものか |
|---|---|---|
| 起動時 | 8 | プロセス起動時に一度だけ。次の回はありません |
| 要求ごと | 5 | 利用者が待っていて、応答でも分かります |
| イベントごと | 15 | 1件ごと。呼び出し側は次のイベントです |
| error を返す | 9 | 呼び出し側が受け取ります。件数はここが足します |
| 仕組み | 1 | `internal/tick` 自身 |

**どれも「回」の単位を持ちません。** つまり `BackgroundFailed` のままで
正しい、というのが今回の結論です —— ただし**それは読んで確かめた結果**で、
それまでは「そのままで正しいはず」と書いてあるだけでした。

## 走査が file を黙って飛ばさないこと（2026-08-12）

この文書の数はどれも AST の走査から出ています。**その歩き方が
`parser.ParseFile` の失敗を黙って飛ばしていると、その file は走査から
消えます** —— 中に何が書いてあっても 0 件です。

気づいたのは変異検査でした。「元の実装に戻す」変異が `internal/tick` で
3件、`internal/api/handlers` で1件、**これだけの理由で生き残っていました**
—— 構文を壊した file は、`go test` の対象 package でなければコンパイルも
走らないので、壊したことに誰も気づきません。

`server/internal` の `*_test.go` を数えたら **16 か所**（`return nil` が
12、`continue` が 4）。全部直しました:

    歩き方（WalkDir/Walk の中）  `return <err>` で上に返す
    ループ（for の中）           `t.Fatalf` で落とす

`server/internal/tick/scan_honesty_test.go` が 0 を留めます。**この検査
自身が同じ穴を持っていないこと**も、わざと壊した file を食わせて
確かめています —— 本物の木はどれも parse できるので、それしか
「返している」と「飛ばしている」を見分ける方法がありません。

## この文書が古くならないようにしてあること

一覧は文章ではなく検査の中にあります
（`server/internal/tick/background_failed_test.go`）。

- **新しい呼び出しは、5つのどれかに分類するまで落ちます。**
  分類を書けない（＝「回」の単位が要る）なら、それは `tick.Run` で包む合図です。
- **消えた箇所の分類が残っていても落ちます。**
- 分類の名前は5つに限ります。「あとで見る」のような自由文は通りません。
- 全部を1つの分類に寄せることもできません。
- **走査の鍵が合っていることも見ます。** 名前の集合を `package|関数名` に
  変えたとき、走査側を直し忘れて**照合が全部外れ、0 件を検査して緑**に
  なりました。いまは「いくつ照合したか」に床があります。
