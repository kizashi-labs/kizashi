# Kizashi — セキュリティ強化ガイド（ハードニング）

**対象読者:** システム管理者・セキュリティエンジニア  
**最終更新:** 2026-06-03  
**対象バージョン:** v1.3.50+

---

## 概要

本ガイドでは、Kizashi サーバーを本番環境に展開する際のセキュリティ強化（ハードニング）設定を説明します。デフォルト設定で運用可能ですが、本ガイドの設定を適用することでセキュリティレベルをさらに向上できます。

## 1. 認証・アクセス制御

### 1-1. デフォルト管理者アカウントの変更

初回ログイン後、**必ず** 以下を変更してください：

- デフォルトパスワード（`Admin1234!`）を変更
- デフォルトメールアドレス（`admin@example.com`）を実際の管理者アドレスに変更

```sql
-- 直接変更が必要な場合（DB アクセス権がある場合）
UPDATE users 
SET email = 'admin@yourcompany.com'
WHERE email = 'admin@example.com';
```

### 1-2. パスワードポリシーの設定

**管理 → 管理 & 設定 → パスワードポリシー** で以下を設定：

| 項目 | 推奨値 |
|------|-------|
| 最小文字数 | 14 文字以上 |
| 複雑性要件 | 大文字・小文字・数字・記号すべて必須 |
| 有効期限 | 90 日（SOCアナリスト・管理者は 60 日推奨） |
| 再利用禁止 | 直近 12 回のパスワードを禁止 |
| ロックアウト | 5 回失敗でロック、30 分後に自動解除 |

### 1-3. 二要素認証（MFA）の必須化

1. **管理 → 管理 & 設定 → MFA管理** を開く
2. **MFA必須化** トグルを有効化
3. 既存ユーザーの次回ログイン時に TOTP アプリの登録を強制

> admin ロールのユーザーは特に MFA を必須にしてください。

### 1-4. 最小権限の原則

ユーザーには必要最小限のロールを付与してください：

| 用途 | 推奨ロール |
|------|----------|
| 経営層・サマリー閲覧のみ | `viewer` |
| SOCアナリスト（日常対応） | `analyst` |
| SOCチームリード | `soc_lead` |
| システム管理・設定変更 | `admin` |

`admin` ロールは必要最小人数に限定してください。

### 1-5. SSO 優先設定

IdP（Okta / Azure AD / Google Workspace）が利用可能な場合は SAML SSO を設定し、ローカルパスワード認証を無効化することを推奨します。詳細は [enterprise/SSO・LDAP連携.md](enterprise/SSO・LDAP連携.md) を参照してください。

> **注意（v1.3.50+）**: SAML 設定が DB に未登録の状態で SAML エンドポイントにアクセスすると 503 が返ります。設定完了前に SAML ログインを試みないでください。

## 2. 通信の暗号化

### 2-1. HTTPS（TLS 1.2+）の強制

本番環境では必ず HTTPS を使用してください。リバースプロキシ（nginx / Caddy）でTLSを終端します。

**nginx 推奨設定（`/etc/nginx/conf.d/edr.conf`）:**

```nginx
server {
    listen 443 ssl http2;
    server_name edr.yourcompany.com;

    ssl_certificate     /etc/ssl/certs/edr.crt;
    ssl_certificate_key /etc/ssl/private/edr.key;

    # TLS 1.2 以上のみ許可
    ssl_protocols TLSv1.2 TLSv1.3;

    # 弱い暗号スイートを除外
    ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384;
    ssl_prefer_server_ciphers off;

    # HSTS（6ヶ月）
    add_header Strict-Transport-Security "max-age=15768000; includeSubDomains" always;

    # HTTP → HTTPS リダイレクト
    location / {
        proxy_pass http://localhost:3000;
    }
}

# HTTP はリダイレクト
server {
    listen 80;
    return 301 https://$host$request_uri;
}
```

### 2-2. エージェント通信の mTLS

エージェントとサーバー間の gRPC 通信には、デフォルトで相互TLS（mTLS）が使用されます。以下を確認してください：

- `GRPC_TLS_CERT` / `GRPC_TLS_KEY` 環境変数が設定されている
- エージェントの証明書有効期限を定期的に確認する（自動更新機能あり）

証明書の有効期限確認：

```sql
SELECT hostname, cert_not_after,
       (cert_not_after - NOW()) AS remaining
FROM agents
WHERE cert_not_after IS NOT NULL
ORDER BY cert_not_after
LIMIT 20;
```

## 3. API・Webhook セキュリティ

### 3-1. APIキーの管理

- スコープは **最小権限**（`read` 専用が可能なら `write` / `admin` を付与しない）
- 有効期限は **90 日以内** に設定
- 不要になったキーは **即時削除**
- CI/CD パイプラインには専用の `read` スコープキーを発行（`admin` スコープは使用しない）

> **漏洩時の対応**: 疑いがある場合は **管理 → 統合 → APIキー → 削除** で即時失効させ、新しいキーを発行してください。

### 3-2. Webhook シークレット

外部システムへの Webhook を設定する場合、シークレット（署名検証キー）を必ず設定してください。

**管理 → 統合 → Webhook → 署名シークレット** に UUID v4 相当のランダム文字列を設定します：

```bash
# シークレット生成例
python3 -c "import secrets; print(secrets.token_hex(32))"
```

### 3-3. レート制限

本番環境の API サーバーには nginx でレート制限を設定することを推奨します：

```nginx
limit_req_zone $binary_remote_addr zone=api:10m rate=30r/s;

location /api/ {
    limit_req zone=api burst=50 nodelay;
    proxy_pass http://localhost:8080;
}
```

## 4. 自動隔離の安全な設定

### 4-1. 誤検知による業務影響を防ぐ設定

自動隔離は強力な機能ですが、誤設定すると業務停止につながります：

```env
# 本番推奨設定（保守的）
AUTO_ISOLATE_MIN_SEVERITY=9
```

詳細な設定方法は [自動隔離・SOAR設定ガイド](自動隔離・SOAR設定ガイド.md) を参照してください。

### 4-2. アラート抑制ルールの空条件ガード

アラート抑制ルールに**空の条件（`conditions={}`）** を設定すると、すべてのアラートが抑制されます。定期的に確認してください：

```sql
-- 危険な空条件ルールのチェック
SELECT id, name, is_active, conditions
FROM suppression_rules
WHERE conditions::text = '{}'
  AND is_active = true;
```

該当がある場合は即座に無効化：

```sql
UPDATE suppression_rules SET is_active = false WHERE id = '<id>';
```

## 5. ログと監査証跡

### 5-1. 監査ログの設定

重要な操作はすべて監査ログに記録されます。ログの転送・保存設定を確認してください：

**管理 → レポート & コンプライアンス → 監査ログ** で確認できる操作：

- ユーザーログイン・ログアウト
- エンドポイント隔離・解除
- ルールの追加・変更・削除
- ユーザー管理操作
- APIキー発行・削除

### 5-2. 外部 SIEM への転送

重要な監査イベントは外部 SIEM に転送することを強く推奨します：

**管理 → 統合 → SIEM統合** で Splunk / Microsoft Sentinel / Elastic SIEM を設定してください。

### 5-3. AI利用ログの保持

個人情報保護法（APPI）の観点から、AI利用ログ（1年間保持）が適切に機能していることを確認：

```sql
-- AI 利用ログのレコード数確認
SELECT function_name, COUNT(*) as cnt, MIN(called_at), MAX(called_at)
FROM ai_usage_logs
GROUP BY function_name
ORDER BY cnt DESC;
```

## 6. データ保護

### 6-1. データ保持ポリシーの設定

コンプライアンス要件に応じてデータ保持期間を設定してください：

```env
# アラート保持期間（デフォルト: 90日）
ALERT_RETAIN_DAYS=90

# プレイブック実行ログ保持期間（デフォルト: 180日）
PLAYBOOK_RETAIN_DAYS=180
```

### 6-2. データベースの暗号化

PostgreSQL のデータを暗号化するには、ディスクレベルの暗号化（LUKS / AWS EBS 暗号化）を使用してください。

### 6-3. バックアップのセキュリティ

- バックアップデータを暗号化した上で保存する
- バックアップ先に適切なアクセス制御を設定する
- 復旧手順を定期的にテストする

詳細は [ops/バックアップ・リストア.md](ops/バックアップ・リストア.md) を参照してください。

### 6-4. データベース接続を最小権限にする（★マルチテナント運用では必須）

既定では、アプリは DB スーパーユーザ `edr` で接続します。この状態には 2 つの問題があります:

1. **アプリ侵害（SQLi 等）が即 DB 全権奪取**につながる。
2. **PostgreSQL の Row-Level Security (RLS) が無条件で素通り**する。スーパーユーザ／`BYPASSRLS` ロールは RLS の対象外のため、**テナント分離が実効しません**。

そこで、非スーパーユーザのアプリロール `edr_app` に切り替えます。ロール作成と権限付与は migration 325 で自動化済みですが、**安全のため `edr_app` は初期状態で `NOLOGIN`・パスワード未設定**であり、切替は運用者が明示的に有効化する必要があります。

```dotenv
# 所有者ロール。migration（DDL）実行に使う。消さないこと
DATABASE_URL=postgres://edr:<pass>@postgres:5432/edrplatform?sslmode=disable

# アプリ実行時接続（非スーパーユーザ）。未設定なら DATABASE_URL にフォールバック
APP_DATABASE_URL=postgres://edr_app:<pass>@postgres:5432/edrplatform?sslmode=disable
```

有効化の全手順（事前確認・検証・切り戻し・よくある失敗）は
[ops/RLSテナント分離有効化ランブック.md](ops/RLSテナント分離有効化ランブック.md) を参照してください。

> **単一テナント運用でも推奨**: テナント分離の実益は無くても、「アプリが DB 全権で動かない」こと自体が侵害時の被害を大きく減らします。

> **多層防御**: 端末への対応アクション（隔離・プロセス kill・ファイル隔離・スキャン）は、RLS とは独立にアプリ層でも呼び出し元テナントを検証しています。`edr_app` 切替前でもクロステナント操作は 404 で拒否されます。

## 7. SSO / SAML 設定

### 7-1. SAML 設定のガイドライン

SAML を設定する際の注意事項：

1. **設定を完了してから運用を開始する** — SAML 設定が未完了の状態で SAML エンドポイントに向けたアクセスが来ると、503 が返ります（v1.3.50 以降はこれが正しい動作です）
2. **証明書の有効期限を監視する** — IdP の SAML 証明書の期限切れはログイン不可能になります
3. **ローカル管理者アカウントを最低1つ維持する** — SSO 障害時の緊急アクセス用

### 7-2. LDAP 通信のセキュリティ

**管理 → 統合 → LDAP/AD連携** の設定：

- `ldap://` ではなく `ldaps://`（ポート 636）または STARTTLS（ポート 389）を使用
- バインドパスワードは長いランダム文字列を使用

### 7-3. OIDC のユーザー情報検証

> **注意（セキュリティ修正）**: 以前のバージョンでは userinfo エンドポイント（`GetUserInfo`）呼び出し時に HTTP ステータスコードを確認しておらず、IdP がアクセストークンを 401/403 で拒否した場合でも空のユーザー情報のまま処理が継続し得る不具合がありました。現在は非 200 応答を認証エラーとして拒否します。詳細は [enterprise/SSO・LDAP連携.md](enterprise/SSO・LDAP連携.md) の「OIDCトークン検証エラー」を参照してください。

## 8. インフラセキュリティ

### 8-1. ファイアウォール設定

サーバーのファイアウォールで不要なポートを閉じてください：

| ポート | 用途 | 許可元 |
|--------|------|--------|
| 443 | HTTPS（Web UI） | 管理端末のIP |
| 9091 | gRPC（エージェント通信） | エンドポイントのIP帯 |
| 8080 | API（内部） | ローカルホストのみ |
| 5432 | PostgreSQL | ローカルホストのみ |
| 4222 | NATS | ローカルホストのみ |
| 6379 | Redis | ローカルホストのみ |

> ポート 8080、5432、4222、6379 はインターネットに公開しないでください。

### 8-2. Docker セキュリティ

```yaml
# docker-compose.yml の推奨設定
services:
  api:
    security_opt:
      - no-new-privileges:true
    read_only: true   # 書き込みが必要な場所は volumes でマウント
    user: "1000:1000"  # rootで実行しない
```

### 8-3. 定期的なイメージ更新

```bash
# 最新イメージへの更新
docker compose pull
docker compose up -d
```

## 9. 定期的なセキュリティチェック

### 日次チェック

- [ ] APIキーの使用状況を確認（未使用キーを削除）

- [ ] ユーザーアカウントの棚卸し（退職者のアカウント削除）

- [ ] AIキーの有効期限とローテーション
- [ ] セキュリティアップデートの適用
- [ ] アクセスログの外部SIEMへの転送確認

## 10. チェックリスト

本番展開前の最終確認リストです。

### 認証

- [ ] デフォルトパスワードを変更した
- [ ] デフォルト管理者メールアドレスを変更した
- [ ] MFA（TOTP）を全 admin ユーザーに設定した
- [ ] パスワードポリシーを設定した（最小14文字・有効期限90日）
- [ ] 不要なユーザーアカウントを削除した

### 通信

- [ ] HTTPS（TLS 1.2+）を設定した
- [ ] HTTP → HTTPS リダイレクトを設定した
- [ ] HSTS ヘッダーを設定した
- [ ] エージェント通信の mTLS 証明書を設定した

### API・Webhook

- [ ] デフォルト以外の APIキーにスコープ・有効期限を設定した
- [ ] Webhook に署名シークレットを設定した

### 自動隔離

- [ ] `AUTO_ISOLATE_MIN_SEVERITY` を要件に合わせて設定した
- [ ] 重要インフラを除外リストに登録した
- [ ] `auto_isolate=true` のルールを意図したものだけに限定した

### ログ

- [ ] 監査ログの転送先（SIEM）を設定した
- [ ] データ保持期間をコンプライアンス要件に合わせて設定した

### データベース・テナント分離

- [ ] `APP_DATABASE_URL` を設定し、アプリが非スーパーユーザ `edr_app` で接続している（6-4）

### インフラ

- [ ] 不要なポートをファイアウォールで閉じた
- [ ] DB・NATS・Redis がローカルホスト以外からアクセス不可であることを確認した
- [ ] バックアップを設定し、リストア手順をテストした
