# 検知ルールの二重管理とデプロイ早見表

2026-06-22 の実機調査で判明したアーキ構造と、その運用上の落とし穴・対策をまとめる。
「ルールを直したのに本番が変わらない」事故（同日発生）の再発防止が目的。

## 1. 検知は2つのエンジン／2つのサービスで並行している

| | API サーバ (`kizashi-api`) | Detection サーバ (`kizashi-detection`) |
|---|---|---|
| エンジン | `AlertPipeline` → `detection.SigmaEvaluator` | `detection.Engine` → `rules.RuleEngine` |
| Sigmaルール源 | **Go ビルトイン** `sigma_builtins.go` ＋ **DB `rules`**（PR #647 以降。`sigma_db.go`） | **DB** `rules`（migration 014/019 等で seed） |
| イベント購読 | core NATS `events.*.<type>` | JetStream `events.>` |
| アラート形式 | `"[Sigma] <title>"` | エンジン独自形式 |
| 付随機能 | Sigma + IOC + UEBA | Sigma + YARA + 振る舞い + 相関 + 自動応答 + playbook |
| 起動箇所 | `cmd/api/main.go` `NewAlertPipeline` | `cmd/detection/main.go` `NewEngine` |

- 2エンジンは**別々のルール源**で同じイベントを処理する……というのが 2026-08-04 までの姿である。
  **PR #647 以降、`rules` テーブルは両方のエンジンが読む**（§7.4 (a) の実装）。ビルトインは
  API サーバ専用のまま。タイトル衝突時は API サーバ側でビルトインが勝つ。
- 同名ルールが両方に存在しうるが**検知ロジックが異なる**ことがある。
  例: `Registry Run Key Persistence` は ビルトイン=`process_creation`（reg.exe のコマンドライン照合）、DB=`registry_set`（TargetObject 照合）。
- `cooldown` / `SequenceEngine`（振る舞い・バースト相関）は **detection サーバ側**（`rules` パッケージ）。
- **ランタイム・ステートフル検知（第3の源、detection サーバ側）**: `internal/detection/*.go` の `*Scorer`/`*Detector`
  （`netScan` T1046 / `dnsAgg` T1071.004 / `killChain` 相関 / `discovery` / `authAttack` T1110 / `fileBurst` T1486 /
  `lateralFanout` T1021 / `exfilVol` T1048）は **Sigma でも DB ルールでもなく**、`Engine.processEventData` が
  flat イベントを直接与えて窓集約する。**ビルトイン Sigma（API サーバ側）は kill-chain に供給されない**ため、
  相関に効かせたい検知はこの detection エンジン経路に置くこと。これらの match は `matches` に載り `KillChainScorer`
  相関へ自動供給される。

## 3. 予算ゼロでの手動デプロイ（GitHub Actions 課金枯渇時）

サーバ箱 `ip-10-0-0-10`（公開 `203.0.113.10`、docker 稼働、ソース `/home/ubuntu/edr-platform`）で:

```bash
cd /home/ubuntu/edr-platform
git pull --ff-only origin main
# 例: detection を反映                 # api を反映するなら "api"
IMAGE_TAG=main docker compose build --no-cache detection
IMAGE_TAG=main docker compose up -d --no-deps detection
```

- migration が無い変更（cooldown・ビルトインSigma 等）はこれで即反映。DB/他サービス無停止。
- compose の各サービスは `build: server/Dockerfile target <svc>` 定義があり、ローカルソースを `COPY server/` してコンパイルする。
- `--no-cache` を付けると Go ビルド層のキャッシュ取り違えを確実に回避（同日、キャッシュで旧バイナリが残った疑いあり）。

## 4. 再発防止（実装済み・案C）

- `TestBuiltinSigmaPrimaryTechnique`（`sigma_builtins_primary_technique_test.go`）: ビルトインの
  multi-technique ルールの**先頭タグ＝主テクニック**を固定。タグ順回帰（例: Run Key が T1112 になる）を検知。
- `sigma_builtins.go` 冒頭に二重エンジンの相互参照コメント。
- **到達性ガード（2026-07-20, PR#492）**: `TestEmittedEventFieldsAreSupported`（`field_support_reachability_test.go`）が
  ingestion(`handler.go`)の emit フィールドと `SupportedSigmaFields` の同期を保証。emit されているのに未サポート＝
  ルールが誤って defer/inert になる「サイレント抑制」を CI で自動検出。`TestBuiltinRuleFieldSupportAudit` は
  ビルトインの inert ルールが増えないことをガード（現在 inert 2件＝真のセンサーギャップのみ）。
- **構文検証ガード（2026-07-25, PR#537）**: 上記のガード群はいずれも「本番の実行時に正しく発火するか」を
  対象にしているが、`rules/sigma/**/*.yml`・`rules/yara/**/*.yar` 自体の**構文が壊れているケース**は
  従来 CI で一切検知されず、本番で無言に読み込み失敗するリスクがあった。`server/cmd/validate-rules`
  （新設の Go CLI、`ci.yml` の `rules-validate` ジョブ）が Sigma は本番と同じ `internal/detection.SigmaEvaluator`
  で、YARA は実 `yara` CLI（未導入環境は構造チェックへフォールバック）でパースし、push/PR ごとに
  構文の健全性を検証する。§1〜§7 の到達性・実発火の議論とは独立した、より手前の静的チェック。

## 5. 将来の一本化（案A・未実施）

ビルトイン Sigma を DB へ seed（重複排除）し、`rules.RuleEngine`（自動応答・相関まで持つ完全版）を
唯一のSigma源に集約、API 側の重複 Sigma 評価を廃止 or DB 読込に統一する。

- 利点: runtime 編集・rules API と整合、単一の真実源、取り違え消滅。
- リスク: 移行時の検知漏れ・二重発火。**専用PR + 予算復旧後の CI 回帰検証**で実施すること。
- 注意: 同名・別ロジックのルールは「片方が process 系・もう片方が registry/file 系」で**両方必要**な場合がある。単純削除でカバレッジを落とさないよう、event_type 単位で突合する。

## 6. 実運用での追加例と教訓（Caldera 採点ギャップ潰し 2026-06-29〜30）

収集→ステージング→アーカイブ→C2持ち出しの検知ギャップを **`rules` テーブルへ migration で投入**して埋めた
（[ops/Caldera多段エミュレーション採点.md](ops/Caldera多段エミュレーション採点.md) に採点結果）。**LIVE 検知は
detection サーバの `rules.RuleEngine`（DB ルール）経路**なので、`sigma_builtins.go` への追加は効かない
（過去に同じ誤りで「直したのに本番が変わらない」を再演）。

| migration | 技法 | 対象 | 反映 |
|---|---|---|---|
| 283 | T1074.001 / T1560.001 / T1041 | Windows | server-detect ＋ migration |
| 284 | T1113 安定化（CommandLine＋ScriptBlockText 両対応） | Windows | server-detect ＋ migration |
| 285 | T1074.001 / T1560.001 / T1041 | Linux（tar・cp・curl 形） | server-detect ＋ migration |
| 307 | Discovery バースト低速偵察耐性化（窓 60s→10m / 閾値 4→5、behavioral/SequenceEngine） | Win/Linux | migration のみ（★下記） |
| 308 | T1005 再帰ファイル列挙（CommandLine＋ScriptBlockText 両対応） | Windows | migration のみ（★下記） |

- ★**307/308 はルール内容（DB 行）だけの変更なので migration 適用のみで反映＝イメージ再ビルド不要**。detection サーバは
  5 分ごと＋`rules.invalidate` NATS で `rules` テーブルからルールを再読込する（`cmd/detection/main.go` の
  `startRuleReloader`）。確実に即反映するなら `docker restart kizashi-detection`。
  詳細＝[ops/Caldera多段エミュレーション採点.md](ops/Caldera多段エミュレーション採点.md) 「低速偵察耐性化と Discovery / T1005 ギャップ潰し（2026-07-06）」。
- ★**DB sigma ルールが `ScriptBlockText`（PS4104）を参照できる理由**: `rules.RuleEngine` の `FieldMappings` には
  ScriptBlockText が**無い**が、detection サーバはイベント平坦化時に `engine.go` の `addSigmaAliases` →
  `addPipelineSigmaAliases`（alert_pipeline.go の superset エイリアス層）を **`e.rules.Evaluate` 前に**適用し、
  `script_block_text → ScriptBlockText` を補完する。よって sigma-go はリテラルキーで解決できる（284/308 が依拠）。
  逆に言えば、**新しい proto フィールドを DB sigma ルールで使うには、この superset エイリアス層への追加が前提**。

- **`rules.RuleEngine` の `platform` ゲート（PR #356, 2026-07-02 で追加）**: 以前は `platform` 配列を無視して
  全ルールを全イベントに評価していた（Windows ラベルのルールが Linux で発火、実測 242件/24h のクロス OS FP）。
  現在は `Evaluate` が `platformMatchesEvent(rule.Platform, event.platform)` でゲートする。**OS 固有ルールは
  当該 OS のイベントにのみ評価**され、platform 未設定/全 OS 網羅ルールは universal として常に評価、event の
  platform が unknown なら fail-open。★`darwin ≡ macos` は正規化（agent は `darwin`、SigmaHQ product は `macos`）。
  緊急回避は `EDR_RULE_PLATFORM_GATE=0`。詳細は [技術的負債と改善計画.md](技術的負債と改善計画.md) P4-5。
  なお**プラットフォーム固有のコマンド形**（Windows=PowerShell、Linux=tar/cp/curl）に合わせた専用ルールを
  用意する方針は引き続き有効（ゲートは誤マッチ防止、専用ルールは検知精度向上で相補的）。
- **sigma-go（RuleEngine の Sigma 実装）の `contains` は大小無視**。Linux の tar 作成フラグ ` -c ` が
  展開時の `-C`(changedir) に誤マッチするので、作成専用の複合フラグ（`zcf`/`czf`/`--create`）に絞る。
  新ルールは `internal/detection/rules/*_rule_test.go` で**実エンジン発火＋良性非発火**を必ず守る。
- **★`enabled=t` でも「コンパイル失敗ルールは黙って未評価」**（2026-07-07 の FIM 計測で遭遇）。`RuleEngine` は
  ルールをロード時に外部 sigma-go（`sigma.ParseRule` → `evaluator.ForRule`）で**事前コンパイル**し
  `e.sigma[ruleID]` に格納する。`compileSigmaRule` が失敗したルールはこのマップに載らず、
  `evaluateSigma` の `cs, ok := e.sigma[ruleID]; if !ok { return false }` で**常に false**＝発火しない。
  DB の `rules.enabled=t` は「有効化の意思」を示すだけで「評価対象である」ことは保証しない。ロードログの
  `Sigmaルールをロードしました compiled=N failed=M` の **`failed` が 0 か**を確認するのが確実。
  「DB では有効なのに本番で発火しない」を調べるときの第一着眼点。新ルールは実エンジンに流して
  コンパイル＋マッチを固定すれば取りこぼさない（複数項目 `TargetFilename|contains` file_event ルールの
  回帰ガード例＝`internal/detection/rules/fim_persistence_rule_repro_test.go`）。
- migration ランナーは `schema_migrations`(PK=ファイル名)で各ファイルを個別追跡＝**順序非依存・安全**
  （別ブランチで番号が前後しても未適用ファイルは必ず一度走る）。冪等化は `WHERE NOT EXISTS`。

### 6.1 ランタイム検知の「到達性」教訓（2026-07-20）

ランタイム・ステートフル検知5種（`authAttack`/`fileBurst`/`lateralFanout`/`exfilVol`/`discovery`）の新設に伴い、
「**検知ロジックは正しいのに、本番のイベントが検知器に届かず一件も発火しない**」サイレント故障を3件是正した。
テストがグリーンでも本番で死ぬクラスで、ライブ検証・コード監査でのみ露見する。

- **クラウドアラート無言脱落（PR#480）**: エージェントを持たないアラート（クラウド不審操作等）の `agent_id` が
  空文字のまま uuid 列にバインドされ `SQLSTATE 22P02` で INSERT 失敗→無言脱落。空なら **NULL** をバインド。
  `rule_id` は `*string`(nil可) で既に回避済みだったが `agent_id` は漏れていた。
- **ランサム検知が本番無反応（PR#491）**: file イベントの action は ingestion(`handler.go`)が flat の
  **`operation`** キーへ格納する（`"operation": f.GetAction().String()` → `FILE_ACTION_MODIFY`）。`action` キーは
  **process 専用**。`fileBurst` 結線が `action` を読んでいたため本番で常に空＝1件も計数せず inert だった。手組みの
  ライブ実証が `action` を使っていたため見逃されていた。→ `operation` 優先読み＋proto enum 形式の回帰テスト。
- **field-support 到達性（PR#492）**: `SupportedSigmaFields` に `bytes_sent`/`bytes_recv`/`state`/`old_path`/`file_size`
  が欠落し、これらを参照するルールが誤って defer/inert。追加＋**emit/supported 同期ガード**
  （`TestEmittedEventFieldsAreSupported`）で再発を自動検出。

**教訓**: 新しい検知器を足すときは「(1)読む flat フィールド名」と「(2)ingestion が実際に emit する flat キー」を
必ず突合すること。名前不一致（`action`↔`operation`）・欠落（`bytes_sent`）・型不一致は静かに検知器を殺す。
`§5「enabled=t でも黙って未評価」`と同じ「本番でだけ死ぬ」系統。詳細＝
[検知率向上_20260720_サマリ_ランタイム相関と到達性ハードニング.md](検知率向上_20260720_サマリ_ランタイム相関と到達性ハードニング.md)。

**回帰ゲート（2026-07-20, PR#519 系）**: `TestRuntimeDetectorsFireThroughEngine`
（`engine_runtime_detectors_test.go`）が、fake store で `Engine.processEventData` を回し、**ingestion 実形式**の
イベント（file の `operation`＝`FILE_ACTION_MODIFY` / network の `bytes_sent` / auth の `success`+`source_ip` 等）を
注入して各ランタイム検知器（T1486/T1110/T1110.003/T1021/T1048＋discovery バースト）が発火することを検証。
**スコアラー単体テストでは捕捉できないエンジンのフィールド結線ミス（＝⑩の `action`/`operation` バグ）を捕捉**する
（バグ再導入で当該サブテストが実際に落ちることを確認済み）。DB/NATS 不要でユニットテスト経路（Server Tests）で走る。
- **Linux はエージェント側の eBPF プロセステレメトリが前提**（出荷ビルドは `process`/command_line を出さない）。
  ルールだけ足しても死蔵になる。[Linux-eBPF短命プロセス検知の修正と実機検証.md](Linux-eBPF短命プロセス検知の修正と実機検証.md) §9 参照。

## 7. ★2026-07-13/14 実機検証で確定：DB Sigma ルールにリアルタイム発火経路が無い（重大）

CreateRemoteThread 注入検知（`create_remote_thread` / ルール「Process Hollowing via Suspicious Executable」, T1055.012, PR#445）を
Windows 実機（13.113.140.160）で発火確認しようとしたところ、**エージェントは正しいイベントを emit・DB 取込するのに、
サーバ側アラートが恒久的に 0 件**（`create_remote_thread` 337件でアラート 0・隔離 0。合成イベントを NATS へ直接投入しても 0）。
掘り下げた結果、§1 の 2エンジン構造に **2つの重大な訂正と 1つの新事実**が判明した。

### 7.1 §1 表の訂正（コード実測）
| 項目 | §1 の記述（旧） | 実測（2026-07-14, 本番稼働コード） |
|---|---|---|
| Detection の Sigmaルール源 | DB `detection_rules` | **`rules` テーブル**（2214件, source=sigma/sigmahq）。`detection_rules` は **0 行の空表**（レガシー）。RuleEngine は `store.RuleStore.ListEnabled`（`WHERE enabled=true`）で **`rules`** を読む |
| API(AlertPipeline) の Sigmaルール源 | Go ビルトインのみ | **ビルトインのみ**（下記 2026-08-03 の訂正を参照。旧記述の「+ `yara_rules`(type=sigma) + `custom_alert_rules`」は成立していなかった）。**`rules` テーブルは読まない** |

→ つまり **`rules` テーブル（本体の SigmaHQ/seeded 2214件）を評価するのは detection-engine の RuleEngine だけ**。API/AlertPipeline はこの表を一切ロードしない。

#### 訂正（2026-08-03）: AlertPipeline は最初からビルトインのみだった

上の行はもともと「ビルトイン + `yara_rules`(type=sigma) + `custom_alert_rules`」と書いていたが、**その UNION は一度も成功していなかった**。スキーマと突き合わせた結果:

- `yara_rules` に `type` 列も `is_active` 列も無い。このテーブルは migration `041` / `085` / `174` がそれぞれ違うスキーマで `CREATE TABLE IF NOT EXISTS` しており、実際に効いているのは最初の `041` だけ。`type` を作る migration は存在しない
- `custom_alert_rules` に `rule_yaml` 列も無い。条件を `conditions jsonb` で持つ構造化テーブルで、Sigma YAML は保持していない

UNION は片方が失敗すればクエリ全体が失敗するため、`loadSigmaRulesFromPoolTyped` は **DB から Sigma ルールを 1 件も読めていなかった**。しかも失敗は Debug ログに落として `nil` を返す実装だったため、「読み込み 0 件」が正常動作に見えていた（これが §7.1 の実測を誤らせた原因）。

現在 `sigma_db.go` は**明示的な no-op** にしてある。有効な供給元が存在しないため。将来 `rules` テーブルを AlertPipeline でも評価する判断をするなら、そこが接続点になる旨をコメントで残している。

`custom_alert_rules` は Sigma ではなく**構造化ルール**として `detection.CustomRuleEvaluator`（`custom_rules.go`）が評価するようになった。UI から作れるのに何も起きなかったのは、この壊れた読み込み経路が唯一の参照だったため。

### 7.2 新事実：detection-engine が慢性ラグ → DB Sigma ルールはリアルタイムで発火しない
2コンシューマの EVENTS ストリーム消費状況（`nats consumer info EVENTS <durable>` / `nats consumer report EVENTS`）:

| コンシューマ | 稼働サービス | 状態 |
|---|---|---|
| alert-pipeline | `kizashi-api` | **追いつき済**（num_pending≈0） |
| detection-engine | `kizashi-detection` | **慢性ラグ**（ack floor が `24,560,844` で固着・未処理 ~128K・配信が流入に負ける） |

- 「Process Hollowing」は `rules` テーブルにある → **detection-engine だけが評価** → だが**ラグで新イベントに到達しない**。
- 追いつき済の AlertPipeline は `rules` を読まない → **ルールをロードすらしない** → 評価もしない。
- ∴ `create_remote_thread` は「**リアルタイム経路=ルール未ロード / 追従経路=処理未達**」の**二重ギャップで恒久未発火**。
- **これは create_remote_thread 固有ではない**：`rules` テーブルの**全 SigmaHQ ルールがリアルタイム経路（alert-pipeline）で未評価**で、ラグった detection-engine 頼み。§6 の migration 投入ルール（283/284/285/…）も同構造の影響を受けうる＝**要棚卸し**。
- ★§6 の「307/308 は migration のみで反映／detection を再デプロイすれば効く」という前提は、**detection-engine がラグっていない場合に限る**。ラグ時は再デプロイ（コンシューマ再作成でカーソルは維持）だけでは即時発火しない。

### 7.3 検証法（コード自体は健全＝結線バグと確定）
実イベント data（`{"source_image":"C:\\Users\\…\\rtinject.exe","target_image":"C:\\Windows\\System32\\notepad.exe",…}`）で **4種のオフライン再現**（Linux docker `golang:1.26`）を実施、いずれも Process Hollowing critical に **MATCH=1**：
1. `detection.SigmaEvaluator`（自前評価器） 2. `engine.go` の `EventEnvelope.FlatMap()` フル往復 3. ライブ経路 `rules.RuleEngine`（sigma-go） 4. `AlertPipeline` の `flattenNormalizedEvent` 平坦化。
→ **ルール・エイリアス（`source_image→SourceImage`）・平坦化・両 Sigma 実装すべて正しい**。バグは「どの表をどのパイプラインが読むか」の結線のみ。

### 7.4 正しい修正
- (a) `loadSigmaRulesFromPoolTyped`（`sigma_db.go`）で **`rules` テーブル（`WHERE enabled=true AND type='sigma'`）を読む**ようにし、追いつき済の AlertPipeline が全 Sigma ルールを評価するようにする。**これが本命**（リアルタイム経路の回復）。
  - **✅ 2026-08-04 実装（PR #647）**。migration 投入分で builtin 301 ＋ DB 225 = 526 ルールを評価する
    （タイトル衝突 5 件は builtin 優先でスキップ、コンパイル失敗 0）。
  - **「UNION に追加する」ではなく「新規に読む」**形になった。既存の UNION は成立しておらず
    `sigma_db.go` は no-op だったので、足す先の動くクエリが存在しなかったためである。
  - `EDR_SIGMA_DB_RULES=0` で API サーバ側の DB ルールだけを落とせる（既定 ON）。
  - **`mitre_tags` 列を YAML タグのフォールバックに使う。** 225 件中 65 件は YAML の `tags:` が空で、
    帰属が列にしか無い。列を無視すると `mitre_technique` NULL のアラートになり、
    後述の二重発火の重複排除（technique で束ねる）から**漏れる**。
  - 詳細は負債台帳 P4-6。
- (b) 併せて **detection-engine コンシューマのラグ/poison（ack floor 固着）を根治**（別課題＝スループット/毒メッセージ）。
- AlertPipeline の `pipelineSubjects` に `events.*.create_remote_thread` を含める（必要条件、ただし (a) が無いと無効）。
- ★注意：単純に AlertPipeline へ `rules` を足すと、detection-engine と**二重発火**しうる。
  実装時に確認したところ、既存の `dedup.deduplicateByTechnique` がこの形を想定していた——
  API 側のタイトルは `[Sigma] <title>`、detection 側は `<title>` で**異なる**ので、
  「同一 technique・同一エージェント・6 分窓・タイトルが複数」の統合対象に入る。
  ⚠️ ただし `mitre_technique IS NOT NULL` で絞るため、**MITRE 帰属を持たないルールは統合されない**。
  上の (a) の列フォールバックはこの穴を 65 件ぶん塞ぐが、列も YAML も空のルールが将来入れば
  同じ穴が開く（そこを弾くゲートは未実装）。

### 7.5 デバッグ手順（「発火しない」の切り分け）
1. **どのコンシューマがどのルール表を読むか**を最初に疑う（本節の 2×3 分裂）。
2. パイプライン・ラグは `nats consumer info EVENTS <durable>` の `num_pending` / ack floor で一撃確認（`nats-box` を `--network edr-platform_kizashi-internal` で起動）。
3. ルールが対象表に在り enabled かを DB で確認（`SELECT … FROM rules WHERE …`）。
4. コードの発火可否は **Linux docker で `go test`**（ローカル Windows は Defender が detection パッケージのテストバイナリ `detection.test.exe` をウイルス隔離してビルド不能）：
   `MSYS_NO_PATHCONV=1 docker run --rm -v <worktree>:/work -w /work/server golang:1.26 go test ./internal/detection/... -run <Name> -v`
5. デプロイ済みバイナリが疑わしければ `docker exec <c> strings /<bin> | grep <PR固有文字列>` でコミット同定（例: PR#445 は `SourceProcessId`）。

## 8. 新しいセンサーのルールを両側に置く（2026-08-03, WMI-Activity の例）

新しい観測面（センサー）を追加するとき、**ルールを DB だけに置くと主系のアラート経路が暗いまま
になる**。§1 の 2×3 分裂がそのまま効くためで、着地当日は気づきにくい。

PR #636（WMI-Activity ETW センサー、T1546.003）での実例:

| 置き場所 | 読むサービス | 置かないとどうなるか |
|---|---|---|
| `sigma_builtins.go` | server-api（`AlertPipeline`） | UI に出る主系のアラートが発火しない |
| `rules` テーブル（migration 370） | server-detect（`Engine`） | server-detect 側が発火しない |

**両方に置き、detection ブロックを同期させること。** 片方だけの状態はテストでは緑になる——
`SigmaEvaluator` にルール本文を直接読ませるテストは、そのルールがどのサービスに配られるかを
検証しないためである。

### 契約テストは shipped の builtin セットを読み込む

`wmi_activity_test.go` はルール本文をテスト側にコピーせず、`LoadBuiltinRules()` で**実際に出荷
される builtin セット**を読み込んで検証している。文面をコピーすると builtin が削除・改名・改変
されてもテストは通り続け、まさに検知したい退行を見逃す。

```go
ev := NewSigmaEvaluator()
if n := LoadBuiltinRules(ev); n == 0 {
    t.Fatal("no built-in rules loaded")
}
```

builtin の `event_type` を 1 文字変えると赤くなることを確認済み。

### ★ ルール名の衝突は DB 側を静かに上書きする

**DB ルール抽出器はルールを名前で同一視する。** migration 370 の新ルールを、既存の migration 329
と同じ `WMI Event Subscription Persistence (DB)` という名前で入れたところ、**329 の内容が新しい
本文で上書きされ**、329 を検証していた `TestMigrationCloudADParityRulesFire` が落ちて発覚した。

同じ技術を別の観測面から見るルールは**別名にすること**。この例では:

| ルール | logsource | 観測するもの |
|---|---|---|
| migration 329 `WMI Event Subscription Persistence (DB)` | `process_creation` | wmic のコマンドライン |
| migration 370 `WMI Event Subscription Registered (ETW)` | `wmi_event` | WMI サブシステムからの登録通知 |

同一技術（T1546.003）でも観測面が違うので**両方要る**。wmic を経由しない登録
（`Set-WmiInstance`、`ManagementClass`、インプロセス WMI クライアント）は 329 では見えない。

### フィールド名は SigmaHQ の語彙に合わせる

ペイロードのフィールド名は ETW の生のプロパティ名ではなく、`sigma_category.go` がマップする先の
カテゴリ（ここでは `wmi_event`）の SigmaHQ 名を使う。加えて `field_support.go` に登録しないと、
そのフィールドを選択するルールは「未対応」として**評価前に退避**され、「WMI 活動が無かった」と
見分けのつかない偽のグリーンになる（§6.1 の到達性教訓と同型）。

## 9. ★P4-6 の副作用：DB ルールの「二重評価」と、その正しい畳み方（2026-08-05, PR #647）

§7.4 の修正（`rules` テーブルを api の `AlertPipeline` にも結線する）を入れると、
**DB の Sigma ルールは 2 プロセスで評価される**ようになる。

| プロセス | 評価元 | 表題 |
|---|---|---|
| server-api（`AlertPipeline`） | `rules` テーブル（P4-6 で追加）＋ builtin | `[Sigma] X` |
| server-detect（`RuleEngine`） | `rules` テーブル | `[SIGMA] X` |

同じ NATS イベントを両方が購読するので、**1 イベントが 2 行のアラートになる**。

### なぜ dedup では消えないか

`internal/dedup` は両者を統合する（実測でクロスエンジン統合 170 件）。しかし統合は
行を `status='resolved'` にするだけで**削除しない**。`fpsoak-report` は状態を問わず
`count(*)` するため、FP ソークのゲートには二重計上がそのまま出る。
「行数」と「アナリストが見る件数」が別物である件は
[FPソーク運用.md](ops/FPソーク運用.md) §4 を参照。

### 畳み方：**消す前に移す**

素朴には「重複する DB ルールを migration で無効化する」（migration 374 の方針）。
だが 374 自身が明記しているとおり、これは **builtin が DB を包含する場合にだけ**成り立つ。
PR #647 でゲートが挙げた 7 件を突き合わせたところ、**包含するペアは 1 つも無かった**
（`WMI Remote Command Execution` は builtin が `process call create` を追加要求する
真部分集合、Container 2 件は builtin が `Image|endswith` でバイナリを固定していて
`crictl` と `sudo docker exec` を取り逃す、残り 4 件は builtin が存在しない）。

そのため migration 377 は、先に `sigma_builtins.go` へセレクタを**逐語移設**し、
そのうえで DB 行を落とす、という順序を取っている。

**新しく重複を畳むときの手順:**

1. FP ソークのスコアカードで `[SIGMA] X`（detect）と `[Sigma] X`（api）の対を見つける
2. builtin が DB を**包含するか 1 件ずつ確認する**（方針ではなくルール単位の事実）
3. 包含しないなら、足りない枝を builtin に足すか、DB ルールを builtin へ移設する
4. `internal/detection/db_rule_builtin_port_test.go` に、**旧 builtin が取り逃していた
   ケース**を代表イベントとして追加する（当たりやすいケースで書くと何も証明しない）
5. migration で DB 行を `enabled = false` にする
6. detect 側の被覆テスト（`migration_coverage_test.go` / `migration_parity_test.go`）は
   **消さず反転**する — 削除すると再有効化に気づけず、skip は「被覆されている」と
   読めてしまう

### severity の丸め

DB 行は `rules.severity` に数値を持つが builtin は Sigma の `level` しか持てず、
`critical=10 / high=8 / medium=5 / low=3` の 4 段階しかない。移設で severity が
1 段ずれる場合がある（PR #647 では 3 件）。ずれは migration 377 のヘッダに列挙してある。
