## ⚠ 隔離コマンドが届かなくても「隔離しました」と答えていました（実測 2026-08-12）

`POST /agents/:id/isolate` は、DB を `isolated` にしたあと端末へ隔離
コマンドを送り、**その送信結果を `_ =` で捨てて**「エージェントを隔離
しました」と答えていました。

**ハートビートの巻き戻しは片側しかありません。** 実測:

| | ある? | 何をするか |
| --- | --- | --- |
| `should_unisolate` | あり | 端末が「まだ隔離中」と言い、DB が解除済みなら次のハートビートで解除させる |
| `should_isolate` | **無し** | —— |

つまり**隔離の送信が失敗したら、その端末は二度と隔離されません。**
DB と画面は「隔離済み」、端末はネットワークに繋がったまま、対応する人は
封じ込め済みだと思って次に進みます。

いまは 500 で答えます（解除の方は次のハートビートが直すので、跡を残す
だけです）。`command_delivery_test.go` が、指示の送信3か所すべてについて
**error を見ていること・5xx で答えること・そこで戻ること**を留めます。
`should_isolate` が足された日には検査が落ちるので、そのとき答え方を
見直せます。

**足しました (2026-08-12)。** ついでに、**巻き戻しが実は片方も
効いていなかった**ことが分かりました:

`should_unisolate` は HTTP のハートビート応答にしかなく、gRPC の応答は
それを運んでいません。**`FallbackSender` は gRPC を先に試す**ので、
gRPC が生きている通常時、解除の巻き戻しも端末に届きませんでした ——
**直る条件（gRPC が落ちている）と直らない条件（gRPC は生きていて指示
だけが落ちた）が入れ替わっていました。**

両方向・両経路にしました:

| どこ | どうしたか |
| --- | --- |
| サーバ HTTP | `should_isolate` を追加 |
| サーバ gRPC | 応答メタデータ `x-edr-should-isolate` / `x-edr-should-unisolate`（`x-edr-keepalive` と同じ形。proto の再生成は要りません） |
| 端末 | `HeartbeatResponse.ShouldIsolate` と `SetIsolateFunc` |

隔離するときに **EDR サーバへの経路は残します** —— 残さないと次の
ハートビートも届かず、解除の指示も受け取れません。その host の求め方は
`response.ServerHost` に集約しました（隔離の入口がコマンドとハートビートの
2つになったので、同じ答えを2箇所で出す必要がありました）。

**それでも隔離は 5xx で答えます。** 直るまで最大 30 秒あり、その間、
対応する人は「封じ込め済み」と思って次に進みます。

## ⚠ 最優先: 接続プーラの下ではテナントの絞り込みが外れます（実測 2026-08-12）

**`docker-compose.scale.yml` は8つのサービス全部の `DATABASE_URL` を
pgbouncer に向けており、`deploy/docker/pgbouncer.ini` は
`pool_mode = transaction` でした。**

テナントの絞り込みは PostgreSQL の RLS が行い、その入力は接続の
セッション変数 `app.tenant_id` 1つです
（`server/internal/store/postgres.go` の `prepareConnForTenant` が
`set_config(…, false)` で設定します）。第3引数の `false` は
「セッション有効」で、**そうでないと同じ要求の続きのクエリから
見えなくなる**ことは、そのファイルのコメントに元から書いてあります。

トランザクション単位のプーリングは、まさにその「トランザクションが
終わった時点で別のサーバ接続に移る」ことをします。加えて
`server_reset_query = DISCARD ALL` がセッション状態を明示的に消します。

### 測りました

PostgreSQL 16.13 と pgbouncer 1.22 を同じ設定で立て、`Connect()` が
組み立てるプールと同じ形（`PrepareConn = prepareConnForTenant`）で、
テナント A の要求を 200 回:

| 経路 | 見えた行数 |
| --- | --- |
| 直接つないだとき | **1 が 200 回**（正しい） |
| pgbouncer 経由 `pool_mode = transaction` | **2 が 199 回、1 が 1 回** |
| pgbouncer 経由 `pool_mode = session` | **1 が 200 回**（正しい） |

「2」は**両方のテナントの行**です。RLS のポリシーは
`app.tenant_id IS NULL OR ''` を全件アクセスとして通すので
（migration 027 / 324）、セッション変数が届かない接続では
**絞り込みが事実上外れます。**

もう1つ測れたこと: pgx の既定（拡張プロトコル＋文キャッシュ）は
transaction モードに**そもそも繋がりません**
（`prepared statement "stmtcache_…" already exists`, SQLSTATE 42P05）。
上の 199/200 は `default_query_exec_mode=simple_protocol` を足して初めて
測れました。**いまの scale 配置は、繋がらないことで漏れていなかった
だけ**です。

### したこと

`pgbouncer.ini` を `pool_mode = session` にしました。**その設定ファイル
自身が「接続ごとに SET/PREPARE を使うなら session が要る」と書いており、
このアプリは接続ごとに SET を使います** —— 元から書いてあった規則を
当てただけです。session モード＋pgx 既定のプロトコルで 200/200 が
正しくなることも測りました。

`server/internal/store/session_state_vs_pooler_test.go` が、この組み合わせ
（セッションに残す設定 × transaction/statement プーリング × プーラ経由の
配置）を見張ります。

### ご判断ください

session プーリングは、pgbouncer の多重化の利点をかなり減らします
（クライアント接続とサーバ接続がほぼ1対1になります）。transaction
モードに戻したいなら、**先に絞り込みをセッション状態から外す**必要が
あります。案:

1. **session プーリングのまま**（いまここ）。接続数の上限と待ち行列は
   効くので、無意味ではありません。
2. **絞り込みを SQL 側に移す** —— 各クエリに `tenant_id = $n` を明示し、
   RLS はもう一段の防御として残す。**全クエリに手が入ります。**
3. **RLS のエスケープ節を外す**（`app.tenant_id` が空なら1行も見せない）。
   漏れる向きは塞がりますが、**テナントを持たない背景の仕事が全部
   0件になります** —— どれがそれなのかを先に洗い出す必要があります。

**3 は単独でもやる価値があります。** いまは「設定し忘れ」と「全権限」が
同じ形です。

**→ 決まりました（2026-08-17）: 1（session プーリングのまま）＋ 3 を 2 表
だけ実施。** transaction モードへの復帰は別途です。

3 の対象は `uninstall_guards` と `uninstall_attempts` の2表です
（migration 446）。**この2表だけ事情が違い、テナントを決められない経路が
1つもありませんでした。** 外す前に洗い出した結果:

| 経路 | 前 | いま |
| --- | --- | --- |
| 管理コンソール 4本 | JWT にテナントがある配備でのみ ctx に載る。**単一テナント配備の JWT はテナントを持たない**ので、`tenantOf()` が既定テナントに落とした値は ctx に載らず、`app.tenant_id` は空のまま —— **ここが抜け道への落ち先** | `tenantScope()` が同じ値を ctx にも載せる |
| HTTP ハートビート | 認証なし。`tenantOf()` が必ず既定テナントを返していた（多テナント配備では**別テナントの端末に既定テナントの材料**） | `agents.tenant_id` から引く。引けない＝行が無い相手には**何も送らない** |
| アンインストール試行の通報 | 同上。必ず既定テナントの行として記録 | 同じく `agents` から。引けなければ既定テナントへ（**記録を落とすのがいちばん悪い答え**で、この経路は「攻撃者が解体している最中の端末からの通報」のためにあります） |
| gRPC ingestion のハートビート | **`agents.tenant_id` を既に引いていて、ctx に載せていないだけ** | 引いた値を ctx に載せる |

登録済みの端末は必ず引けます —— `agents.tenant_id` は migration 244 で
既定テナントの DEFAULT が付き、NULL の行も backfill 済みです。

**残り4表（`agents` / `alerts` / `incidents` / `users`）の抜け道はそのまま
です。** 取り込み・検知エンジン・相関エンジンが依存していて、外すには系と
HTTP を別の DB ロールに分ける必要があります。上の「端末の行からテナントを
引く」も、`agents` の抜け道に寄りかかっています —— **2表だけ外せたのは、
4表が外れていないからです。**

`rls_policy_contract_test.go` の `permissiveWhenUnset` から2表を外しました。
**戻すと落ちます**（「抜け道を持たなくなりました。一覧から消してください」）。

## テストの pool を共有しました（実測 2026-08-17）

`internal/api/handlers` には `testDB(t)` / `testPool(t)` が **441 か所**
あり、**テスト1本ごとに pool を開いていました**。CI の `-timeout` を
600s に上げたのは、その応急処置です。

**「共有すると振る舞いが変わり得る」ので、先に測りました。**
`store.Connect` はテナント/RLS を接続ごとに設定するので、pool を
使い回すと前のテナントが残るのではないか、が心配の中身です。

| 測ったこと | 結果 |
| --- | --- |
| `Connect` ＋ 1 query ＋ `Close` を20回 | **1回あたり 256ms**（`MinConns=5` を張るため） |
| 共有した pool から20回引く | **1回あたり 14ms** |
| テナント付き acquire の**あと**、テナント無しで10回引く | **10回とも空**（前の値は残らない） |
| pool 1つの接続数 / postgres の上限 | total=6 / `max_connections=100` |

**残らないのは、設定が pool 単位ではないからです。** `PrepareConn` は
**接続を引くたび**に `app.tenant_id` を設定し、`AfterRelease` は返す
たびに消します（消せなかった接続は捨てます）。共有しても本番と同じ
経路を通ります。

**441 か所は触っていません。** 全部が `testDB(t)` / `testPool(t)` を
通るので、**helper 2つを `sync.Once` の共有に変えるだけ**で済みます。
`t.Cleanup(db.Close)` は外します —— **戻すと、最初に終わったテストが
以降の全部から pool を取り上げます。**

実測（この環境の docker postgres、TCP 越し）:

| | `internal/api/handlers` の実行時間 |
| --- | --- |
| 共有前 | **900s で打ち切り**（`-timeout` に届かず失敗） |
| 共有後 | **273s** |

残る失敗は8件で、**どれも `origin/main` でも同じように落ちます**
（`information_schema` 走査など、経路を `\` で組み立てている Windows
固有の静的検査です）。CI（Linux）では緑です。

## ⚠ 手で決めた資産の重要度は、一度も効いていませんでした（実測 2026-08-12）

捨てている書き込みの**残り9か所**を1つずつ読んでいて出てきました。
`asset_criticality_handler.go` が `system_metadata` の
`agent_criticality_<id>` に書いていた行の**読み手を探したら、
どこにもありませんでした。**

| 経路 | していたこと |
| --- | --- |
| `PUT /endpoints/:id/criticality` | 手動の点数を書いて 200 で答える |
| `GET /endpoints/:id/criticality` | **計算し直して、同じ行を上書き** |
| `POST /endpoints/criticality/bulk` | 全端末について同じことをする |

つまり手で決めた重要度は「保存されて、次の表示で消える」ものでした。
**一覧の再計算ボタン1回で戻ります —— 再起動すら要りません。**

画面側（`frontend/app/admin/asset-criticality/page.tsx`）は
`manual_override` と `manual_score` を読んでいて、**API が一度も送った
ことのない項目**でした。上書きの UI だけが揃っていた形です。

**直しました。** 手動には `manual_override` の印が付き、計算する側は
その印を見て**計算も上書きもしません**。計算値はもう保存しません ——
誰も読まないうえに、手動を消していたのがその書き込みです。印を持たない
古い行（計算値のキャッシュ）は `false` として読まれるので、migration は
要りません。

### ご判断ください: 手動の重要度を解除する経路がありません

いま `PUT` で手動にすると、**自動計算に戻す方法がありません。**
（元は「次の表示で勝手に戻る」ことで実質的に解除されていました ——
それは解除ではなく、機能していなかっただけです。）

1. **`DELETE /endpoints/:id/criticality` を足す**（推奨）—— 行を消せば
   自動計算に戻ります。画面にも「自動に戻す」を1つ足すだけです。
2. **`PUT` で `score` を省略したら解除**とする —— 経路は増えませんが、
   「0 点にしたい」との区別が要ります。
3. **解除は要らない** —— 一度手で決めた端末は、手で決め直すまで手動の
   まま。運用でそう決めるなら、これで足ります。

**決まりました (2026-08-17): 1（`DELETE` を足す）。実施済み。**

`DELETE /endpoints/:id/criticality` が行を消し、次の表示から
`scoreAgent` の計算値に戻ります。画面（`asset-criticality`）には、
**手動になっている行にだけ**「自動に戻す」が出ます。

消す行が無くても 200 で答えます —— **「もともと自動だった」と「いま
自動にした」は、利用者にとって同じ結果**です。404 にすると、画面は
「戻せませんでした」と出しますが、実際には自動です。

`criticality_clear_test.go` が、鍵の綴りが1つであること（分かれると
解除は 200 を返して**何も消しません**）・消したあと計算し直して
答えること・経路が登録されていることを留めます。実 DB を通す往復

### アラートの保管時暗号化が、一度も有効になっていません

`internal/store` に到達性を掛けて出てきました。**呼ぶ人も、動くと言う
テストもいない公開関数が3つ**あり、そのうち1つがこれです。

- `AlertStore.WithEncryptor` — `raw_event` の AES-256-GCM 暗号化を有効に

- `crypto.NewEncryptor` も、本番では一度も構築されません。
- したがって `s.encryptor` は常に nil で、`Insert` の暗号化分岐

実装はあり、コードのコメントは機能として説明し、
`docs/enterprise/マルチテナントアーキテクチャ.md` は
「**保管時暗号化: テナントごとのAES-256-GCMキーで暗号化**」を事実として
書いています。`docs/enterprise/データ居住要件.md` の表も、イベント種別ごとに
AES-256-GCM を挙げています。

**決まりました: 繋ぎます。** 鍵の置き場所は既存の `DBKeyStore` —— テナント鍵を
Postgres の `tenant_encryption_keys`（マイグレーション 029 で既存）に置き、
マスター鍵で AES-256-GCM ラップします。マスター鍵は環境変数から
（`MDM_MASTER_KEY` と同じ流儀）。既存の平文行は移行しません —— `enc:` の
前置きの有無で1行ずつ判断できるためです。

**繋ぐ前に、順序の問題が1つありました。**

読み出し側が復号していませんでした。`GetAlert` は `enc:` が付いていたら
代入しない書き方で、**暗号化を有効にした瞬間からアナリストの画面は
「生イベントの無いアラート」で埋まります。** 書き込み側だけ繋ぐと、
書けるが読めないデータを作ります。

読み出し側を先に入れました（`decodeRawEvent`）。平文と暗号文の両方を読み、
復号できなかったときは黙って空にせず記録します。暗号化行がまだ無いので
**いまは実質 no-op** ですが、これが入っていないと次の段階が危険です。

### 決まりました: APIキーに持ち主のテナントを持たせます

`api_keys` にテナントの列はありませんが、鍵は利用者に紐づき、利用者は
テナントに紐づきます。`FindByKey` が `users` を LEFT JOIN して一緒に引く
ようにし、`router.go` は `c.Set("tenant_id", apiKey.TenantID)` を置きます。

持ち主のテナントが引けなければ空のままです（`users.tenant_id` は NULL 可）。
**空を「全テナント」と読み替えないのが、この一連の直しの要点です** ——
その場合は拒否される側に倒れます。

これで、上の2件（読み取りの400、隔離の拒否）はAPIキーでも通常どおり
動きます。**鍵は、発行者のテナントの中だけで動きます。**

### RLS は、既定の配備では一度も適用されていません

いちばん奥を見に行って分かりました。**これは新しい発見ではなく、

### 「測れなかった」を 0 で表すのをやめました

macOS の `readDiskFreeGB` の件から入りましたが、**測ってみたらもっと

| | CPU | ディスク空き |
|---|---|---|
| Linux | 実装あり | 実装あり（Statfs 失敗時に 0） |
| macOS | **未実装 → 常に 0%** | 実装あり（同上） |
| Windows | **未実装 → 常に 0%** | **未実装 → 常に 0 GB** |

さらに、ハートビートの CPU は**全プラットフォームで** `return 0.0` の
仮実装でした（コメントは「Simplified - real implementation reads
/proc/stat on Linux, GetSystemTimes on Windows, host_cpu_load_info on
macOS」と、実装されていないことを正しく書いていました）。

**0 は測定値として最も強い主張になります。しかも向きが逆です:**

- CPU 0% =「アイドル」→ 高負荷を探す側からは**問題なし**

恒久的に 0 です。メモリ側も `total_memory_mb` を書く箇所が本番に無く、
常に NULL なので同じです。

直したこと:

- `HeartbeatRequest.cpu_usage` を proto3 の `optional` に。**送らない ＝
  測れなかった**です。旧いエージェントは 0 を送らない（proto3 は既定値を
  載せません）ので、新しいサーバからは「未測定」に見えます —— それが
  実際の状態なので正しく倒れます

  Windows / macOS は未実装のまま、`(値, 測れたか)` の形で「測れなかった」を
  返します
- `UpdateMetrics` は未測定なら列を NULL のままにします
- `resourceSnapshot` の CPU とディスクをポインタ + `omitempty` に。
  **測れなかった欄は JSON に出ません**

### ハッシュを取れなかったファイルは、ハッシュ IOC に永久に当たりません

値を返して先へ進むのが妥当なものです。**正しく扱えているものもあります** ——

問題は4箇所、2つの関数です:

```go

    f, err := os.Open(filepath.Clean(path))
    if err != nil {
        return collector.FileHashes{}     // ← 空のハッシュ
    }
```

`computeHashes`（プロセス実行ファイル用）も同じ形です。呼び出し側は
`evt.Hashes = windowsHashFile(fullPath)` とそのまま載せるので、
**イベントはハッシュ無しで送られます。**

サーバ側では、空のハッシュと「ハッシュを取れなかった」が同じ姿です。
ハッシュ IOC の照合は**一致しなかったのではなく、照合するものが無かった**
のに、黙って通ります。攻撃者のプロセスがファイルをロックしていて開けない、
権限が無い、直後に消された —— どれも「IOC に載っていない実行ファイル」と

いまは記録だけ足しました（`slog.Debug` で、どのパスがハッシュ無しで
送られたかが残ります）。**これは最低限で、直したとは言えません。**

**決めること: 「取れなかった」をイベントに載せるかどうか。**

載せるには proto のイベント定義に1つ足す必要があり（例:
`hashes_unavailable` とその理由）、サーバ側の照合と画面もそれを扱う必要が
あります。**エージェントとサーバの両方に跨るので、私では決められません。**
載せれば、ハッシュ IOC が「当たらなかった」と「見ていない」を区別できる

### プロセス停止が、1件も止められなくても「対処済み」でした

`internal/response` の14件を分類し、いちばん直接的な1件を直しました。

```go
}
```

## 使い方

3つの選択肢はどれも正当です。

1. **サーバ側を作る** — 機能として必要
2. **画面を落とす** — 機能として要らない。サイドバーの項目も一緒に消えます
3. **未実装として明示する** — 決まるまでの中間。`BackendPendingBanner` への登録、
   またはサーバ側の `NotImplemented`（501）。どちらに転んでも無駄になりません

A・B・C は3択のままです。**D はすでに3を適用済み**なので、残っているのは
「作る」か「落とす」の2択になります。放っておいても嘘は出ません。

画面ごとに違う答えで構いません。「フォレンジックは作る、成熟度モデルは落とす、
残りは保留」のような部分的な指示でも動けます。

### メモリは、測れていないのではなく別のものを測っていました

上の項目から。エージェントが `memory_usage_mb` として送っていたのは
`runtime.MemStats.Sys` —— **エージェント自身の Go ランタイムが OS から
取った量**です。サーバはそれを `agents.memory_usage_mb` に書き、
フリート健全性アラータが端末のメモリ使用率として読みます。

`resource_collector` 側も同じで、そちらはコメントに
「For a host-level view we also add stack and other non-heap areas」と
**書いてありました。host-level ではありません。**

（`internal/resource.Throttle` が同じ `ms.Sys` を見ているのは正しい用途です
—— あちらはエージェント自身の使用量を上限と比べています。同じ式でも、
何を主張しているかが違います。）

分母も欠けていました。`total_memory_mb` を書く箇所が本番に1つも無く、
常に NULL です。**分子は別物、分母は空** —— アラータのメモリ判定は
どちらの理由でも発火できませんでした。

直したこと:

- `hostmetrics.Memory()` を足し、**Linux は /proc/meminfo を読みます。**
  used は `MemTotal − MemAvailable` です —— **MemFree ではありません。**
  ページキャッシュは「使用中」ではなく、必要になれば回収されるので、
  MemFree で引くと健全な端末がほぼ全部メモリ逼迫に見えます
- `MemAvailable` の無い古いカーネル（3.14 未満）では、推定せずに
  「測れなかった」と言います。**推定して出すと、0 と同じ種類の嘘です**
- proto に `optional memory_usage_mb` と `optional total_memory_mb` を追加。
  Windows / macOS は未実装なので、欄ごと送りません
- `UpdateMetrics` は総容量だけ `COALESCE` で保持します。**物理メモリは
  毎回変わるものではないので、1回の測定失敗で分母を消すと、その間
  メモリ判定が黙ります**

変異検査 16件、16/16 killed。ここでも自分の検査の欠陥が1つ出ました ——
「未測定の欄を落とす」検査が、**メモリの欄だけ値を入れていました。**
落とす仕組みを確かめる検査が、その欄だけ埋めていたわけです。

**残っている判断は、プラットフォーム実装だけになりました:**
Windows（`GetSystemTimes` / `GlobalMemoryStatusEx`）と
macOS（`host_cpu_load_info` / `host_statistics64` + `sysctl hw.memsize`）。
いまはどちらも「測っていない」と正直に言います。

### 計算したハッシュを、一度も送っていませんでした

`internal/platform/windows` の return 39件を分類していて出ました。
**記録してあった「ハッシュが取れなかったことと空であることが同じ姿」
より、はるかに手前の問題でした。**

エージェントは起動するプロセスごとに実行ファイルを**最大 50 MB 読んで
MD5・SHA1・SHA256 を計算**し、`evt.Hashes` に入れます。
`cmd/agent/main.go` が `v1.ProcessEvent` を組み立てるところで、
20以上のフィールドを載せていますが **`Hashes` はありません。**
proto には `FileHashes hashes = 8` があります。ファイルイベントも同じです。

つまり:

- **サーバのハッシュ IOC 照合は、照合するものを一度も受け取っていません。**
  一致しなかったのではなく、材料が届いていませんでした
- 端末側では毎回ハッシュを計算していたので、**費用だけ払っていました**

載せるようにしました。取れなかったときは欄ごと出しません ——
3つとも空の `FileHashes` を送ると「ハッシュを取ったが空だった」に
見えます。**未測定を測定値にしない、という同じ規則です。**

（記録してあった「空と取れなかったが同じ姿」の件は、これで前提が
変わりました。まず届くようになったので、次はサーバ側が「ハッシュ無し」を
どう扱うかです。）

#### 受け側は用意されていて、届くものが無いまま動いていました

サーバの `ingestion.addHashes` は既にあり、コメントにこう書いてあります:

> Without this, agent-computed hashes never reach the detection layer and
> hash-based IOC matching (known-malware detection) silently never fires.

**正しい説明です。そして、そのまま起きていました** —— 受け側は3箇所
（プロセス・ファイル・イメージロード）から呼ばれていて、`GetHashes()` が
常に nil を返していました。**直したのは送る側だけで、待っている側は
最初からありました。**

**「一致しなかった」と「照合するものが無かった」を数え分けました。**
`edr_ioc_hash_absent_total` —— ハッシュ照合に届いたプロセス・ファイル・
イメージロードのイベントのうち、ハッシュを1つも持っていなかった数です。

0 でないこと自体は異常ではありません（読めないファイル、権限不足）。
**総イベント数に対する比率を見てください。伸びているあいだ、ハッシュ
照合は実質動いていません。**

ネットワークイベントは数えません。**ハッシュが無いのが当たり前なので、
全部数えると当たり前の欠落が本物の欠落を埋めます。**

### 合図と表し方を分けました（前項の続き）

前項で「再試行の合図を別に用意するのが先」と書いた分です。調べたら、

- そのブロックを呼ぶ箇所は**1つだけ**

`"unknown"` に変えれば分かれます。欄の意味はこうなりました:

    ""         トークンを開けなかった（調べるところまで行けていない）
    "unknown"  開けたが、ラベルを読めなかった
    "High" 等  読めた

**どちらも嘘ではありません。** 検知は変わりません
（`IntegrityLevel: High` はどちらにも一致しません）。変わるのは、
運用者が見分けられることです。

あること** —— そちらを `"unknown"` に変えると、**調べて分からなかった
ものをもう一度調べ直します**。表し方を直すつもりで、調べる処理の
回り方を壊す形です。

### FIM の沈黙が、3つの別々のことを意味していました

`internal/collector` の `continue` 13件を見ました。中身はほぼ全部が
FIM（ファイル完全性監視）で、**動いている面としてはここが次に鋭い**
と判断しました。

FIM が何も言わないことは、画面では「そのファイルは変わっていない」と
読まれます。**実際には3つが同じ沈黙でした:**

1. 本当に変わっていない
2. 読みに行ったが開けなかった（権限・I/O）
3. 監視対象そのものを見に行けなかった（stat / walk が失敗）

#### 測ったこと（2026-08-11、このコンテナ、uid=0）

既定の Linux ルールは31本。**そのうち14本が0パスに展開されます**
（`/etc/crontab` `/etc/ssh/sshd_config` `/root/.ssh` `/var/spool/cron`
`/etc/rc.local` `/etc/ld.so.preload` など）。**ログは1行も出ません。**
展開できたパスは 1305 件で、うち `/usr/bin` だけで 1065 件です。

（この測定は一度きりです。実機とコンテナで数が変わるので、上限には
していません。）

#### 直したこと

**(a) 読めなかった時点で基準値を潰していました。**
`f.hashes[p] = ""` を無条件に書いていたので、読めるように戻った瞬間に
`"" != h` となって modified が上がります。**中身を触っていなくてもです。**
`/etc/shadow` や `authorized_keys` —— いちばん信用されている経路での
偽陽性でした。本当に変わっていた場合も `old_hash` が空になり、
「何から何に変わったか」が追えませんでした。
一度も読めていないパスにだけ番人役の `""` を置くようにしました。

**(b) 見に行けなかった対象の配下を「削除された」と報告していました。**
`expandRules` が stat 失敗を黙って飛ばすので、配下のファイルがまるごと
`currentSet` から落ち、削除ループが全部を削除として送り、基準値まで
消していました。次のスキャンではそれが全部「作成」で上がります。
**`/usr/bin` の1回の失敗で、この端末では 1065 件の偽の削除 → 1065 件の
偽の作成です。何も起きていません。**
`os.IsNotExist` かどうかで分け、「見に行けなかった」配下は削除と
言わないようにしました。**抑制は今回のスキャンにだけ効きます** ——
持ち越すと、そのあと本当に消されたものが永久に報告されません。

**(c) 端末の外に出していませんでした。**
`telemetry.Set(fim, ModeFailed, …)` で報告します。ログ1行では SOC の
画面に出ません。

ここで数えるのは「見に行ったのに読めなかった」だけです。**存在しない
ことは正常です** —— `/etc/ld.so.preload` が無いのが普通で、攻撃はそれを
「作る」ことです。作られれば created で上がります（検査で留めました）。
数えると、ほぼ全端末が赤くなり、本当に見えていない端末が埋もれます。

健全なときは**登録しません**。FIM は設計上ポーリングで、劣化では
ありません。常に登録すると全 Linux 端末の集約が倒れます。

（自分の変更で作りかけた穴でした。一度 ModeFailed を登録したら、

### プロセス一覧の 89% が、静かに欠けていました

**この欠陥は、前回の私の修正が作りました。**

`readVmRSS` は読めないと 0 を返していました。0 は「常駐メモリが無い」と
いう測定値なので、消えた直後のプロセスが常駐 0 の生きたプロセスに見えます
—— それを「行ごと落とす」で直しました。**行き過ぎでした。** メモリが
読めなかったことを理由に、**同じ行で読めていた CPU まで捨てています。**

#### 測ったこと（2026-08-11、このコンテナ、uid=0）

```

readProcessStatsRaw     8 件   ← 89% が消えます
```

67 件はカーネルスレッドです。**VmRSS 行が無いのは失敗ではありません**
—— ユーザ空間を持たないという事実で、**CPU は普通に回っています。**

`process_stats` は `CryptoMinerScorer` (T1496) の入力です。**snapshot に
出ない PID は、CPU を焼き続けても永久に検知されません。** そして届いた
側には、全部入りの snapshot と 75 分の 8 の snapshot を見分ける手立てが

答えを3つにしました。**2つに畳んでいたことが原因です:**

| | 意味 | `mem_mb` |
|---|---|---|
| `memMeasured` | 数値が取れた | 出る |
| `memNoUserSpace` | VmRSS 行が無い（カーネルスレッド） | 出さない |
| `memUnknown` | 開けない／数値として読めない | 出さない |

**行はどれも残ります。** メモリだけが `mem_mb` の欠落として表れます

約束と同じです（画面はすでに欠けた値を `—` として出します）。

零値は `memUnknown` にしてあります。**触り忘れたフィールドが「測った 0」
になる向きには倒れません。** Windows の `readOneProcess` は成功したときに
だけ書きます。

darwin の `ps` の RSS 列も、ParseUint のエラーを捨てて 0 を返していました
（`parsePSRSS` に切り出し）。サーバ側の `procStatSample.MemMB` も
`*float64` にしました —— `float64` のままだと欠落が 0.0 に化けます。

#### 走らせられない面を、どう確かめたか

**この端末では Windows も macOS も走らせられません。** syscall と外部
コマンドの呼び出しそのものは確かめようがありませんが、**間違えるのは
ほとんど算術と解析の側です。**

このリポジトリに前例があります。`filetimeSumCentis` は FILETIME を
絶対時刻として扱う `Filetime.Nanoseconds()` を使っていたため、
**全プロセスの CPU 時間が 0 になっていました。** 呼び出しは成功し、
型は合い、値だけが嘘でした。

なので算術と解析を **build tag の無い `platform_math.go`** に出して、
Linux で通しています。加えて、**本物がその算術を通っていることを AST で
見ます** —— 切り出した側だけ検査して本物が別実装なら、検査は緑で値は
嘘です（`readVmRSS` と `scanPidMapsStats` で同じ穴を開けかけました）。

留めた中身:

- **FILETIME の上下32ビットの組み立て**（`Nanoseconds()` を使わないこと）
- **`kernel` に `idle` が含まれること**（MSDN のとおり。二重に足すと
  使用率が低く、落とすと高く出ます）
- **`vm_stat` のページサイズを見出し行から取ること** ——
  **4096 を決め打ちすると Apple Silicon で使用量が実際の 1/4 になります**
- **`Pages occupied by compressor`** と `Pages stored in compressor` の
  取り違え（後者は圧縮前の論理ページ数です）
- **`inactive` を使用中に数えないこと**（Linux 側で MemFree ではなく
  MemAvailable を使っているのと同じ理由）
- **`SystemDrive` を決め打ちしないこと**（D: の端末では、別のボリュームの

#### 経路をたどると

1. **エージェント** —— コマンドが起動できたなら、終了コードが 1 でも

## Sigma／YARA 同期の「前回が実行中」を、いつまで待つか

`sigma_sync_scheduler.go` と `yara_sync_scheduler.go` は、前回の同期がまだ
走っているときに読み飛ばします（`slog.Info` + `return`）。正しい重複防止
ですが、**前回が固まったままなら永久に読み飛ばし続けます** —— 回は毎回
記録され、`last_success` も進むので、外から見えるのは健全なワーカーです。

案（実装はご指示があってからにします）:

- 実行中フラグに開始時刻を持たせ、一定時間（たとえば同期間隔の3倍）を
  超えていたら `fail(ctx, …)` で回を落とす。何回連続で読み飛ばしたかを
  数えるだけでも、外からは見えるようになります。
- あるいは、読み飛ばした回数を計測に出すだけにして、閾値は運用側で決める。

いま測っているのは「読み飛ばした」ことだけで、**「いつから読み飛ばして
いるか」は誰も持っていません。**
